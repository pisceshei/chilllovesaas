# 工作記錄：驗收閉環的第四種失效形態（2026-08-15）

> 分支 `m1/review-loop-fallback`（獨立於 PR-1，理由見下）

## 已完成的工作 (Done)

### 觀察到的事實（**只寫實際量到的**）

| Run | commit | 時長 | `outcome` | PR 上的留言 |
|---|---|---|---|---|
| 37 | `ca094e2`（105 檔 / +6155 行） | 3m32s | **success** | 零 |
| 39 | `6e9a627`（同一 PR ＋ 一個修正） | 3m58s | **success** | 零 |

**連續兩次重現**，不是偶發。

🔴 **`outcome == success` 排除了 max-turns 耗盡**——那個形態會讓步驟 **failure**
（2026-08-14 的 PR #26 就是，annotation 逐字 `Reached maximum number of turns (40)`），
而 workflow 對它有專屬分支與專屬訊息。這次走的是另一個分支。

### 原因**未查明**，而且查不到的原因本身就是缺陷

我試了三條路徑要拿 Claude 的最終輸出，**全部失敗**：

1. GitHub Actions 的 log 檢視器——虛擬捲動，`document.body.innerText` 只有 398–2988 字元，
   點展開在此環境無效；
2. `/checks/{id}/logs` raw endpoint——回傳 gzip 二進位，`response.text()` 拿到亂碼；
3. 未認證的 REST API——私有 repo，`workflow_runs` 回空。

⇒ **在事故當下，診斷資訊等於不存在。** 而原本的處置只有一句
「請到 Actions 分頁查 log 確認它最後做了什麼」——**那句話指向一個拿不到的東西**。

### 修法：把「整份消失」變成「回收 ＋ 診斷」

`anthropics/claude-code-action@v1` 會輸出 `execution_file`（agent 的完整執行記錄）。
解析步驟在「成功但沒留言」這一支改成：撈出最後一則 assistant 文字並貼上來。

這一步同時解決兩件事：
- **審核內容不再整份消失**——若 agent 其實已經寫好了意見、只是漏了最後那個 tool call，
  內容會被回收出來，人可以直接讀；
- **它本身就是診斷**——回收出來的文字會直接顯示 agent 最後在做什麼。

🔴 **回收品的結論標記一律中和（【】→〔〕）**。理由是 workflow 裡已經寫過的那一條：
本步驟的留言是由 `github-actions[bot]` 貼的，**而它在 `REVIEWERS` 清單內**
⇒ 若原文第一行帶著標記，下一輪 `synchronize` 會把**這則回收品**當成正式結論。
**回收是為了讓人看到，不是為了驅動閉環。**

### 另一半：直接對最可能的成因下藥

prompt 末尾新增：

> 🔴🔴 **你的最後一個動作必須是那個 `gh pr comment` 呼叫。**
> **不要把審核意見寫在最終回覆裡**——最終回覆不會出現在 PR 上，整份審核會直接消失。
> **大型 diff 的正確做法是縮小審核範圍並在意見裡說明**，而不是省略掉那則留言。

### 🔴 為什麼這個修正**不能**放進 PR #29

`claude-review.yml` 有反竄改機制：**任何動到本檔的 PR，它自己的驗收整個被跳過**
（workflow 檔頭已逐字記錄，annotation 原文＋判別方法都在）。

⇒ 把這個修正塞進 PR #29，等於**保證那個 105 檔的大 PR 永遠拿不到審核**。
正確順序是：**本分支先合併 → PR #29 重新 push → 那時閉環才是修好的版本**。

## 修改的檔案與核心邏輯 (Changes)

- `.github/workflows/claude-review.yml`：
  - 解析步驟新增 `EXECUTION_FILE` env（`steps.review.outputs.execution_file`）；
  - 「成功但沒留言」分支改為回收 agent 最終文字（`jq` 取最後一則 `type == "text"`，
    失敗則退回檔尾 20KB），**標記中和**後貼出，並截到 55000 字元
    （GitHub 留言上限 65536）；
  - 撈不到執行輸出時的訊息改成明說「這是最難診斷的形態」＋ 指向 `gh run view --log`
    （**而不是指向瀏覽器拿不到的 Actions 頁面**）；
  - prompt 末尾新增「最後一個動作必須是 `gh pr comment`」。

## 尚未完成或需注意的風險 (Pending / TODO)

- 🔴 **本修正無法在自己的 PR 上驗證**（反竄改）。真正的驗證機會是**合併後的第一個 PR**
  ——也就是 PR #29 重新 push 之後。若那時仍然沒有留言，看到的會是回收出來的文字，
  屆時才有辦法判斷根因。
- 🔴 **`execution_file` 這個 output 名稱未經實測**。`claude-code-action@v1` 的
  output 契約我沒有一手來源；程式碼寫成 fail-safe（`[ -n ... ] && [ -f ... ]`，
  取不到就走原本的訊息分支）⇒ **最壞情況是退回現狀，不會讓 workflow 失敗**。
  但若名稱錯了，回收功能等於沒有 —— 合併後第一次觸發要確認留言裡真的有內容。
- 🔴 **根因仍是推測**。「agent 把審核寫在最終回覆而沒呼叫 tool」是最符合觀察
  （`outcome=success` ＋ 3–4 分鐘 ＋ 零留言）的解釋，但**沒有直接證據**。
  不得在任何文件裡把它寫成已確認。
- ⚠️ **大型 diff 的審核品質沒有解**：本修正只保證「意見不會消失」，
  不保證「105 檔的 PR 能被審好」。若 prompt 的「縮小範圍並說明」被採納，
  審核覆蓋率會下降而且**下降幅度只在意見文字裡看得到**，沒有機制量測。
- ⚠️ **`jq` 的取法假設執行記錄是 JSON 且含 `type: "text"` 節點**。
  格式若不同會落到「檔尾 20KB」的退路——那段可能是雜訊。
