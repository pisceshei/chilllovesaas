## 已完成的工作 (Done)

### 1. 到點消費者（D53 §3.1 的五項，沒有第六項）

`Publications::ScheduledPublicationConsumer`：重讀 DB 現值（payload 只作定位）→
列不存在／已改期 ⇒ no-op → 依 `publishable_type` 分流取 status →
`status ∈ Product::PURCHASABLE_STATUSES` ⇒ `bump_publications_stamp!`。
每個 no-op 分支寫一行結構化 log（`decision:` ＝ `row_gone`／`superseded`／
`no_stamp_target`／`not_purchasable`／`unknown_payload`／`bumped`）。

三個最容易做錯的點都按 D53 落地：
- **判準取可見性軸**（`{active, unlisted}`），不是 `== ACTIVE`；
- **不合格一律 `return`，禁止 `raise`**（raise 會讓每筆不合格排程燒 8 次退避、
  在 `last_error` 留假錯誤、進 dead 表被當真事故）；
- **同 topic 兩種 payload 形狀**分流（S5 的 `scheduled` 型 vs
  `Catalog::StatusTransition` 的 `status_transition` 型——後者**沒有** `publication_id`）。

### 2. 🔴 自己抓到一條 D53 沒點名的坑：`superseded` 比對的精度

payload 走 `utc.iso8601`（**秒級**），DB 是 `datetime(6)`（微秒）。直接 `==` 會把
**每一筆合法事件**誤判成 superseded ⇒ 到點永遠不 bump。而 `T01` 那種快樂路徑
仍可能因 usec 恰為 0 而假綠。⇒ `same_second?` 兩邊取 `to_i`；任一邊缺值 ⇒ fail-closed。

### 3. 一次性 backfill

`Publications::BackfillScheduledStamps` ＋ `lib/tasks/publications.rake`。
補 S5 起投出、但因 `REGISTRY` 無該 topic 而被派給零個消費者、直接標 `published`
的排程事件（接上消費者也重放不到）。
🔴 **冪等靠 `at: row.published_at`**（不是 `Time.current`）——用後者每跑一次前進一次。

### 5. 🔴 T08 按實際契約重寫（裁定書寫「若能構造」，實測是構造不出來）

變體排程在**寫入層**就被 reject（`validate_publish_date` 的 R12，官方 help 逐字
`You can't set a future publishing date for individual product variants.`）
⇒ 變體排程事件**沒有真實生產者**。拆成兩格：
`T08a` 用真實生產者證明這條路封死（`INVALID_STATE` ＋零排程事件）；
`T08b` 直呼消費者驗防禦性分支不炸，並在 spec 內**明文標註它不是端到端**。

### 7. 關卡④⑤複驗（外部參考／關聯推理）

全文＝`docs/dev/m2-publication-scheduling.md` §9。三條要點：

- 🔴 **一條與 D53 措辭牴觸**：D53 F2 寫「業界術語＝Quartz `MISFIRE_INSTRUCTION_DO_NOTHING`」，
  但 Quartz 官方對 misfire 的逐字射程只涵蓋 scheduler 關機與 thread pool 無執行緒，
  **不涵蓋業務前置條件在到點時不成立**。而我方架構下事件永遠準時觸發，失敗的是業務條件
  ⇒ 嚴格說兩者都不是 misfire。**本包不自行改裁定**（那要走裁定程序），登記於 §9.1，
  建議下一輪把術語錨換成 K8s `concurrencyPolicy: Forbid`（三句與 F1 三句逐句同側）。
- **六條第一方逐字支持本包既有設計**（K8s 冪等、微軟 Idempotent Consumer 與 Retry pattern、
  Google SRE 重試放大、Rails `cache_version`、Rails Guides `touch: true`），
  其中 `touch: true` 的「不接線就靜默供 stale data」與 §6 的誠實登記同構。
- 🔴 **量化確認 stamp bump 目前是空動作**：全倉零生產程式碼讀
  `products.publications_updated_at`（複驗：`grep -rn "publications_updated_at" app/ lib/`
  ——命中只有寫入面與 model 宣告，無讀取端）。

### 8. 關卡①複驗補完（shopify.dev API reference，2026-07 版）

全文＝`docs/dev/m2-publication-scheduling.md` §10。30 條發現、**零條與實作牴觸**、
17 條登記未取得。三條要點：

- 🔴 **拿到比 D53 更強的判準錨**：`product-publishing` 指南的可見性三條件逐字寫
  `The product has an Active status (or Unlisted on supported channels)`
  ——官方**在同一個判準句裡把 Active 與 Unlisted 並列**，不是推論。
  ⇒ `PURCHASABLE_STATUSES` 現有三個獨立錨。
- 🔴 **修正一處措辭**：官方不是「全面沉默」，有且僅有一句
  `At the scheduled datetime, Shopify sends a product_listing/add event.`
  （且該句用單數 `product_listing/add`，與 enum 的複數 `product_listings/add` 不一致）。
  精確表述＝「官方只說到點會發事件，對補償語義沉默」。這不改變任何裁定，
  但**正面支持我方架構**（到點是事件驅動，正是 S5 投事件＋PR-C 消費的形狀）。
- **登記三處本尊文檔內部不一致**（變體排程的規則面 vs fixture 面／`Publishable`
  描述漏列 ProductVariant／集合排程無對應 SCHEDULED topic），以及一條 S10 硬約束：
  **多 catalog 沒有優先序，是聯集**（只有價格取最低）。
