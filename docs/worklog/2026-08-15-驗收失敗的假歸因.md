## 已完成的工作 (Done)

### 1. 問題：workflow 給出自信但錯誤的診斷

`.github/workflows/claude-review.yml` 在 `REVIEW_OUTCOME != success` 時貼出：

> 最常見原因：**`--max-turns` 用盡**……請到 Actions 分頁看該 run 的 annotation
> （會直接寫 `Reached maximum number of turns`）。

**PR #33 實測（連續兩次 attempt 完全相同）證偽**——
run [31857836612](https://github.com/pisceshei/chilllovesaas/actions/runs/31857836612)：

```json
{ "type": "result", "subtype": "success", "is_error": true,
  "duration_ms": 654, "num_turns": 1, "total_cost_usd": 0 }
```

annotation 實際只有：
```
Action failed with error: Claude execution failed: result is_error:true
Claude result reported subtype success with is_error:true (run did not complete successfully)
```

🔴 **完全沒有**它叫人去找的那句 `Reached maximum number of turns`。

`num_turns: 1` ＋ `total_cost_usd: 0` ＋ `duration_ms: 654` ⇒ 模型 init 成功
（log 有 `"model": "claude-fable-5"`）後**第一個 API 請求就被拒**，零花費。
這與 max-turns 用盡（跑滿 200 回合、耗時數分鐘、有花費）在數據上**完全相反**。

**排除了另外兩種可能**（不是靠推測）：
- **反竄改跳過**（本檔 31–40 行記載的形態，同樣是十幾秒＋job success）——
  排除依據有二：①PR #33 的 `claude-review.yml` 與 `origin/main` **逐字相同**
  （`git diff origin/main HEAD -- .github/workflows/claude-review.yml` 為空）；
  ②log 裡 Claude Code **確實 init 了**，被跳過的話根本不會執行到。
- **大型 diff 燒光回合**——`num_turns: 1`，一個回合都沒燒。

### 2. 修法：不要猜，把真數據撈出來 ＋ 附判準表

- 從 `execution_file` 撈 result payload，直接把
  `is_error` / `num_turns` / `total_cost_usd` / `duration_ms` 貼進留言。
- 附**兩條可自行對號入座的判準**（回合數用盡 vs 第一個請求就失敗），
  而不是替讀的人決定是哪一種。
- 刪掉「annotation 會直接寫 `Reached maximum number of turns`」這句**已被證偽的斷言**。
- `gh run view` 帶上真正的 `$GITHUB_RUN_ID`，讓指令可直接複製執行。

jq 濾鏡沿用本檔下方回收品那段的 `-s` ＋ `..` 寫法（對「單一 JSON 陣列」與「JSONL」都正確），
另加 `select(. != null)`：**沒有 `select` 的話，找不到 result 時 jq 會印出一整行
`is_error=null num_turns=null…`，看起來像有診斷、實際上什麼都沒撈到**——
那會是這次修正自己製造的新假診斷。

**自測**（三種輸入 ×「渲染出來的留言長什麼樣」都跑過）：

| EXECUTION_FILE | 撈到的診斷 |
|---|---|
| JSONL（＝PR #33 的真實形態） | `is_error=true num_turns=1 total_cost_usd=0 duration_ms=654` |
| 單一 JSON 陣列（max-turns 情境） | `is_error=true num_turns=200 total_cost_usd=4.13 duration_ms=212000` |
| 只有 init、無 result | 空 → 走 fallback 訊息（**不是**印出一行 null） |

另：`YAML.load_file` 通過；抽出兩支 `run` 腳本跑 `bash -n` 皆通過
（本檔的 244 行閉環腳本歷史上被 block scalar 與 heredoc 咬過兩次，所以這步不能省）。

## 尚未完成或需注意的風險 (Pending / TODO)

1. 🔴 **本 PR 自己不會被 Claude 驗收**（反竄改機制，見該檔 31–40 行）：
   動到 `claude-review.yml` 的 PR，驗收步驟整個跳過，且 **job 顯示 success 不是 failure**。
   ⇒ 本 PR 的修正**只有合併進 main 之後才生效**，真正的驗證機會是**合併後開的第一個 PR**。
   這也是為什麼引用保真／執行位元那組修正**沒有**綁在本 PR 裡（那組在
   `m1/citation-and-exec-bits`，可正常被驗收）。

2. ⚠️ **沒有讓 job 真的 fail**。驗收步驟失敗時 job 層 conclusion 仍是 `success`
   （被下游 `exit 0` 吞掉）⇒ `POST /actions/runs/{id}/rerun-failed-jobs` 回 **403
   「cannot be retried」**，只能整個 workflow rerun（本輪實測）。
   改成真 fail 會牽動 AUTO_MERGE 與水位邏輯的其他分支，**風險大於收益**，本輪只在註釋登記。

3. ⚠️ **判準表本身也是斷言**，只是換成「可自行核對的」形態。
   `num_turns`／`total_cost_usd` 的語義若日後被 action 改掉，這張表就要重驗。
   ⇒ 但它比上一版好在：**留言裡同時有數據與判準**，讀的人可以當場發現兩者對不上。

   🔴 **而且它初版就犯了同一個錯**（PR #36 第 1 輪 Codex review 指出，已修）：
   把 `num_turns: 1` ＋ 零花費直接判成「配額／額度／認證 ⇒ 重跑通常無效」，
   但**暫時性服務中斷、runner 網路失敗、上游一次性拒絕**會產生**一模一樣**的數據
   ⇒ 光憑這組數據**分不出**是哪一種，而我又一次替讀的人選了答案。
   修法＝兩種都列出來，並用**重跑一次**當分辨手段（重跑就過＝暫時性；
   重跑得到逐字相同結果＝持續性，那時才往帳號側查）。
   **PR #33 那次正是靠「連續兩次 attempt 完全相同」才排除暫時性的**——
   我做對了診斷流程，卻沒把那個流程寫進判準裡。

4. ⚠️ **「第一個 API 請求就失敗」的更細根因沒查出來**（配額？額度？認證？模型可用性？）。
   annotation 與 execution log 都只給到 `is_error: true`，沒有錯誤字串。
   ⇒ 這也是本次判準只寫到「帳號側」的原因，**沒有再往下猜**。
