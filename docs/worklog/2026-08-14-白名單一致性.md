# G24 豁免白名單：規則與機制三處對不上（補寫 docs/dev 時查出）

> 觸發：Codex 與 Claude 都指出「新增功能的 PR 缺 `docs/dev/m{N}-*.md`」（AGENTS.md 第 3 條）。
> 補寫 `docs/dev/m1-identity-tenancy.md` 時要填「資料表」段，逐張對照 `db/schema.rb`——
> **對照本身就查出了問題**。這是功能文檔強制驗收的實際價值，不是形式主義。

## 已完成的工作 (Done)

### 一、查出的不一致（實測 `db/schema.rb` 53 張表）

實際**沒有** `shop_id` 的只有 5 張：`role_permissions`／`roles`／`sessions`／`shops`／`staff_members`。
拿它對照鐵律 2 與 71 §A G24 的白名單，**三個方向都錯**：

| # | 問題 | 嚴重度 |
|---|---|---|
| ① | 白名單列了 5 張**我方根本沒建**的表（`organizations`／`users`／`user_roles`／`user_groups`／`user_group_roles`） | 清單失去可稽核性 |
| ② | 列了 `user_store_assignments`——但它**有且必須有 `shop_id`**，列進豁免是**反的** | 🔴 方向性錯誤 |
| ③ | **漏列 `sessions`**——migration 實際拆掉了它的 `shop_id`、CI 腳本也放行，**但規則從未授權過** | 🔴 違反 G24 配套條款③ |

根因：白名單抄自 R12 對**本尊**的觀察，用的是本尊的表名，不是我方實作的表名。

🔴 **③ 最嚴重**：配套條款③白紙黑字寫「新增白名單表必須改 CLAUDE.md 鐵律 2 與 71 §A G24」，
而 `sessions` 就是在沒改規則的情況下被機制放行的。**規則與機制對不上時，
機制照樣跑、規則變成裝飾**——而 CI 照的是機制那一份。這正是 G24 豁免最不能出事的地方。

### 二、修正（規則三處 ＋ 機制一處）

- `CLAUDE.md` 鐵律 2 註釋、`AGENTS.md` 鐵律 2 註釋、`docs/specs/71` §A G24：
  白名單改用**我方實際表名**並分成「已建 / 未建（M5）」兩列；
  明寫 🔴 `user_store_assignments` 不在豁免內、🔴 `shops` 是租戶根不是豁免項；
  配套條款③的同步對象由兩處改為**三處**（加上 CI 腳本的常數）。
- `scripts/check-tenant-isolation.rb`：
  - `ORG_LEVEL_TABLES` 拆出 `TENANT_ROOT_TABLES`（`shops`）——原本 `shops` 混在裡面，
    下面的迴圈還特地 `next if table == "shops"` 把它排除掉，等於自己知道它不同類卻放同一袋。
    拆開後這個常數**可以逐字對照規則的「已建」列**，這才是配套條款③要的可稽核性。
  - 新增 `MUST_HAVE_SHOP_ID` 常數與**白名單自檢**：把 `user_store_assignments`
    加進豁免清單就直接 exit 1。**把犯過的錯做成擋得住的機制**。
  - 通過訊息改為印出白名單全文，讓 CI log 本身就能對照規則。

### 三、順帶修掉 D8 遺留的過期註釋（驗收基準列為 🔴 的那一類）

D8 改了實作卻沒同步類別註釋，三處：

- `StaffMember` 類別註釋仍寫「**只屬於一間 Shop** 的 administrator model」——
  升組織層後這句已不成立，照它理解會以為 `can?` 不需要 shop context。
- `StaffMember#can?` 上方**疊了新舊兩份 doc 註釋**，舊那份沒提 shop 維度。
- `Role` 類別註釋仍寫「**Shop-scoped** staff role」，兩個方法的 `@note` 還寫
  「tenant-scoped SELECT」——`role_permissions` 已無 `shop_id`，早就不是了。
  已補一句：呼叫端必須自己確定「這是該 staff 在該店的角色」。
- `Role` 另補上「本尊是四段鏈、群組層排 M5」的範圍聲明。

### 四、補寫 `docs/dev/m1-identity-tenancy.md`

PR #21 落地時漏交的功能文檔，依 `docs/dev/README.md` 模板九段補齊。
