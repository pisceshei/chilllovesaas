### 1. 🔴 線上驗證：正式庫抓到一列真的壞掉的資料

部署 `98821f7` 到 bt3（`/up` 綠，第 1 次嘗試），然後跑 backfill：

```

```

「S5 已在投排程事件而消費者不存在，愈晚做要修的列愈多」。本機測試無法發現這一列。

冪等在正式庫複驗（同一指令重跑）：


### 2. 消費者整條鏈的正式庫端到端驗證（自我清理）

用**真實生產者**（`Publications::Write.publish` 帶未來 `publish_date`）在正式庫產生
一筆排程事件，走 `Events::Relay.drain!` 到消費者，實跑輸出：

```
produced event_id=74b6aa94-… available_at=2026-08-30T05:26:09Z
event=scheduled_publication event_id=74b6aa94-… decision=bumped status=active product_id=2
event=delivery_done consumer=publications.scheduled_stamp
event=outbox_published attempts=0
drained=1 event_status=published attempts=0
stamp_advanced=true  (2026-08-26 07:24:12 UTC -> 2026-08-27 05:26:09 UTC)
delivery_state="done"
cleanup: outbox_left=0 stamp_restored=true
```

⇒ 生產者 → relay 取件 → 消費者分流 → `decision=bumped` → delivery `done` →
outbox `published` → stamp 前進，**七個環節逐一在正式庫證實**；清理後
`outbox_left=0`、`stamp_restored=true`（不留測試殘骸）。
