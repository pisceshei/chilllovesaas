# 2026-08-28 · Calendar 跨月聚焦競態（rAF → useLayoutEffect）

## 已完成的工作 (Done)

1. **修掉一個真實的鍵盤可及性缺陷**：`Calendar` 跨月換頁時把補聚焦排進
   `requestAnimationFrame`，在那個窗口內按下的鍵**不經過任何 handler、被整個吞掉**。

## 🔴 根因（4 路獨立調查，3 面對抗性複驗全部反駁失敗）

跨月換頁時 `<td key={day}>` 42 格全部換 key ⇒ 當時被聚焦的那一格被卸載
⇒ `document.activeElement` 掉回 `document.body`。補聚焦排在 rAF，而 jsdom 的 rAF 是
`setInterval(…, 1000/60)` 且**只在 outstanding 數 0→1 時才建 interval**
⇒ 每次跨月都要從零等一個新的 ≈16.7ms 週期。

該窗口內若再按一次鍵：事件 target 是 `document.body`，而 `handleKeyDown` **逐格掛在
`<td>` 上、不在 body 的祖先鏈上** ⇒ handler 不執行、該次按鍵被吞掉。

**本機恆勝 / CI 偶敗的變數已定位到「兩次按鍵之間流逝的真實時間」**——
下表兩列與 §「同一台機器重現兩種結果」的四次取樣即為依據；
複驗：`node -e "let a=[];for(let i=0;i<40;i++){const t=process.hrtime.bigint();setTimeout(()=>{a.push(Number(process.hrtime.bigint()-t)/1e6);if(a.length===40){a.sort((x,y)=>x-y);console.log('p50',a[20])}},0)}"`：

| 平台 | `setTimeout(0)` 粒度 | 兩次按鍵間窗口 |
|---|---|---|
| 本機 Windows / Node 24 | p50 **15.55ms** | **54–97ms** ⇒ 恆勝（單檔 10/10、12/12） |
| CI Linux / Node 22 | 約 **1ms** | 數毫秒 ⇒ 與 16.7ms 同量級，偶敗 |

🔴 **同一台機器上重現了兩種結果**（只用 `userEvent.setup({delay:null})` 縮小窗口，
不碰 rAF）：窗口 22.2／22.8ms ⇒ `activeElement=BODY` ⇒ FAIL；
26.7／33.4ms ⇒ `activeElement=TD` ⇒ PASS。臨界值正好落在 jsdom 的幀週期上。

🔴 **同一個 head `cc09ca76` 自己就一紅一綠**（PR #163 首次 run 紅、rerun 綠），
這是獨立於任何 head 差異的直接證據。

### 反向複驗（可重跑）

不動任何 tracked 檔，用臨時 untracked setup 把 rAF 推遲 400ms：

```bash
cat > app/frontend/zz_raf_delay.ts <<'EOF'
globalThis.requestAnimationFrame = ((cb: FrameRequestCallback) => {
  setTimeout(() => cb(performance.now()), 400); return 1;
}) as typeof globalThis.requestAnimationFrame;
EOF
cat > zz.vitest.config.ts <<'EOF'
import base from "./vite.config";
const cfg: any = base;
cfg.test.setupFiles = [ "test/setup.ts", "zz_raf_delay.ts" ];
export default cfg;
EOF
npx vitest run -c zz.vitest.config.ts app/frontend/admin/components/Calendar.test.tsx
rm app/frontend/zz_raf_delay.ts zz.vitest.config.ts
```

- **修法前**：`Tests 1 failed | 17 passed` — 失敗訊息與 DOM 與 CI **逐字相同**
- **修法後**：`Tests 22 passed (22)`

## 突變測試（逐一實跑）

| 突變 | 結果 |
|---|---|
| **M-A** 把聚焦改回排進 rAF | ✔ 轉紅 **3 格**（C1、C2、既有的「tabindex 跟著焦點移動」） |
| **M-C3** 拿掉 `roving === null` 守衛 | ✔ 轉紅 **2 格**（C3、C4） |
| **M-C4′** 只拿掉 `!inMonth(roving)` 守衛 | ⚠ **未轉紅** |
| **M-C5** 再加上「ref 卸載時不刪」 | ⚠ **仍未轉紅** |

🔴 **M-C4′／M-C5 殺不掉是「預期內」，誠實登記而非硬補測試**：
`ref` 回呼在卸載時 `cellRefs.current.delete(day)`，所以舊月份的 key 早已不在 map 裡；
就算保留失效節點，**對已卸載元素呼叫 `focus()` 依規範也是 no-op**。
⇒ `!inMonth(roving)` 是**純防禦、可證明不可觀測**。保留它是因為代價為零且把前提寫成了程式碼，
但**不得**把它當成有測試覆蓋的防線——這一點已寫進 `Calendar.tsx` 的註釋。

### C2 的第一版在本機假綠（自己踩到同一個坑）

C2 初版用 `userEvent.keyboard` 連按兩次，**M-A 殺不掉它**——因為 userEvent 每個按鍵步驟之間
插一次 `setTimeout(0)`，在 Windows 上把窗口撐到 54–97ms，rAF 恆勝。
改用 `fireEvent` 同步連續派發（窗口為 0）後才轉紅。
⇒ **驗競態的測試不得用會插入 macrotask 的輸入模擬**。
