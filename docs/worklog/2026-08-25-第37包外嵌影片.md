### 先取證再動手（鐵律 16），而取證推翻了三個我原本會寫錯的東西

   不存在（複驗＝external-facts §D1 的兩條官方 URL；`ExternalVideo.host` 的宣告
   逐字是 `MediaHost!`）。憑印象命名會建出一個本尊沒有的型別。
2. **`presentation` 只在 Storefront API，Admin 沒有**；`aspectRatio` 只有 Liquid 有。
   抄錯層＝憑空多一個本尊 Admin 沒有的欄位 ⇒ 兩個都不宣告。
3. **官方對「該貼哪種 URL」自相矛盾**（API 範例用 `youtu.be`、dev 指南說
   "embed or share URL"、help 只列 watch／vimeo 頁 URL），**沒有任何規範性語句**
   ⇒ 我方接受的形態集合**全部標 ours**，不得寫成「對齊 Shopify」。

證據全集（含逐字原文與 URL）落 `docs/dev/external-facts.md` §D1–D8。

### 🔴 注入面的主防線在資料層，不在樣板層

`javascript:` URL 放進 `<iframe src>` 是合法導航脈絡，而 MDN 逐字載明該 script
**繼承載入它的文件的 origin** ⇒ 那是在我方 origin 執行的完整 XSS（讀得到 admin
cookie、打得到 admin API）。`data:` 拿到 opaque origin、偷不到 cookie，但仍可在
我方頁框內渲染攻擊者完全控制的 HTML。

⇒ `Catalog::ExternalVideoUrl` 的設計目標就是**讓使用者字串永遠到不了 `src`**：
落庫的只有一個封閉值域的 `host`（youtube／vimeo）與一個受字元集約束的 `external_id`，
其餘（`?si=`、`&list=`、`&t=`、fragment、userinfo）**一律丟棄**。
`origin_url` 與 `embed_url` 都由 limits 樣板**重建**。CSP `frame-src` 白名單
（第 33 包）是第二道，不是第一道。

### 🔴 embed URL 導出不落庫

隱私決策（youtube-nocookie、Vimeo `dnt=1`）會變。落庫＝改設定之後舊資料還停在舊網域，
要跑 data migration 才救得回來；導出＝翻一個 limits 鍵全店立刻生效。

### 🔴 D48 的窄縫：外嵌影片的 alt 住在媒體列

D48 把 alt 權威搬到 `files.alt_text`（一張圖一份說明）。**但外嵌影片沒有檔案**
——它的 alt 無處可住，除非用回 `media.alt_text` 那個 D48 剛停用的欄位。

處置＝開一條**只認 `media_type == 'external_video'`** 的窄縫。
🔴 **不得放寬成「file 為 nil 就回落」**：那樣 D48 停用的舊語義會從 M0 遺留圖片列
的後門復活。已下反向 spec 釘住（沒有檔案的**圖片**列仍然回 nil）。

同理 `status` 也要分支：A 面外嵌沒有 `stored_file`、湊巧落到 `object.status` 而正確，
但 B 面一旦把縮圖檔掛上 `file_id`，**媒體狀態會被縮圖檔的狀態冒充**——影片好好的、
縮圖還在處理，卡片卻顯示「處理中」。現在就分開，B 面不必回頭改。

### 🔴 兩個 limits 鍵，不是一個

`upload_media_types_enabled`（可上傳）與 `embed_media_types_enabled`（可外嵌）
**是不同的事**。合併成一鍵會把 B9 的閘門一起弄鬆——那個閘門正是靠
`upload_media_types_enabled == [image]` 擋住影片上傳的，而 `m0_configuration_spec`
釘死了它。`MediaContentTypeEnum` 改成兩鍵聯集，`upload_*` **一個字都沒動**。

### 對抗式審查：10 個根因（受審 SHA 已凍結後才派）

25 項主張、14 項經獨立反駁複驗成立、收斂成 **10 個根因**，全部修完。
本輪的複驗品質特別高——確認的 finding 幾乎都附了**在凍結樹上實跑**的復現。

🔴 **最值得記的三個**：

1. **Vimeo unlisted hash 的兩個載體只擋了一個**（EVU-1）。path 形態
   `vimeo.com/{id}/{hash}` 被刻意拒收，但同一個 hash 的 query 形態 `?h={hash}`
   ——**官方 Share→Embed 給的正是這個形態**——被「丟棄追蹤參數」的一般規則
   靜默吃掉 ⇒ 存進去一個缺了 hash、前台一定播不出來的影片，建立當下零錯誤。
   守衛要對「同一個輸入的所有載體」封閉，不是對「我想到的那個載體」。
2. **D48 窄縫的第二個消費者漏了**（R6-EV-1／P37-W1）。窄縫第一版寫在
   `MediaType#alt` 裡，`mediaMissingAltCount` 沒跟上 ⇒ 填了 alt 的外嵌影片被
   永遠算成「缺 alt」，而且**清不掉**。修法＝把判準抽成 `Media#alt_authority`
   單一落點（複驗＝`git grep -n alt_authority app/`，D48 分支只應出現在
   `app/models/media.rb` 一處）——有趣的是 migration 註釋早就在引用這個名字
   （當時它不存在，審查 F6 同時抓到）；兩個 finding 從相反方向指到同一個正解。
3. **影片排第一格時 featuredImage 變 null**（P37-W2／R6-EV-2／FE-2）。
   舊寫法取 position 最小的媒體、沒檔案就放棄 ⇒ 商品列表對一個明明有圖的商品
   顯示「沒有圖片」，而媒體卡首格又掛著「精選」標——前後台兩份互相矛盾的真相。
   修法＝後端改「position 序第一個有檔案的媒體」、前端精選標同步掛到第一個
   圖片 tile，兩邊同一個語義。

其餘：**分派判準用錯謂詞**（EVU-2：「parse 成功」≠「host 命中」——shorts 這種
「認得的平台、抽不出 id」被分派去 FileCreate，伺服器對 youtube.com 抓一份 HTML、
回無關錯誤）／**modal 送出中沒鎖關閉途徑**（FE-1：失敗靜默、成功變「取消了卻加進去」）／
**重開 modal 留著病灶丟了診斷**（FE-3：url 不清、error 清掉）／**一條恆真的假斷言**
（FE-7：`queryByText("處理中")` 對實際文案「處理中…」永遠 null）／
**兩處易腐數字**（F1／F2）／**U 編號錨點解析不到**（F5）／**引用不存在的方法**（F6，
被 alt_authority 的誕生順手治好）。

🔴 修法的七道新守衛同樣逐一突變驗證（刪掉轉紅）。
