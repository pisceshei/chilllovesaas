### 2. 🔴 handle 的權威遷移（本 PR 真正改變行為的那一項）

`Publication.online_store` 從

```ruby
find_by(channel_handle: Shop::DEFAULT_CHANNEL_HANDLE)
```

改成

```ruby
joins(:channel).find_by(channels: { handle: Shop::DEFAULT_CHANNEL_HANDLE })
```

⇒ `publications.channel_handle` 降級為 **legacy 快照**（欄位不刪，刪欄要改所有讀取端，屬 S1）。

**這讓 `channels` 成為載重表而不是預留表**。沒有這一步，三張新表就只是「有寫入者、
沒有讀取者」的空殼——那正是 `publications.catalog_id` 空轉兩週的形態，也正是 S0 要收的口。

副作用（刻意）：**沒有 channel 的 publication 在 `.online_store` 眼中不存在**。
channel 是管道的身分，沒有身分的 publication 是資料損壞，不該被當成可用管道回傳。
兩條建立路徑（`Shop#after_create` 與回填）都保證有 channel。

### 3. 🔴 實作前查官方文檔，推翻設計文件三處（鐵律 16.1）

來源＝shopify.dev 的 `App`／`AppInstallation`／`Channel` 三個型別頁，取證 2026-08-26。

| # | 設計文件原文 | 官方實際 | 處置 |
|---|---|---|---|
| 1 | `has_channel_capability` boolean | **沒有這個欄位**；管道能力是 `App.channels: ChannelConnection!` | 不建該欄——旗標會與現實不同步，connection 不會 |
| 2 | `first_party` boolean | 官方欄名是 `shopifyDeveloped: Boolean!` | 改用 `shopify_developed` |
| 3 | `installed_at` ＋ `uninstalled_at` | 官方 `AppInstallation` **沒有任何時間戳、沒有卸載狀態欄** | 兩欄保留但改標 `ours`，逐條登記於 model 檔頭 |

同批發現 `AppInstallation.channel` 與 `.publication` **都已 deprecated**
⇒ 現行連結方向是 `App.channels`，我方外鍵因此掛在 `channels.app_installation_id` 這一側。

### 4. 刻意不建的官方欄（都有官方定義，都沒有寫入者）

- `channels.name`（`Channel.name: String!`）——🔴 **鐵律 7 判斷不是延後**：
  顯示名的權威在 `sales_catalogs.title`，再開一個就是第三個產生處。
- `channels.supports_future_publishing`——本尊 `Publication` 與 `Channel` 兩邊都有，
  我方只留 `publications` 那一份。
- `channels.account_id`／`account_name`／`resource_feedback_state`／`specification_handle`
  ／`active_regions`（多連線與讀取面衍生，v1 無流程）。
- `platform_apps` 的 `apiKey`／`embedded`／`published`／`developerType`／`publicCategory` 等。

判準統一：**建無人寫的欄＝重演 `publications.catalog_id` 空轉兩週那個坑**。

### 5. `Shop#after_create` 從 2 列變 4 列

`app_installation → sales_catalog → publication → channel`，同一個 transaction。
`Shop` 的 `has_many` 宣告順序改成建立順序的**反序**
（`channels → publications → sales_catalogs → app_installations`），因為 `dependent:`
是逆著外鍵方向刪的。順序錯了不是「刪不掉」這麼明顯，而是**錯誤訊息指不出根因**。

### 6. 配對 migration spec ＋ 四個突變複驗

`spec/migrations/s0_backfill_channels_spec.rb`，13 格（含非交易 DDL 往返群組）。

「installation 已建、channel 還沒建」——而那正是 **migration 半途死掉**留下的狀態
（MySQL DDL 非交易，第 11 包就是這樣炸的）。補上該格之後才轉紅。
覆蓋的情境集合以 spec 為準：
`grep -n "^  it \|^    it " spec/migrations/s0_backfill_channels_spec.rb`

### 7. 🔴 `db:schema:load` 不跑種子段（同一個坑，倉庫三天前踩過一次）

字典空的測試庫上**每一次 `create(:shop)` 都會失敗**，訊息是
`Validation failed: Platform app must exist`——完全看不出是「測試庫少了種子」，
而且會讓一堆**與本改動無關**的 spec 一起紅（實測 24 個失敗，多數在 translations）。
解法照抄既有先例：新增 `spec/support/platform_apps_seed.rb`（`before(:suite)` 呼叫 `seed!`），
與 `spec/support/platform_locales_seed.rb` 同形態。並把這個配套寫進 CLAUDE.md 鐵律 2
的平台字典表段，免得下一張字典表再踩一次。
