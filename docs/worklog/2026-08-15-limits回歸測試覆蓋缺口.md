## 已完成的工作 (Done)

### 1. 先量，再修：突變測試找出缺口

`scripts/test-limits-key-rules.rb` 初版有三條 fixture，看起來是「有回歸測試」的。
但**有測試 ≠ 測到東西**。把 `check-limits-keys.rb` 改壞成六種形態實測：

| 突變 | 補之前 | 補之後 |
|---|---|---|
| M1 判定反轉（`is_a?(String)` → `if false`） | ✅ 抓到 | ✅ |
| **M2 只認 TrueClass**（放行 FalseClass／NilClass／Date） | 🔴 **沒抓到** | ✅ |
| **M3 刪掉 Sequence 遞迴**（陣列裡的鍵不掃） | 🔴 **沒抓到** | ✅ |
| **M4 ERB 閘門收窄**成只認單一字面值 | 🔴 **沒抓到** | ✅ |
| M5 ERB 閘門整個拿掉 | ✅ 抓到 | ✅ |
| M6 只掃第一層（不遞迴進 value） | ✅ 抓到 | ✅ |

**六分之三存活** ⇒ checker 實際擋得住的東西有一大半沒有任何測試在守，改壞了不會有人知道。

🔴 **這正是 65 §K.7「檢查本身也要被測試」要防的東西的下一層**：
上一輪補了回歸測試，本輪才發現那份回歸測試自己有一半是空的。
**「有沒有測試」和「測試有沒有效」是兩個問題。**

### 2. 補五份 fixture，關掉三個缺口

| fixture | 關掉的缺口 | 為什麼這一份重要 |
|---|---|---|
| `limits_false_key`（`no:`） | M2 | 🔴 **`no` 是挪威的 ISO 3166 代碼**——鐵律 11 的法域 pack 最可能踩到的一種。補之前這條路徑完全沒被守住 |
| `limits_nil_key`（`~:`） | M2 | nil 與布林是不同分支 |
| `limits_date_key`（`2026-08-15:`） | M2 | 生效日／匯率日結那類以日期當鍵的表會踩到 |
| `limits_seq_key`（sequence 內的 mapping） | M3 | 真實 `config/limits.yml` 有 **17 處**這種結構，補之前整片沒掃到 |
| `limits_erb_tag`（`<% if %>` 控制流標籤） | M4 | 與輸出型標籤是不同寫法；少了它，把 `ERB_TAG` 收窄成單一字面值不會被抓到 |

CASES 的斷言一併加嚴：除了 exit code，還要求輸出**點名解析出的型別**
（`FalseClass`／`NilClass`／`Date`），否則「擋下來了但擋錯理由」會被當成通過。

### 3. 🔴 修掉 `limits_erb`：它證明不了它宣稱的事

原本那份 fixture 的**註釋裡寫了一個完整的 ERB 標籤**。後果：

```
把下面那行真正的違規刪掉、只留註釋  →  checker 仍然打紅
```

因為閘門讀的是整份檔案的文字，**註釋自己就命中了**。
⇒ 那份 fixture 分不出「擋 ERB 鍵」與「擋註釋裡出現的字串」，等於沒有證明任何事。

修法：註釋改成**不寫出 ERB 標籤字面**（用文字描述），違規行改用 `<%= ENV["SOME_KEY"] %>`。
修後實測：拿掉違規行、只留註釋 → checker **exit 0 通過**（不再自我誤觸）。

🔴 形態＝**檢查器被自己的文字騙過**，與本專案其他幾次同型
（`check-ci-parity.rb` 因此刻意只認 `step` 開頭的行，不認註釋）。

## 尚未完成或需注意的風險 (Pending / TODO)

1. ⚠️ **突變測試本身沒有進 CI**，它是本輪的一次性工具（在 scratchpad）。
   ⇒ 日後有人**新增**檢查規則時，不會自動被提醒「你的新規則沒有 fixture」。
   要機制化的話有兩條路：①把突變清單固化成腳本進 CI（每次跑會慢很多）；
   ②在 `test-limits-key-rules.rb` 加一條「CASES 數量 ≥ checker 的違規分支數」的粗略斷言。
   **兩條都沒做**，本輪只把結論寫進檔頭讓下一個人知道要想這件事。

2. ⚠️ **突變清單不完備**。六種是我想到的，不是窮舉。
   例如「把行號報錯」「把 TARGETS 改成空陣列」「把 exit 1 改成 exit 0」都沒測。
   ⇒ 「6/6 抓到」的正確讀法是「**這六種**改壞法會被抓到」，不是「改壞一定會被抓到」。

3. ⚠️ **`limits_clean` 仍是唯一的反向斷言**。若日後有人把 checker 改成「永遠 fail」，
   只有這一條擋著。它夠用，但只有一條。

4. ✅ **驗收 Y1／Y2／Y3 三條已全部關閉**，並各自有 fixture 守著。
   同批驗收的其餘 6 條（Y4/Y5/Y6 執行位元閘門、Y7/Y8 驗收 workflow、Y12 workflow 語法閘門）

## 驗收後修正（PR #40 第 1 輪 Codex review，三條全部成立）

### 🔴 `limits_erb_tag` 犯了**這個 PR 自己剛修掉的那個 bug**

該 fixture 的註釋裡寫了閘門的正則字面（`/<%/`）⇒ 把下面真正的違規行刪掉、
只留註釋，checker **仍然打紅**（實測 exit 1）。

🔴 **同一個自我觸發的坑，在同一個 PR 裡踩了兩次**——
上半段才把 `limits_erb` 的註釋改成不寫 ERB 字面，下半段新增 `limits_erb_tag` 時又寫了進去。
修後實測：只留註釋 → **exit 0**，不再自我觸發。

### 🔴 sequence case 的斷言太弱，抓不到路徑退化

原本只斷言輸出含 `TrueClass`。Codex 指出：把走訪從 `key_path + [i.to_s]`
改成 `key_path`（診斷路徑退化成 `rules.on`，索引消失）**八條全綠**。

實測確認，並改成斷言**帶索引的完整路徑 `rules.0.on`**。
再跑同一個突變 → **exit 1，抓到了**。

⇒ 教訓：**斷言要貼著「這個 case 存在的理由」**。這條 fixture 是為了守 Sequence 遞迴分支，
那就該斷言只有那條分支才產得出的東西（帶索引的路徑），而不是任何違規都會有的型別名。
