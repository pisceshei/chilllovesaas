### 1. 先量，再修：突變測試找出缺口

`scripts/test-limits-key-rules.rb` 初版有三條 fixture，看起來是「有回歸測試」的。
但**有測試 ≠ 測到東西**。把 `check-limits-keys.rb` 改壞成六種形態實測：

| 突變 | 補之前 | 補之後 |
|---|---|---|
| M1 判定反轉（`is_a?(String)` → `if false`） | ✅ 抓到 | ✅ |
| **M2 只認 TrueClass**（放行 FalseClass／NilClass／Date） | 🔴 **沒抓到** | ✅ |
| **M3 刪掉 Sequence 遞迴**（陣列裡的鍵不掃） | 🔴 **沒抓到** | ✅ |
| **M4 ERB 閘門收窄**成只認單一字面值 | 🔴 **沒抓到** | ✅ |
| M5 ERB 閘門整個拿掉 | ✅ 抓到 | ✅ |
| M6 只掃第一層（不遞迴進 value） | ✅ 抓到 | ✅ |

**六分之三存活** ⇒ checker 實際擋得住的東西有一大半沒有任何測試在守，改壞了不會有人知道。

🔴 **這正是 65 §K.7「檢查本身也要被測試」要防的東西的下一層**：
上一輪補了回歸測試，本輪才發現那份回歸測試自己有一半是空的。
**「有沒有測試」和「測試有沒有效」是兩個問題。**

### 2. 補五份 fixture，關掉三個缺口

| fixture | 關掉的缺口 | 為什麼這一份重要 |
|---|---|---|
| `limits_false_key`（`no:`） | M2 | 🔴 **`no` 是挪威的 ISO 3166 代碼**——鐵律 11 的法域 pack 最可能踩到的一種。補之前這條路徑完全沒被守住 |
| `limits_nil_key`（`~:`） | M2 | nil 與布林是不同分支 |
| `limits_date_key`（`2026-08-15:`） | M2 | 生效日／匯率日結那類以日期當鍵的表會踩到 |
| `limits_seq_key`（sequence 內的 mapping） | M3 | 真實 `config/limits.yml` 有 **17 處**這種結構，補之前整片沒掃到 |
| `limits_erb_tag`（`<% if %>` 控制流標籤） | M4 | 與輸出型標籤是不同寫法；少了它，把 `ERB_TAG` 收窄成單一字面值不會被抓到 |

CASES 的斷言一併加嚴：除了 exit code，還要求輸出**點名解析出的型別**
（`FalseClass`／`NilClass`／`Date`），否則「擋下來了但擋錯理由」會被當成通過。

### 3. 🔴 修掉 `limits_erb`：它證明不了它宣稱的事

原本那份 fixture 的**註釋裡寫了一個完整的 ERB 標籤**。後果：

```
把下面那行真正的違規刪掉、只留註釋  →  checker 仍然打紅
```

因為閘門讀的是整份檔案的文字，**註釋自己就命中了**。
⇒ 那份 fixture 分不出「擋 ERB 鍵」與「擋註釋裡出現的字串」，等於沒有證明任何事。

修法：註釋改成**不寫出 ERB 標籤字面**（用文字描述），違規行改用 `<%= ENV["SOME_KEY"] %>`。
修後實測：拿掉違規行、只留註釋 → checker **exit 0 通過**（不再自我誤觸）。

🔴 形態＝**檢查器被自己的文字騙過**，與本專案其他幾次同型
（**PR #39 的** `check-ci-parity.rb` 因此刻意只認 `step` 開頭的行，不認註釋——
⚠️ 該檔在本 PR 送審時 2026-08-15 尚未進 main）。

## 驗收後修正（PR #40 第 2 輪，多代理驗收 2026-08-15）

### 🔴 第二輪突變：**行號從頭到尾沒有被守**

第 1 輪把「型別分支」的缺口關掉後再突變一次，又有三種存活：

| 突變 | 改法 | 一開始的結果 |
|---|---|---|
| M9 | `key_node.start_line + 1` → `key_node.start_line`（忘了 Psych 是 0-based） | **全綠** |
| M10 | 行號寫死 `1` | **全綠** |
| M13 | 不印 `#{rel}:#{line}` 前綴，只留型別與路徑 | **全綠** |

原因是 needle 只有 `TrueClass`／`Date` 這種**型別名**，行號怎麼算都不影響它命中。
而行號正是這支 checker 的實用價值——真實 `config/limits.yml` 一千多行，
報「有一個鍵是 TrueClass」卻不指到行，人得自己二分搜尋。

**修法**：五條純型別斷言拆成兩條——一條 `config/limits.yml:<行號> 鍵 \`…\``、一條型別名。
拆開而不是合併成一條複合字串，是為了**壞掉時看得出是行號錯還是型別判定錯**。
⇒ `CASES` 8 條 → **13 條 / 9 個 fixture**。

⚠️ **行號寫死在 CASES 裡，這是刻意的耦合**：改動任一 fixture 的行數就必須同步改斷言。
fixture 一動，斷言就該重新確認，不該靜默沿用。

### 🔴 `TARGETS` 的 fail-closed 分支零覆蓋

```ruby
unless File.exist?(path)
  warn "::error::#{rel} 不存在——TARGETS 列了一個不在倉庫裡的檔案⋯"
  exit 1
end
```

`TARGETS` 只有 `config/limits.yml` 一項，而它在本倉庫**一直都在**
⇒ 這個分支在 CI 上**永遠走不到**。把整段刪掉、或把 `exit 1` 改成 `next`
（＝「檔案不在就跳過」），在真倉庫上**完全看不出差別**——
而 checker 已經退化成「**檔案被改名／搬走／誤刪時，照樣 exit 0 報通過**」，
鐵律 6 的唯一上限值來源不見了卻沒人知道。

**修法**：新增 `spec/fixtures/ci_violations/limits_missing_target/`，
內容就是「**它沒有 `config/limits.yml`**」——只放一份 README 把目錄帶進 git
（git 不追蹤空目錄），README 第一行就寫明「不要在這裡建 limits.yml，建了等於刪掉這條測試」。

### 🔴 順手修掉一個寫 Pending 時才發現的真缺口：`TARGETS = []` 會印「通過」

寫上面那條 Pending 時列舉「還沒測的突變」，第一個想到的就是把 `TARGETS` 清空。
實測 → **`OK：limits.yml 鍵型別檢查通過`，exit 0**。

**「沒有違規」與「沒有檢查」在輸出上長得一模一樣**：迴圈一次都沒跑，
`violations` 自然是空的，於是腳本報通過，而鐵律 6 的唯一上限值來源根本沒被讀過。

修法＝加 `scanned.empty?` canary（形態與 `#42` 的 `checked_runs.zero?` 相同），
並把成功訊息從「掃描檔案：config/limits.yml」改成「掃描檔案：**1 個**（config/limits.yml）」
——**把數量印出來**，讓「0 個」在人眼前也是刺眼的。

| 突變 | 結果 |
|---|---|
| M16 `TARGETS = %w[]` | 修前 **exit 0 印「通過」** 🔴 → 修後 **exit 1** ✅ |

⚠️ 這條 canary **無法用 fixture 覆蓋**（見 Pending 8）。

### 本輪新增的 Pending

5. ⚠️ **行號斷言與 fixture 行數是硬耦合，沒有任何機制守著。**
   有人在 `limits_date_key/config/limits.yml` 上面多加一行註釋，

   但如果對方順手把 `CASES` 的期望也改成 0，就沒人擋了。
   ⇒ 更強的做法是在測試裡**主動斷言該目錄下不存在 `config/limits.yml`**，本輪未做。

   但那是**運氣**——它是寫 Pending 時想到的，不是任何機制找出來的。

8. 🔴 **`scanned.empty?` canary 沒有、也不可能有 fixture 守著。**
   `TARGETS` 是腳本內的常數，fixture 目錄改不了它 ⇒ 這條 canary 是**自己守自己**。

   ⚠️ 同型缺口也存在於 `#42` 的 `checked_runs.zero?` canary，兩者是同一種無解形態。
