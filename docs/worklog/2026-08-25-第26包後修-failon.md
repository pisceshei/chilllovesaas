# 2026-08-25 第 26 包後修：`fail_on` 下錯層（線上驗收抓到）

對應規格：第 26 包（PR #127）後續；13 §F3-2（像素上限與壞檔 rescue）。

## 已完成的工作 (Done)

- 🔴 **線上驗收幕五實測推翻既有實作**：截斷檔（JPEG 只剩 1/3）走完整條管線後
  `status=ready`——`fail_on: :error` 下在 `thumbnail_buffer` **無效**。
  bt3 實測兩路徑對照已登記 `docs/dev/external-facts.md` C1。
- `MediaPipeline::VipsBackend` 重構成「**一次 `open` 載入、四個 variant 共用**」：
  `open` 用 `new_from_buffer(bytes, "", fail_on: :error).autorot`（fail_on 在 loader
  層才生效；autorot 一次做掉，後續 `thumbnail_image` 不會再轉），回 `Source`；
  `Source#derive(spec)` 做 `thumbnail_image` → `colourspace(:srgb)` →
  `write_to_buffer`——解碼在此發生，截斷檔的 `premature end` 從這裡拋、由白名單
  分類成 `DecodeFailed`（終態 failed）。
- 代價登記：失去 shrink-on-load（`thumbnail_buffer` 的優勢），由 20MP 上限
  （`content.files_image_max_megapixels`）兜住最壞情況——註釋已寫明。
- `docs/dev/external-facts.md` 新增 §C（影像處理）兩條：C1 `fail_on` 下錯層、
  C2 `Vips::Image#set` 對未知欄位需 `set_type`（後者是驗收腳本造測資時踩到）。

## 修改的檔案與核心邏輯 (Changes)

- `app/services/media_pipeline/vips_backend.rb`：`probe`／`derive` 兩個類方法
  改成 `open` → `Source#derive`；檔頭 ② 寫明實測依據。
