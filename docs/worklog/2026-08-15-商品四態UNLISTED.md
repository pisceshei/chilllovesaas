# 工作記錄：Product 第四狀態 UNLISTED（M1 PR-1 第 2 步，2026-08-15）

## 已完成的工作 (Done)

商品狀態補上第四值 `UNLISTED`（**可購買但不可被發現**）。
`limits.yml:804` 從一開始就是四值，而 `Product::STATUSES` 與 `ProductStatusEnum`
都停在三值——**三份清單各寫一份，漂移沒有任何跡象**。本步把後兩者改成由前者產生。

🔴 **為什麼 UNLISTED 不是「多一個狀態」而已**：它的存在本身就證明
「可購買」與「可被發現」是**兩個獨立維度**。三態時兩維完全同步，所以一個
`published` 布林兼管兩件事剛好不出錯；補上 UNLISTED 必定撞牆——
要嘛它完全買不到（商家把直接連結給客人卻結不了帳），
要嘛它出現在搜尋與 sitemap 裡（SEO 事故）。

**無 migration**：`products.status` 是 `varchar(32)` 且無 CHECK constraint，
本步驗證 `git diff --exit-code db/schema.rb` 為零 diff（動了就是做錯了）。

### 🔴 負面驗證：把 enum 退回三值 → 5 條紅

含**端到端序列化**那條。本輪之前，任何 `status = unlisted` 的商品查詢都會拿到
序列化錯誤，而既有 7 條契約測試全部只用 `draft` 的商品 ⇒ **這條路徑從未被走過**。

### 前端：逐欄對照原型 `P_STATUS`，不自創

| 狀態 | 原型 `bt` | 原型 `pip` | 本輪處置 |
|---|---|---|---|
| ACTIVE | 啟用中 | full | 文案 **「使用中」→「啟用中」**（原文案是本專案自創） |
| UNLISTED | 未列出 | `''`（裸圈） | pip **`half` → `empty`** |
| DRAFT | 草稿 | `''` | 已相符 |
| ARCHIVED | 已封存 | **blocked** | ⚠ 未對齊，見 Pending |

🔴 **pip 也要釘進測試，不是只釘文案**。UNLISTED 原本寫 `half`（半圈＝進行中），
語義上是錯的——它不是「進行中」，它是「啟用但不被發現」。
**文案斷言抓不到這種錯，只有 pip 斷言抓得到。**

### 🔴 刻意不做：`purchasable` / `discoverable` 具名 scope

13 §F1.2(d) 的 scope SQL 用 `product_publications` 與 `variant_publications`
兩張**不存在的表**（我方落地的是多型的 `resource_publications`，見 88 號），
而 `20260814200000` 的回填**一列 ProductVariant 都沒有**：

- 照規格加上變體層 `EXISTS` ⇒ **全站每個商品都靜默變成不可購買**；
- 省略變體層 ⇒ 一個叫 `purchasable` 的 scope 只做了三層 AND 的第一層，**名字在說謊**。

兩條都比「現在沒有這個 scope」更糟。改為只交付狀態集合＋單一產生器，
並用一條 spec（`expect(described_class).not_to respond_to(:purchasable)`）
把「刻意沒有」釘住，避免下一輪有人以為是漏做。

## 尚未完成或需注意的風險 (Pending / TODO)

- 🔴 **ARCHIVED 的 pip 未對齊**：原型是 `pip:'blocked'`（透明底＋斜線），
  而 `docs/design/23-interaction-css-spec.md` §1 的 Badge 規格只定義**三種** pip
  （空圈=未開始／半圈=進行中／實圈=完成），**沒有 `blocked`**。
  ⇒ **原型與 CSS 規格本身不一致**，補第四種 pip 是視覺語言變更，不該夾在
  「加一個商品狀態」裡靜默做掉。測試刻意斷言**現況**（`full`），
  之後真的去對齊時那條會紅，逼人回來讀這段。
- 🔴 **`purchasable` / `discoverable` 具名 scope 延後**，理由見上。
  解鎖條件＝63 §H.2 與 88 的發布模型收斂（`product_publications`／`variant_publications`
  vs `resource_publications` 二選一），且變體層 `resource_publications` 要先有回填。
- 🔴 **13 §F1.2 的六條驗收本輪只完成三條**：狀態值域、GraphQL enum、前端呈現。
  另三條延到 M2／M5——`unlisted_meta_robots` 注入（前台，M2）、
  `unlisted_excluded_from` 的八個排除點（sitemap／搜尋／系列／推薦／feed／
  agent catalog／JSON-LD／hreflang，散在 M2 與 M5）、市場 catalog 排除（M5）。
- **UNLISTED 的狀態機合法轉移邊沒有規格**：`docs/research/06` 只寫
  DRAFT → ACTIVE ⇄ ARCHIVED（無 UNLISTED）；13 §F1.2 的副作用表只定義
  ACTIVE→UNLISTED、UNLISTED→ACTIVE、\*→DRAFT/ARCHIVED 三種。
  DRAFT→UNLISTED、ARCHIVED→UNLISTED、UNLISTED→ARCHIVED 是否合法未寫。
  ⇒ **本輪不加轉移驗證**（加了就是發明規則）；第一支 `productUpdate` 前要裁定。
- **排程發布是否接受 UNLISTED**：88 §5 的 M1 待辦第 3 項寫「排程發布要求商品為 Active」，
  但沒定義 UNLISTED 算不算「Active」——它語義上是「active 但不可被發現」。
  這條會直接決定 `resource_publications.published_at` 設未來時間時的驗證式。
- **admin 商品列表的 status 篩選器沒做**：13 §F1.2(e) 要求「四態全顯示並提供 status 篩選」
  並引 60 §5，但 `docs/research/60` 只記錄了檢視列與排序選單、**沒有實測任何 status 篩選控件**，
  原型 `renderProducts` 也完全沒有篩選器；另 DOCS 條目 `prodtable` 寫
  「封存不出現於預設檢視」，與「四態全顯示」措辭衝突 ⇒ 預設檢視含不含
  ARCHIVED／UNLISTED **未定**。登記為 V 項，需回頭實測本尊。
- **CSV 匯入器的 `never_infer_unlisted: true`**：擴 enum 時**不得**順手把
  `value_maps.status` 補上 unlisted，也不得加「Published=FALSE ⇒ UNLISTED」的推導。
  這是擴 enum 時最自然的「順手」動作，寫在這裡當路障。
- **`Limits` 與 `GraphqlLimits` 兩個入口並存**：刻意的（型別防呆不同），
  但兩者都讀 `Rails.configuration.x.limits`。若日後要合併，`Integer(value)` 那層強制轉型
  不能丟——丟了就會讓 cost point 寫成字串時靜默通過。
