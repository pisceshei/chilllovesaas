# 工作記錄：冪等參數指紋（M1 PR-1 第 5 步，2026-08-15）

> 規格出處：`docs/specs/11` §2.1(d)｜清單讀取器已在 S4 一併落地（`BaseMutation` 依賴它）

## 已完成的工作 (Done)

`Idempotency::CanonicalJson`——把 mutation 的 input 算成一個**穩定的**指紋。

🔴 **不做正規化的後果不是「指紋不準」，是「卡死」**：同一個請求換一下欄位順序就會算出
不同指紋，於是重試被判成「同一把 key 用於不同參數」
（`IDEMPOTENCY_KEY_PARAMETER_MISMATCH`），而呼叫端明明什麼都沒改。
逐字依據是官方的「Ensure consistent ordering of input fields to avoid fingerprinting mismatches」。

五條規則各有理由，也各有**反向**斷言——「規則生效」與「規則沒有過度生效」是兩件事：

| # | 規則 | 反向斷言 |
|---|---|---|
| ① | key 遞迴字典序排序 | 值不同 ⇒ 指紋必須不同 |
| ② | 移除 null 欄位 | **空字串不是 null**、**false 不是 null**，兩者都不得被移除 |
| ③ | 陣列**保持原順序**（順序有語義） | 順序不同 ⇒ 指紋必須不同；但元素**內部**的 key 仍要排序 |
| ④ | 數字一律整數 cents | 負整數**不得** raise（65 §A.7：型別層不驗正負） |
| ⑤ | 不含 `idempotencyKey` 本身 | 換 key 但參數相同 ⇒ 同指紋（**這正是偵測 mismatch 的前提**） |

### 🔴 自家 spec 抓到一個真 bug

第一版把 `idempotencyKey` 在**每一層**都排除，而規格 §2.1(d) ⑤ 的原文是
「不含 `idempotencyKey` **本身**」——**本身＝頂層那把**。

後果：一個巢狀的、真的叫 `idempotencyKey` 的欄位（metafield 值、巢狀 job 規格）
會被靜默丟出指紋 ⇒ 兩個實際上不同的請求算出**同一個指紋**，
而參數不符就**永遠偵測不到**——那正是這整個機制要防的東西在機制自己身上重演。
修法：`normalize(value, root:)`，規則⑤ 只在 `root` 為真時套用。

### 規則④ 遇到 Float 是 raise，不是轉換

`raise TypeError, "指紋不接受浮點數…"`。理由：float 的十進位表示不穩定
（`0.1 + 0.2` 的字串化在不同路徑上可能不同），而金額在本專案一律是 integer cents
（鐵律 3）——**這裡遇到 float 代表上游已經漏了單位邊界**。
靜默轉換會把一個單位邊界事故變成一個「指紋算對了」的假象。

## 尚未完成或需注意的風險 (Pending / TODO)

- 🔴 **claim/replay 完全沒做**（同 S4 的 Pending，此處逐條列出未決點）：
  1. **表形狀與 11 §2.1(a) 不一致**：規格說 `params_fingerprint`／`status`，
     實際欄位是 `request_digest`／`state`；仍帶被明文廢棄的 `response_body`(longtext)、
     `response_digest`、`status_code`；**完全沒有 `mutation_name` 欄**
     （⇒ 目前無法區分「同一把 key 用在不同 mutation」）。
     改表是 migration 級改動，超出本步範圍，但**留著廢棄欄位就等於留著誘餌**。
  2. **claim 在 transaction 內還是外，規格沒寫**。63 §A.2 的三欄表把「限流扣點」
     放在 transaction 外，但沒提冪等；11 §2.1 的範例也沒標 transaction 邊界。
     兩種語義不同：在內 ⇒ 失敗 rollback 會把 `processing` 記錄一併回滾（可能是想要的）；
     在外 ⇒ 需要另一個 transaction。
  3. **缺 key 回哪個 code**：28 §6 的 26 值裡沒有對應的。本輪暫用 top-level
     `IDEMPOTENCY_KEY_REQUIRED`（S4），**尚未進任何 enum**。
  4. **`catalog_create_merge_pending: true`** 表示 `required_for_catalog_create`
     應該併進 `required_for` 但還沒併。
  5. 🔴 **本尊沒說「原請求回了非空 userErrors（業務失敗）算不算成功而被快取」**
     ——官方只說「由當前 DB 狀態重建、非逐字儲存」。這條要自己定義並在 docs/dev 標明。
- ⚠️ **`EXCLUDED_KEYS` 硬編兩種寫法**（camelCase／snake_case）。若日後 input 正規化
  統一成單一形態，這裡要跟著簡化；現在保留兩種是因為 GraphQL 層是 camelCase、
  Ruby 層是 snake_case，兩邊都可能是指紋的呼叫端。
- ⚠️ **指紋沒有納入 `mutation_name`**。同一把 key 用在兩支不同 mutation、參數又剛好相同時，
  指紋會相同 ⇒ 偵測不到。這要等表補上 `mutation_name` 欄（未決點 1）才能真正解決；
  在那之前不得宣稱「同 key 不同 mutation 會被擋下」。
- **`BigDecimal` 也 raise**：`BigDecimal` 本身精度是夠的，但它在本專案的金額路徑上
  不該出現（一律 integer cents）。若日後有非金額的 decimal 需求，這條要重新評估。
