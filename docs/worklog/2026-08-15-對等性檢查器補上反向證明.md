## 已完成的工作 (Done)

### 1. 先問「為什麼只有它沒有測試」——答案是它**寫不了**測試

同批的 `check-limits-keys.rb`／`check-money-boundary.rb`／`check-exec-bits.sh`／
`check-workflow-syntax.rb` 都有回歸測試，只有 `check-ci-parity.rb` 沒有。
原因很具體：它把 `ROOT` **寫死**成倉庫根目錄

```ruby
ROOT = File.expand_path("..", __dir__)
```

⇒ **沒有辦法**餵給它一個故意違反的 fixture。想寫測試的人會發現寫不了，然後就不寫了。

🔴 **教訓：可測性是檢查器的設計需求，不是寫完之後才想的事。**
一支只能對真倉庫跑的檢查器，等於宣告「我永遠不會被反向證明」。
修法＝接受 `ARGV[0]` 當 ROOT，形態比照另外兩支 `check-*.rb`（三行改動）。

### 2. 🔴 加上 ROOT 參數後第一件事就是拿 fixture 打它——**兩個都沒打紅**

| fixture | 內容 | 修前 |
|---|---|---|
| `parity_runner_collapse` | ci.yml 跑 `npm audit`，ci.rb 只有 `pnpm audit` | **exit 0** 🔴 |
| `parity_name_spoof` | `step "TODO: 之後要加 ruby scripts/check-limits-keys.rb", "true"` | **exit 0** 🔴 |

兩個都是活的 bug。**這支測試不是補文件，它在被寫出來的當天就抓到兩個缺陷。**

#### bug ①：兩側用兩套邏輯，而 `"pnpm audit".include?("npm")` ＝ true

ci.yml 那側算出識別字 `key`，ci.rb 那側卻是**另一套**——去「找找看」有沒有哪一行像：

```ruby
ci_rb_commands.lines.any? do |line|
  next false unless line.include?(runner)                                    # ← 子字串
  arg.nil? || line.match?(/#{runner}\s+(?:-\S+\s+)*#{arg}\b/)                # ← 備援正則
end
```

`npm` 是 `pnpm` 的子字串，兩道防線**同時**失效：正則 `/npm\s+(?:-\S+\s+)*audit\b/`
也命中 `pnpm audit` 的後半段。同型還有 `bundle` 命中 `bundler-audit`。

**修法**：抽出 `command_key` lambda，**兩側都用它算 key，再做集合差**。
這樣「寬鬆」不可能只發生在一側——不對稱本身就是這個 bug 的根因。

#### bug ②：`step` 的名稱與指令在同一行，掃整行就等於讓名稱也算數

`step` 的簽名是 `step "名稱", "指令"`。舊寫法把**整行**丟給 `SCRIPT_REF` 掃 ⇒
腳本名寫在**名稱**裡就算「有跑」。

⚠️ 這不是假想的攻擊，是**現存的形態**：ci.rb 今天就有一步叫
`step "Invariants: CI parity (ci.yml ⊆ config/ci.rb)", "..."`，名稱裡真的帶著檔案路徑。
今天沒中只是因為它不含 `scripts/`。

**修法**：`STEP_CALL` 正則只取**第二個引號字串**。
配套兩條 fail-closed：解析不出兩段引號的 `step` 行**報錯**（不得靜默跳過，
靜默跳過＝那一步從比對中消失而症狀是「通過」）；`step` 行掃到 **0 行**也報錯。

**🔴 `config/ci.rb:25` 的「＋ schema drift」是錯的，而且錯得有害**：

`Verify schema.rb has no drift`（`git diff --exit-code db/schema.rb`）在 **`test` job**
（`ci.yml:100`），**不在 quality job**；`services: mysql` 也只掛在 test job 上。

## 尚未完成或需注意的風險 (Pending / TODO)

1. 🔴 **`command_key` 的取樣面仍然很窄，而且這是刻意的。**
   只認 `KNOWN_RUNNERS`（pnpm／npm／bundle／rake）與 `bin/*` 開頭的行；
   `node scripts/x.js`、`docker run …`、`make …` 一律看不到。
   ⚠️ 症狀與這次修掉的一樣：**檢查通過**。加新形態的執行器時要記得同步這張表，
   而**沒有任何機制提醒**（`parity_clean` 的「認出 2 組」斷言只守住既有的，不守新增的）。

2. ⚠️ **`STEP_CALL` 只認雙引號**。`step 'name', 'cmd'`（單引號）會落進 fail-closed 分支報錯——
   這是安全的方向（寧可紅），但錯誤訊息會讓人以為是自己寫錯而不是檢查器不支援。
   要支援單引號就擴充正則，別把 fail-closed 拿掉。

3. ⚠️ **規則 2 仍不看參數**。`pnpm audit --audit-level high` 與 `pnpm audit` 的 key 都是
   `pnpm audit` ⇒ ci.yml 收緊門檻而 ci.rb 沒跟上，本檢查看不到。
   這是檔頭誠實聲明既有的取捨（參數本來就可以不同），不是本輪引入的，但**沒有被測試涵蓋**。

4. ⚠️ **inline shell 步驟仍不在檢查範圍**（檔頭誠實聲明第 1 條）。
   🔴 該條文寫著「正解是把它抽成 `scripts/check-exec-bits.sh`」——**那件事在 PR #41 已經做了**。
   ⇒ #41 合併後，檔頭那段與 `config/ci.rb` 的對應註釋**必須一起更新**，
   否則會留下一句「已知缺口」指著一個已經補好的洞。**這是 #41 的前置條件，不是本 PR 的。**

5. 🔴 **新增腳本忘了執行位元，被 CI 擋下（run #133，39s 紅）。**
   `scripts/test-ci-parity-rules.rb` 進版控時是 `100644`，執行位元閘門直接打紅。
   根因是本機 Windows 的 `core.filemode=false` ⇒ **本地怎麼跑都不會發現**。
   修法 `git update-index --chmod=+x`，並順手稽核 `bin/` `scripts/` 全部為 100755。
   ✅ **閘門運作正常——這正是它存在的理由**，登記在這裡是為了讓下一個在 Windows 上
   新增腳本的人先做這一步，而不是等 CI 紅了才知道。

6. ⚠️ **`parity_*` fixture 的 ci.yml 都是手寫的最小 workflow**，
   與真實 `ci.yml`（含 anchors、多行 `run: |`、matrix）差距不小。
   本輪只覆蓋到「解析得動的簡單形態」，真實檔的複雜寫法沒有 fixture 對應。
