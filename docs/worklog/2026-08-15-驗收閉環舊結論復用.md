## 已完成的工作 (Done)

### 1. 🔴 `LATEST` 取自全部留言 ⇒ 舊結論被當成本輪結論

**Codex 原話**：
> When a PR already has an allowed conclusion from an earlier run, `LATEST` is nonempty,
> so this recovery block is never reached. […] the workflow instead processes the old
> conclusion and can auto-approve the new, unreviewed head or dispatch obsolete fixes.

**查證結果：成立，而且範圍更大。** `LATEST` 是從
`gh api repos/$REPO/issues/$PR/comments` 的**全部留言**算出來的
⇒ 只要任何一輪貼過結論，之後**每一輪**的 `LATEST` 都非空，於是：

| 後果 | 說明 |
|---|---|
| 回收分支變死碼 | 它的守衛是 `[ -z "$LATEST" ]`——而這正是 PR #30 本身要加的功能，**第二輪起就永遠進不去** |
| 自動 approve 未審過的 head | 舊的「通過」被當本輪結論 ⇒ `gh pr review --approve` 直接蓋在沒被審過的新 commit 上 |
| 拿過期意見再派一次 @codex | 舊的「需修改」被重放 ⇒ Codex 收到的是上一輪的意見 |

🔴 **這就是本檔頂部 `AUTO_MERGE` 註解②描述的風險，但原文把觸發條件寫窄了**——
原文寫「在 Claude 步驟失敗時」，實際上**與 outcome 完全無關，每一輪都發生**。
`AUTO_MERGE=false` 只擋住了合併那一半，approve 與派修兩半一直是活的。

**修法：留言 id 水位。** 新增一個**跑在驗收之前**的步驟 `記錄驗收前的留言水位`，
記下當下最大的留言 id；解析步驟只認 `.id > $wm` 的結論。

🔴 **刻意不採用原本設想的「留言內嵌 head SHA 並比對」**：那要靠 prompt 叫模型
自己寫對 SHA ＝ **賭模型配合**。水位由 workflow 自己量，不需要模型配合。
這與本輪另一個判斷同源（見 `2026-08-15-驗收機器人推理強度.md`：不用 alias，
因為不想「不知道自己實際在跑什麼」）。

🔴 **`ROUNDS` 刻意不加水位過濾**：它是「這個 PR 至今被派修幾輪」的累計計數，
用來擋 `MAX_FIX_ROUNDS`。加了水位它每輪歸零，上限就永遠觸發不到。
**兩個變數的時間範圍不同是刻意的**，已寫進註釋以免被後人「順手統一」。

**額外補的 fail-safe**：解析步驟有 `if: !cancelled()`，水位步驟失敗時它照樣會跑。
若此時把水位當 0，行為會**靜默退回**成剛修掉的漏洞 ⇒ 改成水位取不到就
貼診斷留言並 `exit 0`，**不驅動任何自動動作**。寧可停掉閉環也不要安靜地退回不安全版本。

### 2. 🔴 `jq` 少了 `-s`：回收到的是中間輸出，不是最終審核意見

**Codex 原話**：
> this jq invocation evaluates the filter separately for every record and command
> substitution concatenates every assistant text block rather than selecting the last
> one globally. The later 55 KB truncation can consequently retain early intermediate
> output while dropping the final review that this fallback is meant to recover.

**查證結果：成立。實測證明如下**（三筆 JSONL，最後一筆才是真正的意見）：

```
=== 舊寫法（無 -s）===        === 新寫法（有 -s）===
AAA-早期雜訊                  ZZZ-真正的驗收意見
BBB-中間
ZZZ-真正的驗收意見
```

⇒ 舊寫法把三段**全部串起來**，接著 `head -c 55000` 從頭截斷
⇒ **留下開頭的雜訊、丟掉要回收的審核意見**，而且看起來還「有東西」。
🔴 **這是最會騙人的失效形態**：回收功能看起來成功了。

**修法**：`jq -s -r '...'`。並實測確認該寫法對 **JSONL 與單一 JSON 陣列兩種格式都正確**
（`..` 會穿過 slurp 多包的那一層）——因為 `execution_file` 的實際格式仍未經驗證。

### 3. 順手修掉一個同類的潛在缺陷：`per_page=100` 只拿到最舊的一頁

`gh api "…/comments?per_page=100"` 回的是**最舊**的 100 則。
留言破百的 PR，`LATEST`／`ROUNDS`／水位**全部看不到近期留言**。
乒乓 PR（每輪至少一則驗收＋一則派修）累積破百並不罕見。
⇒ 三處都改成 `gh api --paginate … | jq -s 'add // []'`。

🔴 這一條 Codex 沒提，是修水位時發現的——**水位若取自最舊那頁，整個修法就是假的**。

## 修改的檔案與核心邏輯 (Changes)

| 檔案 | 改動 |
|---|---|
| `.github/workflows/claude-review.yml` | ①新增 `記錄驗收前的留言水位` 步驟（在驗收步驟**之前**）；②`LATEST` 加 `.id > $wm` 過濾，`ROUNDS` 維持全域；③水位取不到時 fail-safe 退出；④回收用的 `jq` 加 `-s`；⑤三處 `gh api` 改 `--paginate`；⑥頂部 `AUTO_MERGE` 註解②改標為已修並寫明 `AUTO_MERGE` 仍維持 false 的理由 |

**自測**（都是實跑，不是推理）：
- `jq` 的兩種寫法各跑一次，證明舊寫法串接、新寫法取全域最後一段，且新寫法對兩種格式皆正確；
- 水位過濾跑四種情境：水位 0（等同舊行為）／本輪有貼（取到新結論）／
  **本輪沒貼但存在舊結論（回空 ⇒ 回收分支才進得去）**／空留言時 max 回 0；
- 分頁合併：兩頁合成 3 筆、id 順序正確；
- `YAML.safe_load` 通過，步驟順序為 checkout → 水位 → 驗收 → 解析；
- 兩段 `run` 各過 `bash -n`。

## 尚未完成或需注意的風險 (Pending / TODO)

1. 🔴 **本 PR 自己仍然拿不到 Claude 驗收**（反竄改機制）⇒ 上述修正**全部無法在 PR #30 上驗證**。
   真正的驗證機會是合併進 main 後開的第一個 PR。
   ⚠️ PR #30 上那四則「執行成功但沒貼結論，且執行輸出也取不到」是**預期內的**——
   驗收步驟整個被跳過，自然沒有 `execution_file`。
   🔴 **不要把它當成 `execution_file` 這個 output 名稱錯了的證據**，那條仍未驗證（見 #2）。

2. ⚠️ **`steps.review.outputs.execution_file` 這個 output 名稱仍未經實測**（無一手來源）。
   程式碼是 fail-safe（取不到就走原本的訊息分支），但若名稱錯了，回收功能等於沒有。
   🔴 合併後第一次真正觸發時要確認留言裡真的有內容。

3. ⚠️ **回收分支的根因仍是推測**。「agent 把審核寫在最終回覆而沒呼叫 tool」最符合觀察
   （outcome=success ＋ 3–4 分鐘 ＋ 零留言），但沒有直接證據。不得寫成已確認。

4. ⚠️ **`AUTO_MERGE` 仍為 `false`，且本輪不改**。風險②已修，但①（diff／PR 描述裡的
   prompt injection 誘導「通過」）**完全沒有程式層防禦**。要改回 `true` 等於單獨接受①，
   那是使用者的裁定，不得由實作者順手改掉。

5. ⚠️ **水位法有一個已知的空窗**：若**人類**在驗收步驟執行期間手動貼了一則
   以結論標記開頭的留言，它的 id 會大於水位 ⇒ 會被當成本輪結論。
   現有的 `REVIEWERS` 作者允許清單擋住了一般使用者，但擋不住
   `github-actions[bot]`（它在清單內）在同一時間貼的其他留言——
   不過本步驟自己貼的留言**一律不含結論標記字面值**（已有註釋強制），所以目前無實際觸發路徑。
   🔴 登記於此：**新增任何由 bot 貼出且可能含結論標記的留言時，要回來重看這一條。**
