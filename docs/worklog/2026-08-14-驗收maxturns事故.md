# 驗收閉環第三個失敗形態：`--max-turns` 用盡（PR #26 整份驗收作廢）

> 這是同一條閉環的**第三種**失敗，每一種根因都不同：
> ①作者身分不符（#22/#23，已修）②防竄改跳過（#25，非 bug 是設計）③本次：回合數用盡。

## 已完成的工作 (Done)

### 一、事故現象與根因

PR #26 是「驗收閉環修好了沒」的第一次真實驗證。結果：

| 觀察 | 意義 |
|---|---|
| run 跑滿 **3m20s**（不是先前被跳過的 16–20 秒） | ✅ **防竄改機制這次確實沒攔**——那部分的預測是對的 |
| Job 標 **Failure** | 與 #25 被跳過時標 success 不同 |
| PR 上**沒有任何 Claude 留言** | 身分修正**仍然無法被證實**（沒有東西可解析） |
| 只剩「⚠️ 自動驗收沒有產生結論」 | 🔴 **這次這句話是對的**——Claude 真的失敗了 |

Actions annotation 逐字：

> `Claude execution failed: Reached maximum number of turns (40)`

🔴 **根因**：該 PR 動到 `docs/design/chilllove-admin-v2.html`——**單檔 12,943 行**。
驗收要讀 diff ＋ 對照多份規格，**光讀檔就把 40 回合燒光，根本沒走到 `gh pr comment`**。

🔴 **先前幾個 PR 沒事，不是因為 workflow 寫對了，是因為它們都是小幅的 Rails 改動**。
回合數夠不夠**取決於 diff 大小**——原型檔是本倉庫最大的單檔，任何碰它的 PR 都會壓到上限。

### 二、修正

1. **`--max-turns` 40 → 200**，並在該處寫明事故經過與「為什麼先前沒事」。
2. **`id: review` ＋ `continue-on-error: true`**：讓解析步驟拿得到 `steps.review.outcome`，
   且 Claude 失敗時解析步驟仍會跑完並貼出可讀診斷。
3. **診斷訊息拆成三種**（原本兩種）：
   - 找到結論但作者不在允許清單 → 印出實際作者
   - 🔴 **Claude 步驟自己失敗** → 明寫 outcome ＋ **直接點名 `--max-turns` 是最常見原因**
   - 跑完但沒貼結論 → 另一句

   理由：原本兩種情況都印「可能失敗或逾時」，把人指去看 log **卻沒說要看哪一行**，
   診斷因此多繞了一圈。

### 三、驗證

- workflow YAML 以 Psych 解析通過（steps=3、`continue-on-error=true`、`max-turns 200`、
  `REVIEW_OUTCOME` 綁到 `steps.review.outcome`）。
- `printf` 多行組字串以 bash 實跑確認換行正確。

🔴 **寫這段時又踩了一次 YAML 坑**：多行 `--body` 的續行落在**第 0 欄**，
會終止 block scalar，整份 workflow 不再是合法 YAML。改用 `printf '%s\n\n%s\n%s'` 組字串，
所有行都留在縮排內。**已把這條寫成該處的註釋**——同型事故本檔已發生過兩次（heredoc 那次）。
