# 工作記錄：userErrors 契約與 BaseMutation 地基（M1 PR-1 第 4 步，2026-08-15）

> 規格出處：`docs/research/28` §0.3.1–§0.3.6（本輪考掘後改寫）｜裁定＝`docs/DECISIONS.md` D14

## 已完成的工作 (Done)

寫入路徑的地基。**一支真正的 mutation 都不出**——本步只交付
`BaseMutation`／`DisplayableError`／錯誤碼池／`UserErrors::Path`／冪等清單讀取器，
並且 **`Types::MutationType` 建了但刻意沒有掛上 `ChillloveSchema`**（理由見下）。

### 🔴 三個關鍵決定，每一個都做了負面驗證

| 決定 | 改壞之後 |
|---|---|
| `BaseMutation < GraphQL::Schema::Mutation`（**不是** `RelayClassicMutation`） | 改成後者 ⇒ **9 條紅**（clientMutationId 被注入到 payload 與 input 兩側） |
| `field :field, [String], null: true` ⇒ 渲染成 `[String!]` | 改成 `[String, {null: true}]` ⇒ **1 條紅**（SDL 變成 `[String]`） |
| controller 只 rescue 自家的 `InvalidVariables` | 放寬回 `TypeError` ⇒ **1 條紅** |

第三條值得展開：controller 的 `rescue JSON::ParserError, TypeError` 是**方法層 rescue**
——它包住整個方法體，而 `ChillloveSchema.execute` 就在裡面。
⇒ **任何 resolver 內部拋出的 `TypeError` 都會被渲染成 `BAD_USER_INPUT`**。
這不是假設：鐵律 3 的金額型別閘門（65 §C L3）正是靠 `raise TypeError` 擋住
「把儲存值直接送 PSP」——那是 **P1 級送款事故**，卻會顯示成
「variables 必須是有效的 JSON 物件」，而真正的訊息一個字都不會出現在 log 以外的地方。
改成專屬例外 `GraphqlController::InvalidVariables`，並保留兩條回歸斷言證明
「variables 不是 JSON 物件」與「malformed JSON」**仍然**回 `BAD_USER_INPUT`。

### 🔴 fixture schema：地基必須真的被執行過

`Types::MutationType` 沒掛上 schema ⇒ 地基**沒有任何執行路徑**。
所以新增 `spec/support/mutation_test_schema.rb`：五支 fixture mutation ＋ 一個測試用 schema。

**為什麼非有不可**：上一輪 review 抓到的第一條致命傷是
「`GraphQL::Schema::Mutation` 沒有 `input_object_class`（它定義在 `HasSingleInputArgument`，
只被 `RelayClassicMutation` include）⇒ **類別定義期就 NoMethodError**，Zeitwerk eager load
一跑整個 app 載入失敗」。**那是跑一次就會發現的東西，只讀程式碼的驗收抓不到。**

五支 fixture 各自證明一件事：

| fixture | 證明什麼 |
|---|---|
| `fixtureWidgetCreate` | 一般形態：resource ＋ userErrors；欄位錯誤帶 `["title"]` |
| `fixtureWidgetTouch` | 🔴 **純副作用：payload 只有 userErrors**（本尊 resource 欄位下限是 0） |
| `fixtureWidgetBulk` | 陣列元素錯誤帶十進位索引段 `["titles","1","value"]` |
| `fixtureWidgetTypeError` | resolver 的 `TypeError` 不再被偽裝成 `BAD_USER_INPUT` |
| `fixtureWidgetIdempotent` | 冪等契約走**真的 execute 路徑**（不是用假 context 直接 `new`） |

### 🔴 為什麼建了 MutationType 卻不掛上去

`enforce_idempotency_contract!` **只檢查 key 有沒有帶，不做去重**——
不 claim、不查重、不回放。claim/replay 狀態機刻意延後。
**本 PR 一支 mutation 都不出，所以沒有任何東西獲得虛假的安全感**；
掛上 root 的那一刻這個保護就沒了。`mutation_root_guard_spec` 把這件事釘住，
並把**解鎖條件寫進斷言**（斷言 `mutation_type.rb` 的原始碼含「claim/replay」與
「虛假的安全感」兩個字串），讓要掛上去的人一定會讀到理由。

## 修改的檔案與核心邏輯 (Changes)

- `app/graphql/types/interfaces/displayable_error.rb`（新增）：與本尊的 interface **一字不差**
  ——只有 `field: [String!]` 與 `message: String!`，**沒有 `code`**。
  code 放在各 mutation 專屬的 error object type 上（我方加嚴，D14 偏離 A）；
  加進 interface 就偏離了本尊的 interface 形狀，而那是客戶端寫
  `... on DisplayableError` fragment 的依據。
- `app/graphql/types/errors/code_pools.rb`（新增）：`COMMON`（24 值）＋
  `CONCURRENCY`（5 值，🔴 本輪新開）＋ `DISCOUNT_ONLY`（`CONFLICT`）。
- `app/graphql/types/errors/base_code_enum.rb`（新增）：每支 mutation 一個獨立 enum 的**產生器**
  （GraphQL 形狀照抄本尊）；`from_pools` ＋ `own_value` 兩個 DSL；缺說明的值一律 raise。
- `app/graphql/user_errors/path.rb`（新增）：剝 `input` 外殼、camelCase、索引轉十進位裸字串、
  拒絕 JSONPath 風格字元、無段時回 `nil`。
- `app/graphql/mutations/base_mutation.rb`（新增）：`user_errors_type` DSL
  （`[X!]!`）、`idempotency_required?`、`enforce_idempotency_contract!`。
  **不提供泛型 `resource` 欄位**。
- `app/graphql/types/mutation_type.rb`（新增，**未註冊**）＋ `has_no_fields(true)`。
- `app/models/idempotency/required_mutations.rb`（新增）：清單讀 `limits.yml`；
  刻意不含 `required_for_platform`（那是 pack-scoped 的，混在同一檢查點會讓 HK 首發的
  schema 快照測試直接紅）。
- `app/controllers/admin/api/v202608/graphql_controller.rb`：`InvalidVariables` 專屬例外，
  rescue 收窄。
- `app/graphql/graphql_request_cost.rb`：mutation base cost（讀 `limits.yml`）。
- specs：`base_mutation_spec`（18）、`user_errors_path_spec`（12）、`mutation_root_guard_spec`（4）、
  `products_contract_spec`（+3 條 rescue 回歸）、`spec/support/mutation_test_schema.rb`。

## 尚未完成或需注意的風險 (Pending / TODO)

- 🔴 **claim/replay 完全沒做**，四個未決點同時成立：
  ①`idempotency_keys` 的**表形狀與 11 §2.1(a) 不一致**——狀態欄叫 `state`（不是 status）、
  指紋欄叫 `request_digest`（不是 params_fingerprint）、仍帶被明文廢棄的
  `response_body`(longtext)／`response_digest`／`status_code`、**完全沒有 `mutation_name` 欄**；
  ②claim（搶佔 `processing` 列）在 transaction 內還是外，規格沒寫；
  ③缺 key 回哪個 code——28 §6 沒有，本輪暫用 top-level `IDEMPOTENCY_KEY_REQUIRED`；
  ④`catalog_create_merge_pending: true` 表示兩份清單待合併。
  四個未決點 × 零個真實 mutation ＝ 四次盲猜 ⇒ 整包延後。
- 🔴 **`GraphqlRequestCost.mutation?` 是刻意的低精度實作**：它掃「有沒有 `mutation` 關鍵字
  出現在 operation 位置」，在①多 operation 文件 ②註釋/字串裡的 `mutation`
  ③fragment 內三種情形會高估或低估。取捨方向是**寧可高估**（多扣點數比放行超額請求安全）。
  精確做法要解析 AST，等 M8 的完整 cost analyzer。
- ⚠️ **28 §6 的「20 個泛用碼」與清單對不上**：表列 26 值、標明退貨專屬的只有 2 個 ⇒ **24 才對**。
  `CodePools::COMMON` 以**清單**為準（清單逐字照抄官方，數字是我方寫的摘要）。
  28 §6 的那句「20 個」尚未改——下一輪順手修。
- 🔴 **`UserError` 是否 `implements DisplayableError` 仍未確認**（shopify.dev 對它不印
  Implements 區塊）⇒ 客戶端**不得假設**所有 userErrors 都能用
  `... on DisplayableError` fragment 取用。
- ⚠️ **具名參數形下的多段 path 是假設**（只剝逐字等於 `input` 的參數）。
  三個官方實例都相容，但沒有直接證據。補證要拿真實 Admin API token。
- **`enforce_idempotency_contract!` 要由子類在 `resolve` 開頭主動呼叫**
  ——graphql-ruby 的 `Mutation` 沒有 around hook。忘記呼叫就等於沒有檢查，
  而**沒有任何機制會發現**。第一支真 mutation 落地時要補一條 CI 斷言
  （掃 `Mutations::` 下每個類別的 `resolve` 有沒有呼叫它）。
- **`DISCOUNT_ONLY`（`CONFLICT`）目前只是一個常數，沒有任何 CI 斷言守住它**
  ——「這個 token 只准出現在折扣線的 enum 裡」還停在紀律層。折扣線落地時要補。
