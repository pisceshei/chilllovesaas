## 已完成的工作 (Done)

### 新功能

1. **`Locales::FallbackChain`**——BCP-47 截尾鏈（67 §C.4(a)）。純函式。
   截到 `i18n.forbidden_locale_tags` 就**停止整條鏈**（不是跳過該階繼續截）；
   `never_fallback_pairs` 的雙向過濾；`fallback_chain_mode` 非 `bcp47_truncation` 一律 raise。
2. **`Translations::BlankValue`**——「等於沒有翻譯」的判準，讀寫共用**同一支**
   （消費者導出＝`git grep -n "BlankValue.blank?" -- app/`）。
   `kind: :text | :html`；HTML 走 `Loofah.fragment`（＝與 sanitizer 同一支 parser）。
3. **`Translations::Fields`**——可翻欄位的中繼資料（kind／missing／base 屬性／上限與**單位**）。
4. **`Translations::Resolve`**——67 §C.4 的四步演算法，批載形態，附 `i18n.fallback_hit` 遙測。
5. **`Translations::Audit` ＋ `lib/tasks/translations.rake`**——既有譯文稽核，四條規則
   ＋一條**明文棄權**；`translations:fix` 只修其中兩條。
6. **`Locales::Registry.published_tags`**——前台解析範圍（`published` ≠ `enabled`）。

### 修復的缺口（三個，兩個是線上實測到的）

| # | 缺口 | 實證 | 影響 |
|---|---|---|---|
| 1 | 🔴 譯文 `body_html` **完全不 sanitize** | bt3 正式環境 rev `1a75ceb`，`rails runner` 實跑：同一段 payload 走 base 落庫 `<p>ok</p>alert(1)<img>`，走譯文**原樣落庫**含 `<script>` 與 `onerror` | 第 30／34 包渲染的那一刻＝儲存型 XSS |
| 2 | 🔴 `CsvImport` **完全不重算 `translation_status`** | 同上實跑；`csv_import.rb` 內零個 `recompute_status` 呼叫 | 後台進度徽章不動；`translation_status.updated_at`（67 §G.3 建議的 cache stamp 載體）不推進 ⇒ 第 3 包會在已知破的不變式上建快取失效 |
| 3 | 舊 `blank_value?` 在 `:html` 對照框架下有 **8 格誤判**（見下方更正） | 本機 `bundle exec ruby` 實跑對照矩陣（活矩陣＝`blank_value_spec.rb`） | `<p>&#160;</p>`／`<p>　</p>`／`<p>​</p>`／`<p class="x"></p>` 等被判成「有翻譯」⇒ fallback 永不觸發 ⇒ 商家看到空白區塊而不是原文 |

另修：`CsvImport#write_row` 每列各查一次 `source_tag` 的 N+1；譯文 `body_html`
的長度上限**量錯單位**（base 用 `bytesize`、譯文用 `length` ⇒ 中文譯文拿三倍額度）。

### 一個既有測試的行為被刻意改掉

`spec/requests/product_translations_spec.rb` 原有一格用 **`title`** 送 `<p><br></p>` 並期待被刪。
67 §C.4(b) 原文把 HTML 那一條明文限定在**富文本欄位**（「NULL、空字串、只含空白字元的字串
三者等價視為『無譯文』。🔴 富文本欄位**另加一條**：`<p></p>`／`<p><br></p>` 這類語義空的
HTML 也算空」）。舊實作不看欄位型別 ⇒ 把富文本規則套到純文字欄上 ⇒ 商家在標題欄真的打了
`<p><br></p>`（標題欄不是 RTE）會被靜默刪成「未翻譯」。
⇒ 改成 `body_html` 送空 HTML、`title` 送空字串，並**新增**一格反向斷言純文字欄不判空。

### 🔴 2026-08-25 更正：「8 格誤判全部同一方向」限定於 html 框架（審查 D5）

上表第 3 列與 handoff 首版都寫「全部同一方向（該判空的判成非空）＝本次修正不會刪到
任何既有資料」。**該全稱句對 `:text` 欄不成立**：舊實作 kind-blind，對 `title`／
`meta_title`／`meta_description` 會把 `<p></p>`、`<p><br></p>`、`<p>&nbsp;</p>` 這類
**真內容**判成空——而 `Upsert` 對空值的動作是 `delete_all` ⇒ 那是**反向誤判**，
而且本包自己就是為了修它才改了 `product_translations_spec.rb` 那一格。
⇒ 原句撤回，改為：「在 `:html` 的對照框架下 8 格全部同向；kind-blind 造成的 `:text` 欄
反向誤判另計，正是本包的行為變更理由。」

### 一個裁定（研究建議被否決）

研究階段建議 `read_path_blank_check: text_only`（讀取熱路徑只跑快篩、完整判準留寫入端）。
首版**否決**，依據是「一次判準 ~85µs、50 列列表頁 ~4ms」。

> 🔴 **2026-08-25 同日推翻（審查 C5）**：那兩個數字錯了 20 倍以上。實測 17KB `body_html`
> 一次判準 ≈**1987µs**、50 列全 parse ≈**95ms**（本機，對 ~17KB 中文段落跑 200 次取均值；
> 審查方在較慢機器量到 14ms／700ms）。首版否決時給出的理由只有這組數字一項
> （原文見本節上方保留的敘述）⇒ 依據不成立，裁定翻回。
> 修正後：`BlankValue` 仍只有一份實作，但多一個 `skip_parse_above:` 參數；`Resolve`
> 傳 `i18n.blank_value.read_fast_path_max_bytes`（1024），寫入端與稽核永遠傳 nil。
> 大值誤判成非空落在假陰性側（不刪資料）。limits 兩鍵並存：
> `single_implementation_for_read_and_write: true` ＋ `read_fast_path_max_bytes: 1024`。

**核心不變量**

1. 前台不得靜默空白：required 缺翻 ⇒ 回 base；optional 缺翻且原文也空 ⇒ **整個欄位不輸出**。
2. `translations.value` 的**每一條寫入路徑**都經同一套 sanitize 與同一套判空。
3. 後台 GraphQL 的 `translations` **永遠是精確比對**，不接 Resolve。
4. 遙測只在 `depth >= 1` 發，payload 不含 `resource_id`。

## 整合修復輪（2026-08-25，同日；七方對抗審查後的單一修復 head）

七個維度的對抗審查（correctness／security／docs-evidence ＋ workflow 的
interface-fitness／concurrency／performance／spec-false-greens，後四者每個 finding 另有
獨立反駁者）。確認的 finding 逐條列於下方兩張表（「修掉的」與「更正的已發布宣稱」），

### 🔴 修掉的（依根因分組）

| 群 | 內容 |
|---|---|
| **稽核會製造它要消滅的東西** | `Audit` 的 `--fix` 對「sanitize 後會變空」的列（`<iframe>`／`<video>` 等 content-bearing 但白名單外）走 `update_columns(value: "")`：繞過 `presence` 驗證、造出鬼列、`translation_status` 仍宣稱已翻譯、且第二輪 audit 又把它報成 `blank_value` ⇒ **fix 不冪等**。改成先算 `clean` 再分類（clean 空 ⇒ `blank_value` 刪列），並改用 `update!` |
| **cache stamp 載體仍然不動** | `recompute_status` 只寫四個計數欄；只改譯文**文字**時計數不變 ⇒ `save!` 不發 UPDATE ⇒ `updated_at` 不推進。而那正是 67 §G.3 要當 stamp 的欄位 ⇒ 本包宣稱修好的缺口其實沒修好。加 `touch:` 參數（只對真的動過列的語言 touch，不得無條件） |
| **CPU 放大面** | sanitize 在**量長度之前**跑 ⇒ 無上界輸入先進 parser（64KB≈0.78s、1MB≈14s、5MB≈160s，超線性），nginx 收 32MB、rack-attack 只限 login ⇒ 認證後可耗盡全租戶 app threads。改成先量 raw bytes（0 成本）再 parse |
| **sanitize 靜默毀資料** | 「判空⇒刪列」對「sanitize 把非空內容毀成空」是錯的（`<video>`／`<iframe>`／libxml2 深度 256 懸崖）。改為 userError `INVALID`；raw 本來就空才刪列。🔴 判「raw 有沒有內容」必須 **parser-independent**（`BlankValue.text_bearing?`）——用 `blank?` 判 raw 會撞同一個懸崖，偵測器與失效共用盲點（本包自己先踩到一次） |
| **匯入的失敗路徑** | `CsvImport` 全程無 `rescue`：一列拋例外（實測併發撞唯一鍵的 `RecordNotUnique`）就讓整個 `call` 以例外收場——已 commit 的列不重算進度、`Outcome` 不回傳、controller 500，「逐行報告」的文檔宣稱形同虛設。加逐行 `rescue` ＋ id 範圍檢查 ＋ CSV 端長度閘（先前完全沒有，能寫進 GraphQL 拒收的值） |
| **鎖持有時間** | `Upsert` 的 sanitize 跑在呼叫端 transaction 內（持 product 列鎖、改名時持店鎖）；`Audit#apply_fixes!` 把整批修復＋parse 包在一個 transaction（400 列≈30.9s，~650 列破 `innodb_lock_wait_timeout`）。前者拆 `prepare`／`commit`，後者改逐列短 transaction ＋ TOCTOU 重驗 |
| **depth 語義** | scope 濾掉請求語言時候選塌陷 ⇒ `depth=0`、`fallback?=false`、無 `lang`、無遙測，與「直接命中」無法區分。改成走訪**未過濾**的完整鏈、scope 外「跳過但保留索引」 |
| **成本量測錯 20 倍** | 見上方「一個裁定」的推翻註記 |
| **其餘** | `orphan_locale` 誤報停用語言（`enabled_tags` → 全列）；`Fields.limit` 未知欄位靜默回別欄上限 → `KeyError`；`Resolve.field` 對 Symbol 炸 `KeyError`；`batch` 不驗資源歸屬（跨店物件會回別店 base 文字）；`Audit` 硬編 `body_html` → `Fields.kind`；`CONTENT_BEARING` 誤含 `source` |
| **測試本身的假綠** | `capture_sql` 只收 `translations` ⇒ 兩格 N+1 spec 對 `shop_locales` **結構上盲**（把 batch 改成逐欄位重查會發 76 條查詢仍然綠）。改收全部業務表 SELECT，並補「registry 每批只查一次」的正向斷言 |
