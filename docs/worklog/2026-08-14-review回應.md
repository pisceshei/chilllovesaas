### 一、`docs/specs/86` §3.2 的重複計算（Codex #22-1，🔴 真 bug）

- 原公式第二項是「Σ **取消訂單的訂單總計**」，**沒有扣掉退款**。
  查 `docs/specs/16` §F4 屬實：取消流程「動作＝狀態轉移＋庫存釋放＋**依選項退款（走 F5）**」，
  F4.2 的 `refundMethod` 參數即為此 ⇒ **已付款訂單取消時會實際建立一筆 refund**。
  那筆錢於是同時落在第一項（`refunds`）與第二項（訂單總計）⇒ **撤銷算兩倍、總銷售額被低估**。
- 🔴 **這與本節自己警告的「把 returns 再加一次」是同一個錯誤形態**——
  我在退貨那一側擋住了，卻在取消那一側犯了同一個錯。
- 修正為互斥三項：第二項改成 `取消訂單總計 − 該次取消所產生的退款額`，
  並補**三情境驗算表**（全額退款／未付款取消／部分付款）證明合計恰為訂單總計一次。
- 連帶修正 §5 的一句過度斷言：原文說換貨是「**唯一**能抓到雙重扣除的形態」——
  錯的，取消×退款是第二種形態。改成兩種形態的必測表，並註明
  🔴 **一般測資的取消單多半是未付款取消，那條路徑兩項都是 0，怎麼寫都對**。

### 二、`docs/specs/19` 的三處口徑矛盾（Codex #22-2）

  照哪一段實作會得到不同的數。已改為與 §F1 一致。

### 三、`scripts/check-reversal-naming.rb` 只守住三分之一（Codex #22-3）

- 原腳本**只讀 `db/schema.rb`**，但 86 §3.1 的適用範圍是「rollup 表、**分析 API**、**報表 UI**」
  三處 ⇒ 舊名以 GraphQL 欄位／model 方法／序列化 key／前端報表欄位出現時 CI 全綠。
- 新增**規則 3**：掃 `app/models`／`app/graphql`／`app/controllers`／`app/jobs`／
  `app/frontend/admin/**/*.{ts,tsx}`（排除 node_modules）。
- 🔴 **規則 3 刻意不掃裸 `returns`**，只掃 10 個複合名。理由：`returns` 在 app 代碼裡
  **多半是合法的**——86 §3.1 要求實體退貨資源就叫 `returns`（`has_many :returns`、
  `Return` model），英文散文與 YARD `@return` 也大量出現。
  裸 `returns` 只在 schema 欄位位置判得準，就只在那裡擋。
  ⇒ Codex 給的兩個選項（擴大掃描／收窄宣稱）**兩個都做**：能擴的擴，不能擴的把契約寫實。

### 四、🔴 `claude-review.yml`：整個驗收閉環從未運作過（bot 未提，我查出的）

- 現象：PR #22／#23 都被貼「⚠️ 自動驗收沒有產生結論（Claude 步驟可能失敗或逾時）」，
  但 Claude 明明貼出了完整且正確的驗收意見。
- 根因：解析步驟的 jq 過濾式只認 `github-actions[bot]`，而
  `anthropics/claude-code-action@v1` 是以**自己的 GitHub App** 身分留言——
  實測 PR 頁面的作者連結是 **`/apps/claude`** ⇒ login 為 `claude[bot]`。
- 🔴 **後果不只是誤報**：`LATEST` 恆為空 ⇒ `ROUNDS` 恆為 0、自動 approve 與自動派工
  從未觸發 ⇒ 檔頭畫的那個「乒乓閉環」**從上線起就沒有運作過**。
  沒人發現是因為 `AUTO_MERGE=false` 讓它失效得很安靜——**fail-safe 掩蓋了 fail-silent**。
- 修法：作者允許清單改為 `["claude[bot]","github-actions[bot]"]`。
  🔴 **維持允許清單、不放寬成「內文有【驗收結論】就算」**——那等於讓任何人或
  diff 內的 prompt injection 偽造通過結論（檔頭 AUTO_MERGE 註解①所指的風險）。
- 另把「查無結論」拆成兩種原因分別報：作者不在清單時**直接印出實際作者**。
  原本兩種都印同一句「去看 Actions log」，而 log 裡一切正常——這個 bug 就是這樣藏住的。

## 追加（同日第二輪，回應 PR #25 自己收到的 review）

### 一、🔴 86 §3.2 的第三處重疊——**同一個錯被抓兩次**

Codex 在我剛修好的公式裡又抓到一處：**訂單編輯的負向差額也會走退款**。
查證屬實——`docs/specs/16` §F8.1 第 576 列逐字：
「訂單編輯 commit 造成總額變動 …（同 router）… 總額**下降** ⇒ 折讓」。
⇒ 已付款訂單編輯調降 HK$100 會被算成 HK$200。

🔴 **教訓比 bug 本身重要**：我第一次修的時候**寫的是補丁不是規則**——
宣告了「三項互斥」，卻只檢查了觸發我注意的那一組重疊。
這次改成先寫**不變量**、公式只是它的展開式：

> **`refunds` 擁有「真的動了的錢」的全部；其他每一項只補「沒有走退款的那一部分」。**

並把驗算表從 3 列擴成 5 列（補上「已付款編輯調降」與「未付款編輯調降」），
§5 的必測形態從 2 種擴成 3 種，且明寫
🔴 **形態 2 與 3 都要「已付款」才現形**——一般測資的取消與編輯多半是未付款訂單，
那些路徑不論公式怎麼寫都對。

### 二、🔴 我自己的 workflow 修正裡的陷阱（Codex 對 PR #25）

我加的診斷訊息**內文含 `【驗收結論】` 字面值**，而它由 `github-actions[bot]` 貼出、
該身分又在 `REVIEWERS` 裡 ⇒ 下一輪 synchronize 會把**診斷本身**選成 `LATEST`，
它既非通過也非需修改 ⇒ 落到「無法判讀」分支，**真正的作者身分問題反而再也報不出來**。

修法採 Codex 建議的較強那個：`LATEST`／`ROUNDS` 改為**只認第一行就是標記**的留言
（`split("\n")[0] | startswith($m)`），並讓本步驟產生的所有留言**一律不含標記字面值**。
兩層都做，任一層失效另一層仍擋得住。

實測：新版正確選中真結論，忽略診斷訊息、忽略「內文中段提及」、擋掉人類偽造；
舊版在同一份樣本上選中的是「內文中段提及」那則——**正面重現 Codex 指出的陷阱**。

### 三、🔴🔴 身分修正**無法在 PR #25 上驗證**——原因不是失敗，是設計

PR #25 的兩次 run 都只跑 **16–20 秒**（正常驗收 3–4 分鐘），且**沒有任何 Claude 留言**。
查 Actions annotation 找到根因：

> Skipping action due to workflow validation: Workflow validation failed.
> The workflow file must exist and have **identical content to the version on the
> repository's default branch**.

`claude-code-action` 有**防竄改機制**：PR 只要動到 `claude-review.yml`，驗收步驟整個跳過。

🔴 **這推翻了我寫在 PR #25 描述裡的假設 3**（「本 PR 就是第一次實測」）——
它在原理上就不可能是。真正的驗證機會是**合併後開的第一個 PR**。
🔴 而且 Job 顯示 **success 不是 failure**，極容易誤判成「Claude 逾時」。
已把判別方法（看 run 時長）與整段說明寫進 workflow 檔頭。
