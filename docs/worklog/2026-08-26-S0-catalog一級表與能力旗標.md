## 已完成的工作 (Done)

### 1. `sales_catalogs` 一級表（三層 AND 的第三層有實體了）

`publications.catalog_id` 自 `20260814200000` 起存在，**無外鍵、無寫入者、值恆為 NULL**。
而本尊**每個 publication 都有一個 catalog**（`docs/research/82` §9.5b／§10.3 兩次抓包：
Online Store 與 Shop 的 catalog 都是 `AppCatalog`，`status: "ACTIVE"`）
⇒ 我方三層 AND 的第三層兩週來都是 no-op。本 PR 補上表、回填、外鍵與寫入者。

### 2. 🔴 表名更正：`catalogs` → `sales_catalogs`（實作當下證偽了設計文件的原文）

設計文件（同日稍早）寫的是 `catalogs`／`Catalog`。建檔後 8 個 spec 檔在載入階段失敗：

```
TypeError: Catalog is not a module
  app/models/catalog.rb:33: previous definition of Catalog was here
  # ./app/services/catalog/media_sync.rb:3:in '<main>'
```

`Catalog` 常數**已被服務層命名空間佔用**（`Catalog::SaveProduct`／`MediaSync`／`SaveCollection`／
`CacheStamps`／`HandleChange`／`OptionValuesDigest`／`ExternalVideoUrl`／`DeleteVariant` …），
語義是「商家的**商品目錄**操作」；本尊的 `Catalog` 是「publication ＋ price list 的容器」。
⇒ 表名與模型名加 `sales_` 前綴，`publications.catalog_id` 一併改名 `sales_catalog_id`。

改名安全性：該欄自建立以來 **app 層零讀者零寫者**。複驗——

```bash
grep -rn 'catalog_id' app/ lib/
```

（改名前只有 `db/schema.rb` 與兩支 migration 的註釋提到它。）

### 3. `publications` 補上本尊的五個能力旗標與 `operation_status`

`82` §10.4 實測本尊 `Publication` 有**六個**能力旗標，我方只有 `supports_future_publishing`。
補上其餘五個。其中兩個直接解掉舊的未取得：

- `supports_bundles` 解釋了 `82` §9.4 那個 `includesBundle` URL 參數；
- `supports_publication_for_unlisted_products` 解釋了 help 那句
  「You can't publish unlisted products to any third-party sales channels」
  ——它不是寫死的規則，是**逐管道的能力旗標**。

`operation_status` 對位本尊 `ResourceOperationStatus`——🔴 **恰三值 `created`／`active`／
`complete`，沒有 `failed`**。本步**只建欄位不做狀態機**（狀態機屬 S1）。

### 4. `Shop#after_create` 從建 1 列變成建 2 列

順序 catalog → publication，同一個 transaction（`after_create` 本身跑在 `Shop.create!` 的
transaction 內）。catalog 建失敗 ⇒ 整間店回滾，不留「有 publication 沒 catalog」的半成品。

### 5. 配對 migration spec（第 11／12 包換來的固定處理）

`spec/migrations/s0_backfill_sales_catalogs_spec.rb`，10 格。**先種既有資料再回填**——
回填迴圈的本體只有在庫裡已有 publication 時才執行，CI 跑空庫、開發庫也常剛好沒有
⇒ 兩處都不執行迴圈本體、`db:migrate` 一路綠，**只有正式環境會炸**。

三個突變複驗（本輪實跑，輸出逐字）：

| 突變 | 結果 |
|---|---|
| 拿掉回填的 `ActsAsTenant.without_tenant` | `10 examples, 10 failures` |
| 回填不再只補 NULL（`where(sales_catalog_id: nil)` → `where.not(id: nil)`） | `10 examples, 3 failures` |
| `down` 不清殘留 id（刪掉 `update_all(sales_catalog_id: nil)`） | `10 examples, 2 failures` |
| 還原後 | `10 examples, 0 failures` |

### 6. 實作當下踩到並記錄的兩個工具鏈事實

- **`create_table ... if_not_exists: true` 會真的送出 DDL** ⇒ MySQL 隱式提交，
  RSpec 的測試交易被打斷，第二格起全部撞 `Subdomain has already been taken`。
  ⇒ 回填抽成具名方法 `backfill_sales_catalogs!`（**`up` 呼叫的同一個方法本體，不是副本**），
  spec 主體呼叫它；完整 DDL 往返另立**非交易**群組並自行收尾。
- **`migration.down` 直呼不會設方向** ⇒ `strong_migrations` 把 `down` 裡的 `remove_column`
  當成正在新增的危險操作而擋下。改用 `migration.migrate(:down)`（與 `db:rollback` 同路徑）。

### 為什麼 `has_one :publication` **沒有** `dependent:`

catalog 被 publication 指著，直接刪**應該**被資料庫擋下來——沒有 catalog 的 publication
＝第三層斷掉＝該管道商品靜默不可見。`dependent: :restrict_with_error` 只擋 `destroy`、
擋不住 `delete_all`，而 FK 兩者都擋 ⇒ 讓 FK 當唯一防線，不製造「以為有兩道其實只有一道」。
`sales_catalog_spec.rb` 兩格分別釘住 `destroy` 與 `delete_all` 都拋 `InvalidForeignKey`。
