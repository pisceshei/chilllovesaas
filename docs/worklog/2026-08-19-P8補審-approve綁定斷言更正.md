## 補審第二輪（2026-08-19；#59 對合併提交 4 條＋#60 3 條，**先上網研究再修**）

🔴 **上一版的修正本身又被推翻一次。** 我把「`commit_id` ⇒ dismiss-stale 會忽略舊核准」
更正掉，卻在改寫時寫下「真正關掉要靠 dismiss-stale」——**那個也是錯的**，而且同樣沒查證。

**研究結論（取證 2026-08-19，來源逐條入註釋）**：
- **核准端不存在原子解法，這是 GitHub 的刻意設計**：head 前置條件原語只掛在合併
  （REST merge 的 `sha`「must match to allow merge」＋**409**、GraphQL `expectedHeadOid`、
  `gh pr merge --match-head-commit`），**一個都沒掛在 approve**；`commit_id` 是
  「the commit the review **pertains to**」，端點狀態碼只有 200/403/422；POST 不支援條件式請求。
- **dismiss-stale 押不得**：官方 API 層是事件式（`_on_push`）、概念層是狀態式
  （「records the state of the diff…」），**求值時機從未公布 ⇒ 未取得**。
- ✅ **真正的解**＝`require_last_push_approval`（純狀態謂詞、作為**合併閘門**求值，
  不依賴撤銷是否及時發生 ⇒ 對時序缺口免疫）＋合併時帶 SHA。⚠️ 前者**尚未啟用**
  （main 無分支保護，實測 404），屬 18.4 裁定範圍。
- **業界依據不是推測**：GitHub 官方 Dependabot 自動核准教學就是裸的
  `gh pr review --approve "$PR_URL"`、**零 head 複驗**——大家都不守核准那一步，因為守不住。
