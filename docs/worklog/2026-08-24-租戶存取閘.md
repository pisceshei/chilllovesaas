## 已完成的工作 (Done)

### 修的是什麼

D8 把身分表升為組織層、拿掉 `shop_id` 之後，明文要求由 `Current#can_access_shop?`
在應用層補回「這個人屬於這間店嗎」。**那道閘從未接線**——`grep` 證實它只有定義、
註釋與 spec，零 production 呼叫點。

於是：`SessionsController#create` 全平台查 email、成功即發 session；
`Session.authenticate` 只比對 token digest；`StaffMember#can?` 第一行 `return true if owner?`。
⇒ **A 店 owner 在 B 店 host 用自己的帳密登入即可讀寫 B 店資料**。
曝險面是整個 admin，不只複查發現它的庫存面。

### 怎麼修

兩側都接，判定一律看 `user_store_assignments`：

| 位置 | 作用 | 失敗行為 |
| --- | --- | --- |
| `SessionsController#create` | 發 session 前要求本店指派 | 與帳密錯誤**完全相同**的訊息 |
| `ApplicationController#resume_admin_session` | 每個 request 驗一次 | 當作**未登入**（不是 403） |

- 錯誤訊息相同是刻意的：另給一句「你不屬於這間店」＝用登入表單洩漏
  「這個 email 在平台上存在」＋「這間店存在」，兩個都是枚舉側通道。
- 回未登入而不是 403 同理：403 等於承認這間店存在。
- 閘放在 `ApplicationController` ⇒ `Admin::BaseController` 與 GraphQL controller
  都繼承它，**一處覆蓋整個 admin**。
- 🔴 **不動 `can?` 的 owner 短路**：兩層是 AND（第一層能不能進來／第二層進來能做什麼），
  owner 在自己有指派的店裡本來就該無所不能。缺第一層就補第一層。

### 配套（少一個就是把所有人鎖在門外）

- **backfill migration**：正式站實測 `assignments=0`。不先鋪路，接閘當天所有帳號都進不去。
  恰好一間店才推斷補齊；**多於一間店一列都不建**並在日誌大聲說明——
  猜錯 staff↔shop 對應的代價，正是這支 migration 要防的那個漏洞。
- **seeds 建立指派**：否則新裝的 owner 會被自己的安全閘擋掉，而錯誤訊息刻意不說原因。

### 🔴 我自己先寫出了一組空炮，記在這裡

最初的恢復側測試是「在 A 店登入 → 把 cookie 帶去 B 店 → 應該被擋」。三條**全綠**，
但**把恢復側的閘整個拿掉之後它們還是全綠**——因為 admin cookie 是 host-only
（`config/initializers/session_store.rb` 刻意不設 `domain:`），測試客戶端根本不會把
gate-a 的 cookie 送到 gate-b。那三條斷言的是 **cookie scope**，不是這道閘。

恢復側的閘真正管得到的是**「session 還活著，但指派被撤銷了」**——只擋登入的話，
被踢出商店的人手上那張 cookie 會一直有效到過期。改成測這個之後，M2 注入才會紅。

⇒ 教訓與本輪前半段一樣：**綠不等於有守住，要注入回歸才知道**。
而且這次犯錯的是我自己，就在我剛用同一套方法抓完別人的空炮之後。

**注入回歸驗證**：

## 尚未完成或需注意的風險 (Pending / TODO)

1. 🔴 **建店 onboarding 必須同時建 owner 的指派**。目前沒有 production 的建店路徑
   （只有 seeds／console），所以現在不是問題；做 onboarding 時這是**硬前提**，
   漏了就是「建完店的人自己進不去」。
2. 🔴 **多店部署的 backfill 需要人工**：migration 在 `shops > 1` 時一列都不建。
   這是刻意的 fail-closed，但代表多店環境升級時營運者必須手動指派，否則帳號全鎖。
   目前正式站是單店，不觸發。
3. **GraphQL 對未認證請求回 200 ＋ top-level `errors`**，而鐵律 4 第三層要求
   「認證失敗回非 200」。這是**既存**契約不符、非本輪引入；改它要動 API 契約與前端
   三層錯誤處理，屬另一輪。`spec/requests/tenant_access_gate_spec.rb` 對此
   **刻意只斷言安全性質（不得回任何資料）**，不斷言 HTTP 狀態碼——
   斷言「非 200」會讓它在修好之前一直紅，斷言「是 200」則把待修行為釘成規格。
4. **非 owner 的權限路徑仍未真正啟用**：`roles` 表是空的，`user_store_assignments.role_id`
   目前一律 nil。非 owner 帳號現在等於沒有任何權限（fail-closed，方向正確），
   但完整 RBAC 要等 M5。
5. 本輪**只補第一層**。第二層（`ProductPolicy` 等）的 owner 短路照舊——那是刻意的，
   理由見 D46。若日後要做「owner 也受角色限制」，那是另一條裁定。
