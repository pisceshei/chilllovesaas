## 🔴 突變驗證（18 個突變）

**17 個轉紅。** 剩下 1 個（`mode == :publish` 單獨拿掉）綠是**設計如此**——
U3 的「無效果」由**兩層**各自獨立保證（mutation 的 `normalize` 不傳、
服務層的 `mode` 不驗），複合突變（兩層同時拆）令三格 U3 轉紅，已複驗。

### 🔴 首跑有四個突變全綠——四個的根因**都是同一個形態**

**「測試拓樸沒涵蓋到防線唯一會被觸發的狀態」，不是「沒有防線」。**
這是第 12 包與 S0／S1 反覆出現的同一形態，逐條記在這裡：

| 突變 | 首跑全綠的根因 | 修法 |
|---|---|---|
| M7 立即發布也投事件 | 那一格打在**線上商店**上，而該列已存在且是過去時間 ⇒ 走 R5 no-op ⇒ `published_at` 沒變就**根本不會呼叫** `enqueue_scheduled_event!` | 改用第二個管道，讓它真的建出一列 |
| M8 unpublish 也驗 `publishDate` | U3 送的日期在 publish 側**本來就會通過** ⇒ 有沒有跳過驗證分不出來 | 補兩格**對照組**：變體＋未來日期（publish 側 `INVALID_STATE`）、不支援排程的管道＋未來日期（publish 側 `FEATURE_NOT_ENABLED`） |
| M16 rescue 只在 NULL 時補 | 注入的列照抄 `attrs` ⇒ 它本來就已經帶著呼叫端要的那個未來日期 | 注入時改寫成**現在**，讓對手的列與呼叫端的意圖不同 |
| M17 拿掉鎖順序排序 | 死鎖需要兩個交易以相反順序取鎖，MRI 下無法穩定重現（重現得了也是 flaky） | 改成**直接釘契約**：送遞減順序進 `resolve_publication_entries`，斷言輸出遞增。誠實登記它證明的是排序契約、不是「死鎖不會發生」 |

### 併發測試的一個設計教訓

第一版把 gate 下在 `locked_publication_row` **回傳之後**，結果對手的 INSERT 卡 50 秒
`LockWaitTimeout`——因為 InnoDB 在 REPEATABLE READ 下對**不存在的列**做
`SELECT ... FOR UPDATE` 會取**間隙鎖**，被 gate 住的那一方握著它在等。
⚠️ 那次失敗本身就是列鎖生效的證據，但它讓測試量不到東西 ⇒ gate 改下在取鎖**之前**。

同一個發現讓 `RecordNotUnique` 的 rescue 被重新定性：在 REPEATABLE READ ＋ 列鎖之下
它**自然情境打不到**，是縱深防禦（隔離級別改 READ COMMITTED 就成常規路徑）
⇒ 改用**故障注入**測它，並在 dev doc 誠實這樣標，不假裝那是自然競態。
