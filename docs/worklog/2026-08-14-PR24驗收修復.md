### 一、🔴 多型關聯的跨租戶漏洞（Codex #24-1）

- **查證**（不轉述 review，讀 gem 原始碼）：
  `acts_as_tenant-1.0.1/lib/acts_as_tenant/model_extensions.rb:57-62`——
  `polymorphic_foreign_keys.include?(a.foreign_key)` 把多型外鍵**明確排除**在歸屬驗證外。
  加上 MySQL 無法對多型欄位建外鍵 ⇒ **gem 層與 DB 層都沒有人擋 `publishable`**
  （`publication` 有複合外鍵，`publishable` 沒有）。
- **但實際暴露面比 review 敘述的窄，這點要寫準**：常規請求下 `belongs_to :publishable`
  的存在性驗證會去載入該物件，而三個 Publishable 類別都有 `acts_as_tenant` 的
  default_scope ⇒ 別家店的 id 載不出來 ⇒ 以「must exist」失敗。
  🔴 **但那是偶然的副作用，不是明擋**，以下情況全部失效：
  `ActsAsTenant.without_tenant`（資料遷移／seeds／維運腳本）、明確指定 `shop_id`、
  `insert_all`／`upsert_all`、或日後有人改成 `optional: true`。
- **修法**：新增 `publishable_belongs_to_same_shop` validation。
  🔴 內部用 `ActsAsTenant.without_tenant` 查 owner 的真實 `shop_id`——
  帶著 default_scope 查會被過濾成 nil，那樣**分不出「不存在」與「屬於別店」**。
- **三條測試**，其中關鍵的一條是**在 `without_tenant` 下仍被拒**——
  只測常規路徑的話，測試會綠但綠的原因是那層偶然保護，換言之**證明不到新 validation 有用**。
- ⚠️ **誠實聲明**：本 validation 擋不住 `insert_all`／`upsert_all`（Rails 一律跳過 validation）。
  要拿到 DB 層底線只能改成逐型別關聯表——那是取捨，已寫進 88 §4.1／§6 而非假裝沒有。

### 二、🔴 `collections.published_at` 雙重事實來源（Claude 驗收 🔴 第 1 條）

- `collections` 本來就有一個語義**完全相同**的扁平 `published_at`（schema.rb:96），
  而本 PR 又把 Collection 接進 `resource_publications`
  ⇒ **Collection 同時有兩個上架事實來源**。
- 🔴 這正是本 PR 自己援引、用來移除 `products.published_at` 的那條理由。
  我把理由寫得很清楚，卻沒有把它套用到同批接進來的 Collection 上，
  而且 88 §5／§6 也沒登記成刻意分期 ⇒ **是漏掉不是分期**。
- **修法**：migration 一併回填 Collection 進 `resource_publications` 並移除該欄；
  索引由 `(shop_id, collection_type, published_at)` 改為 `(shop_id, collection_type)`；
  `down` 對稱補上。

`rejects scheduling a single variant` 原本用 `publishable_id: 1`（**不存在的 id**）。
測試會綠，但綠的原因可能是「找不到該物件」而不是「不得為 variant 排程」——
**證明不到它宣稱要證明的事**。改用真的 variant，並加「立即發布仍可」反證。

### 七、驗證

🔴 **本輪發現 `rails db:migrate` 不會執行 migration**：DB 重建時 Rails 看到
`schema.rb` 的版本號已等於最新 migration，直接**載入 schema 而非逐個執行**
（輸出是按字母序一次建完所有表，不是 migration 的順序）——
第一次驗證時因此看到「migration 都 up 了但 `collections.published_at` 還在」。
把 `db/schema.rb` 暫時移開後強制重跑，四個 migration 才真的執行。
