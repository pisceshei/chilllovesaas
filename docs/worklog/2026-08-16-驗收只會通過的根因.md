# 2026-08-16 — 驗收「只會通過、不提意見」的根因，與 Fable 5 回退

> 使用者：「排查下為什麼每次 claude bot 只通過驗收，不提意見。修復下」

---

## 已完成的工作 (Done)

### 1. 根因：**prompt 把驗收方訓練成「清單稽核員」，不是「找缺陷的人」**

🔴 **不是模型能力問題，是任務定義問題。**

證據——PR #29 那則「通過」逐字寫的是：

> 重做紅線抽驗（`app/` 無 `to_f`／`Float(`、無 polaris、admin SPA 無 REST 呼叫、
> `shop.rb` callback 無外部 IO、上限值全走 `Limits.fetch`）

**那是在走清單。** 而 prompt 的「必查硬性紅線」只有十條合規項：float／`shop_id`／
REST vs GraphQL／冪等／transaction 內 IO／硬編上限／polaris／併發測試／註釋／`docs/dev`。

**一個 PR 可以十條全過，同時有五個會炸的 bug。**

### 2. 這不是假設——PR #38 同一份 diff 的對照

我判「通過」的同一份 diff，另一個審核方抓出**五條真缺陷，沒有一條在清單上**：

| 缺陷 | 為什麼清單抓不到 |
|---|---|
| migration 對**既有資料**會 `Duplicate entry` 而中斷 | 清單只問「有沒有違反鐵律」，不問「這支 migration 在非空的庫上跑得過嗎」 |
| ActiveRecord **關聯快取**讓物化欄算出舊值 | 框架語義，清單沒有這一類 |
| 父表漏宣告 `has_many` ⇒ 該資源**永遠刪不掉** | 同上，而且**沒有任何既有測試會紅** |
| 兩份權威文件對同一件事**互斥** | 清單只看代碼，不看文件之間 |
| 驗證只擋「至多一個」擋不住「少給」 | 清單沒有「這個約束真的完整嗎」這一問 |

### 3. 修法：在清單**之前**加一段「你的工作是找缺陷」

🔴 **明寫「清單是地板不是天花板」**，並把上面那張對照表逐字放進 prompt——
讓它知道**這件事真的發生過**，不是抽象叮嚀。

列出**七類必須主動找的缺陷**（找不到要明說找不到）：

1. **migration 對既有資料安全嗎**——🔴「在空庫上跑得過」證明不了任何事；
   失敗會不會留半套用狀態（MySQL DDL **不具交易性**）；`down` 真的可逆嗎
2. **框架語義用對了嗎**——關聯快取 vs DB 現況、`dependent` 的**宣告順序**、
   callback 時機、`insert_all` 繞過什麼、`private` 對 mixin 內部呼叫無效、
   Rails 的 `rescue_responses` 對映
3. **新表／新 model 的關聯宣告完整嗎**——不補 `has_many` 的結果通常是
   「某資源永遠刪不掉」，而且**測試不會紅**
4. **約束真的完整嗎**——「至多一個」vs「恰好一個」、NULL 在唯一索引下不去重、
   CHECK 不能跨表；**擋不住的那一半有沒有第二道防線**
5. **同一件事寫在幾個地方**——本倉庫已有前例（刪除策略三處、`sku/barcode` 兩處）
6. **註釋／訊息宣稱的行為，代碼真的做得到嗎**——**說謊的註釋比沒有註釋更糟**
7. **PR 描述的「假設清單」逐條檢驗**——🔴 那是作者自己標出的弱點，**不得跳過**；
   作者說「這條沒做」時，要問「不做的後果是不是比他寫的更嚴重」

🔴 **並且改了「通過」的門檻**：必須說得出「七類各自看了什麼、為什麼沒發現」。
**只寫「紅線抽驗皆通過」＝沒有做這份工作。**
⚠️ 找不到 🔴 是可以的，但那時**至少要有 🟡 或「未覆蓋」的實質內容**——
一則沒有任何具體觀察的「通過」，本身就是這份工作沒做的證據。

### 4. 🔴 模型回退**已從本 worklog／本分支撤回**——我的診斷被證偽了

本輪原本還做了「`claude-fable-5` → `claude-opus-5` 回退」，理由寫的是：

> 三次數據逐字相同（`is_error=true num_turns=1 total_cost_usd=0 duration_ms≈571–834`）
> ⇒ 第一個 API 請求就被拒、屬持續性 ⇒ **最可能是帳號無 Fable 5 權限**。

**那個「最可能」是錯的，而且是可以被一行 git log 證偽的**（PR #37 的工作階段先查到，
Codex 又補了一刀說我的反向斷言也講得太滿）：

| 證據 | 來源 | 推翻了什麼 |
|---|---|---|
| 模型自 **08-15 00:14** 起就是 fable-5 | `git log -S claude-fable-5` | — |
| PR #33 的驗收在 **01:41／01:54 兩次成功**貼出結論 | PR #33 留言 | 🔴 同一份設定稍早才成功過兩次 ⇒ **不可能是「沒有權限」** |
| 失敗自 **01:55** 起，至 **12:46** 連續 11 小時全滅 | Actions run 列表，全部 ≤47s | 不是暫時性抖動；也不是 5 小時滾動視窗（早該恢復） |
| `claude-review.yml` 最後一次改動是 **01:00** | `git log` | 🔴 **最後一次成功與第一次失敗之間，這個檔一個字都沒改** |
| `CLAUDE_CODE_OAUTH_TOKEN` 最後更新 **Aug 14** | repo Settings → Secrets | token 輪換也不在邊界上 |

⇒ **repo 這一側的每一個變數都被時間戳排除了。**
⇒ 🔴 **換模型（不管換成哪一個）都不會修好它**，PR #37 的結論相同。

**⚠️ 我留下的錯誤不只是猜錯，是猜錯之後把猜測寫成了設定的理由。**
那段註釋會讓下一個人以為「回退 Opus 5＝已修復」，於是合併、失敗、再繞一圈。
⇒ 本分支的 model 改動**已還原成 main 的版本**，模型這件事整個交還給 PR #37
（它有完整的沿革與正確的中立敘述）。本分支只留 prompt 修正。

🔴 教訓：**「與既有註釋裡的預言吻合」不是證據，是確認偏誤最舒服的形態。**
那句預言（「若報模型不存在／無權限，那是帳號權限問題」）是我自己稍早寫的，
於是我讀到吻合的指紋就收工了——而真正該做的第一件事是
`git log` 問「最後一次成功與第一次失敗之間，到底什麼變了」。答案是：**什麼都沒變。**

### 5. 順帶證偽：`Rerun in debug mode` 這條路是死的

action 失敗時印的原話是
「full output hidden for security. **Rerun in debug mode** or enable `show_full_output: true`」。

實測（PR #41 的 run 31865047628，勾 **Enable debug logging** 重跑 attempt #2）：
**沒有用**——raw log 11,704 行裡，那句「full output hidden」照樣印，
`result` 物件依然只有 6 個欄位：

```
{"type":"result","subtype":"success","is_error":true,
 "duration_ms":626,"num_turns":1,"total_cost_usd":0,"permission_denials_count":0}
```

🔴 **`result` 這個欄位（錯誤訊息就在裡面）是被白名單式砍掉的，不是被 log 等級藏起來的。**
⇒ 兩條建議裡只有 `show_full_output: true` 是真的，debug 那條會浪費一次重跑。
這也解釋了為什麼這個 bug 卡了 11 小時、跨四個工作階段：
**每個人拿到的都是同一組去掉了原因的數字。**
