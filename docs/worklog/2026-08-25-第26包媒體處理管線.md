## 已完成的工作 (Done)

- **migration**：`media.status` default `"ready"`→`"uploaded"`（四態起點；原值是 M0
  建表佔位，第 24 包登記的矛盾在此解掉——`media` 表零列，複驗
  `SELECT COUNT(*) FROM media`）＋`media.file_id`（複合 FK，featuredImage 要靠它拿
  衍生尺寸）＋`files.derivatives`（JSON）＋`files.processing_error`。
- **`MediaPipeline::Derivatives`**：四個尺寸的正典（13 §F3-3 逐字 thumb160／card533／
  detail1200／og1200×630）。🔴 **fit 語義是 ours 裁定**（13 §F3 只給數字沒給語義）：
  thumb/card/detail＝最長邊上限且**不放大**；og＝固定 1200×630 居中裁切填滿
  （OG 是版位要求不是上限）。衍生 key 走獨立命名空間
  `shops/{id}/derivatives/{file_id}/{checksum前12}/{variant}.webp`（checksum 段是
  審查 C6 後加的並發隔離）——不用「原 key＋尺寸後綴」形，那正是 12 §C.7:255
  保留字尾清單在防的撞名。
- **`MediaPipeline::VipsBackend`**：libvips 封裝（讀 header 驗像素上限＝防解壓炸彈、
  `thumbnail_buffer` 做 fit/cover、轉 sRGB 後 `strip: true` 去 EXIF/GPS 與 ICC、webp 編碼）。🔴 **可插拔**：`available?`
  為假時拋 `BackendUnavailable`——**libvips 只有 bt3 有**，本機 Windows 與 CI 皆無
  （Gemfile:34-42 已記載這是 image_processing 被退回 1.x 的原因）。不用
  image_processing gem：它只是薄封裝，四個操作 ruby-vips 直接有，少一層版本相容面。
- **`MediaPipeline::ProcessFile`**：狀態機 uploaded→processing→ready／failed。
  🔴 **兩類失敗嚴格分開**（整合規格 §1.3 逐字「不無限重試」）：檔案本身壞（損壞／
  超像素）＝`failed` 終態＋`processing_error`、**不 raise**（delivery done）；
  環境的錯（libvips 沒裝／IO／OOM）＝**raise** 並把 status 還原 uploaded ⇒ relay
  指數退避。把後者標 failed 等於用「檔案壞了」冒充「機器沒裝軟體」。fs 在 txn 外＋失敗補償刪衍生（承第 25 包
  審查 C2/C3/C8 紀律）。冪等：已 ready 且四衍生齊全 ⇒ 直接返回。
- **`MediaPipeline::ProcessConsumer`**＋`Events::Consumers::REGISTRY` 接線
  （REGISTRY 從空表變成有住戶）。`Storage::FileCreate` 落庫改 `uploaded`
  （replace 模式同時清空 derivatives ⇒ 換內容重跑管線）。
- **讀取面**：`Types::ImageType`（原圖＋四衍生 URL；🔴 未 ready 時衍生 URL 一律
  null——不得拿 20MB 原圖冒充縮圖）＋`ProductType.featuredImage`／
  `mediaMissingAltCount`；blob 端點加 `?variant=`（同一支端點＝授權面只有一處，
  variant 取白名單、key 由 file.id 推導不吃輸入路徑）。
  🔴 **alt 的權威在 `media` 那一列不在 `files`**（同檔掛不同商品可有不同 alt，
  62 §F.1 的度量對象也是 media）⇒ ImageType 的 object 是 `Presenter(file, alt)`。
- **SPA**：商品列表縮圖欄（三態：有衍生→`<img loading="lazy">`／處理中／無圖，
  兩種空態分開）＋缺 alt 徽章；i18n 五語 ×5 鍵；CSS 走 token。
- **push 前對抗式審查輪**（34 agents 五維度；18 條確認 11 條反駁——本包最大一批，
  libvips 那維抓到的全是本機測不到的）：
  ①🔴 **錯誤分類倒置**（C0/C5 high）：ruby-vips 只導出一個錯誤類 `Vips::Error`
  （複驗：`grep -rn "class Error" $(bundle show ruby-vips 2>/dev/null || echo .)/lib`），
  OOM／fd 耗盡／缺 webp saver 與「檔案壞」長得一模一樣，原本一律轉 `DecodeFailed`
  ⇒ 環境問題把使用者的圖永久燒成 `failed` 且**無任何恢復路徑**。改**白名單制
  fail-closed**：命中檔案內容問題的訊息才終態，未知一律上拋重試。
  ②🔴 **EXIF orientation 不對稱**（C1 high）：`thumbnail_image` 自動轉正、`resize`
  不轉，`strip` 又刪掉 orientation tag ⇒ 直式手機照片的 thumb/card/detail 全歪、
  og 是正的，瀏覽器無從補救。改**全部走 `thumbnail_buffer`**（自動 autorot＋
  premultiply，順帶解掉 C3 透明圖色暈）。
  ③🔴 **截斷檔不報錯**（C2 high）：libvips 預設 `VIPS_FAIL_ON_NONE`，壞檔用灰色
  填滿當正常圖存下 ⇒ 顯式 `fail_on: :error`。
  ④C4 色彩：`strip` 連 ICC profile 一起刪，廣色域來源會整張偏色 ⇒ 先 `colourspace(:srgb)`。
  ⑤🔴 **並發互蓋**（C6 high）：同一 file 因 replace 有兩輪在飛時寫同一組 key ⇒
  衍生 key 帶**內容 checksum 前綴**＋寫回帶 checksum 條件（內容已換就丟棄本輪）。
  ⑥🔴 **`processing` 是沒有出路的孤兒態**（C7 high）：環境錯 raise 後留在 processing，
  事件 dead 之後沒人撿、錯誤訊息還會隨 outbox purge 消失 ⇒ raise 前**還原 uploaded**
  並把訊息留在 `processing_error`。
  ⑦C8 `complete?` 只看 JSON 不看 blob ⇒ 被刪的衍生永不重生、讀取面 500 ⇒ 加
  `LocalDisk.exist?` 檢查。C9 failed 分支未清 derivatives ⇒ 清空。
  ⑧🔴 **列表 N+1**（C10/C11 high＋C14/C16 假註釋）：`featuredImage`＋
  `mediaMissingAltCount` 每列 2–3 條 SQL，且註釋宣稱的 `KeysetConnection` preload
  **根本不存在** ⇒ resolver 改吃 `to_a`、preload 落在 `QueryType#products`；
  加 N+1 回歸例（拔掉 preload 即紅，已實測）。
  ⑨C15 `def reset_availability! = expr if cond` ——Ruby 解析成
  `(def m = expr) if cond`，條件為假時**方法根本沒被定義**。
  ⑩C17 `VipsBackend` 零覆蓋 ⇒ 新增 spec 專測**錯誤分類邏輯**（純邏輯、不需 libvips），
  順帶抓到相鄰缺陷：vips 未載入時 `rescue Vips::Error` 的常數解析失敗會拋 NameError
  蓋掉契約上的 `BackendUnavailable` ⇒ 改 `rescue StandardError` 再判型別。
  C13 `StoredFile` 過時註釋一併更正。
- 測試：rspec **552/552**（審查後 +8：錯誤分類正反矩陣、reset_availability! 存在性、
