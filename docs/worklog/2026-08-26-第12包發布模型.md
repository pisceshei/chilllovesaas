### 🔴 本輪最值得記的一件事：官方文檔與實測衝突，且我一開始把實測寫得太滿

官方逐字說新變體「published to all channels **where the parent product is published**」，
而我實測到新變體拿到了父商品沒有的管道。我第一版把它寫成「本尊不跟父商品，實測為證」——
**那是過度解讀**：加選項時新變體可能由前身 `Default Title` 變體衍生，而它本來就有全部管道的列，
我這個實驗分辨不了這兩個假說。

回頭補做 UI 側觀察後才看清楚：變體在父商品未發布的管道上**確實有列**（toggle 是開的），
只是被灰掉並附提示「Product must be published to the channel before variants can appear」
⇒ 官方那句描述的是**生效狀態**，我量到的是**儲存狀態**，兩者可以並存、不衝突。

⇒ 最終處置：採「全部 auto_publish 管道」，但在 82 §8.4②、`m2-publication-model.md` §4、
model 註釋與 spec 訊息**四處**都標明這是**我方裁定（ours）而非照抄**，並登記那個排除不掉的
替代假說為未取得。**兩種選法對可見性的結果完全相同**（閘控在讀取層的 AND），所以這是低風險裁定。

### 🔴 當場複驗到第 11 包的部署事故機制

同一支回填 migration：本機**開發庫回填 3 列**（有既有資料）、**測試庫回填 0 列**（空庫），

盯著 migration 檔案本身有沒有 `without_tenant`（spec 用的是邏輯副本，拿掉那行其他格全會綠）。

### 🔴 對抗審查一輪的處置（同一份 worklog，不另建；鐵律 21.4）

兩位審查員（正確性／併發、突變測試）以**不同方法各自獨立**收斂到同一條根因：
**規則有三份實作，而測試守的是它自己那一份。**

| 標的 | 實測後果 | 當時的 spec |
|---|---|---|
| migration 的 `where(shop_id:)` 刪掉一個 token | 寫出跨租戶的列（`mismatched=2`）；`insert_all` 繞過 validation、多型欄位無外鍵，兩層都不擋，而 `down` 不可逆 | **38 examples 0 failures** |
| migration 的 `auto_publish: true` 拿掉 | 回填成完全相反的管道集合 | **全綠** |

**修法（一次根因批次修復，17.2）**：邏輯收斂成一份（`Publications::Materialize.backfill_all!`），
migration 變成薄呼叫端，**spec 改成載入並執行真的 migration 類別**，掃字串的 source-guard 全數退場
——那種守衛可以被一行註釋騙過（實測：`ActsAsTenant.without_tenant do` →
`begin # ActsAsTenant.without_tenant`，守衛照樣過）。

**突變測試找到的七個假綠，逐條補測**：

| # | 假綠 | 為什麼假綠 | 補法 |
|---|---|---|---|
| 4 | `Materialize` 的 `without_tenant` 零覆蓋 | 當時宣稱在守它的那一格（「🔴 沒有 current_tenant 時照樣建列」）自己把建立動作包在 `without_tenant` 裡 ⇒ **環境提供了實作該提供的東西**，兩種實作不分岔 | 加 `with_tenant(nil)` 與「current_tenant 是別間店」兩格 |

### 🔴 審查證偽了我自己寫的一句因果（鐵律 19.5，原文保留、追加更正）

初版 migration 與 spec 都宣稱「拿掉 `without_tenant` ⇒ 正式環境只要有既有商品就 `NoTenantSet`」。
**那是錯的**：初版讀取全走 `.unscoped`（連 default scope 的 raise 一起拿掉）、寫入全走
`insert_all`（不經 model）⇒ 拿掉照樣跑完。那句是從第 11 包 `20260826058000` **誤植**的
——該包成立（它走 `find_or_create_by!`），本支不成立。
⇒ 現行版**刻意移除 `.unscoped`** 讓 `without_tenant` 真正承重，並由行為測試守住。
