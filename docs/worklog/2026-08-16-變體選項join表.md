## 已完成的工作 (Done)

### 1. Migration ＋ schema

`20260816000000_create_product_variant_option_values.rb`：三張父表補唯一索引、
`product_variants.option_values_digest`、join 表、五支外鍵。已在真 MySQL 8.4.9 上
`migrate` → `rollback` → `migrate` 走過一輪，`schema.rb` +26 行。

🔴 **MySQL 8.4 的複合外鍵限制**（實測，不是查文檔）：`restrict_fk_on_non_standard_key = 1`
是**編譯預設**，被指向的欄位組必須**逐字、同順序等於某支 UNIQUE 索引的完整清單**
——最左前綴 `ERROR 6125`、欄序不同也 `ERROR 6125`。
⇒ 既有的 `uq_*_tenant_id (shop_id, id)` 與 `uq_product_options_product_id_name`
**都無法**讓外鍵指向 `(shop_id, product_id)`。那三支新唯一索引不是順手加的，是**必要條件**。

🔴 **digest 欄分三步加**（可空 → 明文回填 → 收緊），不是一步 `null: false`：
MySQL 在 STRICT 模式下對既有列會**靜默填 `''`**，那會寫進一個不是 SHA1 的假 digest。

### 2. `Catalog::OptionValuesDigest`（digest 的唯一產生處）

依 `product_option_id` 升冪 → `"選項id:值id"` → `,` 相接 → SHA1。

| 事件 | digest | 為什麼 |
|---|---|---|
| 選項值改名 | **不變** | 輸入是 `option_value_id`，改名不動 id |
| 選項重排 position | **不變** | 排序鍵是 id 不是 position |
| 加／刪選項 | 變 | 座標真的變了；由寫入 service 在同一 transaction 重算 |

🔴 **輸入用 id 不用字串，依據是 `67` §B.3-4 逐字**：「譯文掛在 `product_option_values.id` 上，
不是掛在字串上…**若變體以「選項值字串」比對，切語言就會找不到變體**」。
連帶好處：這讓 metafield-linked option value（身分是 GID 不是字串）**自動不成問題**。

### 3. 四個 model

`ProductOption`／`OptionValue`／`ProductVariantOptionValue` **全新**——
表在 M0 就建好了，但 `app/` 對 `product_options`／`option_values` 一直是**零讀寫**
（無 model、無 GraphQL type、無 factory、seeds 也沒有）。D12 是它們第一次上線。

`ProductVariant` 加 `before_validation :recompute_option_values_digest` ＋ format 驗證。

## 追加（2026-08-16）：PR #38 的 Codex review，五條全中

🔴 **五條都是真的，其中一條是我的測試漏掉的嚴重 bug。**

### C-1（🔴 最嚴重）：migration 在**任何既有多變體商品**上會直接掛掉

回填一律填 `EMPTY_DIGEST`（join 表那一刻還不存在，**沒有座標可算**）
⇒ 同一商品下每個既有變體拿到同一個 digest
⇒ 唯一索引 `Duplicate entry ... for key 'uq_product_variants_option_values_digest'`。

**實測證實**（在 test 庫用 raw SQL 造一個兩變體的舊商品）：
```
Duplicate entry '9449-9350-da39a3ee...' for key 'product_variants.uq_product_variants_option_values_digest'
```

🔴 **我原本沒發現，是因為跑的時候 `product_variants` 是空的。**
**「在空庫上跑得過」證明不了 migration 對既有資料是安全的**——這條要記住。

**額外發現**：MySQL 的 DDL **不具交易性** ⇒ 失敗後 DB 停在**半套用狀態**
（欄位加了、索引與 join 表沒有）。這讓「重跑」變成要先手動清理。

**修法：fail-closed，而且把閘門放在 `up` 的第一件事。**
🔴 為什麼不自動修：D12 之前**沒有任何地方記錄「哪個變體對應哪個選項值」**
⇒ 那些座標**不是遺失，是從來不存在**，重建不出來。
可選的自動修只有「塞假 digest」或「留 NULL」，兩個都比停下來講清楚糟。
⚠️ 閘門第一版放在三支父表索引**之後** ⇒ 失敗仍留下索引；已移到最前面。

### C-2：`recompute_option_values_digest` 吃關聯快取

寫入 service 的典型形態（先讀變體 → 直接動 join 列 → 再存變體）下，
`product_variant_option_values` 回的是**載入當下的快照** ⇒ digest 算出來是舊的。
修法：已持久化就 `association.reset`。
🔴 **新建的變體不能 reset**——那會清掉呼叫端 `build` 上去、還沒存檔的列。

### C-3：`Product` 沒有 `product_options` 關聯

建了 `ProductOption` 卻沒在父表宣告 ⇒ `fk_product_options_product_id`
會讓**任何有選項的商品永遠刪不掉**，而且沒有既有測試會紅。
⚠️ 這與 `docs/specs/88` §4 那個 `Shop#publications` 的教訓**同型**。
🔴 順帶確立：**宣告順序就是刪除順序**，`product_variants` 必須排在 `product_options` 之前
（join 列被兩者的 `dependent` 涵蓋，但 `OptionValue` 對它是 `restrict_with_error`）。

### C-4：`docs/research/22`:126 與新的刪除契約互斥

本檔是**按鈕級驗收清單**，第 126 行仍寫「被 line_items 引用禁止硬刪」
⇒ 與 `13` §F1-4 的新契約**互斥，舊的阻擋行為隨時會被重新引入**。已改。
🔴 **教訓**：刪除策略現在寫在**三處**（`13` §F1-4／`63` §B.4／`22`:126），
改一處等於製造矛盾。與本輪 barcode 那條同型。

### C-5：座標可以「少給」

DB 擋得住「**至多**一個值」與「值屬於該選項」，但**擋不住少給**
⇒ 有選項的商品上，完全不給座標會被當成合法的 `NO_OPTIONS`；只給一部分也存得進去。
修法：`option_coordinates_cover_every_product_option`。
⚠️ **只能在 model 層擋**（MySQL 的 CHECK 不能跨表）⇒ 它是**唯一**的防線，
`insert_all`／`upsert_all` 繞過它時沒有第二道。

🔴 **這條連帶推翻了 factory 的形狀**：原本「先建變體、後掛座標」在有選項的商品上
是**不合法的中間狀態**。改成 `after(:build)` 先掛座標再一起存。
⚠️ **這不是 factory 的權宜，是真實約束**——寫入 service 也必須這樣做，
factory 照同樣形狀走，測試才代表得了生產路徑。

## 驗收後修正（2026-08-16，多代理驗收三條發現＋衍生）

### 🔴 1. `association.reset` 有兩層靜默資料遺失（實測復現後重寫）

**第一層（吵但指錯方向）**：`build` 未存列在 `before_validation` 被 reset 丟出
autosave 目標 ⇒ 驗證讀到重載後的空關聯，報「缺：N」——錯誤存在但訊息指向不存在的原因。

**第二層（完全靜默，實測 `save! => true`、DB 舊值、digest 舊值、零錯誤）**：
修改已載入 join 列的屬性 → reset 丟棄修改 → autosave 存的是重載的舊物件。

**修法**：廢除 reset，新增 `effective_option_value_pairs`——**以 DB 為底、
疊上記憶體中 autosave 將落地的增量**（新列加入、標記刪除剔除、被改的持久列以
記憶體值覆蓋）。digest 與「每選項恰好一值」驗證**共用同一份**，杜絕
「驗證讀快取、digest 讀 DB」的分裂。reset 原本要修的「直接動 DB 後 digest 過期」
由 db_pairs 的即時查詢繼續蓋住（有回歸測試）。

**衍生發現（修的過程逼出來的，各自實測）**：
- `assoc.loaded?` 當閘門會漏掉「未載入但有 build 列」——`build` 不標 loaded。改讀 `target`。
- 🔴 **預設 has_many 的 autosave 不存被修改的持久列** ⇒ 就算 digest 算對，
  DB 也不會更新——digest 與 join 列不一致的另一條路。加 `autosave: true`。
- ⚠️ Rails 全域語義邊界：未載入關聯上 `.first` 回傳**不在 target 裡**的獨立物件，
  改它再存變體誰都看不見。已寫進註釋（載入後改，或改完自己 `row.save!`）。

### 🔴 2. digest 對 Float 靜默截斷

`Integer(1.9)` 回 1 ⇒ `[[1.9, 2.9]]` 與 `[[1, 2]]` **同 digest**，而檔頭 @raise
宣稱非整數會 raise。改成嚴格 `is_a?(Integer)`（`"7"` 這種可轉字串也擋——
兜底對輸入寬鬆就不是兜底）。spec 補 Float／可轉字串兩組。

### 🔴 3. `restrict_with_error` 的查詢無可用索引

`OptionValue` 刪除前的 exists? 是 `shop_id + option_value_id`，三支既有索引
都只能用到 shop 前綴——migration 註釋卻宣稱「反查哪些變體用了這個選項值」已被
`ix_pvov_option_value` 涵蓋（[shop, option, value] 對此查詢涵蓋不了）。
補 `ix_pvov_by_value [shop_id, option_value_id]`；migration 未合併，就地改。

### schema.rb 重生的坑（記下來）
