# CI 全紅修復：三個獨立根因，全部與程式碼無關

> commit：282896e（執行位元）／fd7932a（YAML 修正）／950b2c1（brakeman）｜
> 結果：**CI #22 綠燈**（test 1m27s ＋ quality，總 1m50s）

## 已完成的工作 (Done)

使用者指出 GitHub 上「基本上都是 failed」。查證後：**CI 已經紅了一段時間，且與剛合的
依賴升級無關**（run #17「救回並改號」在依賴合併之前就已失敗；所有 dependabot PR 的
CI 也全紅）。逐一挖到**三個獨立根因**：

### 根因一：`bin/*` 缺執行位元（test 與 quality 都掛在第一個要執行 bin 的步驟）
- 症狀：`bin/rails: Permission denied` ／ `Error: Process completed with exit code 126`
- 原因：Windows 的 git 預設 `core.filemode=false`，M0 骨架從 Windows 提交時，
  `bin/` 底下 **10 個檔全部以 `100644` 記錄**（brakeman／bundler-audit／ci／dev／jobs／
  rails／rake／rubocop／setup／vite），`scripts/cloud-setup.sh` 同。Linux runner 無法執行。
- 處置：`git update-index --chmod=+x` 全部 11 個檔 → `100755`。
- **防呆**：CI 兩個 job 的 checkout 之後各加一步「Verify bin/ scripts are executable」，
  缺 +x 時早失敗並直接印出修法，不再是神祕的 exit 126。guard 已做正反測試
  （故意把 `bin/dev` 退回 644 → 確實抓到 → 還原）。
- AGENTS.md 新增「🔴 Windows 開發者必讀：檔案執行位元」章節。

### 根因二：我修根因一時把 YAML 寫壞（workflow 根本沒啟動）
- 症狀：run #20 顯示 Failure 但**無任何 job、duration 是「–」**——這不是 job 失敗，是解析失敗。
- 原因：我用 heredoc 寫入 guard 時，`tr '\n' ' '` 裡的 `\n` **被 shell 展開成真正的換行**，
  該字串在 YAML 裡斷成兩行、縮排失效。
- 處置：改成不含跳脫字元的靜態字串。
- **教訓（已寫進 commit）**：改 CI YAML 後要**先本機 `ruby -ryaml` 驗 parse，再把 step 的
  `run` 取出來 `bash` 實跑一遍**，不能只靠推上去看。

### 根因三：`bin/brakeman` 硬塞 `--ensure-latest`（時間炸彈）
- 症狀：quality job 掛在「Scan Rails security」，**exit code 5**，唯一輸出
  「Brakeman 8.0.5 is not the latest version 8.0.6」。
- 原因：Rails 產生器在 `bin/brakeman` 裡寫死 `ARGV.unshift("--ensure-latest")`。
  該旗標在「本機版本 ≠ RubyGems 最新版」時以 exit 5 失敗——看起來像掃描失敗，其實與程式碼無關。
- 處置：**拆掉該旗標**（保留 `--exit-on-warn` 與 `--exit-on-error`），並把 brakeman 升到 8.0.6。
- **為什麼是拆掉而不是只升版**：它把 CI 綠燈綁在**第三方發版時程**上——上游任何時候發版，
  我們的 CI 就無預警變紅，而紅的原因跟該次提交毫無關係。版本更新該走 dependabot PR
  （本倉庫已啟用），不該由 CI 失敗來通知。理由已寫成 `bin/brakeman` 的檔內註釋。
