### 🔴 更正：上表原本的時間軸是錯的

原文寫「失敗自 **01:55** 起、連續 **11 小時**」、以及
「`claude-review.yml` 最後一次改動 **01:00**，最後成功與第一次失敗之間一個字都沒改」。
**兩句都錯。**

| | 原本寫的 | 實際 |
|---|---|---|
| 故障邊界 | 01:55 | 🔴 **09:30 最後一次成功 → 10:14 第一次失敗**，中間 44 分鐘 |
| 中間有沒有成功 | 沒有 | 有，而且很多：02:11(9m23s)、03:53(12m42s)、07:21(14m39s)、**09:30(10m47s)** |
| 本檔最後改動 | 01:00 | 🔴 **10:12（`7234afd`）與 10:25（`4321ba0`）——就在邊界上** |

**根因**：01:55 這個數字是從 **PR #33 單一一個 PR 的留言**推出來的
（它在 01:41／01:54 有兩則成功結論，之後就沒有了）——
但那只代表**那個 PR 不再被觸發**，不代表 workflow 壞了。
🔴 **教訓：故障邊界要從 workflow 的 run 列表量，不是從某一個 PR 的留言推。**
而「最後改動 01:00」更難堤：我自己跑的 `git log` 輸出裡 **10:25 與 10:12 就在第一、二行**，
我却拿了「01:55 之前的最後一次」那一行——**因為我已經相信了 01:55 這個前提**。

⚠️ **結論仍然成立，但要換成查證過的理由**：那兩個邊界 commit 的改動
**全部落在「解析結論」步驟的診斷文字裡**，`with:`／`claude_args`／`prompt`／`uses:`
**一行未動**（逐行 grep 確認）。

⇒ 🔴 **repo 這一側已經沒有變數可以解釋它。**
⇒ 🔴 **換模型（不論換成哪個）都不會修好它**——這一點 PR #37 的結論相同。
仍未排除的都在帳號側：用量上限、OAuth token 在 CI 這條路徑上的獨立額度、訂閱狀態。

### 2. 真正的根因：**錯誤原文被 action 白名單式砍掉了**

失敗時 log 只印：

```
Running Claude Code via SDK (full output hidden for security)...
Rerun in debug mode or enable `show_full_output: true` in your workflow file for full output.
```

而 result 物件只有 6 個欄位——**`result` 欄（錯誤訊息就在裡面）整個不見**：

```json
{"type":"result","subtype":"success","is_error":true,
 "duration_ms":626,"num_turns":1,"total_cost_usd":0,"permission_denials_count":0}
```

🔴 **這就是為什麼四個工作階段都在猜**：大家拿到的是同一組**被拿掉了原因的數字**，
於是只能對指紋，而指紋對不出「額度」與「權限」的差別——**兩者長得一模一樣**。

### 3. 🔴 實測證偽：`Rerun in debug mode` 這條建議是死的

在 PR #41 的 run `31865047628` 勾 **Enable debug logging** 重跑 attempt #2：

- raw log **11,704 行**、`##[debug]` 滿地都是 ⇒ debug mode 確實開了
- **那句「full output hidden for security」照樣印**
- result 物件**照樣只有 6 個欄位**

⚠️ 而 action 的 `base-action/README.md` 明寫
「`show_full_output` is automatically enabled when GitHub Actions debug mode is active」
——**在 `@v1` 上不成立**。⇒ 兩條建議只有 `show_full_output: true` 是真的。

### 4. 修法（兩層，先便宜的再貴的）

**① 先從存檔撈** —— 失敗分支多撈一個 `ERRTEXT`（result 物件的 `result` 欄），撈到就貼原文。
console 是白名單式輸出，但**存檔 `claude-execution-output.json` 有沒有被砍是未知的**
⇒ 撈得到就賺到（噪音為零），撈不到就明說撈不到並指向 ②。

**② 明文開 `show_full_output: "true"`** —— 保證下一次失敗一定看得到原因。

🔴 **開之前先驗證它不是「會被靜默忽略的未知 input」**（本檔上方 `--model` 那段記過這個形態）：

- `anthropics/claude-code-action@v1` 的 `action.yml` **156 行宣告**、
  **325 行 `INPUT_SHOW_FULL_OUTPUT: ${{ inputs.show_full_output }}` 明文映射**。
- 🔴 325 行那個映射**非有不可**：composite action **不會**把 `with:` 自動傳給內層步驟，
  內層讀的是 `process.env.INPUT_SHOW_FULL_OUTPUT`。少了映射，寫了等於沒寫。
- 宣告型別是**字串**（`default: "false"`）⇒ 照字串寫，不寫 YAML 布林。

⚠️ **查證過程本身踩了一個坑，值得記下**：第一次用 GitHub 的 blob 檢視搜 `show_full_output`
得到「找不到」，差點據此寫下「v1 沒有這個 input」。
🔴 **blob 檢視是虛擬捲動**，只渲染前約 150 行（我抓到的 `innerText` 只有 7,119 字元，
實際檔案 460 行 / 23,685 字元），而 `show_full_output` 在**第 156 行**——就差在渲染邊界外。
**「頁面上搜不到」是渲染結果，不是事實**（與鐵律 12 §0 對空白頁的處置同型）。
正解：`raw.githubusercontent.com` 的純文字，或 GitHub code search。

### 5. 🔴 上面那個修法自己弄壞了兩條診斷路徑（同輪發現並修正）

加 `ERRTEXT` 的那一步引入了一個 **blocking regression**：

```
line 172: ERRTEXT: unbound variable      # set -uo pipefail
```

`ERRTEXT` 只在「檔案存在」那個分支被賦值，卻在後面
`if [ -n "$ERRTEXT" ]` **無條件被讀** ⇒ 「EXECUTION_FILE 為空」與「檔案不存在」
兩條路徑直接中止，**PR 上一則留言都貼不出來**。

🔴 那正好是本 PR（Y7 四路分辨）要救的四條路徑裡的兩條，
也正是這份 workflow 花大篇幅在防的「審核整份消失」形態。
**修診斷的改動自己弄壞了診斷。**

⚙️ 根因是自測的取樣面：我只跑了「檔案存在」的兩種輸入（A／B）就收工，
而這個步驟本來就有四條路徑。
🔴 **教訓：新增一個變數時，要走過每一個讀它的地方**，不是只測你新寫的那一條。
（同型前例：2026-08-15 的 `OTHERS` 水位漏改——引入新的過濾維度時漏了一個讀同一份資料的地方。）

順帶修掉同一段的第二個問題：`ERRBLOCK` 的 else 把**兩種完全不同的原因**
收斂成同一句「result 欄被白名單砂掉了」——但連 result 物件都沒有的時候，
那句歸因是**假的**。⚙️ 這正是 Y7 剛修掉的形態，差點在同一個 PR 裡復發。
⇒ 改成三分支（有原文／有 result 物件但無該欄／連 result 物件都沒有）。

並收緊了模型診斷的兩處註釋（PR #37 的 Codex review 成立）：
原文「…不是權限」講得太滿（曾經成功只能證明**當時**有權限），
改成「已證偽的只有『從一開始就沒有權限』這一條」；
並刪掉「換 Opus 5 可能繞過」——它與判準表貼進 PR 留言的「不要靠換模型來試」直接打架。

**修後實測（六條路徑逐一跑，不是只跑新增那條）**：

| 路徑 | RC | 錯誤原文那一行 |

### 6. 🔴 對抗複核又挖出四條（全部是我這段 ERRTEXT 引入的）

| 問題 | 實測現象 | 修法 |
|---|---|---|
| ① `"result": null` 被當成文字 | 貼出一個內容就是 `null` 的程式碼區塊 | 三態→五態：`ERRSTATE` 區分 noobj/nofield/null/empty/text |
| ② `"result": ""` 被誤報成「欄位被砂掉」 | 同上 | 同上 |
| ③ 🔴 **結論標記未中和** | 錯誤原文含【驗收結論】時原樣貼出 | 照姊妹路徑 :552-556 的慢例 `sed 's/【驗收結論】/〔驗收結論〕/g'` |
| ④ ``` 提前關閉柵欄 | 原文含程式碼區塊時留言後半段破版 | 半形反引號柵欄改全形 |
| ⑤ `head -c` 位元組截斷 | 中文錯誤訊息從三位元組字中間切開 ⇒ 非法 UTF-8 | `iconv -c` 丟掉殘缺序列 |

🔴 **③ 最重要**：這份檔案已經為姊妹路徑立了「回收外部文字必須中和標記」這條不變量
（理由就寫在 :552-555：留言由 github-actions[bot] 貼出而它在 REVIEWERS 清單內）。
新路徑不照做，就是把自己宣告的不變量戴個洞。

⚠️ **修⑤ 的時候又踩一個，靠斷言才抓到**：
寫成 `... | iconv -c || printf '%s' "$SAFE_ERR"` 是錯的——
`iconv -c` 丟掉殘缺序列之後**仍然回傳 1**，於是 `||` 觸發，
把原始（非法）內容**再接在清乾淨的內容後面** ⇒ 清完又貼回去，等於沒清，
而且內容還變成兩份。改成先收下輸出再判斷。
🔴 這正是本專案的「破壞那一步本身也要有斷言」——若只看「有沒有報錯」就收工，這個 bug 不會被發現。

**修後實測（九條路徑）**：text／null／empty／nofield／marker／fence／cjk＋env 空／檔不存在
—— RC 全 0；**每一條輸出都是合法 UTF-8**；半形【驗收結論】出現次數恆為 **0**；
有程式碼區塊時半形 ``` 恆為 **2**（開、關各一）。

## 尚未完成或需注意的風險 (Pending / TODO)

1. 🔴 **本 PR 自己驗證不了**（反竄改：動 `.github/workflows/**` 的 PR，驗收步驟整個跳過）。
