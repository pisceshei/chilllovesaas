# 2026-08-25 D48：alt 權威遷回檔案層（跟本尊）

使用者裁定原文：「所有的都跟Shopify」。落點＝`docs/DECISIONS.md` D48。
本份只做 alt 遷移；D48 通則裡的其餘三項（檔案庫排序／選檔器內上傳／列表載入更多）
另包處理。

## 已完成的工作 (Done)

### 裁定與證據

- **推翻的是什麼**：第 26／27 包裁定「alt 權威在 `media.alt_text`，同一張圖掛不同商品
  可有不同 alt」。那個論據本身沒錯（洋裝與外套各寫各的說明確實比較貼近用途），
  但**它不是我們的取捨**——本專案目標是與本尊 1:1（鐵律 12），
  「我們覺得比較好用」不構成偏離理由。
- **本尊的形態**（官方兩項佐證，取證 2026-08-25）：①`MediaImage` 同時 implements
  `File` 與 `Media` 但**只曝露一個 `alt`**②help 逐字 "saves the alt text to **the file**."
  ⚠️ 「在 Files 改 alt 會傳播到全部商品」**沒有官方逐字**，是由①的型別結構推導；
  文中一律標明是推論，複驗法＝測試店同檔掛兩商品後從 Files 改 alt 再讀兩邊。

### 讀取面（漏這半邊的症狀＝「改了沒變」）

- `Types::ImageType::Presenter` 從 `Data.define(:file, :alt)` **收成 `Data.define(:file)`**，
  alt 改為 `def alt = file.alt_text`。
  🔴 這是刻意讓錯誤寫法**在型別上不可表達**：遷移期最容易的錯就是有人照舊
  `Presenter.new(file:, alt: row.alt_text)`，少一個成員它直接 ArgumentError，
  而不是靜默讀到舊值。
- `Types::MediaType#alt` 從 `method: :alt_text` 改成 `def alt = object.stored_file&.alt_text`。
  沒有檔案的 M0 遺留列回 `nil`，**不回落 `media.alt_text`**——回落等於讓舊語義從後門活著。
- `Types::ProductType#featuredImage`／`ProductVariantType#image` 的 Presenter 建構同步收斂。
- `mediaMissingAltCount` 改數「媒體列的**檔案**有沒有 alt」。語義仍是「這個商品有幾張圖
  缺說明」（同張圖在同商品掛兩次算兩次——那確實是兩個要修的格子）。

### 寫入面

- `MediaSync.update`（`productUpdateMedia`）改寫 `row.stored_file.alt_text`。
- `MediaSync.build_media!` 不再寫 `media.alt_text`；改成
  `file.update!(alt_text: alt) if alt.present?`——**沒給 alt 就不動檔案既有的說明**
  （掛既有檔案的常見情形，寫 nil 會把檔案庫裡寫好的清掉）。
- 🔴 **`key?` 而不是取值**（審查抓到的真缺陷）：`UpdateMediaInput.alt` 是 optional，
  原本 `alt: entry.alt` 讓「沒送 alt」變成 nil ⇒ 清除。D48 之前那只清掉一列，
  之後是**清掉所有引用此檔的商品看到的 alt**——爆炸半徑從一列變全站。
- 🔴 **刻意不套 `fileUpdate` 的 ready 前置**：官方那條掛在 `fileUpdate` 上，而
  `fileUpdate` 還能換 `originalSource`（換內容與管線真的衝突）。本路徑只寫 alt，
  管線從不碰 `alt_text` ⇒ 無衝突。套上去只會多一個本尊沒明文要求的失敗態
  （使用者剛拖進圖、趁處理中打 alt 被拒）。本尊 `productUpdateMedia` 是否要求
  ready＝**未取得**。

### 鐵律 6：alt 上限收斂成一個鍵

原本 `MediaSync`／`FileCreate`／`FileWrite` 各自硬編 `ALT_MAX = 512`——三處同時守
**同一個欄位**卻各寫一份。新增 `limits.media.alt_max_length`（官方逐字出處在鍵註釋），
三處改讀它。

### 資料遷移

`20260825120000_move_alt_authority_to_files`：把 `media.alt_text` 搬到
`files.alt_text` 的**空位**。
- 衝突（同檔多個 media 各有不同 alt）取**最早那筆**——可預測且可解釋；
  落選值**不刪**（`media.alt_text` 欄保留），搬錯了還救得回來。
- 已有值的 `files.alt_text` 不覆蓋（那是使用者在檔案庫直接寫的，更接近本意）。
- 🔴 **不用 `GROUP_CONCAT` 取第一筆**：它受 `group_concat_max_len` 限制（預設 1024
  **bytes**），而 alt 上限是 512 **字元**——中文一字 3 bytes、512 字＝1536 bytes，
  **第一筆本身就會被截斷**，寫進去是靜默的資料損壞。改用相關子查詢，無長度上限。
- `down` 刻意 raise `IrreversibleMigration`：只填空位沒覆蓋任何值，回退方式是改讀取端，
  清空 `files.alt_text` 反而會刪掉檔案庫裡寫好的 alt。

### 測試

- **反轉**兩條舊裁定的化身：`product_media_spec` 的「alt 是媒體層的（不寫回 files）」、
  `files_library_spec` 的「不回寫既有 media 的 alt」。後者改成**兩個商品共用一張圖**
  的正向傳播斷言（那才是分野所在）。
- **修正失效 fixture**：`media_pipeline_flow_spec` 的 N+1 例原本三列共用同一個 file、
  靠「第 0 列缺 alt」造三態——遷移後共用檔就等於共用 alt，那個三態塌成一種。
  改成每個商品各一個檔，並**補上值斷言**（原本只驗查詢數，缺 alt 數算錯照樣綠）。
- **新增守衛**：單筆路徑的缺 alt 數不得 N+1。

  超長被擋時檔案層不得被污染。
