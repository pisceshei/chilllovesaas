### 上網研究（鐵律 16.1；官方來源，取證 2026-08-25）

動手前先查本尊的 Files 語義，抓到**三件與原本設計不同**的事，全部已反映進實作：

1. 🔴 **刪引用中的檔案不是錯誤，而且刪完要補位**。官方 `fileDelete` 逐字：
   "When you delete files that are referenced by products, the mutation automatically
   removes those references and reorders any remaining media to maintain proper
   positioning."（<https://shopify.dev/docs/api/admin-graphql/latest/mutations/fileDelete>）
   ⇒ 原本打算做的「in-use 就擋下來回 userError」是**錯的方向**；官方 `FilesErrorCode`
   整份值域裡也沒有「檔案使用中」這個碼。補位那半句更是原本完全沒想到的副作用。
2. 🔴 **錯誤碼要照抄官方 `FilesErrorCode`**。我方本來要自創 `FILE_IS_PROCESSING`，
   官方對應的是 `FILE_LOCKED`（"File has a pending operation."）。同時補齊
   `NON_READY_STATE`（"The file is not in the READY state."）、
   `INVALID_FAILED_MEDIA_STATE`（"File cannot be updated in a failed state."）、
   `FILENAME_ALREADY_EXISTS`（"The provided filename already exists."）。
   另有一個命名陷阱值得記著：官方有**兩個**名字相近的 enum——`FilesErrorCode`
   （mutation 的同步輸入錯誤）與 `FileErrorCode`（`File.fileErrors` 的非同步處理失敗），
   角色完全不同。我方的 `FilesUserErrorCode` 對應前者。
3. 🔴 **`fileUpdate` 要求 ready**：官方逐字 "Files must be in `ready` state before they
   can be updated."，且失敗態是終態（只能刪不能改）。原本沒有這道前置。

另外查到 `FileUpdateInput` 官方支援 `filename`（"The name of the file including its
extension."）⇒ 本包一併做了改檔名。

**未取得（誠實登記，不得補寫成結論）**：staged 上傳的保留期／清掃 —— 官方文檔
對「簽了沒完成 `fileCreate` 的 staged target 會怎樣」**完全沒有任何敘述**。
⇒ 我方的清掃窗是 **ours 裁定**，不是對齊。

### 交付

- **`files` query**（keyset 分頁，與商品同一套）＋`FileConnection`/`FileEdge` type；
  篩選＝檔名子字串／`status`／`usedIn`（`PRODUCT`｜`NONE`）。
  🔴 **不套 `Products::SearchScope`**：檔案庫沒有 `status:`／`vendor:` 這類欄位語法，
  硬套會讓 `status:ready` 被當成檔名文字——比不支援更糟（使用者以為篩了）。
  🔴 LIKE 的 `%`／`_` 一律 `sanitize_sql_like` 跳脫（檔名本來就可能含 `%`）。
- **`File` 進 Relay Node**：`RESOLVABLE_TYPES` ＋ `resolve_type` ＋
  `FileType implements Node` **三處同批**改（第 25 包審查 C6 排除它的理由，就是那時
  只改一處會讓 `node(File-gid)` 從回 null 退化成 500）。
- **`Types::FileType` 擴充**：`width`／`height`／`thumbUrl`／`previewUrl`／
  `usageCount`／`processingError`。
  🔴 `usageCount` 走 `StoredFile::USAGE_COUNT_SELECT` 相關子查詢，**不是逐列 COUNT**
  ——50 列就是 50 條查詢（第 26 包 `featuredImage` 的 N+1 前例）。單筆路徑沒有
  preload 時回落 model 的 `usage_count`，兩者算式逐字同義（不是第二套計數）。
- **`Storage::FileWrite`**（`fileUpdate`／`fileDelete` 的唯一實作）：
  - update：alt／filename；ready 前置；同店撞名擋下（排除自己）。
  - delete：解除引用 → **補位 1..n** → 刪 row → **commit 之後**才刪 blob 與衍生。
    🔴 blob 刪在交易外且在 commit 後：反過來在 rollback 時會留下**指向不存在檔案的
    row**，那比孤兒 blob 嚴重得多（列表整頁破圖 vs 只是佔空間）。
  - 🔴 處理中的檔不得刪（`FILE_LOCKED`）：管線可能正在寫衍生檔，刪 row 會讓它
    寫完 `update!` 撞 RecordNotFound（漏成 500），且新寫的衍生成為永久孤兒。
- **`Catalog::MediaSync.compact_for!`**：補位的公開入口。開這道口而不是讓呼叫端
  自己補，是因為補位必須走兩階段落位（unique 索引，逐列 update 撞 1062），
  那個知識屬於 MediaSync；`FileWrite` 只該說「這個商品少了幾列，請補位」。
- **🔴 `Storage::StagedPurge` ＋ `StagedPurgeJob`（25→26→27 三度順延，在此收口）**：
  判準＝目錄 mtime 早於 `now −(ttl ＋ grace)`。新增 limits 鍵
  `media.staged_purge_grace_seconds: 3600`（ours）。
  🔴 **不查資料庫比對 `files.storage_key`**：staged key 與永久 key 是兩個命名空間，
  fileCreate 從不把 staged key 寫進 `files` ⇒ 「有沒有被取用」在 DB 裡查不到，
  查了只會得到恆空的比對——那正是 fail-open 的典型形態（鐵律 20.2 第 5 類）。
  ⇒ 判準只用時間。排程複驗：
  `grep -n -A 3 "storage_staged_purge" config/recurring.yml`（避開 outbox purge 的時段）。
- **`/admin/content/files` 檔案庫頁**：縮圖／檔名／alt 就地編輯／狀態／**引用數**／
  大小；上傳（批次上限 20，鏡射 `content.files_upload_batch_max`）、批次選取、
  批次刪除、三種篩選、四種頁面狀態（錯誤／骨架／空態／資料）。
  導覽項與 i18n 早就存在（`nav.content.files`），本包只是把 `PlaceholderPage`
  換成真的頁——`App.tsx` 的 `IMPLEMENTED` 加一行。
  🔴 引用數 0 顯示「未使用」而不是 `0`：那是「可安全刪除」的訊號，與「用在 N 個
  商品」是兩件事，印 0 讀起來像數量而不像狀態。
- **`FilePickerModal`（選取現有檔案）**：接第 27 包早就備好的 `fileId` 分支，
  本元件是它的第一個使用者。多選、有上限（達上限後未選的 tile **停用**而不是
  點了沒反應）、搜尋走伺服端、**只列 READY**（處理中的沒有縮圖，掛上去是永久占位）。
  媒體卡那顆 disabled 的按鈕自此可用；`product.media.selectExisting.pending`
  這個 tooltip 鍵隨之退場。
- **`app/frontend/admin/lib/stagedUpload.ts`**：把直傳前兩步抽出共用。
  🔴 抽出的理由不是省行數，是**簽名協定只能有一份**——兩個呼叫端各抄一份的話，
  改協定時一定漏掉一邊，而漏掉的那邊在上傳當下才炸。
- i18n 五語各 +48 鍵；CSS 走 token（本包 20 個 token 全部在 `tokens.css` 有定義，
  複驗指令見下）。
