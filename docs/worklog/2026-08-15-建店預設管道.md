# 工作記錄：建店自動建 online_store publication（M1 PR-1 第 3 步，2026-08-15）

> 規格出處：`docs/specs/88` §4、§5 #1｜`docs/research/82` §0.1–0.2

## 已完成的工作 (Done)

### 主線：88 §5 #1 結案

`Publication.online_store` 對**新建的店**一直回 `nil`——`20260814200000` 只回填了
**它執行當下既有**的店，之後每一次 `db:seed`（新 subdomain）、每一次 spec 建店、
每一次開發者手動建店，都產生一間沒有管道的店。

🔴 **而這不會拋任何錯**。缺了它的後果是：商品的上架區塊沒有任何管道可勾
（88 §1 三層 AND 的第二層永遠不成立）、`resource_publications` 建不起來
（`publication_id` 是 `null: false`）——**新店看起來一切正常，只是所有商品都上不了架**。

🔴 **這個缺陷有兩半，缺一半就等於沒修**：
- **未來** → `Shop#after_create :create_default_publication`
- **歷史** → `20260815000010_backfill_missing_online_store_publication`

掛在 model callback 而不是 service：本倉庫目前沒有 service 層也沒有 shops controller，
而 callback 的好處是**每一條建店路徑都涵蓋**（seeds／factory／rake／未來的 M8 平台後台），
不會有人新開一條路徑而忘了建管道。端到端驗過：
`SEED_SHOP_SUBDOMAIN=pr1check bin/rails db:seed` 之後 `Publication.online_store` 有值、
`auto_publish=true`。

### 🔴 順手發現並修掉一條**與本步無關的活缺陷**：`Shop#destroy` 從來就不能用

寫「空店可以刪除」那條驗收 spec 時炸了：

```
Mysql2::Error: Unknown column 'staff_members.shop_id' in 'where clause'
```

查證：`20260814000000`（身分表升組織層，裁定 D8／§A G24）從
`staff_members`／`sessions`／`roles` 三張表拆掉了 `shop_id`，
**卻沒有同步改 `Shop` 的 `has_many` 宣告**。三條關聯全部會生出
`WHERE <table>.shop_id = ?`，實跑一律 `Unknown column`，`Shop#destroy` 完全不能用。

🔴 **沒有任何測試發現**——全庫 grep `shop.staff_members` / `shop.sessions` / `shop.roles`
**零命中**，也沒有任何一條測試呼叫過 `shop.destroy`。它們是安靜的死宣告，
直到本輪第一個人去用它。

**教訓：拆欄位的 migration 要連 model 宣告一起改。欄位沒了，宣告不會自己失效。**

修法：
- `has_many :user_store_assignments, dependent: :restrict_with_error`
  ＋ `has_many :staff_members, through: :user_store_assignments`
  （保留原本「還有人在的店不得刪除」的意圖，只是改由指派關係表承載）
- **移除** `has_many :sessions` 與 `has_many :roles`：session 屬於 staff_member、
  role 明文「本身不綁店」（見 `app/models/role.rb` 檔頭），兩者都不再是 Shop 的下屬集合。

### 🔴 `around_destroy :within_own_tenant, prepend: true`

`dependent: :destroy` 會走 `publications` 這個受 `acts_as_tenant` 隔離的關聯，
而 `require_tenant = true` 之下：
- **沒有** current_tenant ⇒ `NoTenantSet`，`shop.destroy` 直接炸；
- current_tenant 是**別間店** ⇒ default scope 把它過濾成 0 列，
  於是 publication 一列都沒刪，**而 `destroy` 回報成功**。
  「回報成功但什麼都沒做」比直接炸危險得多。

⇒ 不把「先設對租戶」當成呼叫端的紀律，直接做進 model。
**`prepend: true` 不可省**：`has_many ... dependent: :destroy` 是在關聯宣告當下註冊成
`before_destroy` 的，而關聯宣告在 `around_destroy` 之上 ⇒ 不 prepend 的話 dependent
的刪除會先跑、落在包裹之外（實測過，spec 仍然紅）。

### 🔴 刻意不回填 `resource_publications`

`20260814200000` 當時是把 `products.published_at` **原樣搬**進 `resource_publications`
——但那個欄位已被同一支 migration 移除。時間窗裡建出來的商品從來沒有過它，
所以「原樣搬」無值可搬，只剩兩個都要靠猜的選項：

- 填 `NOW()` ⇒ 這是在實作 `auto_publish` 的行為（88 §2.1：「新增管道時既有商品自動可用」），
  而那是 **§5 #2，明確延後到商品 CRUD**；
- 填 `NULL` ⇒ 與我們正要建的這個 publication 的 `auto_publish: true` **自相矛盾**。

兩條都是發明語義。⇒ 只補確定該有的那一列 publication，`auto_publish` 的實際行為
（既有商品自動納入 ＋ 新商品自動納入）整包留給 §5 #2 一次做對。
並用一條 spec（`expect(source).not_to include("INSERT INTO resource_publications")`）
把這個**刻意的省略**釘住，避免下一輪有人「順手補上」而發明語義。

  （products 是 `restrict_with_error`，理論上會擋，但沒有測試證明）。

  刻意不做成可逆——「刪掉所有 online_store publication」會連 `20260814200000` 建的那一批
