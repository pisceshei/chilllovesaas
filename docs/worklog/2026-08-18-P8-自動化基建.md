## 驗收後修正（PR #59 第 5 輪：🔴 本輪自報 regression——workflow 檔被我改成 invalid）

> 🔴 **事故**：第 3 輪（`e39a96f`）起，`Claude Review` workflow **每次 push 立即 Failure
> 且完全不執行**，annotation 逐字：
> `Invalid workflow file: .github/workflows/claude-review.yml#L1 (Line: 631, Col: 14):
> Exceeded max expression length 21000`。連兩輪（e39a96f／c5de2bd）皆然。
>
> **根因**：我在第 3 輪把 `HEAD_SHA='${{ github.event.pull_request.head.sha }}'` 直接寫進
> `解析結論並驅動閉環` 那個 step 的 `run:` 區塊裡。**含 `${{ }}` 的 run 區塊會被整段當成
> 一個 expression 求值**，而該區塊實測 25,779 字元（複驗：
> `ruby -ryaml -e '…s["run"].length…'`，見下方自測），一插入表達式就越過 GitHub 的
> 21,000 上限 ⇒ 整個 workflow 檔變 invalid。
>
> 🔴 **為什麼本地閘門沒擋住**：YAML 解析（`YAML.safe_load`）與 `bash -n` **都會過**——
> 檔案語法完全合法，違反的是 GitHub Actions 的**執行期表達式長度上限**，只有推上去才
> 看得到。這是「本地全綠但線上 invalid」的形態，與既有的 R4/R5 雙重洞同群
> （閘門存在但覆蓋不到該面）。
>
> **修法**：改走 `env:` 注入——step 的 env 區塊加 `EVENT_HEAD_SHA: ${{ … }}`，run 內讀
> `${EVENT_HEAD_SHA:-}`。這同時是 GitHub 官方推薦的 script-injection 防護寫法。
> **現值：claude-review.yml 的 run 區塊零表達式**（最長 25,779 字元但不再被當 expression）；
> ci.yml 兩個含表達式的 run 區塊分別只有 174／96 字元，未超限。

- 教訓（供 91 收割）：**workflow 的長 `run:` 區塊裡一律不得直接寫 `${{ }}`**，值走 `env:`。
  機制化候選＝掃 workflow：`run` 含 `${{` 且長度 > 20000 即報錯（G-xx 候選，本輪未建——
  依「修復只針對點名處」，本輪只修 regression 本身）。
- 併發現象解讀：Actions 列表上那兩輪顯示為「Triggered via push」而非以往的
  「Pull request synchronize」——**invalid workflow 的失敗是掛在 push 事件上報的**，
  不是 workflow 的 `on:` 被我改了（`on:` 仍只有 `pull_request`，未動）。
