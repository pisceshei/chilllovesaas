# worklog 2026-08-23 — 商品系列列表成員數 N+1 修正

## 已完成的工作 (Done)

- `Collection::MEMBER_COUNT_SELECT`：以相關子查詢在列表查詢中一次帶出手動系列的成員數。
- `Types::QueryType#collections` 加掛該 select；`Types::CollectionType#products_count` 優先讀 `member_count`，
  無該欄（單筆讀取路徑）時才退回逐筆 COUNT。智慧系列仍回 `nil`（不是 0）。
- 新增合約測試「collections 列表用單一子查詢帶出成員數，不逐列 COUNT」，以 `sql.active_record`
  訂閱數 SQL 斷言。**已做突變驗證**：暫時移除 select 後該例確實轉紅（訊息為三筆
  `SELECT COUNT(*) FROM collection_products`），還原後 8 例全綠——確認不是空綠。
- 複驗：`bundle exec rspec spec/requests/collection_set_spec.rb`；`bin/rubocop`。

## 修改的檔案與核心邏輯 (Changes)

- `app/models/collection.rb`：新增 `MEMBER_COUNT_SELECT` 常數（含 shop_id 條件，不靠 default scope）。
- `app/graphql/types/query_type.rb`：`collections` scope 改為 `.select(Arel.sql("collections.*"), Arel.sql(Collection::MEMBER_COUNT_SELECT))`。
- `app/graphql/types/collection_type.rb`：`products_count` 三分支（smart → nil／有 member_count → 讀它／否則 COUNT）。
- `spec/requests/collection_set_spec.rb`：新增一例。
- `docs/dev/m1-collections.md` §4 補記。

## 尚未完成或需注意的風險 (Pending / TODO)

- 這是**單一資源的點修**，不是通用機制：其他列表若也長出逐列聚合欄位，會各自重犯。
  專案目前未啟用 `GraphQL::Dataloader`——刻意不在本包引入，因為它以 fiber 執行 resolver，
  而 `ActsAsTenant` 與 `Current` 的儲存是 fiber-local，貿然開啟有租戶串店風險，
  必須單獨立包並補跨店測試才能評估。這一條是給下一個看到 N+1 的人的說明，不是待辦。
- 子查詢的 `cp.shop_id = collections.shop_id` 是刻意寫死的關聯條件：少了它，
  複合索引（shop_id 開頭）用不上，且在理論上會跨店聚合。改這段時不得省略。
