# 87 — 快照值 vs 當前值：商品維度雙軌契約（2026-08-14）

> 裁定來源：**71-R11-V7**（84 §1 A-3）｜實測與官方對照＝`docs/research/80` §1.2、`docs/research/81`｜
> 既有先例：`docs/specs/16` §159（`order_pickup_points` 是「快照，不是外鍵——門市會關」）

---

## §0 一句話結論

> **同一個商品屬性有兩個值：現在的值，和賣出當下的值。它們是兩個欄位，不是一個。**

🔴 **這是 84 號分流裡唯一「錯過就永久遺失資料」的一條**——商品的名稱、廠商、類型隨時可被編輯，
沒在下單當下存下來，事後 join 回去拿到的是**改過之後的值**，歷史報表會失真而且**補不回來**。

---

## §1 本尊的雙軌事實

### §1.1 兩組維度並存（80 §1.2「銷售營收」類）

| 當前值維度 | 售出時快照維度 |
|---|---|
| 產品名稱 | **售出時的產品名稱** |
| 產品廠商 | **售出時的產品廠商** |
| 產品類型 | **售出時的產品類型** |
| 產品子類選項名稱 | **售出時的產品子類選項名稱** |
| 產品子類選項 SKU | **售出時的產品子類選項 SKU** |

### §1.2 預設值是「當前值」，這是 2024 改版的結果
help 逐字（81 §7 引 analytics-updates）：2024 新分析平台**改為使用「當前」的
product title / variant title / SKU / vendor**，而非銷售當下的資訊；
要貼近歷史，**必須改用新欄位 `Product title at time of sale`**。

⇒ 兩個推論：
1. **快照欄不是可選的**——它是「貼近歷史」的**唯一**手段；
2. **預設行為會讓人以為報表壞了**（改個廠商名，過去三年的報表分組全變）——
   這是本尊的刻意設計，我方照抄時要在 UI 標明用的是哪一軌。

## §2 我方現況與本次補齊

`line_items` 的表註釋原本就寫著「下單當下不可回溯改寫的商品與金額快照」——**意圖正確**，
但只做了 5 個裡的 3 個：

| 快照維度 | 欄位 | M0 狀態 | 本次 |
|---|---|---|---|
| 售出時的產品名稱 | `line_items.title` | ✅ 已有 | — |
| 售出時的子類選項名稱 | `line_items.variant_title` | ✅ 已有 | — |
| 售出時的子類選項 SKU | `line_items.sku` | ✅ 已有 | — |
| 售出時的產品廠商 | `line_items.vendor` | ❌ 缺 | ✅ **本次補上** |
| 售出時的產品類型 | `line_items.product_type` | ❌ 缺 | ✅ **本次補上** |

**為什麼是 nullable、且不回填**：M0 既有列（若有）補不出正確的歷史值。
🔴 **寧可留 NULL 表示「不知道」，也不要用當前值回填假裝知道**——
回填會製造看起來正確、實際錯誤的歷史資料，而且之後沒有任何辦法分辨哪些是真的。

## §3 寫入規則（M3 建單時）

- 建立 line item 當下，從 variant 與其 product **複製**這五個值，之後**永不更新**。
- 🔴 **商品編輯不得回頭改 line item**——這是 `line_items` 表註釋「不可回溯改寫」的意思。
- 自訂商品（`custom = true`，無 variant）：`title` 由使用者輸入，其餘四欄留 NULL。
- 讀取時的選擇規則：
  - 要「這筆訂單當時賣的是什麼」→ 讀 `line_items.*`（快照）
  - 要「這個商品現在叫什麼」→ join `product_variants` / `products`（當前值）
  - **報表分組預設用哪一軌＝產品決策**，M5 建 rollup 時定案並在 UI 標明。

## §4 🔴 附帶發現：外鍵讓賣過的商品刪不掉（新登記 R11-V7b）

查證結果（`information_schema.REFERENTIAL_CONSTRAINTS`）：

```
fk_line_items_product_variant_id   DELETE_RULE = NO ACTION
```

`NO ACTION` 在 MySQL 等同 `RESTRICT` ⇒ **只要一個變體被下過單，它就永遠刪不掉**。

### §4.1 為什麼這與快照設計互相矛盾
快照欄存在的前提是「被參照的東西可能改變或消失」。若外鍵保證它不會消失，
快照就只剩「防編輯」一半的作用——而**商品刪除是 M1 的範圍**（商品 CRUD 含 delete，
且本尊的權限樹裡「產品 › 刪除」是一個獨立權限，見 81 §1.4）。

### §4.2 為什麼不能直接改成 `ON DELETE SET NULL`
外鍵是**複合**的：`(shop_id, product_variant_id)` → `(shop_id, id)`。
MySQL 的 `SET NULL` 要求**所有** FK 欄位可為 NULL，而 `shop_id` 是 `NOT NULL`。
⇒ **這個改法在複合外鍵下不成立**，不是設定一下就好。

### §4.3 三個可能方向（🔴 需在 M1 做商品刪除前裁定）
1. **不做硬刪除**：商品只能封存（`products.status` 已有 `ARCHIVED`）。
   最簡單，但與本尊的「刪除」動作分歧，且權限樹裡那顆按鈕會沒有對應行為。
2. **拆掉變體外鍵**，改為純快照＋弱參照（`product_variant_id` 不帶 FK）。
   與 16 §159 的既有先例一致（`order_pickup_points` 就是「快照，不是外鍵」）。
   代價：失去資料庫層的參照完整性保證。
3. **刪除時改寫 line_items**：先把 `product_variant_id` 設 NULL 再刪。
   保住外鍵，但**刪除變成需要跨表交易的操作**，且大訂單量下是重寫熱點。

⚠️ **本檔不裁定**——這是 M1 商品 CRUD 的範圍，需要先確認「我方要不要支援商品硬刪除」。
已登記為 **71-R11-V7b**。

## §5 未涵蓋（誠實聲明）

- **其他資源的雙軌需求未盤點**：顧客名稱、地址、折扣標題在本尊也可能有快照/當前雙軌
  （80 §1.2 的「售出時的」前綴只出現在商品五欄，但這不代表其他資源沒有類似問題）。
  M3/M4 建訂單詳情時要逐欄問一次「這個值會變嗎、變了要不要留歷史」。
- **報表預設走哪一軌未定**——M5 建 rollup 時定案（§3 末）。
- **本檔只保證欄位存在，不保證寫入正確**：實際的複製邏輯在 M3 建單流程，
  屆時要有測試證明「改商品不影響既有 line item」。
