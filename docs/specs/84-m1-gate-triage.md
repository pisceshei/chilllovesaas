# 84 — M1 閘門分流（2026-08-14）

> 起因：parity R0–R13 累積 81 條未結案，其中 16 條標「M1 相關」。但沒人確認過這 16 條
> **是不是真的都擋 M1**——標籤是各輪當下順手打的，沒有統一判準。
> 🔴 **判準（本檔唯一標準）**：**這條沒答，M1 會不會寫出「之後必須重寫的表或欄位」？**
> - 會 → **A 真的擋**（動工前必須有答案）
> - 不會，但會影響某個畫面怎麼做 → **B 邊做邊決定**（實作到那一頁時再答，答錯只改該頁）
> - 根本不是 M1 的事 → **C 移出 M1**（改掛正確的里程碑）
>
> 依據：`docs/specs/71` §F｜里程碑定義見 `HANDOFF.md` §5（M1＝商品·庫存·CRUD 與後台骨架）。

## 1. A 桶：真的擋 M1（5 條）

這五條的共同點：**都會決定表的欄位長相**。沒答就動工，等於保證要寫 migration 回頭改。

### A-1｜R11-V14 撤銷款項術語改造 🔴 最該先答
- **為什麼擋**：11 組欄名對照（`returns`→`sales_reversals`、`net_returns`→`net_sales_reversals`…），
  且**`returns` 這個字沒有消失，它現在專指「實體退貨」**。M1 的訂單/退貨相關表如果沿用舊詞，
  之後不是改欄名而已——是**兩個概念要拆開**。
- **答案形態**：一份欄名對照表落進 19/76 號，並明確 `returns` 表與 `sales_reversals` 指標的邊界。
- **成本**：低（純命名決策），**不答的代價高**（拆概念比改名貴）。

### A-2｜R11-V12 總銷售額可為負
- **為什麼擋**：金額欄位的**約束條件**（能不能存負數）是建表當下就要定的。
  若 M1 給金額欄加了 `unsigned` 或 CHECK ≥ 0，之後撤銷 > 銷售的日子會直接寫不進去。
- **答案形態**：明定「金額欄一律允許負值」，並在 UI 元件層要求支援負數顯示（tabular-nums 對齊）。
- **關聯**：已由 §A **G25** 部分覆蓋（AOV 例外那條的配套），但**建表約束這一面還沒落到 spec**。

### A-3｜R11-V7 商品維度雙軌（當前值 vs 售出時快照）
- **為什麼擋**：這是**要不要多存一組欄位**的問題。「售出時的產品名稱／SKU／廠商／類型」
  是下單當下的快照，不是 join 得回來的——**沒在 line item 上存，事後永遠補不回來**。
- **答案形態**：決定 order line item 要快照哪幾欄（本尊是 名稱/SKU/廠商/類型/子類選項名稱 五欄）。
- **成本**：低，**但這是唯一「錯過就永久遺失資料」的一條**，優先度僅次於 A-1。

### A-4｜R12-V3 時區與語言是使用者層級
- **為什麼擋**：決定 `user.timezone` / `user.locale` 這兩欄**存不存在**。
  我方目前做成商店級單一值；若 M1 建 users 表時沒放，之後要加就是 migration ＋ 回填 ＋
  所有時間顯示點都要改讀取來源。
- **注意**：這條與 §A **G24**（身分表白名單）同一批表——**兩件事一起做，成本會低很多**。
- **答案形態**：確認 users 表要不要帶 timezone/locale；若要，訂單時間的顯示語義同步定案。

### A-5｜R13-V4 發布模型三層 AND
- **為什麼擋**：`Publishable × Publication × Catalog` 是**三張表的關係**，不是一個布林欄。
  M1 建商品表時若把上架做成 `product.published: bool`，之後要拆成三層是**結構改造**。
- **答案形態**：確認 M1 是否先建 `publications` / `product_publications` 兩張表
  （即使 M1 只有一個管道，結構先對）。
- **成本**：中（多兩張表），**但這是四個掛載點的共同地基**（商品頁／目錄／市場／代理式）。

## 2. B 桶：邊做邊決定（6 條）

共同點：**影響某一頁怎麼做，但不影響表結構**；答錯只需改那一頁。

| # | 條目 | 為什麼可以延到實作那頁 |
|---|---|---|
| B-1 | **R8-V1** 庫存「箱名稱」欄與「Not Fulfillable」檢視 | 是**欄位顯示與檢視定義**，庫存表本來就要有 bin 欄位空間；做庫存頁時一起決定即可 |
| B-2 | **R8-V5** 庫存 CSV 19 欄／4 可寫欄＋防誤覆寫 | 匯入器是**獨立元件**，欄位面可後補；且 CSV 契約已有 G14 打底 |
| B-3 | **R8-V2** 批量編輯器不建立稽核歷程 | 這是**行為裁定**不是結構：ledger 表本來就要建，差別只在批量路徑寫不寫。做批量編輯器時再定 |
| B-4 | **R8-V4** 2026 系列建立式「來源卡」vs 我方手動/智慧二分 | 影響**建立流的 UI 與轉換規則**；`collections` 表兩種都撐得住。做系列頁時再定 |
| B-5 | **R12-V1** 禮品卡設定歸屬 | 純**導航歸屬**（R13 已實測證實在「付款」底下）；設定頁重組時搬即可，不動資料 |
| B-6 | **R12-STRUCT2** 品牌歸屬（一般的子頁） | 同上，純導航；R12 已補正確進入路徑，完整歸位排在設定頁重組 |

## 3. C 桶：移出 M1（5 條）

| # | 條目 | 原標 | 改掛 | 理由 |
|---|---|---|---|---|
| C-1 | **R2b-V1** 搜尋結果富形態（分類計數 chips／關鍵詞粗體／再顯示 20 個） | M1 | **M1 後段**（14-F4 落地時） | 依賴搜尋後端，M1 前段沒有可搜的資料 |
| C-2 | **R4-V4** 財務導航子項動態化 | M1 | **M4** | 財務模組本身在 M4；M1 只需要導航殼支援資料驅動 |
| C-3 | **R12-V6** 權限依賴是圖不是樹（雙向傳播＋不可取消邊） | M1 前 | **M5** | 🔴 **依賴圖是「角色編輯器」的邏輯，不是權限表的結構**。表只需 `role_permissions(role_id, permission_key)`；傳播規則是應用層的事。M1 建表不受影響 |
| C-4 | **R12-V9** 使用者群組 Groups（第四段） | M1 前 | **M5** | 同上——是**要不要多做一層**的產品決策，且 help 明載 Plus 專屬。M1 的 8 張白名單表（G24）已含 `user_groups`/`user_group_roles` 兩張**預留**，建了不用不會錯 |
| C-5 | **R13-V6** POS 權限模型與 admin 不同 | M1 前 | **不做** | 🔴 已由 §A **G26** 裁定不實作 POS。本條應直接標為「因 G26 不適用」，不再掛任何里程碑 |

## 4. 建議的動工順序

1. **先答 A-1／A-3**（撤銷術語、line item 快照欄）——兩條都是「錯過就要拆概念或永久遺失資料」。
2. **A-4 與 G24 的 8 張身分表一起做**——同一批 migration，順手把 `timezone`/`locale` 帶上。
3. **A-2 定成建表約束**（金額欄允許負值）寫進 65 號，一次管住所有金額欄。
4. **A-5 決定要不要先建 publications 兩張表**——這條可以接受「先建結構、M1 只用一個管道」。
5. B 桶六條**不用現在碰**，各自在做到那一頁時回頭讀本檔對應列。
6. C-5 直接在 71 §F 標「因 G26 不適用」，C-1~C-4 改閘門標籤。
