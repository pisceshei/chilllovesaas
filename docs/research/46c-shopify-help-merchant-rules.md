## §1 全域決策樹：取消 vs 退款 vs 退貨（**特別挖清楚項 ①**）

這三者在 Shopify 是**三條獨立的流程**，切分依據是**品項的履行狀態**與**是否要收回實體貨**。

### 1.1 三者定位對照

| 維度 | **取消訂單**（Cancel） | **退款**（Refund） | **退貨**（Return） |
|---|---|---|---|
| 中文按鈕 | `取消訂單` | `退款` | `退貨` |
| 適用品項狀態 | **未出貨**的品項（H03：「訂單一旦已部分履行，就無法取消」） | 任何已付款品項（不論是否履行） | **已履行且尚未退款**的品項（H11 逐字：「僅能為已履行且尚未退款的品項建立退貨」） |
| 是否收回實體貨 | 否（貨還沒出） | 否（純金流動作） | **是**（有逆向物流、退貨單、檢查） |
| 是否一定退錢 | 否 — 可選「稍後退款」 | 是（本質就是退錢） | 否 — 可在處理退貨時退，也可稍後單獨退（H11） |
| 是否一定回補庫存 | 預設回補，可取消勾選（H03） | 「將品項重新入庫」預設勾選，僅在有追蹤庫存時可用（H05） | 處理退貨時選擇「重新入庫地點」（H11） |
| 訂單層狀態結果 | `已取消`；付款轉 `已作廢`（未請款）或 `已退款`（全額退） | `已退款` / `部分退款` | 退貨狀態列另計（`已提出退貨申請` / `退貨進行中` / `檢查完成` / `退貨完成`） |
| 出處 | H03 zh-TW / H04 en | H05 zh-TW / H06 en | H11 zh-TW / H12 en |

### 1.2 先後順序限制（**這是最容易踩雷的一段**）

1. **同一張訂單可以同時存在「取消流」與「退貨流」**。44 號實測 `/settings/legal/cancel-return-rules/{id}` 的規則頁把兩者並列，且明寫：`退貨規則`「套用於訂單中**已履行**的品項」、`取消規則`「套用於訂單中**未出貨**的品項」。
   → **前台「申請」入口必須逐 line item 判斷要顯示「退貨」還是「取消」**。
2. **已部分履行 → 訂單層取消按鈕不可用**（H03 zh-TW 逐字）。英文版補了解法：`though you can cancel the fulfillment first`（H04 en）——先取消該筆 fulfillment，才能取消訂單。
3. **退款不可撤銷，所以退款應排在最後**。H05 zh-TW 逐字：「在 Shopify 管理介面啟動退款後，您無法取消或撤銷該退款」。
4. **退貨可以不含退款**（先收貨檢查、後退款），但**退款不會自動產生退貨**——退款只是金流，不會建立逆向物流單。
5. **開發文檔另有一條 help 完全沒寫的互鎖**：「有進行中的退貨（active returns）就不能取消訂單」（46a §7，來自 shopify.dev）。詳見 §4 衝突清單 C-01。

### 1.3 建議的商家操作順序（依 help 文檔推導）

```
貨還沒出？ ──是──> 取消訂單（選是否回補庫存、選退款方式或「稍後」）
   │否
   ▼
要收回實體貨？ ──是──> 建立退貨 → 寄/上傳退貨單 → 收貨檢查 → 選重新入庫地點 → 退款
   │否
   ▼
直接退款（全額或部分，可多次部分退款直到達原始金額）
```

## §2 動作分節

---

### A1. 取消訂單（`更多動作 › 取消訂單`）

**1. 前置條件**
- 需具備**訂單權限**；退至商店抵用金另需「退至商店抵用金」訂單權限（H03 zh-TW 逐字：「需要具備適當的訂單權限，才能取消訂單並核發退款」）。
- 訂單**未部分履行**。H03 zh-TW 逐字：「訂單一旦已部分履行，就無法取消」。
- 訂單非「待處理付款且已排定付款」狀態。
- 訂單未曾被取消或刪除。

**2. 會發生什麼（完整副作用鏈）**
| 面向 | 行為 | 出處 |
|---|---|---|
| 庫存 | **預設自動重新入庫**（勾選預設開），可手動取消勾選 | H03 zh-TW / H04 en 逐字：「The **Restock inventory** option is selected by default」 |
| 金流 | 三選一：**退回原付款方式** / **商店抵用金** / **稍後退款**（不立即動金流） | H03 zh-TW |
| 付款狀態 | 未請款 → `已作廢`；全額退款 → `已退款` | H03 zh-TW |
| 訂單狀態 | → `已取消`。H02 註記：「若未全額退款，仍可能有待處理的事項」 | H02 zh-TW |
| 通知信 | **預設寄送顧客取消通知**，可取消勾選。範本＝`訂單取消`（44 §18.7 實測範本清單有此項） | H03 zh-TW |
| 記錄 | 詳情寫入**訂單時間軸** | H03 zh-TW |
| 取消原因 | 下拉選單必選，**help 文檔未列舉選項內容**（見 §4 C-02） | H03 zh-TW / H04 en 皆未列舉 |

**3. 可逆嗎**
> 🔴 **不可逆（文檔立場）**。H03 zh-TW 與 H04 en **均未提供任何「復原取消」的方法**，且明寫「已取消或已刪除的訂單無法再次取消」。**沒有 un-cancel 按鈕**。
> 🔴 附帶不可逆：若取消時選了「退回原付款方式」，該退款**無法撤銷**（H05）。
> 🟡 可逆的只有：勾不勾「重新入庫」、勾不勾「通知顧客」——這兩個是取消當下的選擇，事後只能靠手動調庫存/手動寄信補救。

**4. 影響範圍**
- **只影響此單** + 該單品項所屬地點的庫存。
- 不影響顧客帳號、不影響全店設定。
- **會影響報表**（訂單計入已取消）。

**5. 常見錯誤情境（文檔明列的「無法執行」）**
| 情境 | 說明 | 出處 |
|---|---|---|
| 已部分履行 | 無法取消；需先取消該筆 fulfillment | H03 zh-TW / H04 en |
| 待處理付款且已排定付款 | 無法取消 | H03 zh-TW |
| Facebook / Instagram 建立的訂單 | 需在該平台取消；曾在 Commerce Manager 編輯過的更是 | H03 zh-TW / H04 en |
| 第三方出貨服務訂單 | 需先在其系統取消 | H03 zh-TW |
| 第三方 app 建立的訂單 | 可能有取消限制 | H04 en |
| 已取消／已刪除 | 無法再次取消 | H03 zh-TW |
| 權限不足 | 缺訂單權限 | H03 zh-TW |
| 批次取消超過 250 筆 | **一次最多 250 筆**，超過需分批 | H04 en |

**6. 方案差異**
- **文檔未載明**任何 Basic/Grow/Advanced/Plus 差異。取消訂單為全方案功能。

### A2. 封存訂單（`更多動作 › 封存`）

**1. 前置條件**
- 文檔未載明限制；44 §2.2 實測 `更多動作` 選單中 `封存` 與 `退款/編輯/退貨/複製/查看訂單狀態頁面` 同列。

**2. 會發生什麼**
- 定義（H03 zh-TW 逐字）：「封存訂單代表您已完成此筆訂單，並想將它從未完成訂單清單移除」。
- 訂單狀態 → `已封存`（H02 zh-TW：「此訂單已手動或自動封存」）。
- **不動庫存、不動金流、不寄通知信**（文檔未提及任何副作用）。
- **自動封存**可在 `設定 › 結帳頁面 › 訂單處理` 開啟，條件為「已付款且已出貨」或「已全額退款」（H32 zh-TW）。

**3. 可逆嗎**
- 🟢 **可逆**。封存只是清單過濾；且**開發文檔記載：建立/申請退貨會自動解除封存**（46a §4：「Archived orders — Auto-unarchives when return created/requested」）。**help 文檔未載明此自動解封行為**（見 §4 C-06）。

**4. 影響範圍**：只影響此單的清單可見性。

**5. 常見錯誤情境**：文檔未載明。

**6. 方案差異**：文檔未載明。

### A3. 刪除訂單（`更多動作 › 刪除`）

**1. 前置條件（限制最嚴的一顆按鈕）**
> H04 en 逐字：訂單必須**先被封存或取消**，才能刪除。
> 且**只有以下種類的訂單可以刪除**：
> - 測試訂單
> - 以**手動付款方式**付款的訂單
> - 標記為已付款的**訂單草稿**
> - 透過 **Shopify API 匯入**的訂單
> - 訂單草稿
>
> → 換言之：**一般線上付款的真實訂單無法刪除**，只能封存或取消。

**2. 會發生什麼**
- H03 zh-TW 逐字：「刪除訂單代表您要將它從 Shopify 管理介面移除」。
- 其餘副作用（庫存、報表、訂單編號是否回收）**文檔未載明**。

**3. 可逆嗎**
> 🔴 **不可逆，且是本文最高危動作**。文檔未提供任何還原方式，且明寫「已取消或已刪除的訂單無法再次取消」。
> 🔴 **UI 必須有二次確認 + 明示「此操作無法復原」**。

**4. 影響範圍**：此單永久移除；對報表的影響文檔未載明。

**5. 常見錯誤情境**：不符上列五種可刪類型 → 按鈕不可用／不出現（文檔以「只有這些可刪」的正面表列表達，未列舉錯誤訊息）。

**6. 方案差異**：文檔未載明。

### A4. 退款（全額／部分）（訂單頁 `退款` 按鈕）

**1. 前置條件**
- 訂單有可退金額。多次部分退款可累加，**直到達到原始訂單金額**（H05 zh-TW）。
- 需訂單權限（比照 A1）。

**2. 會發生什麼**

### A5. 發放 / 退款至「商店抵用金」

**1. 前置條件**
- 需 **商店抵用金** 與 **編輯商店抵用金** 權限（H37 zh-TW）。
- 🔴 **必須使用「新版顧客帳號」**。H37 zh-TW 逐字：「商店抵用金不適用於傳統顧客帳號」。
- 44 §18.5 實測：`設定 › 顧客帳號 › 商店抵用金` 有獨立 toggle（實測為開）。

**2. 會發生什麼**
- 商家在顧客資料頁 `商店抵用金 › 編輯` 選「入帳」、選幣別、輸入金額、設定到期日、可選是否通知顧客。
- 通知信範本＝`已發放商店抵用金`（44 §18.7 實測有此範本）。
- 顧客登入顧客帳號或使用 Shop Pay 時，結帳頁才會出現抵用金。
- 多筆不同到期日的抵用金：**最早到期的先用**（H37 zh-TW）。
- 到期時間一律以**商店時區的當日結束**為準，與顧客所在地無關（H37 zh-TW）。

**3. 可逆嗎**
- 🟡 **部分可逆**：抵用金可再退回顧客；商家亦可對原付款方式做超額退款（H37 zh-TW）。發放後的撤銷流程文檔未載明細節。

**4. 影響範圍**
- 影響**顧客帳號**（跨訂單持續存在的餘額），不只此單。這是本文少數「影響顧客帳號」等級的動作。

**5. 常見錯誤情境**
| 情境 | 說明 |
|---|---|
| 傳統顧客帳號 | 完全不支援 |
| 單一顧客累計抵用金 ≥ 15,000 美元 | 不允許（H37 zh-TW：「must be less than $15,000」） |
| 訂單草稿 / 已編輯訂單 / 第三方銷售管道 | **不支援使用抵用金** |
| 訂閱商品 | **僅首購可用**，續訂扣款不可用 |
| 結帳幣別與抵用金幣別不同 | 結帳頁只顯示與結帳幣別相符的抵用金 |
| 未登入 | 不顯示抵用金（需登入顧客帳號或 Shop Pay） |

**6. 方案差異**
- 交易手續費：Plus + Shopify Payments **免收**，其他方案自 2025-05-12 起收取（H37 zh-TW）。
- 支援管道限：**網路商店、POS、Shop app**。

### A6. 建立退貨（訂單頁 `退貨` 按鈕）

### A8. 換貨（Exchange，退貨流程內的子動作）

**1. 前置條件**：在建立/處理退貨時加入換貨品項；不可為自訂品項；含關稅的訂單不可換貨（H11 zh-TW）。

**2. 會發生什麼（差價處理是重點）**
> H12 en 逐字：「Return fees and exchange items are applied against returned items to determine whether a refund is due or payment needs to be collected.」
>
> 三種結果：
> 1. **新品較便宜** → 商家退差額給顧客
> 2. **新品較貴（或含退貨費）** → **向顧客收取差額**
> 3. **等值換貨** → 「The money paid for the returning items is applied to the new items」

- 🔴 **訂單層級折扣不能套用到換貨品項**；但**可以對換貨品項加商品折扣**（H12 en 逐字：「Order level discounts can't be applied to exchange items, but you can add a product discount to exchange items.」）。
- 🔴 **換貨品項的庫存在「處理退貨」之前完全不保留**（H11/H12）。
- 換貨品項需**自行履行**（H12 en）。

**3. 可逆嗎**：文檔未載明。

**4. 影響範圍**：此單；換貨品項會產生新的待履行項目。

**5. 常見錯誤情境**：自訂品項不可換貨；含關稅訂單不可換貨；換貨品項在處理前售罄（文檔未載明售罄後的處理方式）。

**6. 方案差異**：文檔未載明。

### A10. 設定「退貨與取消規則」（**特別挖清楚項 ④**）

**1. 前置條件**
- 位置：44 §18.6 實測在 `設定 › 政策 /settings/legal` 的**第一張卡**（不是法務條款卡），內含 `預設規則` + `⊕ 新增規則` → **可有多條規則**。
- 規則頁 `/settings/legal/cancel-return-rules/{id}` 內含兩個獨立 toggle：
  - `退貨規則`「套用於訂單中**已履行**的品項」
  - `取消規則`「套用於訂單中**未出貨**的品項」

**2. 會發生什麼（可設定的內容）**
| 設定項 | 選項 | 出處 |
|---|---|---|
| 退貨期間 | **14 天 / 30 天 / 90 天 / 不限 / 自訂天數** | H13 zh-TW、H14 en |
| 起算點 | 個別品項配送日，或**訂單最後一項品項配送日** | H13 zh-TW |
| 退貨運費 | ① 提供免費退貨運送 ② 每次退貨收固定運費（一次性）③ 顧客自行購買退貨單 | H13/H14 |
| 重新上架費 | 選填，**以退貨金額的百分比**計算 | H13/H14 |
| 最終銷售品項 | 以 **`商品系列`** 或 **`商品`** 為粒度指定（44 實測為 radio 二選一） | 44 §18.6、H13/H14 |

**3. 規則綁購買時點（本節核心）**
> 🔴 **H14 en 逐字**：「**Changes to your return rules apply only to future orders. Changes don't apply to previous orders, so that they don't impact customers who've already placed an order.**」
> 🔴 **H13 zh-TW 逐字**：「對退貨規則所做的變更僅適用於未來的訂單。這些變更不會套用於先前的訂單」。
> 🔴 **44 號實測後台頁尾灰底提示逐字**：「退貨與取消規則適用於在啟用或更新規則後所購買的品項」。
>
> **三方一致。實作含意**：規則**必須在下單當下 snapshot 到 line item**，不能只存 `rule_id` 外鍵（規則會被改，改了不能回頭影響舊單）。44 §18.6 已下此結論（`order_line_items.return_policy_snapshot_id`），本次 help 文檔**正面證實**。

**4. 最終銷售品項實際怎麼運作**
> H14 en 逐字：「products or collections aren't eligible for returns or cancellations as final sale items. **Your customers can't submit return or cancellation requests for final sale items.**」
> → **是「不能提交申請」，不是「提交後被拒」**。前台入口層就要擋掉。
> → 44 §18.6 的推論（「命中即完全不出現退貨/取消入口，不是提交後才拒絕」）**被文檔證實**。
- **套裝組合（bundles）不能設為最終銷售品項**（H13 zh-TW / H14 en 逐字）。
- 規則關閉時，最終銷售品項整卡 disabled/灰化（44 實測）。

**5. 覆寫（override）**
- 建立退貨時會顯示退貨運費，**可針對單筆退貨編輯**；重新上架費**可按個別品項編輯**（H13 zh-TW / H14 en）。
- → **規則是預設值，不是硬約束**；商家在 admin 端永遠可以覆寫。

**6. 可逆嗎 / 影響範圍 / 常見錯誤 / 方案差異**
- **可逆嗎**：🟢 規則本身隨時可改，但**改動不追溯既往**（見上）。
- **影響範圍**：**全店**（或該規則命中的範圍），影響所有未來訂單的顧客可見行為。
- **常見錯誤情境**：bundles 不可設最終銷售；規則對「從 admin 手動處理的退貨」也會自動套用（H13 zh-TW）。
- **方案差異**：🔴 **「若要在 Shopify POS 使用退貨規則，您必須擁有 Shopify POS Pro」**（H13 zh-TW / H14 en 逐字）。線上商店端未載明方案限制。

### A12. 請款（Capture）／作廢（Void）／授權逾期

**1. 前置條件**

**2. 會發生什麼 — 四種請款模式（H33 zh-TW）**

**3. 授權效期表（H33 zh-TW，Shopify Payments）**
| 卡別 | 一般 | Plus 延長 |
|---|---|---|
| 全部（Shopify Payments 預設） | **7 天** | — |
| Visa / Mastercard / American Express | — | **最長 30 天** |
| Discover / JCB | — | **最長 10 天** |
| Diners Club / China Union Pay | — | **7 天** |

- 未請款時，顧客銀行帳單上的 pending hold 最長顯示 **30 天**。
- 🔴 **超過授權期限後才請款，需付 1.75% 附加費**（超出標準手續費之外）（H33 zh-TW）。

**4. 可逆嗎**

**5. 常見錯誤情境**
- 授權過期未請款 → H02 狀態 `已到期`「授權期限已過但未請款」。
- H02 另有 `即將到期` badge（**兩天內到期**，非獨立狀態）與 `到期`（超過付款期限未收到款項）。

**6. 方案差異**：見上表；`每次履行時自動請款` 與延長授權期皆為 **Plus 專屬**。

## §3 專章：庫存欄位定義與加減時機（**特別挖清楚項 ③**）

### 3.1 官方定義（H18 zh-TW / H19 en，逐字）

| 狀態 | zh-TW 官方用詞 | 定義（H18 逐字） | 何時增加 | 何時減少 |
|---|---|---|---|---|
| On hand | **現有庫存** | 「您在某個地點擁有的所有庫存單位。現有庫存由已分配、不可販售與可販售庫存的總和組成。」 | 收貨、盤點上修 | 出貨、盤點下修 |
| Available | **可販售** | 「可供銷售的庫存。可販售庫存**不會分配至任何訂單**，也**不會保留給任何訂單草稿**；此外，也**不包含被視為待入庫的庫存**。」 | 待入庫收貨、退貨重新入庫、取消訂單回補、編輯現有數量 | 訂單成立（轉入已分配）、訂單草稿保留（轉入不可販售）、標記損壞等 |
| Committed | **已分配** | 「已納入訂單但尚未履行的單位數。**若單位屬於訂單草稿，顧客無法購買，且在該草稿轉為訂單之前，不會計入已分配庫存**。」 | **訂單成立時** | **訂單履行時**（或取消訂單時） |
| Unavailable | **不可販售** | 「因訂單草稿保留、由 app 保留，或其他擱置原因而被保留的單位數。不可販售庫存雖然存放在您的地點，但無法銷售。」 | 訂單草稿保留庫存、app 保留、標記損壞/品管/安全庫存 | 保留到期、解除擱置、調整回可販售 |
| Incoming | **待入庫** | 「從庫存轉移或 app 正在運送至您地點的庫存。在收到待入庫庫存且狀態變更為可供販售前，這類庫存無法供銷售。」 | 建立庫存轉移/採購單 | 收貨（自動轉為可販售） |

### 3.2 公式

```
現有庫存 (On hand) = 已分配 (Committed) + 不可販售 (Unavailable) + 可販售 (Available)

不可販售 (Unavailable) = 訂單草稿保留 + app 保留 + 損壞 + 品質控管 + 安全庫存 + 其他

待入庫 (Incoming) 不計入現有庫存
```

**連動規則**（H18/H19）：
- 編輯 **現有庫存** 數量 → **可販售**等量變動
- 編輯 **可販售** 數量 → **現有庫存**等量變動

### 3.3 對「五欄」假設的修正

**任務描述中的「可用/已承諾/待收/損壞/安全庫存」五欄，與官方模型不符**：

| 任務描述的欄 | 官方模型中的實際地位 |
|---|---|
| 可用 | ✅ 頂層狀態 `可販售 / Available` |
| 已承諾 | ✅ 頂層狀態 `已分配 / Committed`（後台實測譯為「已承諾」） |
| 待收 | ✅ 獨立狀態 `待入庫 / Incoming`，**但不計入現有庫存** |
| 損壞 | 🔴 **不是頂層欄**，是 `不可販售` 的**子分類** |
| 安全庫存 | 🔴 **不是頂層欄**，是 `不可販售` 的**子分類** |

**正確的頂層五態應為**：`現有庫存` / `可販售` / `已分配` / `不可販售` / `待入庫`
**`不可販售` 的四個子分類為**：`損壞` / `品質控管` / `安全庫存` / `其他`（H20 zh-TW）
**另有「保留（Reserved）」**：H19 en 把 Reserved 列為 Unavailable 的子態（訂單草稿保留），H18 zh-TW 未單獨列出。

### C-01 🔴 取消訂單的阻擋條件，三方各不相同

| 來源 | 說法 |
|---|---|
| **help zh-TW（H03）** | ①「訂單一旦已**部分履行**，就無法取消」②待處理付款且已排定付款 ③FB/IG 訂單 ④第三方出貨服務 ⑤已取消/已刪除 ⑥權限不足 |
| **shopify.dev（46a §7）** | ①已取消 ②有**待處理的付款授權** ③**有進行中的退貨（active returns）** ④有無法履行的未結出貨 |
| **44 實測** | 未直接測取消；但 §2.2 觀察到一張 `已付款 + 部分已出貨` 的訂單，其 `更多動作` 選單為 `退款｜編輯｜退貨｜複製｜封存｜查看訂單狀態頁面` — **沒有「取消」**，與 help「部分履行不可取消」一致 |

**分歧點**：
1. **「有進行中的退貨就不能取消」只有開發文檔寫**，help 完全沒提 → **UI 需要這條互鎖，但商家不會知道為什麼**。
2. **「部分履行不可取消」只有 help 寫**（開發文檔的措辭是「unfulfillable outstanding fulfillments」，語意不同）。
3. help en（H04）補了 help zh-TW 沒有的解法：**先取消 fulfillment 再取消訂單**。

**建議採用**：兩份的聯集，並在 UI 上把原因說清楚（「此訂單有進行中的退貨，需先關閉退貨」）。

### C-03 🔴 `restock` 與 `notifyCustomer` 的預設值，UI 與 API 相反

| 欄位 | help（UI 行為） | shopify.dev（API 行為） |
|---|---|---|
| 取消時重新入庫 | **預設勾選（true）**（H03/H04 逐字：「selected by default」） | `orderCancel.restock` 是 **`Boolean!` 必填，無預設**（46a §7：「reason 與 restock 都是必填」） |
| 取消時通知顧客 | **預設寄送（true）**（H03） | `orderCancel.notifyCustomer` **預設 `false`**（46a §7） |
| 編輯訂單減量時重新入庫 | help 未載明 | `orderEditSetQuantity.restock` **預設 `false`**（46a §8） |

**分歧點**：**API 的安全預設（不動庫存、不寄信）與 UI 的便利預設（動庫存、寄信）相反。**
**實作含意**：我們的 admin UI 必須在 UI 層顯式帶入 `restock=true, notify=true`，**不能依賴 API 預設**，否則行為與商家在 Shopify 的肌肉記憶不符。

### C-07 🔴 退貨狀態機的不可逆轉移，help 完全沒寫

| 來源 | 說法 |
|---|---|
| help（H02） | 只列 4 個退貨狀態：`已提出退貨申請` / `退貨進行中` / `檢查完成` / `退貨完成`。**未提任何不可逆性** |

**建議採用**：dev 的 5 值狀態機 + help 的 `檢查完成`（作為 `OPEN` 底下的子進度）；**UI 必須對「核准/拒絕」加不可逆警告**。

## §6 對 CHILL LOVE 的落地結論（10 條，可直接進 backlog）

1. **`order.cancellable?` 判斷式 = help 六條 + dev 四條的聯集**，且錯誤訊息要說人話（見 C-01）。
2. **UI 層顯式帶 `restock=true, notify=true`**，不依賴 API 預設（見 C-03）。
3. **`return_policy_snapshot` 必須存在 line item 上**，規則改動不追溯（§A10，三方一致）。
4. **最終銷售品項在前台入口層就要擋**，不是提交後拒絕（§A10，三方一致）。
5. **前台「申請」按鈕逐 line item 判斷顯示「退貨」或「取消」**（§1.2）。
6. **退款、刪除訂單、核准/拒絕退貨、升級顧客帳號（>30天）** 這四個動作要有**不可逆二次確認**。
7. **庫存資料模型 = 4 彙總欄 + incoming + unavailable 子分類**，不是平行五欄（§3.3、C-11）。
8. **i18n 詞彙表以 44 實測後台譯名為準**（`無法供貨/已承諾/可供貨/現有庫存`、`最終銷售品項`），不用 help 頁譯名（C-04、C-05）。
9. **合併運費以「費率名稱」為合併鍵**，UI 要對跨設定檔的名稱不一致提出警示（§E4）。
10. **顧客帳號設定拆出獨立頁**，結帳頁只留「要求先登入」布林開關（C-13）。
