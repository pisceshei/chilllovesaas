## 1. 目標與可見成果

本包無畫面。可見成果＝bt3 上一次 `rails runner` 觀測三件事：

1. 寫入一筆業務變更後，`event_outbox` 的 pending 列在 N 秒內轉 `published`
   （N ≤ 2 × `limits.events.outbox_poll_interval_s`）。
2. 人為把一列標成 `locked_at` 過期，下一輪 relay 把它回收重派。
3. 對同一 `(item, location)` 連續多次呼叫 `Inventory::Adjust`，合併窗把 M 筆
   併成 1 筆（`coalesced_count` = M），而 `availability_flipped: true` 的那筆**沒有**被併掉。

## 4. 要新建的東西（一個實作 PR；本規格 PR 只做 §4.0 的文檔更正）

### 4.0 本規格 PR 隨附的文檔更正（總交接 §4.1 明文要求）

- 18 §F1-1 的 `events_outbox` → `event_outbox`（就地更正註，表名以實物為準；
  **別反過來改表名**——CI test job 有 schema drift 檢查）。
- 63 §C 全章同型字樣同批更正。

### 4.1 第一個 commit＝limits 先行（鐵律 6）

```yaml
events:
  outbox_poll_interval_s: 5        # 18 §F1-2「每 5s」
  outbox_batch_size: 100           # 18 §F1-2「LIMIT 100」
  outbox_dead_letter_attempts: 8   # 18 §F1-5「attempts ≥8 → dead」
  outbox_retention_days: 30        # 18 §F1-5「保留 30 天 purge」
  outbox_lock_timeout_s: 300       # 🔴 裁定候選——規格沒給值（見假設清單 A1）
```

lock timeout 的提案理由：relay 單批 ≤100 筆、無外部 IO（本包零真實消費者），
正常一批秒級完成；300s ＝ 給未來慢消費者留 60 倍餘裕、又足夠短讓 worker 死亡後
孤兒在下一兩輪內被回收。**不得靜默發明**——此值列 PR 假設清單，使用者可改。

### 4.2 migration（第一個交付物；strong_migrations 全程）

- `event_outbox` 加兩欄：`dedupe_key` VARCHAR(191) NULL、
  `coalesced_count` INT NOT NULL DEFAULT 1。
- 唯一索引 `(shop_id, dedupe_key)`。🔴 **依賴 MySQL 的「唯一索引允許多個 NULL」**：
  不參與合併的事件（商品事件、豁免筆）`dedupe_key = NULL` ⇒ 天生不碰撞
  （總交接 §4.5 的「豁免筆天生不碰撞」判準由 schema 本身保證）。此語義必須有一條
  spec 釘住（兩筆 NULL 並存＋兩筆同值被拒）。
- 🔴 **published／failed／dead 時把 `dedupe_key` 清成 NULL**（release-on-terminal）：
  這是「合併窗只在 pending 內」（63 §C.6）的機械保證——已發布列的鍵被釋放，
  晚到的同 key 事件開新列而不是 upsert 到已發布列上。
- 🔴 bt3 是有資料的庫而 CI 的庫是空的（#113 教訓）：migration 的每個資料狀態分支
  都要在「有店有 pending 列」的本機庫實跑一次，結果記 worklog。

### 4.3 三道形狀裁定（總交接 §4.1；migration 同 PR 落地）

1. **`dead` 進 `EventOutbox::STATUSES`**（pending/published/failed/dead）。
   18 §F1-5 的 attempts≥8→dead 語義靠它；status 欄是 string，不需 migration，
   改 model 常數＋spec。
2. **`event_deliveries`／`processed_events` 本包不做**。63 §L-4 已證單一 status 欄
   做不到逐消費者投遞——但本包真實消費者數＝0（§5），單 status 語義自洽。
   🔴 **門檻寫死：第一個掛真實多消費者的包，開工前置＝先建 `event_deliveries`**，
   此門檻同批寫進 63 §L-4 旁（規格 PR 的更正註帶上）。
3. **`dedupe_key` 形態**：
   - 合併型（庫存事件、非豁免）：`"inv:#{inventory_item_id}:#{location_id}"`
     （shop_id 已在索引第一欄，不重複進 key）。
   - 豁免筆與所有商品事件：`NULL`。
   - 豁免判準＝payload 布林 `availability_flipped`（引 `limits.catalog_flow.
     inventory_event_coalesce_exempt` 現值，不硬編字面）。

### 4.5 產生端修理（總交接 §4.2：不只 relay）

**(a) `Catalog::SaveProduct`**——payload 升級到 63 §C.2 形：

- `resource_version` ＝ `products.lock_version`（欄已存在，複驗
  `grep -n lock_version db/schema.rb`）；`changed_fields` 從 `saved_changes.keys`
  取（🔴 只有欄位名，沒有值——63 §C.2 紀律 1）；status 變更時附
  `status_transition: {from:, to:}`。
- topic 改引 `Events::Topics`；同 transaction 邊界不動。
- 🔴 **`Catalog::StatusTransition` 一處實作**（13 §F1.2(e) 明文；現況全倉零命中，
  複驗 `grep -rn StatusTransition app/ | wc -l` → 0）：本包做**事件面**——status
  變更集中經它產生 `status_transition` 欄位與 `product.publication.changed` 事件；
  發布讀取層／管道語義（塊 A 的包）不在本包。

**(b) 庫存產生端（`Inventory::Adjust`，現況只有註釋）**：

- topic 裁定＝**`inventory.adjusted`**（63 §C.2 第三個 payload 形；
  `inventory.level.changed` 保留給非調整型變化，本包不發——寫進常數表註釋）。
- payload 照 63 §C.2：`adjustment: {reason, from_state, to_state, sub_type, delta,
  ledger_id}`＋`availability_flipped`＋`coalesced_count`。
  🔴 **不帶數量值**（63 §C.3 防線④）：`delta` 是變動量不是餘額，餘額一律查 DB。
- `availability_flipped` 在**算出 leaf 新值的同段**算（available leaf 跨 0 邊界：
  舊值 >0 ⇄ 新值 ≤0）——它是合併豁免的唯一依據，事後補算會拿到已被後續呼叫
  改過的值。
- 寫入必在既有 transaction 內（鐵律 5）；掛載點＝`adjust.rb` 註釋預留的位置。
- 合併窗＝對 `(shop_id, dedupe_key)` 唯一鍵做 `INSERT ... ON DUPLICATE KEY UPDATE`
  （`coalesced_count = coalesced_count + 1`、payload 覆蓋為最新一筆、
  `available_at` 不延後）。🔴 邊界（總交接 §4.5）：**窗只跨呼叫不跨 change 列**
  （同呼叫內重複 `(item, location)` 在第 17 包已 reject，不會走到這裡）；
  **ledger 永不合併**（紅線 3：一次呼叫＝一鍵＝一 group＝N 列 ledger，本包不碰）。

### 4.6 `Events::Relay`（核心交付；service 先行、job 薄包裝）

- `Events::Relay.drain!(now: Time.current)`：可直呼的 service。
  `SELECT ... WHERE status='pending' AND available_at<=now AND (locked_at IS NULL
  OR locked_at < now - lock_timeout) ORDER BY id LIMIT batch FOR UPDATE SKIP LOCKED`
  → 標 `locked_at` → 逐筆「投遞」→ 成功標 `published`＋清 `dedupe_key`；
  失敗 `attempts+=1`、指數退避寫 `available_at`、`attempts >= dead_letter_attempts`
  → `dead`＋清 `dedupe_key`。
- 🔴 本包消費者路由表＝**空**：「投遞」＝標 `published`。這不是佔位敷衍——
  歷史 pending（總交接 §4.4-4 的洪水）因此被**安全地** drain 成 published 而
  不產生任何副作用，三選一的處置自然落在「照常 drain」。上線前仍要量：
  `ActsAsTenant.without_tenant { pp EventOutbox.group(:status, :topic).count }`，
  數字記 worklog。
- **租戶模式＝A 案**（總交接 §4.4-1）：`without_tenant` 取件、逐筆（按 shop_id 分組）
  `with_tenant` 處理。選 A 的理由：B 案（逐店 enqueue）仍需先全表掃出哪些店有
  pending，等於 A 案之上再加一層佇列。🔴 隨附 spec：「處理完 N 店後
  `ActsAsTenant.current_tenant` 為 nil」＋「店 1 的事件處理中拋錯不會讓店 2 的事件
  帶著店 1 的 tenant 跑」。
- ActiveJob 薄包裝 `Events::RelayJob`（無參數、不是租戶 job）＋ `config/recurring.yml`
  加 `events_relay: schedule: every 5 seconds`（間隔引 limits，落檔時把數值寫進
  recurring.yml 並在旁註明來源鍵——recurring.yml 不會讀 Limits）。
- retention purge：`published/dead` 超過 `outbox_retention_days` 的列每日刪
  （recurring 每日一條；`dead` 要不要豁免 purge 列假設清單 A2，預設＝一樣刪，
  理由：18 §F1-5 只說「保留 30 天 purge」未分狀態）。
- **觀測降級**（總交接 §4.4-3）：結構化 log 一行一事件
  （`event=outbox_published|outbox_dead|outbox_reclaimed shop_id=… event_id=… topic=…
  attempts=…`）。**明文降級**：18 §F1-5 的「告警」與 63 §C.3 的 metric 不在本包，
  登記進總交接 §7 未結帳（實作 PR 的 handoff 帶上）。不默默降級。

## 6. 測試要求（每條都是 DoD）

1. relay：pending→published；退避（attempts 遞增、available_at 後移）；
   attempts 到閾值→dead；locked_at 逾時回收；**兩連線併發 drain 不重複取件**
   （SKIP LOCKED 實測，MySQL 兩 connection）。
2. 合併窗：窗內 M 筆併 1（coalesced_count=M、payload 為最新）；豁免筆不併；
   **published 後同 key 開新列**（release-on-terminal）；
   `(shop_id, dedupe_key)` 兩筆 NULL 並存、兩筆同值被拒。
3. 租戶：A 案殘留 spec 兩條（§4.6）。
4. 產生端：save_product 新 payload 形（resource_version/changed_fields/
   status_transition）；adjust 事件與業務寫入同 transaction
   （**rollback 時事件一併消失**的反向案例）；availability_flipped 邊界
   （>0→0、0→>0、>0→>0 三態）。
5. 守衛注入回歸（總交接 §6）：每個新守衛注入缺陷→紅→還原→綠，記 worklog；
   注入後全綠先驗「注入沒生效」。

## 8. 坑位登記（前包踩過、本包必撞的）

1. `.squish` SQL 禁 `--` 行內註釋（relay 的原生 SQL 會踩）——只用 `/* */`。
2. SQL 現在時間一律 `UTC_TIMESTAMP(6)`；Ruby 側一律 `Time.current`。
3. Zeitwerk 一檔一類：`Events::Topics`／`Events::Relay`／`Events::RelayJob` 各自一檔。
4. GraphQL type 的 `private` 必須在所有 field 方法之後（本包若碰 type 檔留意）。
5. migration 資料狀態分支 CI 驗不到（CI 庫是空的）——見 §4.2 末條。
6. queue_adapter 未設＝async＝隨機紅——§4.7 第一條就是修它。
7. 🔴 MySQL 唯一索引多 NULL 不衝突是**本設計依賴的特性**——spec 釘住（§6-2），
   將來若換 DB 或加 NOT NULL 約束，這條 spec 會先紅。

## 9. 兩條需要注意的邊界

1. **與第 17 包**：合併的只有事件，ledger／group／idempotencyKey 鏈一個都不動
   （紅線 3）。`Adjust` 的掛載點在既有 transaction 內、Guard 之後，不改變任何
   現有 user_errors 語義。
2. **與塊 A（2–14 未做）**：本包的事件流出口今天沒有任何消費者，這是**刻意的**
   （§5-1）。後包接消費者時的前置＝event_deliveries（§4.3-2 門檻）＋各自的
   塊 A 依賴，不回頭改本包的 relay 語義。
