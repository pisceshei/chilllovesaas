# S0 決策文件：管道的身分模型

> 分步方案 `docs/plans/2026-08-26-發布與可見性-分步執行方案.md` 的 **S0**，六道關卡的第⑤道。
> 完整證據＝`docs/research/82-admin-channels.md` **§10**（實測）＋ 官方文檔研究（十一個 agent，2026-08-26）。
> 🔴 **本檔要一個裁定**：四個方案選一個。它會動 schema，屬鐵律 17.3 的例外，不自動決定。

---

## §1 問題

我方把「銷售管道」整個概念壓成**一張表的一個字串欄**：

```
publications(shop_id, name, channel_handle, auto_publish, supports_future_publishing, catalog_id)
```

沒有 `App`、沒有 `Channel`、沒有 `Catalog` 實體；`catalog_id` 無外鍵、無寫入者、恆為 NULL。
`Shop#after_create` 無條件建一筆 `online_store`。

而 2026-08-14 就有一條裁定 **R13-V2**（`docs/research/82` §7 第 2 條）逐字說：

> 資料模型應是 `App` 之下的 `Channel`（帶 channel capability），不是兩張平行表。

**這條裁定至今沒有人動過。** S0 就是來處理它的。

---

## §2 本尊的真實形態（實測，非推論）

一個 payload 抓齊四層（`82` §10.3）：

```
Publication/209681744107  name:"Shop"
  ├─ 六個能力旗標 ＋ operation ＋ publishablesStatusSummary{status, includedIds}
  └─ catalog: AppCatalog/99441377515  "Channel Catalog 209681744107 for Shop"  status:"ACTIVE"
       ├─ apps.nodes[0]: App/3890849 "Shop"
       │     ├─ installation: AppInstallation/725054128363
       │     └─ feedback: null
       └─ channels.edges[0]: Channel/209681744107  handle:"shop-72"  resourceFeedback: null
```

三條對裁定最關鍵的：

1. 🔴 **`Channel` 的數字 id 與 `Publication` 相同**（都是 `209681744107`）⇒ 第一方管道上兩者共用 id，
   官方 SDL 的 `Publication : Channel = 1 : N` 在實務上退化成 1:1。
   ⚠️ 多帳號連線的管道是否真的 1:N＝**未取得**（需要多連線管道才測得到）。
2. 🔴 **channel handle 帶每店後綴**（`shop-72` 不是 `shop`）⇒ handle **不是全域常數**。
3. 🔴 **Publication 有六個能力旗標**，我方只有一個：
   `supportsFuturePublishing`（有）／`supportsBundles`／`supportsCombinedListings`／
   `supportsVariantFixedBundles`／`supportsSubscriptions`／`supportsPublicationForUnlistedProducts`（皆無）。

## §3 十三條代價，只有一條現在就在痛

完整表在 `82` §10 與研究輸出。摘要：**C-1 到 C-13 之中，十二條在 v1（只有一個 online_store）
都不會出事**，出事時機分別落在「第二個管道」「M5 RBAC」「第 32 包 Markets」「S10 catalog」。

唯一**現在就在邊緣**的是 **C-9**：

> `Publication.online_store` 用 `find_by(channel_handle: "online_store")`，
> 而 `Shop::DEFAULT_CHANNEL_HANDLE` 是同一個值的另一個產生處。
> 改了常數而沒改這裡 ⇒ 靜默回 `nil` ⇒ **整店商品前台不可見且不拋任何錯**。

🔴 **C-9 已在本輪修掉**（與方案選擇無關）：`online_store` 改用常數、新增 `online_store!`（缺就炸）、
加兩格守衛測試（含一格結構性斷言盯著字面量不得復活）。

⚠️ **研究報告在 C-9 上有一處高估**：它說字面量「散在多個檔」，實測**只有兩處**
（`publication.rb` 與 `shop.rb` 的常數定義本身）。複驗：`grep -rn '"online_store"' app/ lib/ db/ config/`

## §4 四個方案

| 方案 | 動的表 | 遷移成本 | 解掉的代價 | 仍未解 |
|---|---|---|---|---|
| **A** 維持一張表，只補欄位與登記 | 無（A-1）／`publications` 加欄（A-2）／加 JSON 欄（A-3） | 0～1 支 migration | C-9（已修） | C-1、C-2、C-5〜C-8、C-13 全部延期 |
| **B** 加 `channels` 表 | 新建 `channels`；FK 在 `channels.publication_id` | 1 建表 ＋ 1 回填（每店一列） | C-1、C-2、C-7、C-8 | C-5、C-6、C-13（無 App／安裝態）；C-3、C-4 |
| **C** 照 R13-V2：`apps` ＋ `app_installations` ＋ `channels` | 三張新表 | 3 建表 ＋ 1 回填（每店 3 列）＋ 可能 seed | C-1、C-2、C-5〜C-8、C-13 | C-3、C-4（要等 S10 的 catalogs） |
| **D** 方案 C ＋ `catalogs` 一級表（本尊全形） | 四張新表 ＋ `publications.catalog_id` 上 FK ＋ `name` 降級 | 4 建表 ＋ 回填 ＋ **資料搬遷** | 全部 | — |

**A-3（JSON 欄）已可排除**：無唯一約束、無 FK，把 C-1 的衝突從「拋錯」退化成「靜默寫入兩筆重複」
——比 A-2 更差的失敗模式。

**方案 C 的隱藏成本**：若 `apps` 走平台字典表形態，就要改 `scripts/check-tenant-isolation.rb` 的
`NON_TENANT_TABLES` ＋ 改 CLAUDE.md 鐵律 2 本文 ＋ 同步 `docs/specs/71` §A G24
（鐵律 2 配套條款③）⇒ **該 PR 落入鐵律 18.3 的人工合併範圍**。

**方案 D 的爆炸半徑**：它把 S10 的全部未決（catalog 成員三值 Included/Excluded/All、
`Publication.operation` 的非同步鎖、price adjustment）拉進 S0。
`82` §9.5d 已實測 catalog 成員是非同步計算且進行中會鎖住逐商品切換
⇒ S0 做方案 D ＝ S0 的爆炸半徑等於 S0 + S1 + S10。

## §5 四個方案都成立的不變式（不論選哪個，先寫下來）

1. 新表一律帶 `shop_id`，複合索引以 `shop_id` 開頭（鐵律 2）。例外只有平台字典表，且須走配套條款③。
2. 新表照本倉庫既有的 tenant-safe FK 形態：`uq_<table>_tenant_id` on `["shop_id","id"]`
   ＋ composite FK `[shop_id, x_id] → [shop_id, id]`。
3. **訂單／歷史層存管道字串快照，不存 FK**（外部平台的共同經驗：Saleor 刪 channel 會把訂單改掛別的管道）。
4. **禁止硬刪管道**（查過的四家平台無一硬刪）。
5. GID Type 名稱對齊 `Channel`／`AppCatalog`／`Publication`／`ProductFeed`（鐵律 4）。
6. 🔴 **`publications` 集合不可以從「已安裝管道」集合導出**——已有兩個活例證偽：
   Shop 的商品可被發現「regardless of whether you've installed the Shop channel」；
   Agentic 不在已安裝清單卻在發布 modal（`82` §10.1）。
   任何「安裝＝INSERT publication、卸載＝DELETE publication」的實作都與實測衝突。

## §6 我的建議：**方案 B**，但**先只做 §5 的登記與 C-9**

理由三條：

1. **十三條代價裡十二條在 v1 不會出事**，而它們的出事時機集中在
   「第二個管道」「第 32 包 Markets」「M5 RBAC」——那三件事都還很遠。
   現在建三張空表（方案 C）等於為一個**還沒有需求的形狀**先付遷移成本，
   而形狀本身有一個**未取得**（`Publication : Channel` 是否真 1:N）沒解。
2. **方案 B 的增量最小而解掉最痛的四條**（C-1 多連線、C-2 handle 歸屬、
   C-7 product feed 掛載點、C-8 channel market），且它**不擋** 日後升到 C
   ——`channels` 表在 C 裡照樣存在，只是多長出 `apps`／`app_installations`。
3. **方案 C／D 都需要先解一個未取得**才能定形（C 需要知道安裝／卸載的實際語義，
   D 需要知道 AppCatalog 的標題規則與建立時機），而那兩件事**都要安裝管道才測得到**，
   使用者已裁定不安裝。

⇒ **具體建議的執行順序**：
- **現在**：只做 §5 的六條不變式登記 ＋ C-9（已完成）＋ 把 `channel_handle` 在 `docs/specs/88`
  明文標成「`channels.handle` 的前置佔位」。**零 schema 變更。**
- **第 32 包（Markets）開工前**：做方案 B 的 `channels` 表。屆時 channel market 是硬需求，
  形狀也會因為 Markets 的實作而更清楚。
- **方案 C／D**：等到有第二個真管道、或使用者決定要開放安裝管道時再說。

🔴 **這是建議不是裁定。** 要選 A／C／D 我照做；選 C／D 我會先把它們各自的未取得列成
「必須先取得才動工」的清單。
