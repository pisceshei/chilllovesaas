## 一、系列模型

### 1.1 本尊怎麼做

**資料模型層（Admin GraphQL `2026-07`）**：`Collection.sources: [CollectionSource!]!` 取代單一
`Collection.ruleSet`（後者同版 deprecated 但仍可查）。

🔴 **UI 形態與資料模型形態不是同一件事，這是本節最容易錯的地方。**

| 面 | 看到什麼 |
|---|---|
| **admin UI**（我方實測，94 §1.3） | 來源型別下拉有**四項**：`Products` ／ `Variants` ／ `Collection` ／ `App` |
| **GraphQL 資料模型** | 具體 source 型別只有**兩個**：`CollectionConditionsSource`（帶 `shareable: Boolean!` 與 `targetType: PRODUCTS｜VARIANTS`）與 `CollectionSubCollectionsSource` |

⇒ UI 的 `Products`／`Variants` 是**同一型 source 的 `targetType`**；`App` 是 `CollectionSource.app`
**欄位**而不是型別；`shareable` 是布林狀態不是第三型。

其餘四條關鍵語義：

1. **include/exclude 不是 source 上的極性旗標**，而是 conditions source **內部**的兩個區塊：
   `inclusion`（必有）與 `exclusion`（可選），各自帶 `conditions ＋ matchType(ALL/ANY) ＋ selections`。
   ⇒ 「條件納入 ＋ 手動排除三件商品」是**一個** source，不是兩個。
2. **排除只在自己這個 source 內結算**：官方原文「evaluated per source and reconciled into the
   collection's final membership」⇒ **最終集 = ⋃ₛ ( inclusion(s) − exclusion(s) )**。
   A source 排掉商品 X、B source 包含 X ⇒ **X 仍在系列裡**。
3. **`exclusion.matchType` 與 inclusion 不同構**：它只管非 collection 類排除條件；
   collection 類排除**永遠獨立以 ANY 生效**；兩類混用時該欄位**回 `null`**（不是 ALL 也不是 ANY）。
4. **巢狀只有一層**：`SubCollectionIneligibleReason` 三值
   `SELF_REFERENCE` ／ `CHAIN_REFERENCE`（「chains of depth > 1 are not supported」）／
   `INVALID_COLLECTION_REFERENCE`；`Collection.subCollectionEligibility` 對 inclusion 與 exclusion
   **分開**回可用性。`CollectionRuleColumn` 的值域裡**沒有** `COLLECTION` ⇒ 巢狀不走 rule。

排序：`CollectionSortOrder` 九值，欄位型別是 **enum 非 String**；預設 `MOST_RELEVANT`（實測 94 §1.5）。

| 代碼 | `Collection::TYPES = %w[manual smart]`；`SORT_ORDERS` 八值硬編；前端再硬編第三份 |

**不是 GraphQL 的資料模型**。五處與 `2026-07` schema 不符：

## 二、庫存 `on_hand`

### 2.1 本尊怎麼做

**語義層：導出。** 官方恆等式＝`available + committed + reserved + damaged + safety_stock + quality_control`
六項之和（`incoming` **不在內**）。

🔴 而且本尊不只在散文裡寫這條——它把組成關係做成**機器可讀的 API 面**：
`inventoryProperties.quantityNames: [InventoryQuantityName!]!`，每個 name 帶
`comprises` / `belongsTo` / `displayName` / `isInUse`；官方範例直接回
`on_hand.comprises = [available, committed, damaged, quality_control, reserved, safety_stock]`、
`available.belongsTo = [on_hand]`。

**商家可見面**（我方實測，94 §2.2）：On hand 欄的 tooltip 逐字
「The total amount of inventory at a location. This is the **sum** of unavailable, committed, and
available items.」（三個詞為 Shopify 自己加粗）。

**介面層：`on_hand` 同時是一等可寫的 name。** `InventorySetQuantitiesInput.name` 明文
「The only accepted values are: available or on_hand」。互動上沒有主從——改 Available 則 On hand
同額變動，改 On hand 則 Available 同額變動，因為 committed 由 Shopify 獨佔、其餘四項只能用
adjust/move 動，恆等式強迫另一端跟著移。**真正的獨立變數是六個 leaf state，`on_hand` 是它們的和。**

### 2.2 我方怎麼做

**規格與代碼逐句對撞**：`docs/specs/13:574` 逐字寫 on_hand「**derived，不落庫**（避免雙寫漂移）」，
而 `db/schema.rb:402` 是 `t.integer "on_hand", default: 0, null: false`——實體欄、NOT NULL、
非 generated、無 CHECK。`inventory_adjustments` 有第二個雙寫點 `on_hand_delta`。

**更深一層是粒度問題**：我方是四欄制（available／committed／unavailable／incoming），把本尊的
`reserved`／`damaged`／`safety_stock`／`quality_control` 四個**官方 quantity name** 壓成一個
`unavailable` 彙總欄 ⇒ `unavailable` 是**第二個被落庫的導出值**，而它根本不是本尊的 API name。

三道防漂移機制（`Inventory::Adjust` 唯一入口、禁直寫 cop、nightly 對帳）**一道都不存在**。

**唯一慶幸**：三張庫存表**零讀寫**（grep 只命中 migration、schema.rb 與一支表名字面比對 spec）
⇒ 現在改表幾乎免費。

### 2.3 建議

**裁定：`on_hand` 導出，且在資料庫層強制導出（MySQL 8 STORED GENERATED COLUMN）；
對外 API 面保持可寫，寫入語義＝翻譯成 `available` 的 delta。同批把 `unavailable` 一起改成導出，
並把欄位粒度補到本尊的六個 leaf state。**

- `inventory_levels`：保留 `available`／`committed`／`incoming` 為實體欄；**新增**
  `reserved`／`damaged`／`safety_stock`／`quality_control` 四個實體欄；
  `unavailable` 與 `on_hand` 改成 STORED generated。
- 🔴 兩個 generated 都**直接引用基礎欄**，不得寫成 `available + committed + unavailable`
  （避免 generated 引用 generated 的定義順序相依，且讓兩式各自獨立可驗）。
- 選 STORED 而非 VIRTUAL 的理由：列表排序與低庫存查詢要建索引，VIRTUAL 建不了。
- `incoming` 維持實體且**不進任何 generated 式**（本尊明文不計入 on_hand）。

⇒ 這道裁定**規格是對的、schema 是錯的**。不是二選一，是把 schema 改到規格說的那樣，
並且用 DB 層的 generated column 讓「不落庫」變成**機制**而不是**紀律**。

### 2.4 一條由此帶出的、原本沒人問的問題

`InventoryQuantityName.isInUse` 是 **per-shop 狀態**，官方範例裡 `damaged`／`quality_control`／
`safety_stock` 三個的 `isInUse` 都是 **false**。⇒ 我方新增的四個 leaf 欄要不要有對應的
per-shop 啟用開關？未啟用的 state 在 `quantities(names:)` 上回什麼？**待裁定（見 §五）。**

## 三、庫存冪等：一把鍵對 N 筆異動

### 3.1 本尊怎麼做

**兩套機制並存、職責分離。**

| 機制 | 管什麼 | 形態 |
|---|---|---|
| `@idempotent(key:)` directive | **重送去重** | 2026-01 起可用、**2026-04 起強制**；17 支 mutation |
| `changeFromQuantity` | **併發覆寫** | 官方明文稱 compare-and-swap；2026-04 起必須顯式給值，跳過檢查傳 `null`；**取代已移除的 `compareQuantity`／`ignoreCompareQuantity`** |

🔴 **鍵的粒度＝一次 mutation 呼叫**：一把鍵覆蓋整個 `changes[]`／`quantities[]`，指紋涵蓋全部 input
欄位且**對順序敏感** ⇒ 不能只重送失敗子集（回 `IDEMPOTENCY_KEY_PARAMETER_MISMATCH`）。
整批 N 筆 change 在 payload 上收斂成**一個 `inventoryAdjustmentGroup`**。

bulk operation 的粒度**相反**：逐 JSONL row 各自一把鍵。

`referenceDocumentUri`（頂層，答「為什麼」）與 `ledgerDocumentUri`（逐 change，答「動到哪筆分錄」）
**都是純稽核欄位，文檔全文零 uniqueness／dedup 語義**——同一 URI 重送會產生第二筆調整。

商家可見面的佐證（我方實測，94 §2b③）：一次 `Save` 套用**跨列、跨商品、跨地點**的多筆調整。
⇒ 「一把鍵對 N 筆」是本尊的**常態形狀**，不是邊角。

### 3.2 我方怎麼做

**現行 Guard 的模型是「一把鍵 → 一個 resource」，對 N 筆撐不住，而且是必然失敗不是偶發：**

- `app/services/idempotency/guard.rb` 寫死 `resource_type: resource.class.name, resource_id: resource.id`；
  回放端是 `find_by(id:)`。block 若回 N 列，`resource.id` 直接 `NoMethodError`，
  被同檔的 `rescue StandardError` 吞成 `mark_failed` ⇒ **每一次多筆調整都必然失敗**。
- `inventory_adjustments.idempotency_key` 是 NOT NULL ＋ 唯一索引 `(shop_id, idempotency_key)`
  ⇒ **第 2 筆 change 直接 `RecordNotUnique`**。
- 而這一欄與 `idempotency_keys` 表**無外鍵、無關聯登記、TTL 語義相反**（前者永久、後者 24h）
  ⇒ 這是**第二套從沒人定義過的平行冪等**。

### 3.3 建議

🔴 **裁定：鍵的粒度＝一次 mutation 呼叫。**

```
一次呼叫 ＝ 一把 idempotencyKey
         ＝ 一列 inventory_adjustment_groups（＝本尊的 InventoryAdjustmentGroup）
         ＝ Guard 的唯一 result_ref
         ＝ N 列 append-only inventory_adjustments 子行
```

全有全無，不做部分成功。具體：

- **新增 `inventory_adjustment_groups` 批次頭表**，`idempotency_key` **從 ledger 行搬上來**，
  唯一索引 `(shop_id, idempotency_key)`。
- **`inventory_adjustments` 移除 `idempotency_key` 欄與其唯一索引**（兩套平行冪等的來源），
  改帶 `inventory_adjustment_group_id`。
- 併發控制走 `changeFromQuantity` 的 CAS，**不是**樂觀鎖版本號。
- `referenceDocumentUri`／`ledgerDocumentUri` 照抄語義：**純稽核、不去重**。

⇒ 這樣 Guard 的「一把鍵 → 一個 resource」模型**不必改**：那個 resource 就是 group 列。

## 四、🔴 三道裁定之間的交互衝突（必須先消解才能寫 migration）

完整性批判找出 **9 條交互衝突**，其中四條是同一張表被兩道裁定改成兩種形狀：

| 衝突 | 內容 | 處置 |
|---|---|---|
| `from_state`／`to_state` | on_hand 裁定要**刪**（改用 `mutation_kind`，理由是移動已由相反符號的 delta 表達）；冪等裁定要**新增並拿它當唯一鍵的一部分** | 先定 ledger 行的身分（一列＝一個 (level, quantity_name) 的 delta，還是＝一次 from→to 移動），再談索引 |
| `idempotency_key` 欄 | on_hand 裁定說「保留唯一索引」；冪等裁定說「刪掉這一欄」 | 以冪等裁定為準（鍵搬到 group 頭） |
| actor 掛哪一層 | on_hand 放 ledger 行；冪等放 group 頭 | 本尊 `InventoryAdjustmentGroup` 上有 `app` 與 `staffMember` **兩個分開的欄位**、`InventoryChange` 上沒有 actor ⇒ **冪等的層級對、on_hand 的錯**；但要用兩個欄位而非多型 |
| `ledger_document_uri` 掛哪一層 | on_hand 放 ledger 行（對）；冪等折疊到 group（錯） | 只在 `inventory_adjustments` 建一次 |

**⇒ 兩道庫存裁定必須合併成一份「庫存 ledger 形狀總裁定」再寫 migration，
順序是先定 ledger 行的身分、再定欄位與索引。** 系列那道與庫存無耦合，可並行。

另有一條**判準衝突**值得單獨記：兩道裁定對「什麼樣的加嚴可以接受」用出了相反結論
（一道論證「不得把 quantity name 上 enum，因為那是改錯誤分層」；另一道卻把
`idempotencyKey` 從 runtime 檢查升成 schema 上的 `String!`，同樣是改層）。
建議在鐵律 4 下增訂第三個子條款：
**「必填性可以往 schema 推（我方是唯一客戶端），值域不可以（值域可能 per-shop）」**——
這一條能同時解釋兩案。

## 五、需要你拍板的（真正需要的，只有這些）

三道裁定本身在技術上都有唯一合理解，**不需要你選**。真正需要你拍板的是下面四條：

1. **`idempotencyKey` 要不要上 `String!`（缺鍵直接變 GraphQL 驗證錯誤，非 200）？**
   這是對本尊的**刻意加嚴**（本尊是 runtime 檢查），依鐵律 12 必須進 `71` §A 保護清單，
   而 §A 入表**只能由你裁定**。同理 `changeFromQuantity` 的 `required: :nullable`。
2. **四個 leaf state（reserved／damaged／safety_stock／quality_control）要不要 per-shop 開關？**
   本尊有（`isInUse`，且官方範例裡三個都是 false）。做＝多一張設定表與一層過濾；
   不做＝所有商店都看到四個狀態欄。
3. **`MOST_RELEVANT` 排序落地時，相關性依據是什麼？** 官方描述只有「By most relevant products.」，
   沒有定義算法，而我方沒有搜尋引擎。選項：暫不出現在下拉（登記 V）／退化成某個代理指標。
4. **系列 source 的 `title`／`description` 算不算可翻譯資源？**
   若前台可見就要進 `translations` 的 `resource_type` 值域（會改 CSV 欄語義與進度分母，
   而譯文**正在累積**）；若只是 admin 內部標籤就不是。
