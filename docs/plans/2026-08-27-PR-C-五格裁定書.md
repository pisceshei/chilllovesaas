#### ③ 外部參考

| 平台 | 對「到點時前置條件不成立」的做法 | 逐字 |
|---|---|---|
| **Kubernetes CronJob**（可類比格） | **skip、不建立 Job、不清除未來排程、發 Normal 級事件** | `concurrencyPolicy: Forbid` — `the CronJob skips the new Job run`；controller 事件 `JobAlreadyActive`，**EventTypeNormal**，`Not starting job because prior execution is running and concurrency policy is Forbid`；`suspend` 那格官方用字是 `count as missed Jobs`（非 failed） |
| Kubernetes（**不可類比格**，R8） | `startingDeadlineSeconds` 的 "treats them as failed Jobs" 射程是 **controller 沒能準時起跑**，**預設不啟用**，且無 terminal 落點（`CronJobStatus` 只有 `active`／`lastScheduleTime`／`lastSuccessfulTime`） | — |
| **Strapi**（R9 收窄後） | 容器層 `Blocked` 徽章，屬**手動 Publish 前的自我檢查面**，需手動 `Refresh` 重算；排程章節不提徽章；官方**未說明**到點時 Blocked 會怎樣 | `content has been added to the release but at least one issue in an entry prevents the release from being published` |

⇒ **業界可類比的那一格（K8s Forbid）三句與 S2 建議值逐句一致**：不投遞、不清排程、不向使用者報錯（但留 Normal 級營運痕跡）。

#### ⑤ 🔴 裁定

> **到點時，消費者以 DB 現值重新評估該筆發布是否應生效：**
> **(a) 該 `resource_publications` 列不存在，或其 `published_at` ≠ payload 的 `published_at` ⇒ no-op success；**
> **(b) 主體為 `Product`／`ProductVariant`（讀父商品）且 `status ∉ Product::PURCHASABLE_STATUSES` ⇒ 不 bump cache stamp、不改寫 `published_at`、不刪列、不 raise；**
> **(c) 主體為 `Collection` ⇒ 本規則不適用（無 status 軸、無 stamp 落點），no-op success；**
> **(d) 上述任一 no-op 分支都必須寫一行結構化 log（Normal 級，含 `event_id / topic / publishable_type / publishable_id / status / decision`）。**
> **本裁定為 ours：官方對「排程列去留」與「是否報錯／通知」全面沉默（D 級，掃描清單見 ①）。**

**程式碼上的具體形態：**

```ruby
<!-- 上下各 2 行內的路徑是 PR-C 的交付物，**尚未建立**（規格指定的落點，不是既有檔）。 -->
# app/services/publications/scheduled_publication_consumer.rb（新建）
def call(event)
  # payload 只作定位，DB 現值才是權威（改期／取消都由此擋住）
  row = ResourcePublication.find_by(shop_id: event.shop_id, ...)
  return log_skip(event, :row_gone)      if row.nil?
  return log_skip(event, :superseded)    if row.published_at != parsed_payload_published_at

  case row.publishable_type
  when "Collection" then return log_skip(event, :no_stamp_target)
  when "Product", "ProductVariant"
    product = resolve_product(row)                      # variant ⇒ 父商品
    return log_skip(event, :row_gone) if product.nil?
    # 🔴 鐵律 6：判準取既有唯一產生處，不硬編 "active"
    return log_skip(event, :not_purchasable) unless Product::PURCHASABLE_STATUSES.include?(product.status)
    Product.bump_publications_stamp!(shop_id: product.shop_id, id: product.id, at: Time.current)
  end
end
# 🔴 全部不合格分支一律 return，禁止 raise —— raise 會走進 relay 的 2**attempts 退避
```

**🔴 相對 S2 建議值的三處修改：**

| # | S2 建議 | 本輪證據要求改成 | 理由 |
|---|---|---|---|
| **F1-①** | 「**不投遞事件**」 | 「**到點消費者不執行副作用**」 | 事件在 S5 建列時就以 `available_at = published_at` 投出，到點時**一定會被 relay 取出**（`available_at <= now`，無上界、無 stale 判斷，`relay.rb:73-80`）。「不投遞」在我方架構上**做不到**，除非改 S5 生產者。裁定必須落在**消費端** |
| **F1-②** | 「**status 非 ACTIVE**」 | 「**`status ∉ purchasable_statuses`（＝{ACTIVE, UNLISTED}）**」 | ①A 級：`UNLISTED` 官方逐字「is active but…」，且 Storefront API／Liquid 會回傳；②B 級：Visibility rules 把 Unlisted 與 Active 並列；③F 級：13 §F1.2 已裁定兩維度、`m1-product-status.md:32-33` 明文「單一 scope 設計已作廢」；④**到點事件的載荷是 cache stamp（可見性設施），不是發布動作** ⇒ 判準必須與可見性同軸。寫 `!= ACTIVE` 的具體事故形態見 ⑥ |

**維持 S2 建議值的部分（以及支持它的具體證據）：**

- 「**不清除排程**」**維持**。支持它的**不是** R1（已推翻，零鑑別力），而是：
  - **F 級架構後果**：清除意味著 `published_at → NULL` 或刪列。NULL 列在 `currently_published`／`staged`／`published_or_staged` 三個 scope 下與「不存在」不可區分（純隱形狀態），且佔住 `uq_res_pub_target` 唯一索引；刪列則讓商家把商品改回 ACTIVE 後**永遠不可見**。
  - **X 級同側**：K8s Forbid「future occurrences are still scheduled」。
  - **M 級旁證**：本尊給商家一個**顯式的 `Remove schedule` 一等操作**——排程的移除在本尊是一個要商家主動做的動作。
  - ⚠️ 🔴 **必須同時寫明**：這是**取捨不是唯一可行值**（repo-pr-c 原斷言「唯一可行值」已被推翻——刪列可行，`unpublish` 就是硬刪）。拒絕「清除」的真正理由是**語義**：查詢時判定之下，到點之後那筆列已經不是「一個待執行的排程」而是「一筆已生效的發布」，清除它＝回頭撤下一個商家要求發布的資源。

**🔴 需使用者明示確認的子格（五格表未涵蓋）**

> S2 原本把「**UNLISTED／ARCHIVED 到點**」列為**獨立裁定項**（`docs/plans/2026-08-26-S2-規格草案.md:276`：「🔴 **裁定項**｜官方 `[?]`。**不得**由『Draft 不發布』外推」），使用者給的五格表把它併進了 F1。
> 本文的 F1-② 對這一格給出**推薦值**（UNLISTED 照 bump、ARCHIVED 不 bump），**但它超出五格表射程，需使用者對這一行明示確認。**
> 若使用者裁定改採單一 `== ACTIVE` 閘門，則必須同批把 UNLISTED 的 stale-cache 形態逐字登記為**已知缺陷**（S2 §4.D 已明文要求「不得靜默」）。

#### ⑥ 反面選項與為什麼不取（含具體事故形態）

| 反面選項 | 具體事故形態 |
|---|---|
| **A. 用 `raise` 表達「條件不合」** | 每一筆不合格排程 ⇒ `attempts` 1→8，`available_at` 依 2,4,8,16,32,64,128 秒後移，**累計約 254 秒**燒完，`event_outbox.last_error` 留下一則**假錯誤**訊息，最終 `status=dead`。營運端看到 dead 列會當成真事故追查；而每一個 DRAFT 商品的排程都會產生一筆。 |
| **B. 到點清除排程（`published_at → NULL`）** | NULL 列在三個 V2 scope 下與「沒有列」不可區分 ⇒ 隱形狀態；且它**佔住 `uq_res_pub_target`**，商家重新 publish 時走 R3 分支。更糟的是：商家把商品改回 ACTIVE 後，商品**永遠不可見**、且**沒有任何錯誤訊息**——這正是 WordPress missed-schedule 事故的完整形態（X 級：WordPress 因狀態機驅動，沒跑到 job 就永遠停在 `future`，社群被迫用第三方掃描器補救）。 |

| **D. 判準寫 `status != ACTIVE` 就跳過** | UNLISTED 商品到點：`Product.purchasable`（含 UNLISTED）**已放行**、`published_at` 已是過去 ⇒ **前台實際上已可購買**；但事件因非 ACTIVE 而未 bump `publications_updated_at` ⇒ **前台快取繼續供應舊內容、無錯誤、無日誌**。這個落差 S2 §4.D 自己已預先寫下：「這是 UNLISTED 裁定必須一併處理的邊際條件，**S2 必須在 dev doc 明列，不得靜默**」。 |

| **F. 用 `discoverable_statuses` 當判準** | 今日恰為 `[ACTIVE]`，看起來正確；但它的語義軸是「可被**發現**」（搜尋／sitemap／feed），不是「可見性是否在這一刻改變」。日後該集合若加值，到點語義會**靜默改變且無任何測試轉紅**。 |
| **G. 在寫入層（`publishablePublish`）擋非 ACTIVE 排程** | ①S2 §4.D 已裁定檢查層在**到點事件投遞層**；②本尊 admin **不擋輸入**（M 級 banner 是資訊性 `tone-auto`，控件不禁用）；③`publishablePublish` 官方**未定義**任何相關 `userErrors` code（A 級）。擋在寫入層會讓商家無法「先排程、之後再改成 Active」這個本尊允許的工作流。 |
| **H. 不對 `Collection` 分支** | Collection 沒有 `status` 欄也沒有 `publications_updated_at` ⇒ 消費者對它會在 `nil.status` 或 `bump` 落空處炸開，走進反面選項 A 的整套事故。 |

| WP-Cron | `all scheduled tasks are put into a queue and will run at the next opportunity`（無界排隊） | ❌ |

**🔴 最有力的外部反例（X 級，支持我方架構安全）**：WordPress 的 `future → publish` 是**狀態機驅動**，`Publish: Viewable by everyone. (publish) / Future: Scheduled to be published in a future date. (future)`。missed schedule 之所以讓文章**永遠不出現**，正因為沒跑到 job 就永遠停在 `future`。**我方是查詢時判定，結構上不可能發生這種事故**——這正面支持「不補發布」是安全的：缺的只有事件與 cache stamp，不是可見性。

#### ⑤ 🔴 裁定

> **不自動補發布。「不補發布」的射程精確定義為三層，缺一層就會與機制實況矛盾：**
>
> **(a) 可見性層**：不做任何事，也不需要做。到點後 `published_at` 已是過去，可見性由查詢時判定與 `status` 兩軸決定；商家把商品改回 ACTIVE 的那一刻，同一查詢立即放行。**沒有「發布動作」可補。**
> **(b) 事件補送層**：既有 relay 的 `available_at <= now` 必然把錯過時點的事件補送出來。**本裁定不改變它**，也不新增任何 max-age 丟棄（理由見 F4-⑤）。
> **(c) 補發布動作層**：**不存在，也不新增**。禁止任何「掃描 due 的 `resource_publications` 並重寫 `published_at` 或重新投遞」的機制（承接 `m2-resource-publication-semantics.md` §6 的既有禁令）。
>
> **catch-up 的實現方式**：商家改回 ACTIVE 時，既有 `Catalog::StatusTransition` 已投的 `status_transition` 型事件由 PR-C 的**同一個消費者**分支處理，做一次商品級 cache stamp bump。**這不是補發布，是把已由查詢時判定自然發生的可見性變更同步到快取層。**
>
> **本裁定為 ours：官方對 catch-up 全面沉默（D 級）。業界術語為 Quartz `MISFIRE_INSTRUCTION_DO_NOTHING`（非 Airflow catchup）。**

**程式碼上的具體形態：**

```ruby
# 同一個消費者，以 payload 形狀分支（🔴 不得假設 payload 一定有 publication_id）
if event.payload["scheduled"]           # S5 排程到點型
  handle_scheduled_arrival(event)
elsif event.payload["status_transition"] # StatusTransition 型（catch-up 路徑）
  # 只做商品級 stamp bump；🔴 該 payload 不帶 publication_id，
  #    因此無法、也不應重放任何 per-channel 到點副作用
  bump_product_stamp(event.payload["product_id"], event.shop_id)
else
  log_skip(event, :unknown_payload_shape)  # 🔴 fail-closed，不 raise
end
```

**🔴 相對 S2 建議值的兩處修改：**

| # | S2 建議 | 本輪證據要求改成 | 理由 |
|---|---|---|---|
| **F2-①** | 「不自動補發布」（單句） | 拆成上述**三層**表述 | `relay.rb:73-80` 的取件條件無時間上界 ⇒「錯過的事件不會補送」在機制上為假。只寫一句會讓實作者以為要加 stale 判斷 |
| **F2-②** | 反直覺點寫成「錯過時點之後前台其實已經可見了」 | 「**改回 ACTIVE 的那一刻自然可見**」 | DRAFT 期間 status 層先擋住（`PURCHASABLE_STATUSES` 不含 draft），前台**不可見**。原表述在 DRAFT 情境下是錯的 |

**維持 S2 建議值的部分（支持它的具體證據）：**

- F 級：`m2-resource-publication-semantics.md` §6 已明文禁止翻狀態 job；
- X 級：WordPress 的 missed-schedule 事故證明「狀態機驅動＋無 catch-up」才危險，我方是查詢時判定，不需移植它的補丁思路。

**PR-C 必須額外交付的一件事（S2 五格未涵蓋）：**
> **一次性 backfill**：處理「S5 合併後、PR-C 上線前」被零消費者消化掉的排程事件所對應的列——掃 `resource_publications` 中 `published_at` 已過去、且對應 `products.publications_updated_at < published_at` 者，bump 一次。
> 🔴 **不得掛到 `catalog:resync:publications`**（該 task 零實作，且 63 §H.3 定義它是「重新查管道現況，不是重推」，語義不同）。

> **沿用 `Events::Relay` 既有退避與 dead-letter，不新增任何重試參數。**

**🔴 決定性的射程證據（B 級）：**
> 全站唯一把 `ResourceFeedback` 與排程綁在一起的句子是 **步驟 4**：
> `If the product fails validation, then the channel app sends feedback to the merchant using the ResourceFeedback object.`
> 而官方立場明文是**提前驗證**：`you need to validate products **before** their scheduled publication datetime.`
> 到點那一步（步驟 8→9）是 `At the scheduled datetime, Shopify sends a product_listing/add event.` → `The channel app reads the product data and displays the product.` ——**無任何驗證、無任何回饋**。
>
> ⇒ **本尊沒有把 feedback 當作「排程到點動作失敗」的回報通道。**

**🔴 本尊的提前驗證有一個我方缺少的前置條件（A 級）：**
> 三個排程生命週期 webhook（`scheduled_product_listings/add | update | remove`）是提前驗證的**觸發點**。我方 S5 只有到點事件，**沒有這三個前置事件**。

**沉默（D 級）：**
> 對「**第一方 Online Store 排程到點不合格**」的商家可見回饋，官方無任何正面證據：`notification / notify / email / alert / warning` 在 help future-publishing、publishablePublish、publishableUnpublish、PublicationInput 四頁**全部 not found**。
> 🔴 **這只證明文檔未寫，不證明 admin UI 沒有 banner。**

**🔴 三處必須避免的錯誤寫法（R15／R16／R17）：**
1. 不得寫「**第三方** app → 商家」——官方逐字是 `apps`，**無 third-party 限定**，本尊自家管道本身即 app（82:868 實測 `App.feedback` 與 `Channel.resourceFeedback` 兩個掛載點）。
2. 不得寫「本尊此處**無平台側對位物**」——未查證，且已找到 `Shop.alerts: [ShopAlert!]!`（`An alert message that appears in the Shopify admin about a problem with a store setting, with an action to take.`，唯讀、無 `shopAlert*` mutation）。其射程是 **store setting 級非 product 級** ⇒ 正確寫法是「**本尊是否有 product 級、平台自寫的商家回饋對位物＝未取得**」。

#### ⑤ 🔴 裁定

> **不做 ResourceFeedback 等價物，登記 `docs/specs/91-pit-register.md` §3.23 為 ⚪（不擋通過）。**
>
> **🔴 但 S2 原理由必須整個換掉。** S2 寫的是「本尊有 `ResourceFeedback` 提前驗證＋回饋機制；我方尚無」——這句在事實層對，在推論層錯用（它把 ResourceFeedback 讀成排程失敗的回報通道）。**正確的三條理由：**
>
> **(a) 射程不對**：官方全站唯一把 `ResourceFeedback` 與排程綁在一起的句子落在**到點之前的驗證**（步驟 4，B 級逐字），不是到點失敗回報。我方 PR-C 要處理的是後者 ⇒ **本尊在這個情境沒有已取證的對位物**。
> **(b) 缺 producer**：本尊此角色由**管道 app** 承擔（寫入端另有 `write_resource_feedbacks` scope ＋ app 型態雙重門檻）。我方是單體 SaaS、平台與管道角色合一，**沒有對位的 app 身分**來寫這個回饋。
> **(c) 缺前置觸發點**：本尊的提前驗證之所以成立，是因為平台先發三個排程生命週期 webhook（`scheduled_product_listings/add|update|remove`，A 級）。我方只有到點事件 ⇒ 做出來的等價物**只能退化成事後回報**，而事後回報正是本尊沒有的形態（＝自創）。
>
> **🔴 兩種寫法明文禁止**：
> - 不得寫「本尊沒有這個東西」（本尊確有，且 M 級實測到逐通路的三層 channel error UI）；
> - 不得寫「本尊此處無平台側對位物」（未取得；`Shop.alerts`／`ShopAlert` 存在，但射程是 store setting 級）。
>
> **🔴 但「可觀測性」不隨 F5 一起不做**（這是 F5 與 F1／F3 的交界，必須明文切開）：
> 消費者對**每一次**「條件不合 ⇒ no-op」寫一行結構化 log（Normal 級，含 `event_id / topic / publishable_type / publishable_id / status / decision`）。這是**營運可見**不是**商家可見**，成本近零，對照 K8s 可類比格的 Normal 級事件形態，且是 `docs/specs/11` §0 可觀測維度的最低要求。

**🔴 ⚪ 登記必須包含的五項內容**（缺任一項，下一輪驗收方會重新提出，或日後要做時得重查一遍）：

1. **目標形態（日後要做時的值域，可直接落 `limits.yml`）**：兩態 enum `ACCEPTED`／`REQUIRES_ACTION`；商品級最多 10 則、每則 ≤100 字元、批次 ≤50；店級單則 ≤100 字元、句點結尾、`[Explanation of the problem]. [Suggested action].`；upsert-latest（`Sending feedback replaces previously sent feedback`）；`ACCEPTED` ＝清除訊號（讀回 null 是成功）；去重靠 `feedbackGeneratedAt`（＋商品級 `productUpdatedAt`）。
2. **surface 兩處**：admin 首頁 ＋ 商品詳情頁（bulleted list of errors）——**不是「加一個 badge 就好」**。
3. **M 級 UI 對照物**：本尊 admin 的三層形態（Publishing 卡 badge tooltip `1 channel error` ／ 通路列前置警示圖示＋chevron ／ 展開面板 `1 error` ＋可行動說明句），以及 Agentic 分頁的「標題＋狀態 badge＋說明句」列形態。
4. 🔴 **隱藏代價（不寫進 ⚪ 就會在日後被當成 bug 重查）**：本尊有 `availablePublicationsCount`（**排除** feedback error）與 `resourcePublicationsCount`（**包含**）兩個不同的數，以及 `error_feedback` 商品篩選器。我方沒有 feedback 維度 ⇒ **發布計數與商品篩選在語義上與本尊不同源**；未來要做時是**破壞性契約變更**。
5. **前置條件與一條反向約束**：要做等價物得先補三個排程生命週期事件；且 `FEEDBACK_DATE_IN_FUTURE` 證明**本尊禁止用 feedback 預告未來時點的問題** ⇒ 「排程建立時就預先警告商家」在本尊沒有對位做法（不得憑直覺自創）。
