# CHILL LOVE 最終執行順序（2026-08-24）

## 1. 一句話結論

**智慧系列 → M1 目錄殘量（庫存地基 → 變體 → 媒體）→ 前台**，因為前台是唯一含**不可逆決定**（URL 前綴形態，67 §I L7 明文「不得拆成兩期」）的一塊，而它的每一個輸入（成員物化、庫存數字、變體、媒體、發布可見性）都來自前兩塊；把它排在最後不是為了省事，是為了讓那個一次定案的決定在資料模型全部就緒後才做。

## 2. 關鍵發現（改變了排序判斷的事實）

### 2.1 與直覺相反的五條

**① 「庫存必須整塊做完才能開工變體」是錯的——只有庫存地基是前置。**
`docs/specs/63-product-data-flow.md:1141` 的 §B.5 驗收條逐字是：「建立無變體商品 → 加選項 → 斷言原 variant.id 與 inventory_item.id **完全相同**、ledger 連續」——**全程沒有任何數量調整動作**，因此不需要 `Inventory::Adjust`、不需要 inventoryAdjustQuantities、不需要併發測試。它只需要兩樣：InventoryItem 記錄存在、ledger 既有列不斷，兩者都在「四模型＋開帳鏈＋backfill」那一包的射程內。
⇒ 變體寫入包的真實前置是 {庫存地基, FK 裁定, 讀取面契約}，**不含 Inventory::Adjust 那一包**。變體 UI 因此提前兩個包。

**② 「line_items 外鍵改 ON DELETE SET NULL」是一支建不起來的遷移，不是 S 級小改。**
實測 `db/schema.rb:1101`：`add_foreign_key "line_items", "product_variants", column: ["shop_id", "product_variant_id"], primary_key: ["shop_id", "id"]`，而 line_items 建表段是 `t.bigint "shop_id", null: false`（鐵律 2 要求）。MySQL 的 SET NULL 會把**所有**參照欄設為 NULL，任一欄 NOT NULL 即拒絕建立約束（對抗驗證在本機 MySQL 8.4.9 以相同欄位形狀實測 ⇒ `ERROR 1830`）。
更嚴重的是：`db/schema.rb:1094` 的 `fk_inventory_items_product_variant_id` 是同型複合鍵，且 inventory_items.product_variant_id 是 `null: false` ⇒ **庫存 backfill 一落地，刪變體就多一道擋板**。
⇒ 這是一個裁定包（三選一：把 shop_id 移出外鍵／保留 RESTRICT 由應用層先 nullify 再刪／改軟刪），且它的射程必須涵蓋 backfill 造出來的那條 FK。`grep -c on_delete db/schema.rb` = 0（實測）。

**③ 「variants 由 list 改 connection 是純換形狀、畫面零回歸」是錯的。**
`app/graphql/types/product_type.rb` 的 `def variants; object.product_variants.order(:position); end`（position 序，欄位說明逐字寫「變體（position 序）」），而倉庫唯一的 connection 實作 `app/graphql/products/keyset_connection.rb:5/92/107` 把排序鍵**寫死**成 `(created_at, id)`，cursor 也編碼 created_at。直接改用它，變體順序就從 position 變成建立時間序——加選項後既有變體 position 會重排、created_at 不會。單變體時看不出來，會在選項編輯器落地那天才紅。
⇒ 這一包必須含 KeysetConnection 排序鍵一般化，量級不是「小 PR」。

**④ outbox 有寫入者、沒有發布者，而三份排程都沒有 relay 包。**
實測 `ls app/jobs` ⇒ 只有 `application_job.rb`；全倉 `EventOutbox` 只有兩處命中：模型自身與 `app/services/catalog/save_product.rb:431`。模型檔頭逐字：「發布端（relay job）在 M1 後續包落地；在那之前本表只進不出」。
而 `docs/specs/63 §A.2` 要求媒體衍生尺寸／EXIF／webp 走 outbox → job，`config/limits.yml:2661-2666` 的 `inventory_event_coalesce_window_ms: 1000` 與 `availability_flipped` 豁免註釋逐字說它「驅動快取 stamp、JSON-LD availability、IndexNow、feed。漏掉＝已售罄的商品在前台還能加入購物車」。
⇒ 這是一條跨三個方向的共用前置，三份盤點各自只看到自己那一半（庫存看到「事件產生端」、前台看到「快取失效」），合併時整條掉出去。

**⑤ 商品列表的「庫存」欄與「型別」欄現在是死的，後端做完也不會活。**
實測 `app/frontend/admin/pages/ProductsPage.tsx` 的 `PRODUCTS_QUERY` 只選 `nodes { id title status }`；同檔型別宣告卻有 `totalInventory` / `productType` / `vendor` ⇒ 三者值恆為 undefined，庫存欄恆走 untracked 文案、型別欄恆為「—」。`app/graphql/types/product_type.rb` 的欄位全集也沒有這三個。
⇒ 任何「庫存後端做完，列表就會顯示件數」的宣稱都不成立。ProductType 欄位與 query 選取必須列成交付物（並注意鐵律 7：加總必須與 /admin/inventory 同一份查詢）。

### 2.2 另外五條同樣改變包邊界的事實

**⑥ cache stamp 是七個維度、缺四欄，不是缺一欄。**
`config/limits.yml:2622-2629` 逐項為 products.updated_at／products.variants_updated_at／products.publications_updated_at／products.media_updated_at／shops.catalog_version／market_settings_version／price_list_updated_at。實測 `grep -cE "variants_updated_at|publications_updated_at|media_updated_at|catalog_version|products_updated_at" db/schema.rb` = **0**（五個欄名全部不存在，含 14 §F1 另外要求的 `collections.products_updated_at`）。`limits.yml:2630-2632` 還有 render 期自檢（`touched_sources ⊆ cache_stamp_sources`，開在 development/test/staging）⇒ 前台一建渲染管線，這個自檢要嘛紅、要嘛被關掉。

**⑦ 「前台可見件數」不是狀態過濾，發布讀取層沒有主人。**
`app/models/product.rb` 註釋逐字：「本方法只做第一層（狀態），呼叫端不得把它當成完整判準」「一個叫 `purchasable` 的 scope 只做了三層 AND 的第一層，**名字在說謊**」；`docs/specs/88-publication-model.md §1` 說前兩層屬 M1。三份排程沒有一包負責 Publishable × Publication 讀取路徑。系列的「後台 N 件（前台可見 M 件）」與前台的「未發布到管道的商品」共用同一層。

**⑧ TLS 沒有人負責，而它是前台上線的前提。**
實測 `config/deploy/nginx-chilllove.conf`：檔頭逐字「⚠️ TLS 尚未終結……本檔只聽 80，對應 Rails 側 `DISABLE_FORCE_SSL=1`」、`listen 80 default_server;`、`client_max_body_size 32m;`。`DISABLE_FORCE_SSL` 同時控 force_ssl／assume_ssl／session cookie secure 三處。

**⑨ 媒體排序會撞唯一索引，不能照系列那套抄。**
實測 media 表有 `uq_media_product_id_position` **unique**，而 collection_products 的同型索引 `ix_collection_products_collection_id_position` **不是** unique。所以 `sync_members!` 那種逐列 `save!` 重排在媒體上會在交換兩張圖時撞 1062，必須兩階段寫入或單句 CASE。

**⑩ Liquid PoC 的 drops 是樣本資料驅動，「drops 接 DB」這一層沒有主人。**
`poc/liquid-engine/drops.rb:95` 的 `collections` 回 `[]`、ShopDrop 全硬編、RoutesDrop 19 條無前綴常數、`render_ella.rb:18-38` 是手寫樣本商品。三份排程分別把「引擎生產化」與「多語言化 drops」排了，中間那層（Product/Variant/Image/Collection drop 改由 DB 供給）沒有任何一包負責。另：`pages` / `menus` / `menu_items` 三表已在 schema、無 model，而排程要開 `/{prefix}/pages/:handle` 路由。

## 4. 為什麼不是另外兩種排法

### 4.1 不是「可見成果優先」（每包必須在瀏覽器多出一個看得到的東西）

**它會怎麼排**：搜尋 → 挑選器 → 媒體上傳 → 影像管線 → Liquid 生產化 → **前台第 6 包** → ML-6 → SEO → 檔案庫 → 標籤 → 庫存 → 庫存 UI → 智慧系列 → 前台系列頁 → 規則編輯器 → 變體後端 → 選項編輯器 → 變體子頁 → 301 → sources 展開 → 影片 3D。21 個包裡 20 個可見。

**它會踩到什麼**（每條都有具體出處）：

1. **漏掉 variants list→connection**。m1-variants 盤點逐字要求「要嘛本包一併改、要嘛明文裁定維持 list——**不能兩邊各留一份**」，而它的第 16 包兩者都沒做。到第 16 包時消費者已從 1 個增為 3 個以上（前台 drops、媒體卡、庫存卡）。
2. **把兩條盤點記載的硬依賴宣告成「零硬依賴」**：第 11 包（庫存）漏掉 91-pit-register 逐字的「庫存線落地前必須先解此矛盾」；第 3 包（媒體）把四條硬依賴折進一個 L 包，其中 Active Storage 那條盤點註明「沒有任何一處記載這個裁定」，卻由排程代選了邊。
3. **自承要付一次資料遷移**：第 2 包先照現行 collectionSet 寫 collection_products，第 13 包若依 B-4 走 sources 模型就要退位成 collection_source_members。而 B-4 是**零代碼裁定**，提前取得的成本是 0——本方案把它放在第 2 包，這次遷移直接消失。
4. **第 6/7 包之間有一個索引窗**：第 6 包交付「第一次有店」，但「未發布語言前綴回 404」在第 7 包。L7 禁令保護的正是第一個可索引頁面那一組 URL。
5. **「Disk service 走完整條兩段式」驗不到問題**：Disk 的直傳端點在 Rails 上，檔案仍穿過 nginx 32m → puma，等於把兩段式要解的那個問題延到換 S3/R2 那天。
6. 第 2 包與第 20 包**都宣告交付手動成員排序**，責任歸屬重複。

**本方案吸收了它的三個手法**：基建包一律掛可見出口（第 9、16、26 包）；Liquid 生產化以後台 /admin/store 預覽當驗收面（第 30 包）；伺服器端搜尋單獨排第一（第 1 包）。

### 4.2 不是「依賴與返工風險優先」

**它會怎麼排**：14 條裁定綁成第 1 包 → limits 落鍵 → 一次改表 → Resolve → Modal → 搜尋 → 庫存三包 → 變體四包 → 媒體五包 → 系列六包 → 前台六包。買家可見的店在第 28 包。

**它會踩到什麼**：

1. **前 11 個包有 8 個零可見，最長連續黑暗是三個包（L+L+S）**。而部署目前仍是人工在伺服器跑 `scripts/deploy.sh`（CD-2 未落地）⇒ 連續無可見成果會讓「到底部署了沒有」無法自我察覺。
2. **14 條裁定綁成單一 PR**：任一條卡住（尤其需要使用者裁定的 B-4、Active Storage）就擋住六個包，逃生口只有五個 blocked_by 為空的包。本方案只把**三道決定遷移形狀**的裁定放在第 2 包，其餘貼在各自的擁有包之前。
3. **它自己承認製造了它最想避免的返工**：前台排到第 28 包才第一次消費後台資料模型，屆時若發現成員數與 discoverable 疊加不對、媒體 URL 形態撐不住、或變體渲染需要不同讀取面，返工發生在 M1 全部完成之後。它在 sacrifices 裡提出了對沖（一條薄的垂直切片）卻沒有排它——本方案的第 30 包就是把這個對沖排進來，並誠實標成 XL。
4. **把零依賴、CP 值最高的挑選器延後 19 格**，理由是「原型每列要顯示縮圖與金額・庫存」——那是展示層軟依賴被當成排序硬約束，而盤點對挑選器內部形態標的是 UNKNOWN。
5. 第 2 包標 S 卻含既有列的 sort_order 值遷移與前端 select 改動，量級與「修復只針對點名問題」的紀律兩面都對不上。

## 5. 風險與前提

**這份順序建立在七個假設上；標 🔴 的一旦不成立就要重排。**

|---|---|---|
| 1 | 🔴 「每一步都部署給使用者看效果」是**強偏好而非硬約束** | 第 20–22 包連續三個零可見（其中 22 是 XL 且不可拆）。若是硬約束，唯一的重排是把媒體塊（24–28）整個移到變體塊之前——包數不變、ProductDetailPage 仍被改三輪，只是把黑暗段換到媒體那一側。⚠️ 該指令的逐字措辭只存在於使用者本地記憶檔 `dev-mode-d40.md:29-30`，**不在倉庫內**，建議先複核 |

| 3 | 🔴 第 20 包的裁定不推翻鐵律 2 的複合外鍵慣例 | 若裁定「把 shop_id 移出外鍵」，就是放棄該表的複合租戶完整性，需要改鐵律 2 的白名單條文並過 `scripts/check-tenant-isolation.rb` |

**另外三條非假設性的風險**：

- **第 22 包是全排程最大的單點**（XL、不可拆、blocked_by 三項）。63:311-317 的事故形態（跳過階段 A ⇒ 全部 variant id 被換掉）在實作時「看起來很自然」地就會做錯。

- **第 33–35 包之間有一段可被索引卻無 canonical/sitemap/hreflang 的窗口**。緩解手段（robots disallow 或先掛非公開 host）必須在第 33 包的驗收條件裡寫明，不能靠記得。
