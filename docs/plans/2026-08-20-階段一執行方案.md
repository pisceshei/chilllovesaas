4. **備份鏈路實際啟用**：每日 `mysqldump --single-transaction --source-data=2`，保存 dump 內的
   binlog file／position，並從該座標起連續歸檔 binlog；備份須先加密，

### 6.2 單 PR 收斂協議（目標初始候選＋一次整合修復）

**產物頻率（D38／鐵律 21）**：每個可獨立合併 PR／原子工作包維護一份 tracked worklog，
初始候選與產物同 commit；只有 finding 真改 tracked tree 時，才在一次整合修復 commit 更新同一份。
每個工作包／PR 另維護一份四段式倉庫外本地 handoff，從研究到遠端終態都更新同一檔。下列步驟、
命令、查詢、等待、push 或驗收輪都不另建 worklog／handoff；no-tree disposition 與遠端狀態只更新
合規 PR／DECISIONS 落點與本地 handoff，不改 Git head。只有真正拆 PR、正式轉交或 rollback 後
另起恢復包才另建；附錄 A 每份 tracked worklog 只登一次。

1. `git fetch origin`，以最新 `origin/main` 為 base，在專案同層的工作區建立唯一 worktree 與
   分支 `m0/<包名>`（或對應里程碑前綴）；並行工作不得在共用 checkout 內 `checkout`。
2. 實作（涉外部語義先上網查證：官方文檔優先，附 URL＋取證日期；純內部一致性也用
   `git log -p` 追沿革——鐵律 16）。
3. **兩層驗證**：編輯期依改動只跑 targeted gate；準備候選 head 時凍結 tree，再把全部正典
   閘門逐支跑完並親眼看退出碼。正典入口 `bin/ci`；純文檔包最小必跑集＝
   `ls scripts/ | grep -E '^(check|test|lint)-'` 枚舉的 scripts 子集（總方案 §9.3 口徑）。Windows
   顯式 `PYTHONIOENCODING=utf-8`；cp950 的 UnicodeEncodeError 是輸出編碼，不冒充檢查失敗。
4. 鐵律 15 逐款，並依 PR 是否已存在分兩條可達成路徑：
   - **兩條路徑共用的 commit 後閘門**：commit 完成後、任何 push 前，必須再跑
     `ruby scripts/check-doc-claims.rb`，並親眼核對退出碼與 `Warnings`；非零或任何 warning 都
     fail-closed，修正後回第 3 步重凍結 tree 並重跑**全部**閘門，再補跑本閘門。未 push 時把
     修正收進同一候選 commit，不為 checker 結果另造遠端 head。該腳本以已提交 diff 為輸入，
     commit 前那輪不能證明新散文。
   - **首次交付（尚無 PR、PR 編號與基準 tag）**：倉庫外處置清單 → commit（含 worklog 三段與
     該工作單位入庫產物；handoff 四段只存本地、不進 commit）→
     `git fetch origin main`＋`git diff origin/main...HEAD`
     做 15.1 初始交付盤點；依 15.2 的明文豁免不呼叫尚不存在的 PR 端點 → push 分支 →
     `gh pr create` 取得編號 N → `git tag -f pr{N}-last-push HEAD && git push -f origin
     pr{N}-last-push`。該 tag 只記首次已發布 head，不得假稱存在上一輪修復 diff。
   - **整合修復 head（PR 與基準 tag 都已存在）**：須先完成第 5 步的原子攝取與第 6 步的批次
     修復，才可 commit。以 `pr{N}-last-push..HEAD` 兩點 diff 逐項核對凍結 ledger；push 前再
     全量重拉三個 paginated REST 集合與 paginated GraphQL `reviewThreads`，並在 head guards 間
     取得連續兩次相同的 canonical digest vector。任一集合／頁面未取、review `.body` 未讀、
     GraphQL 錯誤、分頁未走完、兩掃不穩定或同一受驗 head 新增 finding 都 fail-closed；
     新意見併回同一 ledger，完成後才 push 並更新遠端 `pr{N}-last-push`。
5. **監視並原子攝取**：每次 push 後（首次建立 PR 亦同）先執行
   `gh pr comment <N> --body '@codex review'`，保存留言 id；push 本身觸發 Claude Review，
   留言則明確觸發 Codex 對新 head 重審。**Claude、Codex 與 CI 都對 exact head 完成以前不得
   改檔**。0e／0f 尚未合併時，以 CLI 在同一個有界 deadline 內直接輪詢三方載體；已合併後只用
   0e evaluator 的版本化輸出。舊 `scripts/await-verdict.sh` 只屬已部署歷史／排隊訊號，不能證明
   C1、C3、雙清或可合併。CI 間隔執行 `gh pr checks <PR> --json name,bucket,link`；每一輪查詢
   **前後**都執行
   `gh pr view <PR> --json headRefOid --jq .headRefOid` 並要求等於凍結的 `HEAD_SHA`，任一不等就
   丟棄該輪 checks、以 head drift 非零終止；凍結 ledger 前再比一次。不得直接用無 deadline 旗標的
   `--watch`。**零 check 集合**在 deadline 內視為尚未開始並繼續輪詢；deadline 到仍為空才記
   證據未取得／C3=0，不得 vacuous all-pass，也不得把 no-check 回應誤歸成可立即終止的 API 故障。
   `pending` 繼續輪詢；`gh pr checks` 此時會回退出碼 8，消費者必須先解析已取得的 JSON bucket，
   不得讓 shell 非零處理把它當 API failure；JSON 未取得／不可解析才走 API failure。非空集合全部
   `pass` 是乾淨完成；無 `pending` 且有 `fail` 是完成的 CI
   finding，待兩 reviewer 完成後連 check 名稱／URL 凍結進 ledger，允許修法。`skipping`／`cancel`
   先對**同一 head 的 owning check** rerun 一次；仍 terminal non-clean 才保存兩次證據後轉人工。
   這是該 check 的 transport 恢復，不是因 Codex timing whole-run rerun Claude；API／
   deadline／head drift 才是未取得。合併前另用
   `gh pr view <PR> --json headRefOid --jq .headRefOid` 確認 `HEAD_SHA` 且全部 bucket 為 `pass`。
   官方 CLI 契約見 `docs/dev/external-facts.md` A11。若 current-head run 已實查命中
    validation-skip，不等待該 run 結構上不會產生的 Claude 判詞；改以**同一個明列 interval、
    max-polls、deadline 的有界預算**輪詢 exact-head Codex、機械 CI 與 skip run。每輪保存三項
    存在狀態、poll count 與 UTC elapsed；三者都存在後走第 10
    步，狀態仍是「Claude 證據未取得」。先碰到最大輪次或 deadline 時必須停止發新請求、在同一
    本地 handoff 列出 exact head、已取得／缺少的證據、poll count、elapsed 與最後錯誤，通知
    使用者後以非零終止；不得無限重試、不得前進合併。這個 deadline 與腳本契約一樣只界定等待
    預算，不冒充 API 單次呼叫的硬牆鐘上限，也不得從舊腳本繼承權威預設值。
   三方完成後全量拉 issues comments、review body、inline 與 GraphQL threads；每掃前後 guard
   `headRefOid`，四集合用 0e 版本化 serializer 計算 SHA-256，只有非零 settle interval 前後連續
   兩掃 digest vector 相同才按 comment／thread／根因去重成凍結 finding ledger。端點間插入
   finding、same-ID body edit、thread 變化或單掃一律 fail-closed。若 Codex 晚於 Claude 完成，**不得**因舊 workflow 內嵌
   evaluator 曾留下 `noreview`／C1=0 而 whole-run rerun Claude：0e／0f 前由 CLI 對凍結載體重算，
   0e／0f 後只再調用版本化 evaluator。這個 evaluator invocation 不產生第二則 Claude 判詞，也不
   新增 reviewer surface；head drift、任一 reviewer finding 或 CI non-clean 仍按本步矩陣處置。
   若 Claude 已貼判詞但只因 18.1④格式驗證失敗，沿用同一 exact head 最多整體 rerun 一次；不得
   以 commit／push 刷新格式。第二次仍畸形即保存兩次 run 與原判詞，轉第 10 步獨立人工審核，
   不建立第三次 attempt；缺標記、互斥結論與未知結構仍不得被評估器當通過。
6. 有未清意見 ⇒ 修法先查證，再做**一次根因批次修復**。射程包含被點名根因在同一
   producer／consumer／元件內的完整狀態矩陣與反向 fixture；不在影響圖內的同型既有問題搬
   `91` §3，不擋且不順手改。若 exact-head 終態只新增 ⚪，改在 PR body 寫 exact
   `DEFERRED_WHITE head=<40hex> comment=<decimal> item=<decimal>`，下一個本來會改 tree 的 PR
   首候選批量入籍，不為登記造 head。整批完成後回第 3 步，產生一個整合修復 head。
   第二個 finding-bearing head 仍見同根因時，禁止第三次沿用小修小推；在本地重建影響圖、狀態
   矩陣與 mutation，必要時拆成語義獨立 PR 後再產生候選，任務不中止。
7. 收斂到 **雙零**（Codex 零未清 ∧ bot 通過零未清）；Codex 的「零未清」只能由當前 head 的
   三個 paginated REST 集合、每則 review `.body` 與 paginated GraphQL `reviewThreads` 完成集合
   對帳，且兩次連續 canonical digest vector 相同後成立。current-head run 命中 validation-skip 者不宣稱達成本步，改走第 10 步的獨立人工
   審核停點。Codex finding review 由 REST review `.user.login` 精確等於
   `chatgpt-codex-connector[bot]` 且 `.commit_id == headRefOid` 綁 head；body 或以
   `.pull_request_review_id` 關聯的 inline／thread 有 finding 即為 finding review。connector 也可能在
   issues comments 發 finding；第一個非空行精確為 `## 驗收結論：需修改` 才是已觀測 finding 型，
   並只有獨立 `Reviewed commit:` 欄能以受控 parser 綁 head，一般散文 SHA 不讀。disposition 不抹除
   event time／endpoint-local ID。
   本倉庫實測乾淨 completion 是同一 bot 的 issue comment，fixture 鎖定兩型：A 型首行以精確
   前綴 `Codex Review: Didn't find any major issues.` 開頭，句點後同一行自由尾句不參與分類；
   B 型前兩個非空行精確為 `## 驗收結論` 與 `**未發現需要新增 inline 意見的重大問題。**`。
   A 型固定 About-Codex details 與 B 型確認敘述／checks 都屬同一 completion 說明，不用 prose NLP
   重分類；同一 comment 出現第二個頂層 verdict marker 時 ambiguous／C1=0。兩型都須有恰一個
   `Reviewed commit:`，只含 10–40 位十六進位且為完整 head 的前綴。PR #61 comment `5352954268`
   後有較晚 finding review `4980284182`，fixture
   必須證明先到 clean 會被較晚 finding 推回 C1=0。先後只比較 review `submitted_at` 與 issue comment
   `created_at` 的 UTC event time；clean 必須嚴格晚於最後 finding，缺值、解析失敗或相等都
   fail-closed，數字 ID 不跨端點排序。finding 集合為空時時間下界是負無限：有合法 completion
   才可通過，沒有 completion 仍 C1=0。缺／多／錯 ref、未知 envelope、
   作者自貼或只有 reaction 都 fail-closed；未來 clean REST review 也須先有 fixture 與權威
   exact-head 欄位才收。GraphQL 未解 threads 仍須為零。
   GitHub 官方允許 PR 作者或具 write 權限者 resolve，所以
   `isResolved=true` 只是必要狀態、不能單獨證明獨立驗收；review body 也可能承載 body-only finding，
   未讀或沒有較晚乾淨 completion 都 fail-closed（官方證據見 `docs/dev/external-facts.md` A9）。
   OpenAI 官方要求 Codex reaction 後仍發布 review 結果；reaction-only 不算 completion，缺可綁
   exact-head 的受控載體時 fail-closed 轉第 10 步人工審核（官方證據見同檔 A10；跨載體時間欄位
   見 A12）。REST
   inline 歷史總數只作攝取，不是未清數。證偽／裁定不修以合規落點處置；作者 resolve 不能取代
   更晚 reviewer completion。處置未改 tree 時只送一次同 head review 請求並作有界等待；官方未
   保證同 SHA 重複請求必產生新 review，deadline 內沒有更晚 completion 時 C1 保持 0，保存請求／
   reaction／review 水位後轉第 10 步獨立人工審核與人工合併，不再請求或造 head。禁止拿 unrelated、
   evidence、worklog、handoff 或空白 commit
   刷新 C1。0e evaluator 與 0f workflow 接線未各自合併前，舊 evaluator 不得授權代行合併；過渡期
   全部 PR 走第 10 步人工合併。
8. **合併前更新 base，再做四條件齊判定**：先 `git fetch origin main` 並保存
   `VERIFIED_BASE=$(git rev-parse origin/main)`；若
   `git merge-base --is-ancestor "$VERIFIED_BASE" HEAD` 不成立，先把該 base 合入工作分支，
   新 head 從第 3 步重新跑閘門、push 與雙方驗收。準備代行合併前再次 fetch；若
   `origin/main` 不再等於 `VERIFIED_BASE`，回本步重做，且編排器一次只收口一個合併。
   四條件仍依鐵律 18.1 的存在型判定（沒跑≠零意見）：①Codex 當前 head 全 surface 已取，最後
   finding 後有 reviewer-controlled 乾淨 completion，且 GraphQL 未解 review threads 為零
   ②bot 判詞通過且零未清；run-specific candidate 明取 `github.event.pull_request.head.sha`，並依
   同時提供 `verdict_comment_id` 與最終回讀 `.body` 的 `verdict_body_sha256`，0e 依 ID 重取／重算
   相等，再依 run id 複驗 `event=pull_request`、目標 `pull_requests[].head.sha` 與 run／job／
   check-run `head_sha` 都等於 candidate（最後三欄是本倉庫 canary，不是平台永久保證）
   ③candidate head checks 排除 workflow jobs `check_run_url` 指出的 evaluator 精確 self ID 後仍為
   非空集合且全部綠；only-self／錯或多 self ID／其他 pending 都 C3=0 ④0e／0f 現行 evaluator 對 exact head
   輸出 C1–C4 全通過；0e／0f 未合併時本步結構上不可達、只能人工合併 ⇒
   **代行合併**：`gh pr merge <N> --squash --match-head-commit <head_sha>`（D31 授權；
   `--match-head-commit` 只擋合併瞬間的 **head** 競態，不是 base 前置條件；base 的更新靠
   本步 fetch／比較迴圈，且不得宣稱消除最後一次比較後由外部合併造成的服務端競態。
   GitHub 旗標證據見 `docs/dev/external-facts.md` A3）。合併後刪遠端基準 tag：
   `git push origin :refs/tags/pr{N}-last-push`（15.4 尾步）。
9. CD 收口後：合併自動觸發部署 ⇒ `/up` healthcheck 綠 ⇒ 下一包；紅 ⇒ 自動 rollback＋
   開坑條目＋通知。
10. 18.3 清單 PR：未命中 validation-skip 者走到第 7 步雙零即停；實查命中者取得第 5 步三項
    存在證據後即停，並明載「Claude 證據未取得／未達雙清」。兩者都通知使用者獨立人工審核
    與合併，**不代行**；使用者未明文決定前不解鎖下游。

### 6.3 推送節奏

攢一批改動再推——連續推送會被 `claude-review.yml` 的 `cancel-in-progress: true`
砍掉前面的 review run（#58 曾一次浪費三個 run）。初始候選只 push 一次；等雙方＋CI 完成並
凍結 ledger 後，整合修復只 push 一次。若進 17.4 收斂模式，先在本地重建模型或拆包再推；
D38 起一個可獨立合併 PR 只維護一份 worklog、一個工作包只維護一份倉庫外 handoff；兩者都
不按驗收輪增殖。no-tree disposition／遠端證據不改 worklog，不得用 worklog、evidence、handoff
或空白 commit 刷新受驗 head／C1。

## §10 防重複犯錯硬清單（開工前必讀；鐵律 20 操作摘要）

1. **易腐數字必附複驗指令**，解釋括號裡也不例外——總方案 P-1 格同一格腐化過兩次
   （151→155→156）。寫法二選一：量測程序＋錨定 ref，或不寫數字改附指令（AGENTS §2）。
2. **新條目主鍵用內容錨（grep 式），禁行號**——`83` 號的 `A:<行號>` 引用全滅是前科。
3. **15.2 三端點全量拉、每則 review 的 `.body` 也要看、`--paginate` 必加**——
   「只看最後一則」與「只拉 inline 漏 body」各躺過兩輪真問題；inline 超過 100 則時
   不分頁會誤判成「沒給意見」。
4. **`git ls-files` 比對集合必加 `-c core.quotepath=false`**——非 ASCII 檔名輸出跳脫形式，
   不加會得到「全部都缺」的假結果。
5. **markdown 兩坑**：表格儲存格裸 `|` 必跳脫（會當場破表）；圍欄內不用 `**`（原樣顯示）。
   改完用「每列恰 N 個未跳脫 `|`」＋GitHub `/markdown` API 複驗；不能只數 `<td>`，還要
   選末欄 sentinel 並斷言該列最後一格渲染後仍含 sentinel 全文，避免超額 cell 被丟棄仍假綠。
6. **workflow 四坑**：`${{ }}` 讓整個 YAML 純量成為單一 template expression、受 21000
   字元上限（本機 `ruby -ryaml`／`bash -n`／action-validator 全過、只有 GitHub 判得出來）；
   未指定 `shell:` 即 `bash -e`（`set -uo pipefail` 關不掉）；改 workflow 的 PR 零判詞
   （伺服器端反竄改，靜默 skip 不 setFailed）；推後必確認 `Claude Review` run 出現。
7. **禁 fail-open 複驗式**——`git show <ref>:<path> | grep -c` 三重吞錯（ref 不存在時

  （<https://support.shoplineapp.com/hc/zh-tw/articles/204906315>）；付款狀態值域
  「未付款／已付款／付款失敗／超過付款時間／已部分退款」，其中兩個自動態、其餘可手動
  （<https://support.shoplineapp.com/hc/zh-tw/articles/115005489043>）。
- EasyStore：mark-paid 副作用＝"Your customer will receive an email notification once
  the order is marked paid."
  <https://support.easystore.co/en/article/what-should-i-do-when-i-received-an-order-pvy6uq/>
- **對我方尚未選案**：`unpaid → customer_reported(附件+留言) → merchant_verified → paid`
  四態、mark-paid 發 outbox 通知，以及自動態／可手動態分開標記，都是綜合三家資料後的方案
  合成，不是 Shopify 官方契約，也尚未獲使用者批准。S-14／`specs/112` 採用前須完成 Shopify
  測試店的顧客與管理員流程，逐個 transition 補證據並由使用者選案；不得因 SHOPLINE／EasyStore
  有相似能力就把這組狀態機寫成 CHILL LOVE 既定契約。

### 11.8 自動化營銷（→ `specs/113`，尚未建立，S-15 引入）

- Shopify Messaging 現行官方頁面四個表逐列計數為 **3＋2＋4＋2＝11** 個預建類型：
  abandoned browse／cart／checkout、welcome 單封／系列、drive-to-retail、thank you、upsell、
  win back、birthday、VIP。這是依當日表格重算的快照，不作永久數量契約。預設收件界線逐字
  "Marketing automations send only to customers
  subscribed to email marketing by default."；自訂／第三方路徑逐字 "you can instead create
  a workflow in the Shopify Flow app."（取證 2026-08-20；
  <https://help.shopify.com/en/manual/promoting-marketing/create-marketing/shopify-messaging/marketing-automations/create>）。
- Mailchimp 官方（取證 2026-08-20）把 Trigger 定義為 "An event or action that adds a contact
  to a flow."、Exit condition 定義為 "An event or action that removes a contact from a flow."，
  並列 rules／actions、Conditional Split、Percentage Split、Wait for Trigger；這只證明 Mailchimp
  自己的節點能力。Klaviyo 頁只證明一個以 flow filter 排除已下單者的 abandoned-cart 案例。
  <https://mailchimp.com/help/about-customer-journeys/>、
  <https://help.klaviyo.com/hc/en-us/articles/115002779411>
  兩頁不能證成「六件套是業界標準」，也不能替 CHILL LOVE 批准
  `trigger→condition→wait→split→exit→action` 架構。
- SmartPush（SHOPLINE 體系）：預設 6 模板（歡迎／棄購物車／瀏覽未購／棄單／沉睡／
  訂單確認）；棄單首封建議 30–60 分鐘、後續間隔 24–48 小時、共 3 封。
  <https://smartpushteam.zendesk.com/hc/zh-tw/articles/12203867127319>、
  <https://smartpushteam.zendesk.com/hc/zh-tw/articles/13503905890327>
- **對我方尚未選案**：trigger enum 候選 `cart_updated \| checkout_abandoned \| order_created \|
  subscribed \| date_based \| product_low_stock \| product_price_drop \| segment_joined`；
  limits 鍵候選：`automation.flow_filter_max_conditions: 10`、
  `automation.split_max_conditions: 5`、
  `automation.abandoned_cart_first_send_delay_minutes`。S-15／`specs/113` 採用前須取得 Shopify
  測試店證據、逐節點映射與使用者選案；競品能力與單一案例不能直接成為我方 enum、節點或上限。
- 存疑：Shopify 各範本預設等待時間未取得；SmartPush 觸發器全量清單文章 404。

### 11.9 通知中心（→ `specs/115`，尚未建立，S-15 引入）

- Shopify alerts 形態（取證 2026-08-20）：頂欄 notification icon＋未讀數；官方逐字支撐
  "toggle specific alerts as read or unread, or mark all alerts as read"，並說 alerts 會送給
  "staff with relevant permissions"。同頁現值列舉營運中斷預防、營運中斷、產品合規、
  與 Shopify 的金錢交易、長任務完成五種情境；這是供應商現頁情境快照，不是我方固定 enum。
  <https://help.shopify.com/en/manual/shopify-admin/shopify-admin-overview>
- 顧客通知：**預設不可停**（"Most customer notifications are sent automatically and
  can't be deactivated."），可停白名單只有六項（Order canceled／Order refund／Shipping
  confirmation／Shipping update／Out for delivery／Delivered）；客製兩層＝全域品牌層＋
  單範本內容層。
  <https://help.shopify.com/en/manual/fulfillment/setup/notifications/customer-notifications>
- **對我方證據邊界**：Shopify parity 已支撐 bell＋badge＋alerts feed＋逐條／全部已讀＋
  relevant-permission 過濾；S-15 可用這些已取證行為核對總方案 §5.1 #10 的 `openAlerts()`，但
  五種情境不得直接發布成我方 enum。逐範本 `can_deactivate` 與 default false 目前只是 schema
  候選；取得 Shopify 測試店逐範本完整流程證據並由使用者選案前，禁止寫入 `specs/115`。
  範本總數見 §11.0 更正 2（待實測，不沿用 45+）。

### 11.10 通路 feed／GMC（→ `specs/114`，尚未建立，S-15 引入）

- Google：必填核心集 `id/title/description/link/image_link/availability/price`＋brand
  條件必填；disapprove 三大類（識別碼／圖片（非服飾 ≥100×100）／價格可用性不符可觸發
  pre-emptive disapproval）；帳號級 suspension 存在。
  <https://support.google.com/merchants/answer/7052112>、
  <https://support.google.com/merchants/answer/13693497>
- 🔴 Content API 已關（見 §11.0 更正 3）⇒ **目標 API＝Merchant API (v1)**。
- Meta：必填集另含 `condition`；價格格式 "a number, followed by a space and then the
  3-letter ISO 4217 currency code"；image ≥500×500、≤8MB；排程 feed **最快一小時一次**
  （"don't support uploads more frequently than once per hour."），更快走 Direct Upload API。
  <https://developers.facebook.com/docs/marketing-api/catalog/reference/>、
  <https://developers.facebook.com/docs/marketing-api/catalog/guides/scheduled-feeds/>
- TikTok Ads catalog 的官方頁支援 feed URL 排程／手動／檔案上傳；TikTok Shop 第一方 Partner
  Center（取證 2026-08-20）逐字說 "The Product API helps sellers manage their product catalog
  at scale."，Methods and endpoints 頁另列 production endpoint
  `https://open-api.tiktokglobalshop.com`。這證明兩個產品面各自存在 feed 與 Product API 能力，
  **沒有證明 TikTok Shop 的 feed URL 存在或缺席**，該項仍為「未取得」。
  <https://ads.tiktok.com/help/article/create-manage-catalogs?lang=en>、
  <https://partner.tiktokshop.com/docv2/page/products-api-overview>、
  <https://partner.tiktokshop.com/docv2/page/methods-and-endpoints>
- **對我方證據邊界**：Google／Meta 的已取證格式差異支持 per-channel 欄位映射；TikTok Product
  API 只使 API adapter 成為候選，不能把所有通路先窮舉成互斥的「feed 型／API 型」兩種。
  S-15 須逐通路補齊能力矩陣後才選 adapter 抽象。已取證的 limits 鍵候選為：
  `feeds.google.image_min_px: 100`、`feeds.meta.image_min_px: 500`、
  `feeds.meta.min_fetch_interval_minutes: 60`。
  ⚠️ feed 的價格輸出走 `Money::Decimal`（十進位主單位字串）——與 PSP 的
  `Money::PspDecimal` 不是同一件事，鐵律 3 原文明令不得合併。

### 11.11 財務對帳（→ `specs/119`，尚未建立，S-15 引入）

- Shopify payouts：對帳報表構成 "transactions, fees, refunds, chargebacks, adjustments,
  and payouts"；Summary 七欄（Starting balance…Ending balance）；排程值域
  `daily \| weekly \| monthly` 且**法域可縮值域**（"merchants in Japan…can't have a
  daily payouts schedule"——正合 jurisdiction pack 形態）；只算 business days、
  週五六日的款併成一筆。
  <https://help.shopify.com/en/manual/payments/shopify-payments/payouts/payout-reconciliation-report>、
  <https://help.shopify.com/en/manual/payments/shopify-payments/payouts/schedule-payouts>
- Stripe（provider 研究，不是我方模型底表）：每筆資金移動一張 balance transaction
  （`net = amount - fee`，
  smallest currency unit 整數——**與鐵律 3 同構**）；pending→available 由 `available_on`
  驅動；🔴 "Each payout reflects your available account balance at the time the payout
  is created."（payout 只含 available 複驗成立）；`payout.reconciliation_completed`
  webhook＋`GET /v1/balance_transactions?payout=po_xxx` 反查成員。Balance Transaction object
  雖公開 Stripe 自己的 `type` enum，官方同頁明載 "To classify transactions for accounting
  purposes, consider `reporting_category` instead."（取證 2026-08-20）。
  <https://docs.stripe.com/api/balance_transactions/object>、<https://docs.stripe.com/payouts>
- **對我方尚未選案**：payout 對帳表的期初／期末餘額、activity、fees 與成員反查是候選呈現；
  Stripe provider taxonomy 不得直接作我方 ledger entry type，也不固定手抄 enum 數量。
  S-15／`specs/119` 採用前須保存可重跑的 Stripe 現行 enum 快照，並完成它與 CHILL LOVE
  事件的雙向覆蓋映射（包含非 Stripe 來源）；limits 鍵候選仍為
  `payouts.schedule_options`（per-jurisdiction）。
