your workflow must be in the default branch."、"use the `secrets` context to access secrets you've
created"；<https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow>、
<https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets>）。
因此 SSH 私鑰只由 workflow 從 GitHub Actions secrets 讀取，不落本機、不貼對話；CD-1a 雙清後
由使用者依 18.3 人工合併，再由本互動式工作階段用 CLI dispatch 並監視結果。

**CD-1b — 部署基礎與實測證據**：

1. 🔴 **第一件交付＝先加 `/.kamal/secrets` 的 ignore 規則，再產生任何檔**——現值
   `.gitignore` 零 `.kamal` 規則（複驗 `grep -n kamal .gitignore`，應在本包後命中）。
   樣板 `.kamal/secrets.example`（只含變數名）入庫；真檔永遠 ignore；**不得同名靠紀律區分**。
2. Dockerfile＋`bin/docker-entrypoint`（Rails 8 產生器為底）＋`config/deploy.yml`
   （尚未建立，CD-1 引入；Kamal 2；web＋Solid Queue worker＋MySQL accessory＋kamal-proxy TLS）。
3. 回寫 CD-1a dispatch 的伺服器初始化證據（Docker、防火牆、swap）；先立 **staging** 子網域，
   production 在 M3 後。
4. **備份鏈路實際啟用**：每日 `mysqldump`＋binlog 保留；備份須先加密，再傳到與 production
   主機不同故障域的 object storage，不能只留同機目錄。CD-1 開工輸入須裁定 provider／bucket／
   endpoint、費用上限與 retention；建議候選基線為 daily 7、weekly 4、monthly 12，未裁前不啟用
   可能產生費用的資源。CISA 的 3-2-1 原則明載 "Store 1 copy offsite"；MySQL 官方區分
   local／remote backup，並指出 logical backup 可跨機器還原（取證 2026-08-20；
   MySQL 原文 "Backups stored in logical format are machine independent and highly portable."
   （<https://www.cisa.gov/sites/default/files/publications/data_backup_options.pdf>、
   <https://dev.mysql.com/doc/refman/8.4/en/backup-types.html>）。
5. 從**異地加密副本**下載後完成一次最小還原演練（還原到臨時庫、驗 schema 與關鍵表列數、
   記錄耗時與 checksum）；同機副本演練不得冒充本項。演練通過之前不得開啟 production。
6. `docs/specs/120-deploy-pipeline.md`（尚未建立，CD-1b 引入）落庫，行內判準四件
   （總方案 §八 CD-1）：管線階段與通過條件／staging→production 開通序與 secrets 檔名紀律
   與 expand/contract migration 前提／`/up` 判綠與 rollback 界線／備份與還原演練程序。
   🔴 `config/deploy.yml`（尚未建立，CD-1 引入）能機械表達的鍵值**不得重抄**進該檔。
7. 🔴 migration 紀律自 CD-1 起：**expand/contract**。這是本專案的相容性契約，不等於已證明
   Kamal 的通用 rollback／schema 行為；總方案 §9.2 第 4 點的舊 `〔推論〕` 依鐵律 19 只算
   「未取得」缺口，CD-3 必須對實際 Kamal 版本＋本專案配置完成六步實測後，才能發布該範圍結論。

收口＝CD-1a 已合併且 bootstrap dispatch 成功，CD-1b 檔案與靜態檢查通過、伺服器初始化

## §6 全自動化執行迴圈（D31）

### 6.1 階段編排器（Codex 自管，無人值守）

```
載入 §2 序列 → 先把 umbrella 物化為具名子 PR → 取全部「無未完成依賴」的原子包
  → 每個並行包從最新 origin/main 建立**獨立 git worktree、獨立分支、獨立 PR**；
    禁止在共用 checkout 裡切換並行分支，也禁止兩包共用同一 worktree
  → 每包走 6.2 單 PR 迴圈 → 合併完成 ⇒ 解鎖其下游 → 取下一批
  → 合併後確認 worktree 無未提交內容，再移除該 worktree；分支／路徑不得重用
  → 直到階段一' DoD（§2 全表收口）⇒ 產出收官 worklog＋handoff ⇒ 通知使用者
停點只有三種（鐵律紅線，不是請示習慣）：
  ① 18.3 清單 PR：未命中 validation-skip 者在雙零後通知人工合併；實查 current-head run
     命中 validation-skip 者，取得 Codex＋CI＋skip 證據後以「Claude 證據未取得」通知獨立人工審核
  ② 17.3 例外：憑證紅線／破壞性操作／改鐵律本文／不可逆 schema 裁定／產生費用
  ③ §7 表列「做到該包時問」的裁定點
```

### 6.2 單 PR 迴圈（每個 PR 一律走完，無輪數上限）

**逐步 handoff 閘門（鐵律 21）**：下列每個編號步驟、步驟 4 的首次／後續分支、每次驗收
攝取與修復輪，以及任何逾時、阻塞、合併、部署或 rollback 結果，都是獨立交接節點。進下一個
節點前，先新增一份具名 handoff，詳細記問題與證據、執行命令／產物／驗證、未解事項與下一步
前置，並與該節點產物一起 commit。同一節點內的命令收在同一份文件，不逐命令遞迴建檔；
worklog、終態回寫與 `91` 附錄 A 對帳仍照原規則並存。

1. `git fetch origin`，以最新 `origin/main` 為 base，在專案同層的工作區建立唯一 worktree 與
   分支 `m0/<包名>`（或對應里程碑前綴）；並行工作不得在共用 checkout 內 `checkout`。
2. 實作（涉外部語義先上網查證：官方文檔優先，附 URL＋取證日期；純內部一致性也用
   `git log -p` 追沿革——鐵律 16）。
3. **全部閘門逐支親眼看退出碼**：正典入口 `bin/ci`；純文檔包最小必跑集＝
   `ls scripts/ | grep -E '^(check|test|lint)-'` 枚舉的 scripts 子集（總方案 §9.3 口徑）。
   Windows 座標：`PYTHONIOENCODING=utf-8`（cp950 的 UnicodeEncodeError 是輸出編碼不是
   檢查失敗）。
4. 鐵律 15 逐款，並依 PR 是否已存在分兩條可達成路徑：
   - **兩條路徑共用的 commit 後閘門**：commit 完成後、任何 push 前，必須再跑
     `ruby scripts/check-doc-claims.rb`，並親眼核對退出碼與 `Warnings`；非零或任何 warning 都
     fail-closed，修正後回第 3 步重跑**全部**閘門、另做 commit，再補跑本閘門。這是因為該腳本
     以已提交 diff 為輸入，commit 前那輪不能證明新 worklog／handoff 的散文。
   - **首次交付（尚無 PR、PR 編號與基準 tag）**：倉庫外處置清單 → commit（含 worklog 三段
     固定＋handoff 四段固定三件套）→ `git fetch origin main`＋`git diff origin/main...HEAD`
     做 15.1 初始交付盤點；依 15.2 的明文豁免不呼叫尚不存在的 PR 端點 → push 分支 →
     `gh pr create` 取得編號 N → `git tag -f pr{N}-last-push HEAD && git push -f origin
     pr{N}-last-push`。該 tag 只記首次已發布 head，不得假稱存在上一輪修復 diff。
   - **後續修復輪（PR 與基準 tag 都已存在）**：倉庫外處置清單 → commit → 15.1 以
     `pr{N}-last-push..HEAD` 兩點 diff 逐項核對 → 15.2 **全量重拉**（三端點都拉：
     `gh api .../issues/{N}/comments --paginate`＋`.../pulls/{N}/reviews --paginate`＋
     `.../pulls/{N}/comments --paginate`；🔴 每則 review 的 `.body` 本身也可能帶意見）＋照
     `docs/dev/m0-review-convergence.md`「重犯根因收斂稽核」的完整入口，以
     `gh api graphql --paginate` 全量讀 `reviewThreads` 並對帳 `isResolved`。任一集合／頁面未取、
     GraphQL 錯誤或分頁未走完都 fail-closed，不得宣稱已全收 → push＋更新遠端
     `pr{N}-last-push`。
5. **監視驗收**：每次 push 後（首次建立 PR 亦同）先執行
   `gh pr comment <N> --body '@codex review'`，保存留言 id；push 本身觸發 Claude Review，
   留言則明確觸發 Codex 對新 head 重審。未命中 validation-skip 的 PR 再用
   `bash scripts/await-verdict.sh <PR> <HEAD_SHA> [INTERVAL] [MAX_POLLS] [DEADLINE_S]`
   倒計時輪詢（參數契約見該檔檔頭；退出碼分義）。若 current-head run 已實查命中
   validation-skip，不用該腳本等此 run 沒有產生的 Claude 判詞；改輪詢 Codex、機械 CI 與 skip
   run，三者都存在後走第 10 步人工停點，狀態仍是「Claude 證據未取得」。
6. 有未清意見 ⇒ **只修點名處**（🔴 鐵律 17.2；修法先查證，驗收方事實陳述通常對、
   修法方向常錯）⇒ 重跑閘門 ⇒ commit ⇒ push ⇒ 重掛倒計時。⚪ 一律搬 `91` §3 不擋。
7. 循環到 **雙零**（Codex 零未清 ∧ bot 通過零未清）；Codex 的「零未清」只能由當前 head 的
   review、三個 paginated REST 集合與 paginated GraphQL `reviewThreads` 完成集合對帳後成立，
   不能以 review 外殼或 `isOutdated` 代替 `isResolved`。current-head run 命中 validation-skip 者
   不宣稱達成本步，改走第 10 步的獨立人工審核停點。
8. **合併前更新 base，再做四條件齊判定**：先 `git fetch origin main` 並保存
   `VERIFIED_BASE=$(git rev-parse origin/main)`；若
   `git merge-base --is-ancestor "$VERIFIED_BASE" HEAD` 不成立，先把該 base 合入工作分支，
   新 head 從第 3 步重新跑閘門、push 與雙方驗收。準備代行合併前再次 fetch；若
   `origin/main` 不再等於 `VERIFIED_BASE`，回本步重做，且編排器一次只收口一個合併。
   四條件仍依鐵律 18.1 的存在型判定（沒跑≠零意見）：①Codex 已完成本輪審查且零未清
   ②bot 判詞通過且零未清 ③全部機械 CI 綠 ④評估器貼出 1111 評估留言 ⇒
   **代行合併**：`gh pr merge <N> --squash --match-head-commit <head_sha>`（D31 授權；
   `--match-head-commit` 只擋合併瞬間的 **head** 競態，不是 base 前置條件；base 的更新靠
   本步 fetch／比較迴圈，且不得宣稱消除最後一次比較後由外部合併造成的服務端競態。
   GitHub 旗標證據見 `docs/dev/external-facts.md` A3）。合併後刪遠端基準 tag：
   `git push origin :refs/tags/pr{N}-last-push`（15.4 尾步）。
9. CD 收口後：合併自動觸發部署 ⇒ `/up` healthcheck 綠 ⇒ 下一包；紅 ⇒ 自動 rollback＋
   開坑條目＋通知。
10. 18.3 清單 PR：未命中 validation-skip 者走到第 7 步雙零即停；實查命中者取得第 5 步三項
    存在證據後即停，並明載「Claude 證據未取得／未達雙清」。兩者都通知使用者獨立人工審核
    與合併，**不代行**；使用者未明文決定前不解鎖下游。

### 6.3 推送節奏

攢一批改動再推——連續推送會被 `claude-review.yml` 的 `cancel-in-progress: true`
砍掉前面的 review run（#58 曾一次浪費三個 run）。每輪修復＝一個 commit 一次 push。

## §10 防重複犯錯硬清單（開工前必讀；鐵律 20 操作摘要）

1. **易腐數字必附複驗指令**，解釋括號裡也不例外——總方案 P-1 格同一格腐化過兩次
   （151→155→156）。寫法二選一：量測程序＋錨定 ref，或不寫數字改附指令（AGENTS §2）。
2. **新條目主鍵用內容錨（grep 式），禁行號**——`83` 號的 `A:<行號>` 引用全滅是前科。
3. **15.2 三端點全量拉、每則 review 的 `.body` 也要看、`--paginate` 必加**——
   「只看最後一則」與「只拉 inline 漏 body」各躺過兩輪真問題；inline 超過 100 則時
   不分頁會誤判成「沒給意見」。
4. **`git ls-files` 比對集合必加 `-c core.quotepath=false`**——非 ASCII 檔名輸出跳脫形式，
   不加會得到「全部都缺」的假結果。
5. **markdown 兩坑**：表格儲存格裸 `|` 必跳脫（會當場破表）；圍欄內不用 `**`（原樣顯示）。
   改完用「每列恰 N 個未跳脫 `|`」＋GitHub `/markdown` API 複驗。
6. **workflow 四坑**：`${{ }}` 讓整個 YAML 純量成為單一 template expression、受 21000
   字元上限（本機 `ruby -ryaml`／`bash -n`／action-validator 全過、只有 GitHub 判得出來）；
   未指定 `shell:` 即 `bash -e`（`set -uo pipefail` 關不掉）；改 workflow 的 PR 零判詞
   （伺服器端反竄改，靜默 skip 不 setFailed）；推後必確認 `Claude Review` run 出現。
7. **禁 fail-open 複驗式**——`git show <ref>:<path> | grep -c` 三重吞錯（ref 不存在時
   die(128) 被管道吞、pipefail 零鑑別力、Windows 冒號 MSYS 轉換）；用 `git grep -c <ref> --`。
8. **攢批推送**——`cancel-in-progress` 會砍掉未完成的 review run。
9. **全部聲明先取證才發布**（鐵律 19）：外部語義帶官方／第一方 URL＋日期＋英文原文；
   內部與執行狀態帶可重跑命令／精確版本證據。取不到只寫「未取得」＋缺口與取得法，
   不得以 `〔推論〕` 作實作輸入、驗收或發布結論；🔴 不引 AI 自動生成 wiki。
10. **宣稱「N 條全收」前先逐條數過**——「三條全部轉交」實為四條是最近一次前科；
    Codex 把溢出意見放 review body 的形態要專門檢查。
11. **白名單／閘門類交付必須同時寫「它擋不住什麼」**——不寫的話下一個人會以為封死了
    （25 網域白名單與內建預核准網域的前科）。
12. **「規則存在」≠「規則生效」**——熔斷閘門失效六輪、doc-claims 淺 clone 假綠都是前科；
    新 checker 必附 fixture 打紅證據＋確認 `config/ci.rb` 與 `ci.yml` 兩處都掛
    （parity 只保證單向）。
13. **送驗前先跑重犯矩陣，不把已知類型留給 bot 抽樣發現**——依 CLAUDE.md 鐵律 20 與
    `docs/dev/m0-review-convergence.md`「重犯根因收斂稽核」圈出適用類型，逐項執行固定處理與
    反向複驗；復發時記根因與防線失效。這不擴張 17.2，同型未點名處仍只登記 `91`。
14. **每個步驟先 handoff 再前進**——依鐵律 21，一個步驟一份不可覆寫的具名 handoff；
    詳細記問題與證據、做過的動作／命令、產物與驗證、未解風險及下一步入口。失敗、純讀取與
    阻塞同樣要交接；命令收在所屬步驟內，不把 handoff 收尾遞迴成新步驟。
