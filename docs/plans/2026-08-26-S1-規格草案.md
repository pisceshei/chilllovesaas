### 1.2 `publicationUpdate`

來源：`https://shopify.dev/docs/api/admin-graphql/latest/mutations/publicationUpdate`、`.../input-objects/PublicationUpdateInput`（取證 2026-08-26；🔴 **該路未展開版本選擇器，「latest 對應哪個版本號」＝未取得**，見 U-14）

**Mutation 描述（逐字）**：
```
Updates a Publication.

You can add or remove products from the publication, with a maximum of 50 items per operation. The autoPublish field determines whether new products automatically display in this publication.
```

**參數（2 個，皆標 required）**

| 參數 | 型別 | 官方預設 | 官方描述（逐字） |
|---|---|---|---|
| `id` | `ID!` | 無（required） | `The ID of the publication to update.` |
| `input` | `PublicationUpdateInput!` | 無（required） | `The input fields to use when updating the publication.` |

**`PublicationUpdateInput` 欄位（該頁 Fields 區塊**只有**這三個；無 `publicationId`、無 `name`、無 `catalogId`）**

| 欄位 | 型別 | 官方預設 | 官方描述（逐字） |
|---|---|---|---|
| `autoPublish` | `Boolean`（nullable） | **未取得**（🔴 該欄在 input object 頁**未標 default**，與另兩欄不同 — 不得外推 create 頁的 `false`） | `Whether new products should be automatically published to the publication.` |
| `publishablesToAdd` | `[ID!]`（list 可 null、元素非 null） | **`[]`**（頁面標 `default:[]`） | `A list of publishable IDs to add. The maximum number of publishables to update simultaneously is 50.` |
| `publishablesToRemove` | `[ID!]` | **`[]`** | `A list of publishable IDs to remove. The maximum number of publishables to update simultaneously is 50.` |

> 🔴 **50 的切分語義＝未取得**。官方兩句措辭不同（input object 頁 `simultaneously`／mutation 頁 `per operation`），皆未指明是 add 與 remove **各自** 50 還是**合計** 50。→ U-05。

**`PublicationUpdatePayload` 回傳欄位**

| 欄位 | 型別 | 官方描述（逐字） |
|---|---|---|
| `publication` | `Publication`（nullable） | `The publication that's been updated.` |
| `userErrors` | `[PublicationUserError!]!`（頁面標 non-null） | `The list of errors that occurred from executing the mutation.` |

**官方 Mutation Reference 範例（逐字）**
```graphql
mutation publicationUpdate($id: ID!, $input: PublicationUpdateInput!) {
  publicationUpdate(id: $id, input: $input) {
    publication {
      # Publication fields
    }
    userErrors {
      field
      message
    }
  }
}
```
> 🔴 官方範例的 selection set **只選 `field` 與 `message`，沒有選 `code`** — **不得**據此推論 `code` 不存在（`code` 在 `PublicationUserError` 頁確實存在）。

## §2 `ResourceOperation` 的完整形狀

來源：`https://shopify.dev/docs/api/admin-graphql/latest/interfaces/ResourceOperation`（latest 與 unstable 各抓一次，描述與四欄位**逐字一致**）、`.../enums/ResourceOperationStatus`（抓 2 次一致）、`.../objects/{AddAllProductsOperation,CatalogCsvOperation,PublicationResourceOperation,RowCount}`（取證 2026-08-26）

### 2.1 interface 本體

描述逐字＝`Represents a merchandising background operation interface.`

| 欄位 | 型別 | 官方描述（逐字） |
|---|---|---|
| `id` | `ID!` | `A globally-unique ID.` |
| `processedRowCount` | `Int`（nullable） | `The count of processed rows, summing imported, failed, and skipped rows.` |
| `rowCount` | `RowCount`（nullable） | `Represents a rows objects within this background operation.`（原文文法即為 `a rows objects`） |
| `status` | `ResourceOperationStatus!` | `The status of this operation.` |

> 🔴 語義落差已登記：`processedRowCount` 的描述**明文含 `failed` 列**，但 status enum 裡沒有失敗態 ⇒ 「列級失敗」與「操作級狀態」是兩層，官方**未說明**兩者如何對應。

### 2.2 三個實作型別

| 型別 | 官方 Implements | 描述（逐字） | 欄位 |
|---|---|---|---|
| `AddAllProductsOperation` | `Node`、`ResourceOperation` | `Represents an operation publishing all products to a publication.` | 與 interface 四欄逐字相同，無額外欄位 |
| `CatalogCsvOperation` | `Node`、`ResourceOperation` | `A catalog csv operation represents a CSV file import.` | 同上 |
| `PublicationResourceOperation` | `Node`、`ResourceOperation` | `A bulk update operation on a publication.` | 同上 |

> 🔴 **「恰三個」＝未正面窮舉**。interface 頁（latest 與 unstable）**沒有** `Possible types`／`Implemented by` 區塊。目前只有兩條**間接**官方索引，兩者都指向同一組三型：
> (a) `ResourceOperationStatus` 頁的「Fields with this enum」＝`AddAllProductsOperation.status`、`CatalogCsvOperation.status`、`PublicationResourceOperation.status`；
> (b) `RowCount` 頁的 References＝同樣這三型＋interface 本身。
> interface 的 `status` 為 non-null ⇒ 任何實作必有該欄位；故 (a) 若窮舉則實作集合即這三型。但**官方從未聲明該索引窮舉** ⇒ 不得寫成事實。取得方法見 U-13。
> ⚠️ 另有一路研究從 `Publication` 物件頁報稱 `PublicationOperation` union 的 possible types＝`AddAllProductsOperation`、`CatalogCsvOperation`、`PublicationResourceOperation`；但抓 `Publication` 頁的那一路明確登記「該欄位下方為摺疊的 `Show union types`，**未展開＝未取得**」。→ 矛盾 C-02。

### 2.3 `ResourceOperationStatus` — 「沒有失敗態」的正式回答

enum 描述逐字＝`Represents the state of this catalog operation.`；第二次抓取明確回報「Valid Values (**3 total**)」。

| 值 | 官方描述（逐字） |
|---|---|
| `ACTIVE` | `Operation is currently running.` |
| `COMPLETE` | `Operation is complete.` |
| `CREATED` | `Operation has been created.` |

**明確回答：**

1. ✅ **已被官方證實的部分**：`https://shopify.dev/docs/api/admin-graphql/latest/enums/ResourceOperationStatus` 的 Valid Values **全集恰為 ACTIVE／COMPLETE／CREATED 三個**（取證 2026-08-26，兩次獨立抓取一致，第二次自報 3 total）。其中**不存在 `FAILED`，也不存在 `ERROR`／`CANCELLED`／`PARTIAL` 之類的失敗或中止態**。這是「該 enum 頁列舉之全集」的正面事實陳述。
2. ❌ **未被官方證實的部分**：官方**沒有任何一句**寫「本 enum 沒有失敗態」，也**沒有**說明：①操作整體失敗時 `status` 回什麼；②`processedRowCount` 明文計入的 `failed` 列與操作級狀態如何對應；③`COMPLETE` 是否涵蓋「跑完但部分列失敗」。⇒ **「失敗如何表達」＝未取得**（U-16）。
3. 🔴 **官方文檔在這一點上自相矛盾**（同一家公司、不同層）：指南頁 `https://shopify.dev/docs/apps/build/product-merchandising/products-and-collections/sync-data` 逐字要求 `Poll the productOperation query with the operation ID from Step 1 until the status changes to COMPLETE or FAILED.` 與 `If FAILED, check userErrors for details.`，但同族的 `ProductOperationStatus` enum 頁與 `productOperation` query 頁都只列 `CREATED`／`ACTIVE`／`COMPLETE`。→ 矛盾 C-01；**輪詢終止條件必須以 schema 值域為準，不以散文為準**，否則會寫出永遠等不到的 FAILED 分支。
4. 官方**未給**狀態轉移圖、轉移條件、是否可逆、有無中止路徑、輪詢建議間隔或終態定義；enum 頁的呈現是**字母序**（ACTIVE→COMPLETE→CREATED），**不得**當作時序證據。

### 2.4 `RowCount`

描述逐字＝`A row count represents rows on background operation.`

| 欄位 | 型別 | 官方描述（逐字） |
|---|---|---|
| `count` | `Int!` | `Estimated number of rows contained within this background operation.` |
| `exceedsMax` | `Boolean!` | `Whether the operation exceeds max number of reportable rows.` |

> 🔴 `count` 官方明文是 **Estimated**（估計值），不是精確列數 ⇒ 拿它當進度百分比分母，官方只保證是估計。

### 4.1 `operation` 要不要落表？還是 `publications.operation_status` 一欄就夠？

**建議：v1 不新建 operations 表；但「一欄」不夠，最小可行是「狀態欄＋開始時刻／世代欄」兩欄，且加欄須先取得使用者裁定。**

理由逐條：

1. **不新建表，有本尊資料模型的正面依據**：`Publication.operation` 是**單數、可空**的 union 欄位（`A background operation associated with this publication.`，`.../objects/Publication`，2026-08-26）⇒ 本尊在**資料模型層**就保證「一個 publication 同時最多一個背景操作」。做成 `operations: [Operation!]!` 歷史清單反而偏離本尊，且鎖的唯一性就得靠應用層判斷而不是資料模型。
2. **`operation_status` 欄已存在，不需新 migration 加它**：`db/schema.rb` 的 `publications.operation_status`＝`varchar(16)`、nullable、**無索引、無 CHECK**；model 層有 `validates ... inclusion: { in: OPERATION_STATUSES }, allow_nil: true`。NULL＝無進行中操作，既有列全 NULL ⇒ **不需要資料回填**。
3. 🔴 **一欄不夠的具體理由＝中間態沒有出路**。倉庫已有明文教訓：`app/services/media_pipeline/process_file.rb` 檔頭逐字「raise 前把 status **還原成 `uploaded`**（審查 C7）：留在 processing 會變成沒有出路的孤兒態」。若 S1 把 publication 標成 `active` 後 worker 死掉，沒有回收機制就**永久鎖死該管道的逐商品切換**——商家看到本尊那句訊息永遠不消失且無法自救。可選的兩種既有回收形態：
   - `Events::Relay` 的 **`locked_at` 逾時回收**（`.where("locked_at IS NULL OR locked_at < ?", now - timeout)` ＋ `events.outbox_lock_timeout_s: 300`）→ 需要一個 `operation_started_at`（或 `operation_locked_at`）欄；
   - `MediaPipeline::ProcessFile` 的 **raise 前還原**（只擋得住同一 process 內的例外，擋不住 process 被 kill）。
   ⇒ **建議兩者都要**：逾時回收作底線、raise 前還原作即時。
4. **進度欄位（`processedRowCount`／`rowCount`）v1 不加**：我方 schema **完全沒有落點**，且只有在交付 `AddAllProductsOperation`（B1）時才需要。S1 若不做 add-all，加了就是第二個零消費者欄位。

### 4.2 「進行中的鎖」掛在哪一層？沿用哪個既有先例？

**先講前提（C-12）**：我方倉庫**現在根本沒有「逐資源發布切換」這個動作**——`resource_publications.published_at` 只在建立時被寫入（`Publications::Materialize` 的 `create!` 與 `insert_all`，加上兩支 migration 的原生 SQL），全倉零 UPDATE 路徑、零 publish／unpublish mutation。⇒ **鎖與被鎖的動作必須同批設計**，否則鎖是空的。

**建議的四層分工（每層都指名倉庫既有先例）：**

| 層 | 做什麼 | 沿用的既有先例 | 備註 |
|---|---|---|---|
| **① 序列化（承重）** | MySQL advisory lock：`GET_LOCK('chilllove:publication_op:<shop_id>:<publication_id>', wait)`，`ensure` 內 `RELEASE_LOCK` | 🔴 **`Collections::Rebuild#with_rebuild_lock`**（`app/services/collections/rebuild.rb`）。鎖名格式 `chilllove:<用途>:<shop>:<資源>`（<64 字元，MySQL 上限）可直接沿用 | 等待預算與重排延遲**必須引 `config/limits.yml`**（鐵律 6）。🔴 **不得挪用** `collection.rebuild_lock_wait_seconds`（語義不同），須在 `sales_channels:` 下新增鍵並補出處註釋。Rebuild 檔頭已記過「逐批列鎖只序列化單一批、不序列化整場」的事故（重現輸出 BASELINE members=[1282]／FINAL members=[]，兩場都回報 OK）——這正是為什麼需要 advisory lock 這一層 |
| **② 業務拒絕（model）** | 新增 `validate :publication_not_locked_by_operation`，讀 `publication.operation_in_progress?` | 🔴 **`ResourcePublication#future_publishing_supported_by_channel`**（`app/models/resource_publication.rb`）——它就是「讀 publication 上的旗標 → 不符就 `errors.add`」，與 S1 要的完全同構。**這就是「沿用倉庫既有形態而不是自創」的具體答案** | ⚠️ **擋不住 `insert_all`／`upsert_all`**（Rails 一律跳過 validation）——該限制已在 `resource_publication.rb` 與 `docs/dev/m2-publication-model.md` §6 明文登記。S1 必須在 dev doc **誠實登記「批量路徑不受守衛」**（鐵律 19.3），**不得**寫成「已鎖住所有寫入」（那句會被兩支原生 SQL migration 直接證偽） |
| **③ 對外錯誤（GraphQL）** | `userErrors{field,message,code}` ＋ HTTP **200**（鐵律 4①），typed code；被鎖住取 **`INVALID_STATE`**（`docs/research/28-api-contract.md` §6 明文「狀態機違規統一碼，全專案沿用」） | `Mutations::BaseMutation#user_errors_type`；既有 code enum 檔命名範式 `app/graphql/types/errors/*_user_error_code.rb`；`CodePools::COMMON`／`CONCURRENCY` | 🔴 **不得拋例外**。🔴 **不得自創碼**：`CONFLICT` 永遠不在共用池（只准出現在折扣線）；樂觀鎖一律 `STALE_OBJECT`。admin SPA 收到該 code 時要能把使用者**導回進行中的 operation**，不是只彈紅字 |
| **④ DB 約束** | `operation_status` 的 CHECK ／索引 | — | **S1 不做**，登記 `91` §2 待裁定（B8）。現況：值域約束**只在 model 層**，`update_all`／`insert_all`／raw SQL 全部繞得過 |

**🔴 鎖的射程硬邊界（不得外推）：**

- 本尊唯一的倉庫內證據錨是 `docs/research/82-admin-channels.md` §9.5d，訊息逐字 `Publishing for this catalog can't be changed while updates are in progress.`，它**只涵蓋「逐商品發布切換」**。同節另記本測試店的 `operation` 欄為 **null**（實測時沒有進行中操作可觀察）。
- ⇒ **不得**把鎖套到以下三條路徑，除非先取得新實測證據：
  1. **`Publications::Materialize.for` 的 `after_create` 路徑**（新建 Product／ProductVariant／Collection 時自動物化）。理由：本尊未實測；且該 callback 的契約是「出錯要炸掉整個 create 交易」⇒ 鎖若以 raise 表達，商家在管道同步進行中就**完全建不了商品**；若以靜默跳過表達，商品建成但**沒有發布列**，症狀是「前台看不到且不拋錯」——正是該服務檔頭記載的靜默事故形態。**兩種都不能預設**。→ U-21
  2. **`backfill_all!` 的回填路徑**（migration 期間本來就不該被商家操作擋住）⇒ 建議明文**豁免**，但必須寫成明文裁定，**不得靠「`insert_all` 剛好不跑 validation」這種偶然**。
  3. **四個 `dependent: :destroy` 級聯刪除入口**（`Publication`／`Product`／`Collection`／`ProductVariant` 各一）⇒ 見 §4.3。
- 讀取面（`ResourcePublication.published_exists_sql` 及其五個消費點）**不動**：本尊的鎖是否影響前台可見性＝未取得（U-22）。若真要動，注意三個 `PUBLISHED_ON_SQL` 都是**類別載入時凍結的常數**，要改成執行期組裝是三個檔的連動改動，不是一行。

**併發 spec 是必交付項**：S1 需一支 `publication_operation_concurrency_spec`（gated-threads 形態，Rebuild 的 F2 就是這樣重現出 advisory lock 缺口的）。目前 `operation_in_progress?` **零消費者、零 true 分支測試** ⇒ 沒有任何既有測試會在鎖被誤實作時轉紅，S1 必須自帶正反 fixture（進行中擋／`complete` 放行／`NULL` 放行／逾時回收後放行）。

### 4.3 `publicationDelete` 之後 `resource_publications` 怎麼辦？

**官方層：完全未取得**（三路一致）。`publicationDelete` 全文只有 `Deletes a publication.` 一句，沒有級聯說明、沒有 unpublish 說明、也沒有反向保證。

**我方現況**：`app/models/publication.rb` 有 `has_many :resource_publications, dependent: :destroy`；DB 層有 `fk_res_pub_publication_id`。

**建議：S1 維持 `dependent: :destroy` 不改，但必須把它從「預設行為」升格成「明文裁定」，並同批補四件事。**

理由：

1. **官方無反向證據**（既未說會、也未說不會）⇒ 我方自行裁定是合法的，但依鐵律 19 必須標為 **ours**，不得寫成「照抄本尊」。
2. **切分原則有外部旁證**（Saleor `channelDelete` 逐字：`Orders associated with the deleted channel will be moved to the target channel. Checkouts, product availability, and pricing will be removed.`，`https://docs.saleor.io/api-reference/channels/mutations/channel-delete`，2026-08-26）：**交易類資料（訂單）必須遷移不得刪；配置類資料（上架狀態、價格）可直接刪**。`resource_publications` 是**配置類**（可重建），不是財務憑證 ⇒ 刪除合理。
3. 🔴 **Medusa 的語義區分必須照做**（`https://docs.medusajs.com/learn/fundamentals/module-links/link`，2026-08-26）：`dismiss`（解除關聯，兩邊記錄都在）與 `delete`（連帶刪被連記錄）是**兩件事**。⇒ 我方硬性判準：**刪 publication 的關聯清理，絕不可連帶刪 `Product`／`Collection`／`ProductVariant` 本體**，且必須有**反向測試鎖死**。

**同批必補的四件事：**

| # | 事項 | 為什麼非做不可 |
|---|---|---|
| D1 | **反向 fixture**：刪 publication → 該 publication 的 `resource_publications` 歸零 ∧ `Product`／`Collection`／`ProductVariant` 本體筆數不變 | 見上第 3 點；沒有這條測試，未來有人加 `dependent: :destroy` 到 publishable 側就是靜默資料遺失 |
| D2 | **「不可刪的 publication」守衛** | 我方**目前沒有任何守衛**。Medusa 有 `canDeleteSalesChannelsOrThrowStep`（store 的 default sales channel 不得刪，違反直接 throw）；Saleor 有 `at least one channel is always required`。我方 `Shop#create_default_publication` 建的 online_store publication 若被刪，`Types::QueryType` 那唯一一處 `Publication.online_store` 會回 nil ⇒ `visibleProductsCount` 全面回 null。🔴 **但我方沒有 `default_publication_id` 欄**（Medusa 是 `Store.default_sales_channel_id` 單欄）⇒ **需要裁定**：用 `channel_handle == online_store` 判定，還是加欄 |
| D3 | **`channels` 側的連動** | `add_foreign_key "channels", "publications", column: [shop_id, publication_id], ...` 已存在。刪 publication 會撞這條 FK ⇒ S1 必須先確認 `Channel` 側的 `dependent` 行為（S0 的 `20260826070000` 另有「找不到對應 platform_app 就跳過」的路徑，會留下**沒有 channel 的 publication**，而 `Publication.online_store` 走 `joins(:channel)` ⇒ 那些 publication 在該入口根本查不到） |
| D4 | **cache stamp** | 🔴 **實際缺口**：`dependent: :destroy` **不會** bump `products.publications_updated_at`。刪 publication 會讓大量商品的前台可見性改變，但快取不失效**而且不拋錯**。S1 必須在刪除路徑顯式呼叫既有的 `Product.bump_publications_stamp!`。⚠️ 該方法刻意用 `update_all` 的**字串形式**避開樂觀鎖遞增（`app/models/product.rb` 註釋逐字：hash 形式「會把商家**開著的編輯表單直接作廢**（`StaleObjectError`）」）——**照抄 hash 形是災難** |

### 4.4 `publishablesToAdd`／`publishablesToRemove` 的批次上限要不要跟？

**建議：跟 50。進 `config/limits.yml` 的既有鍵 `sales_channels.publication_bulk_products_max`（值已是 50，出處註明 R13／`docs/research/82`，help 源）。**

逐條理由與配套：

1. **不新建 `markets.publication_update_batch`**。`config/limits.yml` 根本沒有 `markets:` 頂層鍵；同值兩鍵違反鐵律 6 的單一來源精神。處置：在 `docs/research/90-blueprint/11-markets.md` 的落地清單旁註明「已由 `sales_channels.publication_bulk_products_max` 承接」，並在 `docs/DECISIONS.md` 留裁定條目（目前 `grep publication_bulk_products_max docs/DECISIONS.md` 無輸出＝無裁定）。
2. 🔴 **切分語義 fail-closed 取「合計 ≤50」**（`publishablesToAdd.size + publishablesToRemove.size <= 50`）。官方兩句措辭不同且都未指明切分（C-04／U-05）⇒ 取較嚴的一側，並在 spec 明文標為 **ours 加嚴 ＋ 官方未取得**。取得證據後（測試店以 add/remove 各 26 個實測）再放寬。
3. **與 `api.array_input_max_items: 250` 的關係**：50 更嚴者勝出。這屬 `docs/research/90-blueprint/15-platform-core.md` 所稱「具名例外」的**反向**（更嚴）情形 ⇒ S1 必須在 `docs/research/28-api-contract.md` §0.3 明文登記這個例外，否則兩個鍵各跑各的。
4. **超限的錯誤碼**：從 `CodePools::COMMON` 取 **`TOO_BIG`**。
   - 🔴 **不得自創 `LIMIT_EXCEEDED`**（28 §0.3.2 的值域紀律：各 enum 的值必須從共用池取）。
   - 🔴 **不得照抄 `PUBLICATION_UPDATE_LIMIT_EXCEEDED`**：該 code 與 50 的綁定關係官方**從未陳述**（U-12），照抄等於把推測寫成事實。
5. **`userErrors.field` 的 path**：若照抄本尊 `publicationUpdate(id:, input:)`，path 第一段是剝殼後的 `publishablesToAdd`；若走 28 §0.3.4 的具名參數，第一段是參數名。**兩種都要帶十進位裸字串的陣列索引**（28 §0.3.1）——50 筆一起送時，帶索引是前端定位「第幾筆出錯」的唯一方式。此點須與 C-18 的裁定一併定案。
6. 🔴 **批次寫入的實作陷阱**：50 筆很自然會寫成 `insert_all`／`upsert_all`，但那條路徑**繞過唯一那道租戶守衛**（`ResourcePublication#publishable_belongs_to_same_shop`；多型 `publishable` 側**無 DB 外鍵**，`acts_as_tenant` 也明確排除多型外鍵驗證）。⇒ S1 那條路徑**必須**自行做 shop_id 一致性檢查，或明文選擇逐列 `create`。**S1 是第一個真的會踩到 B7 這個已登記缺口的批次寫入者。**
7. **重複 publish 必須是 no-op success**（官方逐字：`If the variant is already published to that publication, the mutation succeeds with no change.`，已在 `docs/plans/2026-08-26-第12包執行規格.md` §2.4 取證完畢）⇒ 批次寫入要用 **upsert 語義**，DB 兜底是既有的 `uq_res_pub_target` 唯一索引（`shop_id, publication_id, publishable_type, publishable_id`）。與第 6 點張力：upsert 又繞過 validation ⇒ 建議「逐列 `find_or_create_by` + 唯一索引兜底」或「先查後批次插入 + 顯式 shop_id 檢查」，**在 spec 明寫選了哪一種與為什麼**。
8. **冪等**：`config/limits.yml` 的 `idempotency` 區塊明文把 `publishablePublish` 這類**宣告式覆寫型**「刻意不列入」強制冪等（併發防線是 `lock_version` 樂觀鎖）。但 **`publicationCreate` 是建立型**（重放會憑空多出一個實體，`docs/specs/63-product-data-flow.md` §A.3 的判準）⇒ 它**應該**進 `required_for_catalog_create`。🔴 這需要 **S1 明文裁定**（且同步更新 CI 的無條件斷言），**不得**沿用「publishablePublish 不強制」推導。另有 `idempotency.bulk_key_per_row: true`（「Bulk 操作每個 JSONL row 一把獨立 key，絕不共用」）——若 S1 的批次要走冪等，須遵此。
