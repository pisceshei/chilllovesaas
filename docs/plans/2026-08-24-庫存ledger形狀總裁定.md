## 一、核心裁定：ledger 行的身分

**一列 ＝ 一個 (group, inventory_level) 的異動，帶六個 leaf delta 欄。**

```
inventory_adjustment_groups   （批次頭；＝本尊 InventoryAdjustmentGroup）
  └─ inventory_adjustments    （ledger 行；一列 = 該 group 對某個 level 的全部 delta）
       available_delta / committed_delta / reserved_delta /
       damaged_delta / safety_stock_delta / quality_control_delta   ← 六個 leaf（實體欄）
       unavailable_delta  = STORED GENERATED（四個不可售 leaf 之和）
       on_hand_delta      = STORED GENERATED（六個 leaf 之和）
       incoming_delta       ← 實體欄，不進任何 generated 式（本尊明文不計入 on_hand）
```

**為什麼是這個形狀而不是「一列一個 name」**：

| 需求 | 六 delta 欄一列 | 一列一 name |
|---|---|---|
| 歷程頁（一列多欄） | **直接就是**顯示形狀 | 要把多列 pivot 回一列 |
| API `changes[]`（每 name 一筆） | 讀取期展開非零 delta（含 generated 的 on_hand/unavailable） | 直接就是 |
| 狀態間移動（damaged→available） | **一列**（兩個相反符號的 delta），語義自含 | 兩列，配對關係要靠額外欄位 |
| 對帳六式（SUM(delta)=現值） | `SUM(available_delta)` 一句 SQL | 要先按 name 過濾 |
| 冗餘 | **零**（衍生量全是 generated） | on_hand 列與 leaf 列冗餘，可漂移 |

讀取期展開的方向與 `inventory_levels` 的 generated column 同一原則：**衍生量永不落庫，投影時計算**。
API 回 `on_hand` change 是投影，不是儲存。

**唯一索引**：`uq_inv_adjustments_group_level (shop_id, inventory_adjustment_group_id, inventory_level_id)`。
同一呼叫對同一 (item, location) 出現兩筆 change ⇒ **reject（userError `DUPLICATE_INVENTORY_ITEM` 語義）**，
不合併——合併會讓 per-change 的 `ledgerDocumentUri` 與 `quantityAfterChange` 失去落點。
⚠ 本尊對此的實際行為未查到 ⇒ fail-closed 取嚴，登記 **V-96.1**。

## 三、表形狀（migration 藍圖；🔴 仍不寫 migration，見 §六）

**`inventory_adjustment_groups`（新表）**
```
shop_id / idempotency_key / reason(限 95 §3 的 17 值) / quantity_name(呼叫層的目標 name)
reference_document_uri / reference_type + reference_id(ours：內部來源多型)
staff_member_id / client_source / changes_count / created_at
UNIQUE (shop_id, id)、UNIQUE (shop_id, idempotency_key)
INDEX (shop_id, reference_type, reference_id)、(shop_id, created_at)
```

**`inventory_adjustments`（改）**
- 刪：`idempotency_key`（＋其唯一索引）、既有 `on_hand_delta` 實體欄、`unavailable_delta` 實體欄
- 加：`inventory_adjustment_group_id`（NOT NULL）、四個 leaf delta（reserved/damaged/safety_stock/quality_control）、
  `ledger_document_uri`、`position`（group 內順序，供 API changes 排序）
- 改：`unavailable_delta`／`on_hand_delta` → STORED GENERATED（各自**直接引用基礎欄**，
  不得 generated 引用 generated）
- 唯一索引：`(shop_id, inventory_adjustment_group_id, inventory_level_id)`

**`inventory_levels`（改；沿用 on_hand 裁定，無對撞）**
- 加四個 leaf 實體欄；`unavailable`／`on_hand` → STORED GENERATED；
  `(shop_id, on_hand)`／`(shop_id, available)` 索引；`incoming` 維持實體、不進 generated 式。

## 四、由實機證據直接定案的三件事

1. **期初庫存＝物化的第一列**（實機「Initial inventory (+9)」）。⇒ 建店／建變體的 backfill
   寫的是一個 `reason: correction`（或專用 `initial`？——本尊 Activity 顯示「Initial inventory」，
   API 的 17 值 reason 裡**沒有** `initial` ⇒ 待查它映射到哪個 reason，登記 **V-96.3**）的 group。
   **180 天修剪的 checkpoint 方案照此形態**：修剪時寫一列期初餘額 group，六個 leaf 各帶期初值。
2. **`quantityAfterChange` 有 UI 落點**（「increased by 1 for a total of 10」）⇒ 讀取期以
   window running-sum 提供，`Inventory::Reconcile` 的斷言含「running-sum 期末值＝levels 現值」
   （八式：六 leaf ＋ group.changes_count ＋ running-sum 期末）。
3. **歷程頁 7 欄**（Date/Activity/Created by/Unavailable/Committed/Available/On hand，
   無 Incoming、無獨立 reason 欄——reason 就是 Activity 標籤，參考文件在 Activity popover）。
   ⇒ 排程第 18 包（調整記錄頁）的欄位契約以此為準；71-R8-DOC1 的「歷史 8 欄」與本次實測的
   7 欄不一致，**以本次親自點擊為準**，差異登記 **V-96.4**（可能是欄位設定或方案差異）。

## 四b、Activity 標籤對照（help 雙源補充，取證 2026-08-24）

> URL：`https://help.shopify.com/en/manual/products/inventory/adjusting-inventory/adjustment-history`

**reason → Activity 顯示標籤**（歷程頁的 Activity 欄不是 reason 識別字，是翻譯後的標籤）：

| reason（API） | Activity（歷程頁） |
|---|---|
| `correction` | Inventory correction |
| `cycle_count_available` | Inventory manually counted |
| `received` | Inventory received |
| `restock` | Items restocked |
| `damaged` | Damaged |
| `shrinkage` | Theft or loss |
| `promotion` | Promotion or donation |
| （未選 reason） | **Manually adjusted** |
| 系統事件 | Data correction ／ Transfer created ／ Removed from location ／ Reservation created/updated/deleted |

三條要點：

1. 🔴 **help 與實測有一處出入，實測為準**：help 說 `Adjust by` 的 Activity 顯示
   「Moved to [destination]／Moved from [origin]」，但本輪實測（94 §2.5）用 `Adjust by`
   ＋ reason `Received`，Activity 顯示的是 **reason 標籤「Inventory received」**。
   ⇒ 有 reason 時 reason 標籤優先於移動標籤（或 help 已過期）。我方實作照實測：
   **有 reason 顯示 reason 標籤，無 reason 且為移動時才顯示 Moved to/from**。登記 **V-96.5** 待更多樣本。
2. **「未選 reason」在歷程頁顯示「Manually adjusted」**——與 95 §3「`correction` 是預設」**不衝突但要分清層**：
   UI 的 Add reason 未選時 API 端落 `correction`（help 明文 default），
   「Manually adjusted」是**更舊的或 bulk 路徑**的顯示形態。實作時以 95 §3 的 default 為準。
3. **保留 180 天**：help 逐字「You can view only the last 180 days」＝`limits.inventory.adjustment_history_retention_days: 180` 的出處再確認。
4. **欄位數**：help 列 **8 欄**（含 Incoming），本輪實測 **7 欄**（無 Incoming，該品項 incoming 恆 0）。
   ⇒ V-96.4 的方向：Incoming 欄很可能**條件性出現**（有採購單／轉移才顯示）。
   第 18 包的欄位契約要做成「Incoming 條件性欄」而不是二選一。
5. 「Initial inventory」**不在** help 的 Activity 清單裡 ⇒ 它是 app 建立或較新的標籤，V-96.3 維持開放。

## 五、與既有裁定的關係

- on_hand 裁定的 §1（levels 的 generated column）**全數沿用**；其 `inventory_adjustments` 段
  被本文 §三**取代**（該段寫於不知道 group 表的情況下）。
- 冪等裁定的 group 表**沿用**，但 `ledger_document_uri` 從 group 移回 ledger 行、actor 改兩欄。
- `mutation_kind`（adjust/move/set/activate）**保留在 group 頭**——它是稽核與除錯欄，
  與 reason 正交（同一個 reason 可來自不同 mutation）。
