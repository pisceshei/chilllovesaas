### 1.3 🔴 明確回答三個提問

**Q1：`isPublished` 的語義在兩者間是否真的相反？**

**答：在「已排程但尚未到點」這一個狀態上，是真的相反；在其餘狀態上不是相反，而是「一邊有值、一邊沒有這一列」。**

| 資源實際狀態 | V1 `isPublished` | V2 `isPublished` |
|---|---|---|
| 已發布（publishDate ≤ now） | **true** | **true** |
| 🔴 已排程、尚未到點（publishDate > now） | **true**（"Also returns true if ... scheduled to be published"） | **false**（"then the resource publication is **staged** to be published"） |
| 既未發布也未排程 | **false**（"neither published nor scheduled"） | **該列不存在**（V2 "can't be unpublished. It must either be published or scheduled to be published"） |

⇒ 官方原文分別是上表引號內兩句，逐字見 §1.1。
⚠️ **兩處措辭差異照登記、不代為調和**：V2 的**欄位描述**用 `staged to be published`，V2 的**物件描述**用 `scheduled to be published`；官方沒有任何一句把兩詞等同 `[?]`。撰寫我方註釋時**不得**把兩詞合併成單一術語。
⚠️ 「相反」這個字是**由兩段逐字描述導出的判斷**，不是官方原文；我方文檔寫「相反」時必須同時附上兩段原文（鐵律 19.1）。

**Q2：未發布時 V1 的 `publishDate` 是不是回 epoch？**

**答：官方有正面陳述，且型別是 non-null。**
`[S]` 逐字："If the product isn't published, then this field returns an epoch timestamp."（<https://shopify.dev/docs/api/admin-graphql/latest/objects/ResourcePublication>，2026-08-26）

三項附帶事實，缺一不可：
1. 型別是 **`DateTime!`** ⇒ **不存在 null 第三態**，客戶端不得用 `if (publishDate)` 或 `publishDate == null` 判斷未發布。
2. ⚠️ 官方該句主詞寫的是 **`the product`**（不是 resource），與物件其餘描述用詞不一致。**逐字登記，不得外推**成「只適用產品」或「適用所有 resource」任一側。
3. 🔴 **epoch 的確切字面值、時區與序列化格式（是否為 `1970-01-01T00:00:00Z`）＝`[?]`**。官方只寫 "an epoch timestamp"。**不得**在我方規格或測試 fixture 裡寫死 `1970-01-01T00:00:00Z`。

**Q3：兩個投影並存的原因？**
**官方從未解釋** `[?]`。已窮盡路徑：changelog 首頁列表、`?search=` query param、site: 搜尋、2020-10 release notes 全文、community.shopify.dev 鏡像（HTTP 404）。
可用的兩條**事實**（非理由）：
- 引入時間＝**2020-10 版**，release notes 的 "Product status" 分類下逐字兩行：`[C]` "ResourcePublicationV2 object was added"、"ResourcePublicationsV2 connection was added to type Publishable"（<https://shopify.dev/docs/api/release-notes/previous-versions/2020-10>，2026-08-26）。同段對 rationale 追問回覆＝NO RATIONALE SENTENCE PRESENT。
  🔴 「因為引入 ProductStatus 所以需要 V2」是**推論**，鐵律 19.3 禁止當結論；只能寫成「同版釋出的時間共現」。
- 「V2 是 V1 的 deprecation 過渡」這個假說**已被反證**：兩者在 latest(2026-07) 皆無 deprecation 標記，並存已逾六年 `[S]`。**不得寫入規格**。
- 官方**隱性**指引：《Product and variant publishing》指南通篇只教 V2，raw .txt 字串檢查回報 `resourcePublications`（無 V2 後綴）不出現於全文 `[G]`；2026-07 changelog 明文要 channel app 讀 `ProductVariant.resourcePublicationsv2` `[C]`。
  🔴 但**官方從未寫過**「resourcePublications is legacy」或「use V2 instead」的正面句 `[?]` —— 我方文件**不得代寫這句**。

### 4.A 🔴 投影選型：V1 還是 V2？還是兩個都出？

**建議：S2 只出 V2 投影（`resourcePublicationsV2` 形態），不出 V1。**

理由（逐條可查）：
1. **admin SPA 是唯一客戶端**（鐵律 4 的 ours 註）。我方沒有第三方 channel app，V1 的存在理由（`Channel.*PublicationsV3` 這條線 `[S]`）在我方不存在。
2. V1 帶兩個**已知誤用源**：`isPublished=true` 涵蓋排程態、`publishDate` 用 epoch 哨兵（`DateTime!`）。兩者都是「測試在非排程態下 100% 綠」的形態（見 §4-B）。
3. 官方指南只教 V2 `[G]`，2026-07 changelog 對 variant 也只指向 V2 `[C]`。
4. V2 的 `catalogType` 是唯一能表達 **MARKET / COMPANY_LOCATION（B2B）目錄**發布狀態的路徑 `[S]`；V1 沒有。鐵律 11 的 per-jurisdiction 與 B2B 路線日後只能走 V2。

🔴 **這個建議有一個前置未取得，必須先解**：V2 連線是否也有 `onlyPublished` 參數（`[?]`，兩路報告不一致，見 §1.2）。
- 若 **有** ⇒ V2 是 V1 的功能超集，只出 V2 無缺口，本建議直接成立。
- 若 **沒有** ⇒ V2 無法表達「只回目前已發布」，我方需自己補一個等價參數，且那是 **ours 加嚴**，必須在 `docs/research/28` 登記。

**登記義務（不得省略）**：
- 在 `docs/research/28` 明文登記「我方只實作 V2 語義投影，不提供 V1」為 **ours 偏離**，並附 §1.3 的兩段官方原文作為「為何不能兩個同名欄位並存」的理由。
- 🔴 **不得**寫「官方建議改用 V2」——官方無此句 `[?]`。只能寫「官方指南只教 V2」。
- 🔴 命名紅線：**不得**把 `ResourcePublication#published?` 直接命名成 `isPublished` 或 `available`。`docs/specs/88` §3 已明文它**只是三層 AND 的第二層** `[M]`；第三層（catalog）在 S10 之前恆真，S10 落地時語義會靜默改變。GraphQL 欄位 description 必須寫明「不含 catalog 層」。
- 若日後要補 V1 相容面：**必須用不同型別承載**（`ResourcePublicationRow` vs `ResourcePublicationV2Row`），不得共用同一個 struct 或同一個 `is_published` 欄名 —— 形態與鐵律 3 的 `Money::Storage` / `Money::PspMinor` 型別隔離同構。

### 4.B 排程要不要做？「到點生效」用哪一種？

**答：要做語義與規則面；「到點生效」＝查詢時動態判定，我方已經做完了。不新建任何翻狀態的 job。**

**現況（`[M]`，可重跑）**：
```
app/models/resource_publication.rb:38
  PUBLISHED_SQL = "%<a>s.published_at IS NOT NULL AND %<a>s.published_at <= :at"
app/models/resource_publication.rb:98-100
  def published?(at: Time.current) = published_at.present? && published_at <= at
```
`published_exists_sql(target)` 是唯一 SQL 產生處，`VISIBILITY_TARGETS` 恰 5 鍵（product / collection / variant / variant_of_pv / product_of_p）。`Product.purchasable/.discoverable/.published_on`、`Collection.published_on/.visible_member_count_select/.with_member_counts`、`ProductVariant.purchasable_on` 全部吃 `at:` 並傳進 `:at` bind。`spec/models/publication_visibility_spec.rb:120-144` 有 SQL 側／Ruby 側 parity 測試。

**這代表什麼**：
1. 🔴 **可見性面已經完成**。到點那一刻資料庫不需要任何寫入，商品自動出現在查詢結果裡。**任何「掃描 due 的列並 UPDATE 成已發布」的設計都是自創形態＋鐵律 7 違反**（製造第二個事實來源）。
2. Saleor 走同一條路 —— `[外部]` "Models can be visible or hidden... `publicationDate` (Date): Can schedule a future publication. The model won't appear on the storefront until this date."（<https://docs.saleor.io/developer/models>, 2026-08-26）。Medusa 走反例（無內建排程、外掛 cron 翻 status），缺點正是我方要避開的：cron 粒度決定精度、job 沒跑就永遠不上架、無法表達「已排程」中間態。
3. Shopify 讀取層有 `onlyPublished` 參數區分 currently published / scheduled `[S]` ⇒ **排程列必須現在就寫進 DB**，不是放在 job queue 裡等。我方架構已符合。

**還缺什麼（四件，逐條）**：

| # | 缺口 | 錨點 | 誰交付 |
|---|---|---|---|
| B-1 | 🔴 **全倉沒有任何能修改既有列 `published_at` 的路徑** | `write.rb:11-13` 檔頭自陳「全倉零 UPDATE、零 DELETE、零 publish／unpublish 入口」；`write.rb:166-182` add 走 `find_or_create_by!` 的**建立區塊**（既有列完全不寫 `published_at`），remove 走 `destroy_all`（硬刪列，不是設回 NULL） | **S5**（S2 只做裁定，見 §4-F） |
| B-2 | 🔴 **cache stamp 到點不會前進** | `products.publications_updated_at` 只在寫入路徑被 bump（`product.rb:209-212`、`materialize.rb:207-216`、`write.rb:337-353`）。排程到點那一刻**沒有任何寫入** ⇒ 以該戳為 key 的前台快取會在邊界之後繼續供應舊內容，**且不拋任何錯** | 設計歸 S2，實作跟 S5 |
| B-3 | **`at:` 沒有任何呼叫端傳非預設值** | GraphQL 三支 mutation 都不傳；`app/graphql`／`app/frontend`／`app/controllers` 對 `publishedAt│published_at│publishDate` **零命中** | S2 建立讀出面時可選擇性接 `at:`（見下方「禁止事項」） |
| B-4 | **到點的「必須是 ACTIVE」條件未實作** | `resource_publication.rb` 全檔無 status 字樣；`88` §5 #3 開啟 | 見 §4-D |

**B-2 的正解（強烈建議，零新增基建）**：用既有的 `event_outbox.available_at`。
- `[M]` `db/schema.rb:346` `t.datetime "available_at", null: false`；`:363` index `(shop_id, status, available_at)`
- `[M]` `app/services/events/relay.rb:73-80` 取件條件含 `.where(available_at: ..now)` ＋ `FOR UPDATE SKIP LOCKED`
- `[M]` `config/recurring.yml` `events_relay` 每 5 秒跑一次
- `[M]` 全部 6 個 producer 一律寫 `available_at: Time.current` ⇒ **「延後投遞」是既有但零使用者的能力**

⇒ 在建立排程列的**同一個 transaction** 內補一筆 outbox，topic 用既有的 `Events::Topics::PRODUCT_PUBLICATION_CHANGED`，`available_at: published_at`。消費者到點 bump cache stamp。
好處：不加 job、不改 `recurring.yml`、不加 limits 鍵、不加索引；自動繼承既有的 SKIP LOCKED、`locked_at` 逾時回收、指數退避（`2**attempts` 秒）與 dead-letter（`outbox_dead_letter_attempts`）。
🔴 **必須在 dev doc 明寫「本包是 `available_at` 未來值的第一個使用者」**——既有 spec 從未覆蓋該分支。

**為什麼不用 cron／recurring 排程**：`[M]` solid_queue 用 `SolidQueue.time_zone` 作 cron 預設時區，而全倉 `SolidQueue.` 零命中（`rg -rn 'SolidQueue\.' -- config app lib` 無輸出）⇒ `recurring.yml` 現有的 `at 4am` / `at 4:30am` **沒有明確時區歸屬**。清掃任務偏移幾小時無害，商品上架時間偏移就是商家的事故。`available_at` 是絕對 UTC 時間戳，語義無歧義。

**索引（重要，影響方案選擇）**：`[M]` `ix_res_pub_published_at` 是 `(shop_id, publication_id, published_at)`。**跨租戶全域 sweeper**（`WHERE published_at BETWEEN ... AND NOW()`）走不到這支索引，會全表掃。走 outbox 路線則完全不需要這種查詢 ⇒ **不需要新增索引，也就不需要走鐵律 18.3 的 schema 裁定**。這是第三個選 outbox 的理由。

🔴 **測試矩陣的強制項（與鐵律 3 的 zero-decimal 陷阱同型）**：
V1／V2 的語義分歧**只在「已排程」這一個狀態顯現**——已發布時兩邊都 true，完全未發布時 V1 是 false 而 V2 根本沒有這一列。⇒ **沒有排程 fixture 的測試矩陣會 100% 全綠**。
現有測試缺口（`[M]` 實查，`grep -n from_now spec/models/publication_visibility_spec.rb` 只命中 :128/:181/:185）：
- ❌ ⑤ `with_member_counts` 組**零**未來 `published_at` 格 ⇒「排程中的成員商品不得計入前台可見件數」**無反向 fixture**
- ❌ ④ `ProductVariant.purchasable_on` 組**零**未來 `published_at` 格 ⇒「父商品排程中 ⇒ 變體不可購買」（靠 `merge` 才成立）**無反向 fixture**

⇒ **S2 必須把「未來 publishDate 的排程態」列為強制 fixture，比照 `docs/specs/65` §H 讓缺者 CI fail。**

### 4.C 時區來源

**候選盤點（`[M]` 實查）**：

| 候選 | 現況 | 判定 |
|---|---|---|
| `shops.timezone` | string(64), default `Asia/Hong_Kong`, null:false（`db/schema.rb:1125`）；**app/ 與 lib/ 零讀取者**（唯一 `timezone` 命中是 `inventory/history_query.rb:37` 的一行註解）；無 validation、無 GraphQL 曝露、無 UI 寫入者 | ✅ **唯一合法來源** |
| `staff_members.timezone` | 同型欄位（`db/schema.rb:1141`），來源是 parity 登記 71-R12-V3（本尊時區掛使用者帳號） | 🔴 **禁用**。排程到點是全店一致的事實，不能因為是誰在看而不同 |
| jurisdiction pack | `config/limits.yml` 的 `jurisdictions:` 區塊為 2181–2662 行；三個 timezone 命中（1960 / 2119 / 3694）**全部在區間外** | 🔴 **禁用**。時區在我方是**租戶層級**不是法域層級 |
| 應用層 `config.time_zone` | `config/application.rb:79` 為註解狀態 ⇒ Rails 8.1.3.1 預設 **`"UTC"`** | ✅ 核心判定層維持 UTC |

**建議分層（與鐵律 3「儲存尺度 ≠ 顯示位數 ≠ 對外單位」同構）**：

```
輸入層（admin UI 日期時間選擇器）  → 以 shops.timezone 解讀
API 層（GraphQL DateTime）        → 只收帶 offset 的 ISO 8601；無 offset 一律 reject
儲存層（resource_publications.published_at） → UTC 絕對時刻
判定層（published_at <= :at）      → UTC，Time.current
顯示層                             → 轉回 shops.timezone
```

🔴 **四條硬約束**：
1. **不得**接受無時區的 naive 字串再「用店鋪時區猜」——那會讓 API 客戶端與 admin UI 對同一字串得到不同結果。無 offset 一律 reject，走 `userErrors` typed code（鐵律 4）。與鐵律 3「未宣告一律 reject，不得預設」同精神。
2. **商家改店鋪時區時，已排程的絕對時刻不得跟著漂移**（否則等於偷改排程）。這一條要進註釋第④欄。
3. 任何走原生 SQL 的時間比較用 **`UTC_TIMESTAMP()` 不用 `NOW()`** —— 照抄 `[M]` `app/services/inventory/history_query.rb:35-39` 的既有教訓逐字：「`NOW()` 跟著 MySQL session 時區走 ... 目前 bt3 的 session tz 是 SYSTEM＝UTC 所以兩者同值，但那是**環境巧合不是保證**」。
4. 🔴 **dev doc 必須誠實登記**：`shops.timezone` **從未被讀取或寫入過**，意味著它現在一定是預設值 `Asia/Hong_Kong`，任何依賴它的商家自訂行為都**還不存在**。**不得寫成「沿用既有店鋪時區設定」**。

⚠️ 官方對「排程輸入以哪個時區解讀」**無正面陳述** `[?]`（R6）。上述分層是 **ours 裁定**，須登記；**不得寫成「照本尊」**。DST 處理 `[?]`、輸入格式契約 `[?]` 同樣不得補齊。

### 4.D 「到點時商品必須是 Active」要不要跟？在哪一層檢查？

**答：要跟。但只在「到點事件的投遞條件」這一層檢查，不進可見性謂詞。**

**證據基礎**：
- `[H]` "Products must be in **Active** status for future publishing to work."／"If a product is in **Draft** status **at the scheduled publish time**, then the product won't be published..."（<https://help.shopify.com/en/manual/shopify-admin/productivity-tools/future-publishing>, 2026-08-26）
- 🔴 **shopify.dev API 側對此完全沉默** `[?]`（三頁已讀確認）⇒ 此規則目前**只有商家文檔背書，缺 API 文檔背書**。寫進 API 契約時必須標明來源層級。
- `[M]` `config/limits.yml:4649` `future_publishing_requires_active_status: true`（零消費者，且該鍵**無出處註釋**——本身就是 `[?]`，見 §5）
- `[X]` `90` X-18／A9 逐字：「job 到點**重讀 `product.status`** 驗證仍為 ACTIVE ... **不得套用排程當下的快照**」，並列為 §01 §E 的**必備併發測試**

**為什麼不進可見性謂詞（解 C-5）**：
`Product.purchasable` 已含 `with_status_set(PURCHASABLE_STATUSES)`，而 `purchasable_statuses: [ACTIVE, UNLISTED]`（`[M]` limits.yml:912）。`90` V-2 已裁定「寫死 `status=ACTIVE` 會把 UNLISTED 全判不可購」。⇒ 在謂詞裡再加一個 `= ACTIVE` 會**打爛 V-2**。
兩者講的是不同層：R9 講「到點那一刻要不要**生效**」，V-2 講「已發布之後**誰看得到／買得到**」。

**建議實作分層**：

| 層 | 檢查什麼 | 說明 |
|---|---|---|
| 寫入時（設排程） | **不檢查 status** | 官方明說判準是**到點時**的 status。設定當下拒不拒絕 `[?]`（見 §5）⇒ 不得發明 |
| 可見性謂詞 | **維持現狀不動** | `PURCHASABLE_STATUSES` / `DISCOVERABLE_STATUSES` 照舊，V-2 不受影響 |
| 🔴 到點事件投遞前 | **重讀 `products.status`，必須 `ACTIVE`** | 非 ACTIVE ⇒ 不投遞事件。這是 `90` X-18／A9 的正典要求 |
| UNLISTED / ARCHIVED 到點 | 🔴 **裁定項** | 官方 `[?]`。**不得**由「Draft 不發布」外推 |

⚠️ **注意可見性與事件的落差**：到點時 status 是 UNLISTED 的商品，在可見性謂詞下**已經可購買**（V-2），但事件因非 ACTIVE 而未投遞 ⇒ cache stamp 沒 bump ⇒ 前台快取可能仍看不到。這是 UNLISTED 裁定必須一併處理的邊際條件，**S2 必須在 dev doc 明列，不得靜默**。

🔴 **禁止硬編 `"active"` 字面值**（鐵律 6）：一律 `Limits.fetch(:sales_channels, :future_publishing_requires_active_status)` ＋ `Limits.fetch(:product, :status_values)` 導出。**不得誤用 `purchasable_statuses` 當到點判準**（它含 UNLISTED，比 ACTIVE 寬）。

### 4.F 補償語義 —— 是不是裁定項？

**答：是，而且是 S2 唯一的裁定項。**

**官方全面沉默（R19）**：排程到點不合格後排程本身的去向、Draft 錯過時點後改回 Active 是否 catch-up、失敗是否有任何提示、到點的執行精度與延遲、商品已刪除／管道已卸載／缺 catalog 指派等情境 —— **一律 `[?]`**。
`[X]` 我方計畫檔逐字：「**官方無補償語義**（我方要自訂 ⇒ 裁定項）」。
`[X]` `90` X-18／A9 兩處 ⚠️ 標「到點的事件粒度**無官方保證**」。

**倉庫已有正典先例可照抄形態**（`[M]` `docs/specs/91-pit-register.md:2226-2233`，第 28 包 staged 保留期）：
> 「⇒ 我方 `media.staged_purge_grace_seconds: 3600` 與每日排程是 **ours 裁定不是對齊**，不得寫成「照本尊」。🔴 也不得反向斷言「本尊沒有清掃」——文檔沒寫不等於行為不存在。」

**建議的最小 ours 裁定（送使用者裁定，不得由執行方自定）**：

| 裁定點 | 建議值 | 說明 |
|---|---|---|
| 到點時 status 非 ACTIVE | **不投遞事件、不清除排程、不報錯** | 對齊 `[H]` 的失敗形態（"won't be published"，不是報錯）；且官方沒有把排程一併作廢的說法 `[?]` |
| catch-up（錯過後改回 ACTIVE） | **不自動補發布** | 需 `[?]` 才能對齊。維持「查詢時判定」的自然結果：`published_at` 已是過去 ⇒ **前台其實已經可見**，缺的只有事件與 cache stamp。⚠️ 這一點**必須寫進 dev doc**，因為它與「不補發布」聽起來矛盾 |
| 到點事件的重試 | **沿用 outbox 既有退避** | `outbox_dead_letter_attempts` ＋ `2**attempts` 秒。**不新增** `catalog_flow.publication_retry_*`（那組註釋出處是**跨系統發布失敗重試**（63 §H.2），未證實適用於到點，見 §5） |
| 到點延遲的可接受窗 | **≤ relay 間隔（5 秒）＋ 一次退避** | 由 `events_relay` 的 `every 5 seconds` 導出，非官方數字 |
| 不合格的商家可見回饋 | **S2 不做**（無 ResourceFeedback 等價物） | `[G]` 本尊有 `ResourceFeedback` 提前驗證＋回饋機制；我方尚無。登記 `91` §3 為 ⚪ |

🔴 **登記義務**：裁定入 `docs/DECISIONS.md`，坑登記入 `docs/specs/91-pit-register.md`，兩處都必須逐字寫「官方未取得」且**不反向斷言本尊沒有補償機制**。任何常數進 `config/limits.yml` 並帶出處註釋。
