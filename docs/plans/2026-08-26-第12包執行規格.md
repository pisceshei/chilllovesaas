> 建立 2026-08-26。基準 `main` = `3f18dac`。

>
> 🔴 **本包的每一條設計決策都來自對 Shopify 本尊的實測，不是專案裁定。**
> 使用者 2026-08-26 明示：「我們要和 shopify 本尊一樣的處理方式」。

## §0 這一包在解什麼

一句話：**`resource_publications` 這張表已經存在快兩週，但倉庫裡沒有任何一行程式碼會建立它的列。**

後果是靜默的，而且形態最壞：

| | |
|---|---|
| 現在 | 沒有人建列 ⇒ 三層 AND 的第二層永遠不成立 |
| 若照規格加上 scope | **全站每個商品都變成不可購買**，而近千支 spec 全綠——因為沒有任何一支斷言過「新商品必須有 publication 列」 |
| 為什麼沒炸 | 沒有人**讀**它。`Product` 刻意不提供 `purchasable` scope（`app/models/product.rb` 的註釋逐條寫明為什麼），前台也還沒接 |

⇒ 本包＝**把生產者補上，然後才敢把讀取面打開**。順序不能反。

<!-- 🔴 這個形態值得單獨記一筆：一個「寫入端缺席」的缺陷，在只有寫入端測試的專案裡
     是**測不出來的**——每一支測試都在測「我建了列之後讀得到嗎」，沒有人測
     「不建列的那條路徑會發生什麼」。第 11 包的部署事故（migration 回填缺
     without_tenant，CI 空庫與開發庫都不執行迴圈本體）是同一個家族：
     **缺陷藏在「沒有資料」那一格，而測試永遠先種資料**。 -->

## §1 本尊怎麼做（實測結論，逐條帶錨）

全部證據＝`docs/research/82` §8。這裡只列**直接決定實作**的六條：

| # | 實測結論 | 錨 | 對實作的意義 |
|---|---|---|---|
| 1 | 讀取面**正向、稠密**：只列已發布的 publication，未發布者不在陣列 | 82 §8.2 | 我方多型設計方向正確 |
| 2 | 🔴 **未觸碰的變體回 3 列不是 0 列** ⇒ 不是「無列＝繼承父商品」 | 82 §8.2 | **每個變體都必須實際有列**，不能靠繼承省掉 |
| 3 | 建立商品時**當下就物化**，預設全開 | 82 §8.4① | 生產者掛在**建立**時點，不是第一次讀取時 lazy 建 |
| 4 | 🔴 新變體跟的是**全部 `auto_publish` 的 publication**，**不是父商品的集合**（實測：父商品只在 2 個管道，新變體拿到 3 個） | 82 §8.4② | 變體生產者**不得**讀父商品的 publication |
| 5 | 🔴 **層與層不連動**：商品層關掉某管道後，變體層的列原封不動 | 82 §8.4③ | 不變量**不能**靠寫入時串聯維持，只能在讀取時取交集 |
| 6 | `status` 與 publication **正交**：改成 Unlisted 後 publication 列完全沒變 | 82 §8.4④ | status 不是 publication 的寫入來源 |

🔴 **第 5 條是最容易照直覺做反的一條**。寫入時串聯（父關子也關）會讓資料庫裡永遠滿足不變量、
讀取只看一層就好——但本尊不是這樣做的，而且照抄那個直覺有**不可逆的資訊損失**：
父層關掉再開回來時，使用者原本刻意關掉的子層設定會被一起還原，且還原不回去。
本尊選的是**保留每層的獨立意圖、讀取時取交集**。

## §2 必做（做完這些這一包就結束）

### §2.1 生產者 `Publications::Materialize`

新檔 `app/services/publications/materialize.rb`。

```
Publications::Materialize.for(shop:, publishable:)
  → 對 shop 底下所有 auto_publish = true 的 publication，
    各建一列 resource_publications(published_at: Time.current)
  → 已存在的列不動（冪等）
```

**掛載點＝model callback，不是 service**。理由與 `Shop#after_create :create_default_publication`
完全相同（該處註釋已寫明）：callback **涵蓋每一條建立路徑**（GraphQL、seeds、factory、rake、
日後的匯入器），service 只涵蓋 GraphQL 那一條。

| model | callback |
|---|---|
| `Product` | `after_create` |
| `ProductVariant` | `after_create` |
| `Collection` | `after_create` |

🔴 **`ProductVariant` 的 callback 不得讀 `product.resource_publications`**（§1 第 4 條實測）。
三個 model 用**同一支**服務、**同一條**規則。

<!-- 🔴 為什麼特別寫這一句：「變體應該跟著父商品」是壓倒性的直覺，任何 reviewer 看到
     變體與商品各自獨立去撈 publication 都會想提「這裡沒有跟父層對齊」。
     實測結果是本尊確實不對齊（82 §8.4②：父商品只在 2 個管道，新變體拿到 3 個）。
     這條註釋是給下一個人的——**不要「修好」它**。 -->

### §2.2 回填 migration

既有的 Product／ProductVariant／Collection 全部補列。

🔴 **必須附一支「先種既有資料、再在無租戶情境下跑回填」的 spec**——這是第 11 包的部署事故
換來的固定處理（`spec/migrations/p11_backfill_tenant_spec.rb` 是現成範本，含一格盯 migration
原始碼本身的 source-guard）。理由：回填迴圈的本體只有在**資料庫已有資料**時才執行，
而 CI 跑在空庫、開發庫也常剛好沒資料 ⇒ **兩處都不執行迴圈本體，`db:migrate` 一路綠**，
只有正式環境會炸。

### §2.3 讀取面 scope

`Product.purchasable` / `Product.discoverable`。

🔴 **不變量用構造保證，不用兩份 SQL 各寫一次**：

```ruby
scope :discoverable, -> { purchasable.where(status: DISCOVERABLE_STATUSES) }
```

因為 `discoverable_statuses ⊆ purchasable_statuses`（`config/limits.yml` 已有正典
`discoverable_subset_of_purchasable: true`），且 publication 條件完全共用
⇒ `discoverable ⊆ purchasable` 是**定理不是測試項**。兩支各寫一份 SQL 才需要靠測試盯漂移。

判定鏈（三層 AND 的前兩層 ＋ status）：

```
purchasable = status ∈ PURCHASABLE_STATUSES
            ∧ 商品層 EXISTS(resource_publications 已發布)
            ∧ 變體層 EXISTS(至少一個變體已發布)
```

第三層 catalog **不在本包**（§3）。

### §2.4 GraphQL 面——**本包不做**（範圍對齊）

<!-- 🔴 2026-08-26 自我修正：本節原本列了 publish／unpublish 兩支 mutation ＋ 三個讀取欄位。
     那**超出權威計畫表**——`docs/plans/2026-08-24-三方向執行順序.md` §3 第 12 列的
     包名逐字是「發布**讀取層**：Publishable × Publication 兩層 AND 過濾器 ＋
     ProductVariant 發布回填」，沒有寫入面。
     而且本包沒有任何 v1 消費者會呼叫那些 mutation（發布 UI 在後面的前端包）
     ⇒ 正是第 11 包教訓要防的「為沒有入口的功能先蓋機制」。⇒ 移出，登記到 §3。 -->

已為後續包取證完畢的契約形態（做的時候直接用，不必重查）：

- **publish／unpublish 必須是兩支獨立 mutation**，不是一支吃全集的 `setPublications`。
  實測：admin 送的是獨立的 `ProductVariantUnpublish`（82 §8.3）；
  官方 `publishablePublish(id: ID!, input: [PublicationInput!]!)` /
  `publishableUnpublish(...)` 同形，`input` 是**陣列**、可一次打多個 publication。
- **重複 publish 必須是 no-op success**，不得回 userError。官方逐字：
  「If the variant is already published to that publication, the mutation succeeds with no change.」
- `publishablePublishToCurrentChannel` / `publishableUnpublishToCurrentChannel`
  本尊**已 deprecated**，我方不實作。
- 讀取欄位 `resourcePublications` / `resourcePublicationsV2` 的 `onlyPublished` **預設一律 `true`**；
  `resourcePublicationsV2` 的 `catalogType` 未指定時預設 `APP`。

## §4 規模與併發

**列數**：v1 每店只有 1 個 publication（`online_store`）
⇒ 列數 = (products + variants + collections) × 1。**每個實體一列**，可接受。

<!-- 本尊是 P × V × C 的稠密物化，C 在測試店＝3。我方 v1 的 C＝1，
     所以「稠密」在這裡不構成規模問題。等 C 長到十幾個再談分區或稀疏化，
     現在為它設計等於第 11 包那個「為沒有前端入口的功能蓋併發設施」的重演。 -->

**併發**：生產者跑在**建立實體的同一個 transaction 內**（`after_create`），無外部 IO（鐵律 5）。
冪等靠 `resource_publications` 既有的唯一索引 `(shop_id, publication_id, publishable_type, publishable_id)`。
🔴 **不引入 advisory lock、不引入世代標記、不引入拓樸序**——第 11 包的教訓是
「修法需要新機制時，先問這個功能 v1 有人用得到嗎」。這裡沒有任何跨實體的順序依賴，
一個唯一索引就夠。

## §5 測試矩陣（含反向 mutation）

正向格容易寫，**反向格才是防線**。逐條列出必須讓突變轉紅的守衛：

| # | 突變 | 必須轉紅的測試 |
|---|---|---|
| 1 | 拿掉 `Product` 的 `after_create` | 「新建商品後 `resource_publications` 有列」 |
| 2 | 拿掉 `ProductVariant` 的 `after_create` | 「新建變體後有列」——🔴 且要有一格是**透過 `SaveProduct` 建變體**，不只是 `ProductVariant.create!` |
| 3 | 🔴 把變體生產者改成「讀父商品的 publication 集合」 | 需要一格：**父商品只發布到部分管道**，斷言新變體仍拿到全部 `auto_publish` 管道（＝82 §8.4② 的實測形態）|
| 4 | 把 `discoverable` 改寫成獨立 SQL（不再由 `purchasable` 導出） | 結構性斷言：`discoverable` 的定義必須引用 `purchasable` |
| 5 | 生產者忽略 `auto_publish = false` | 需要一格有 `auto_publish: false` 的 publication，斷言**不**建列 |
| 6 | migration 回填拿掉 `without_tenant` | source-guard（第 11 包的現成範本）|
| 7 | 讓 `purchasable` 少掉變體層 EXISTS | 一格：商品已發布但**所有變體都沒發布** ⇒ 不可購買 |
| 8 | 讓商品層寫入串聯改寫變體層 | 一格：商品層取消發布某管道後，**變體層的列不變**（＝82 §8.4③）|

🔴 **突變測試的假綠家族**（第 11 包踩了六種變體，全部同一個根因）：
測資落在兩個實作**不會分岔**的那一格。逐格自問：**這筆測資在突變前後真的會走不同路嗎？**
第 3、5、7、8 格特別容易寫成假綠——它們都需要一個**刻意不對稱**的起始狀態。

## §8 驗收方式（D40 直接開發）

分支 → PR → CI `quality`＋`test` 兩個 job 綠 → 自行 squash 合併（帶 `--match-head-commit`）
→ 部署 bt3 → 線上驗證。

🔴 **審查輪次紀律（第 11 包的教訓，`review-loop-overrun`）**：
**一輪對抗審查抓初始候選的真缺陷，修完即合併。** 之後再發現的登記進 `91` 由後續包處理，
不在同一個 PR 內無限收斂。硬判準：**連續兩輪的 🔴 有一半以上來自我自己上一輪的修法 ⇒ 立刻停手合併。**
