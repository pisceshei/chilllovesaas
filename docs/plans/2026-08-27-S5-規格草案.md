### 1.1 `publishablePublish`

來源：<https://shopify.dev/docs/api/admin-graphql/latest/mutations/publishablePublish>（2026-08-27，層級 A）

**Mutation description（逐字）**
> Publishes a resource, such as a Product or Collection, to one or more publications. For products to be visible in a channel, they must have an active ProductStatus. Products sold exclusively on subscription (requiresSellingPlan: true) can only be published to online stores. You can schedule future publication by providing a publish date. Only online store channels support scheduled publishing.

⚠️ 2025-10 版頁面（<https://shopify.dev/docs/api/admin-graphql/2025-10/mutations/publishablePublish>）僅回傳首句，**這是抓取限制不是版本差異**，不得寫成「該版只有一句」（未取得，見 §6）。
⚠️ 另一次抓取（同 URL、同日）只取到首句且 `Product`／`Collection` 帶反引號 ⇒ 兩次 verbatim 存在格式差異（見 §4-M6）。

| 參數 | 型別 | 官方描述（逐字） | Default | 備註 |
|---|---|---|---|---|
| `id` | `ID!` | The resource to create or update publications for. | 無（non-null 必填） | 🔴 全頁**無任何 GID 型別值域宣告**。頁上唯一具體值＝Example variables 的 `gid://shopify/Product/558169081`（層級 C，單一例子）。值域窮舉見 §1.5 |
| `input` | `[PublicationInput!]!` | Specifies the input fields required to publish a resource. | 無（non-null 必填） | 🔴 陣列長度上限＝**未取得**。對 `maximum`／`limit`／`up to`／`at most`／`partial` 五個關鍵字逐一搜尋皆 Not found on page（層級 D）。⚠️ 頁上 Example variables 把 `input` 寫成單一物件而非陣列，官方未說明原因，不得推測 list coercion |

| 回傳欄位 | 型別 | 官方描述（逐字） |
|---|---|---|
| `publishable` | `Publishable`（nullable） | Resource that has been published. |
| `shop` | `Shop!` | The user's shop. |
| `userErrors` | `[UserError!]!` | The list of errors that occurred from executing the mutation. |

**Access requirements（逐字）**
> Requires `write_publications` access scope. Also: The user must have permission to create and edit products or create and edit catalogs.

latest 與 2025-10 兩版逐字相同。⚠️ 官方**只列一個 scope**；`write_products`／`read_publications` 是否亦被接受＝未取得。
指南頁（層級 B）另給更寬的一組：「Your app has the `read_publications` and `write_publications` access scopes. You also need `read_products` to query products.」（<https://shopify.dev/docs/apps/build/sales-channels/product-publishing.md>，2026-08-27）——**與 A 不衝突**（B 講的是完整 channel app 情境，含查詢）。

**官方 Example（層級 C，逐字保留 GID 字面值）**
```graphql
mutation publishablePublish($id: ID!, $input: [PublicationInput!]!) {
  publishablePublish(id: $id, input: $input) {
    publishable { availablePublicationsCount { count } resourcePublicationsCount { count } }
    shop { publicationCount }
    userErrors { field message }
  }
}
```
```json
{ "id": "gid://shopify/Product/558169081",
  "input": { "publicationId": "gid://shopify/Publication/762454635" } }
```
官方範例只選 `field`／`message` 兩欄 ⇒ 與「UserError 無 code」互相佐證。

### 1.2 `publishableUnpublish`

來源：<https://shopify.dev/docs/api/admin-graphql/latest/mutations/publishableUnpublish>（＋同頁 `.txt`，2026-08-27，層級 A）

**Mutation description（正文全文，逐字）**
> Unpublishes a resource, such as a `Product` or `Collection`, from one or more publications. The resource remains in your store but becomes unavailable to customers.
>
> For products to be visible in a channel, they must have an active `ProductStatus`.

🔴 「The resource remains in your store」講的是**資源本身**，**不是**講發布紀錄。不得讀成「紀錄保留」。

| 參數 | 型別 | 官方描述（逐字） | 備註 |
|---|---|---|---|
| `id` | `ID!` | The resource to **delete or update** publications for. | 🔴 整頁**唯一**觸及「publications 被怎麼處理」的規範性措辭。對照組：publish 側同一參數為 "The resource to **create or update** publications for."。但它描述**參數用途**，未說何時是 delete、何時是 update |
| `input` | `[PublicationInput!]!` | Specifies the input fields required to unpublish a resource. | 上限同樣未取得 |

| 回傳欄位 | 型別 | 官方描述（逐字） |
|---|---|---|
| `publishable` | `Publishable`（nullable） | Resource that has been unpublished. |
| `shop` | `Shop!` | The user's shop. |
| `userErrors` | `[UserError!]!` | The list of errors that occurred from executing the mutation. |

**Access requirements**：與 publish 側逐字相同。

### 1.3 `PublicationInput`（兩支共用）

來源：<https://shopify.dev/docs/api/admin-graphql/latest/input-objects/PublicationInput>（＋`.md`＋同頁 schema payload，2026-08-27）。三版（2026-07 latest／2025-10／unstable）文字完全相同。

**Input object description（逐字）**：`The input fields required to publish a resource.`（注意寫的是 publish，被兩支 mutation 共用）

**權威 SDL（層級 A′，逐字取自同頁 `rawSchema`）**
```graphql
input PublicationInput { channelId: ID  publicationId: ID  publishDate: DateTime }
```
⇒ 三欄**全部 nullable**（皆無 `!`），且**無任何 `= value` 子句** ⇒ SDL 層沒有宣告預設值。渲染頁與 `.md` 也無 `Default:` 標註。
排序差異：渲染頁／`.md` 為 `publicationId → publishDate → channelId`；SDL 為字母序。

| 欄位 | 型別 | 官方描述（逐字） | Default | Deprecated |
|---|---|---|---|---|
| `publicationId` | `ID` | ID of the publication. | 未宣告 | 否 |
| `publishDate` | `DateTime` | The date and time that the resource was published. Setting this to a date in the future will schedule the resource to be published. Only online store channels support future publishing. This field has no effect if you include it in the `publishableUnpublish` mutation. | 未宣告 | 否 |
| `channelId` | `ID` | ID of the channel.（🔴 **僅 payload 層**取得） | 未宣告 | **是** |

🔴 `channelId` 的 provenance 必讀：渲染頁與官方 `.md` **只顯示 `Deprecated` 一字，無描述、無 reason**（三版皆同）。描述與 reason 僅存在於同一官方 URL 的伺服器端 schema hydration payload，逐字片段：`"channelId","ID of the channel.",[],"Use publicationId instead."`。已逐字元複驗該 reason 字串**不含反引號**（對照同 payload 內 `publishDate` 描述確實保留反引號，可證非解析失真）。⇒ 若驗收口徑要求「渲染層可見文字」，`channelId` 的描述與 reason 應記為**渲染層未取得、僅 payload 層取得**。

**優先序（層級 A，僅存在於 unpublish 頁）**
> If you provide a channel ID and publication ID, then only the publication ID is used.

來源：publishableUnpublish 頁 Examples 之「Unpublish a product using both a channel ID and publication ID」的 Description 欄。
🔴 **publish 側完全沒有對應句**：對 `publishablePublish.md` 全文（44,057 字元）與 `product-publishing.md`（20,754 字元）搜尋，`channelId` 出現 **0** 次、`both` 0 次、`either` 0 次、`ignore` 0 次、`takes precedence` 0 次 ⇒ publish 側優先序＝**未取得**（不對稱，見 §4-M4）。

**排程的旁證（層級 B）**：`A `publishDate` in the future indicates that the product is scheduled to display on the channel at the specified datetime.`（<https://shopify.dev/docs/apps/build/sales-channels/scheduled-product-publishing.md>，2026-08-27）

### 1.4 `UserError`（兩支的 error 型別）

來源：<https://shopify.dev/docs/api/admin-graphql/latest/objects/UserError>（2026-08-27，六次獨立抓取／三個版本，欄位集合恆一致）

**Object description（逐字）**
> An error in the input of a mutation. Mutations return `UserError` objects to indicate validation failures, such as invalid field values or business logic violations, that prevent the operation from completing.

| 欄位 | 型別 | 官方描述（逐字） |
|---|---|---|
| `field` | `[String!]` | The path to the input field that caused the error. |
| `message` | `String!` | The error message. |

🔴 **`code` 欄位不存在**。證據形態＝Fields 區窮舉為上述兩欄（六次一致，其中兩次為針對 `"code"` 字串的定向提問，皆回 does not appear）。屬**缺席型證據**（層級 D）——官方不會正面宣告「沒有 code」。與 CLAUDE.md 鐵律 4 既有登記一致。
🔴 **Admin 版 `UserError` 頁不顯示 `Implements: DisplayableError`**。此結論做過控制組驗證（非單純擷取失敗）：同模板在 `ProductVariant` 頁渲染出 `## ProductVariant Implements`（列 HasEvents…Publishable），在 `MediaUserError` 頁渲染出 `Implements: DisplayableError`；但 `UserError` 頁三版四抓皆無該區塊，且 `DisplayableError` 介面頁（latest／2024-01）亦無 `UserError` 字串。
⚠️ **跨 API 不可外推**：Storefront API 與 Payments Apps API 的**同名** `UserError` 頁**有** Implements 區塊（但欄位同樣只有 field／message、無 code）。
🔴 `DisplayableError` 介面本身也**只有 `field`／`message`，沒有 code**（<https://shopify.dev/docs/api/admin-graphql/latest/interfaces/DisplayableError>，2026-08-27）⇒ 本尊「有沒有 code」不是由介面決定，而是各 mutation 的 typed error 型別自行加。

**typed error 對照組（本尊確實有這種形態）**：`MediaUserError` 三欄＝`code: MediaUserErrorCode` "The error code." ／`field` ／`message`，且 **implements DisplayableError**（<https://shopify.dev/docs/api/admin-graphql/latest/objects/MediaUserError>，2026-08-27）⇒ typed error 的 code 是**專屬 enum**不是 String。
**機制證據（層級 A，changelog）**：`from a `UserErrors` type to a `BulkOperationUserError` type`（<https://shopify.dev/changelog/bulk-query-operation-usererrors-now-includes-code-field>，2026-08-27）⇒ 本尊「要加 code 就換型別」，欄位名不變。⚠️ 該頁完整 body 逐字未取得（兩次抓取皆為摘要體）。
⚠️ 「本尊正在把泛用 UserError 逐支遷往 typed error」＝**未取得官方聲明**；上述 changelog 只證明單一 mutation 換過型別，屬**單點證據**，不足以支撐鐵律 4 註記中的全稱句（見 §6）。

### 1.5 官方 userErrors 實際形狀（🔴 層級 C，直接推翻我方一個既有「未取得」）

publishableUnpublish 頁三個錯誤範例回應的 `userErrors` 逐字：
```json
{ "field": ["input", "0", "publicationId"], "message": "PublicationId cannot be empty" }
{ "field": ["input", "0", "publicationId"], "message": "Channel does not exist or is not publishable" }
{ "field": ["input", "0", "publicationId"], "message": "Publication does not exist or is not publishable" }
```
🔴 **三條可直接驅動實作的事實**：
1. **`field` path 不剝殼**：第一段是參數名 `"input"`，索引是**十進位裸字串段** `"0"`，平鋪在同一維陣列。這正是 `docs/research/28-api-contract.md` §0.3.1②④ 的形態，且 §0.3.6 原本登記「剝殼規則射程沒有官方範例可證」——**本 fixture 就是那個範例**（層級 C：形狀證據，非規則宣告）。我方 `Publications::Write.resolve_publishables` 現行的 `[ "input", field, index.to_s ]` 形態**與官方一致**。
2. **錯的是 `channelId` 時，`field` 仍回 `["input","0","publicationId"]`**（第二則的觸發輸入是 `channelId: gid://shopify/Channel/0`）⇒ 本尊的 field 歸屬**不精確**。我方不實作 `channelId`，此不精確不會出現，但**不得**照抄成「一律指 publicationId」。
3. **錯誤情境下 `publishable` 仍有值**（該三則的 `resourcePublicationsCount` 回 `count: 4`）⇒ mutation **不是整體失敗**、payload 的 resource 欄仍被解析。這與 all-or-nothing **不衝突**（沒寫入 ≠ 不回資源）。

**計數變化（層級 C）**：成功範例回 `availablePublicationsCount: 3` / `resourcePublicationsCount: 3` / `shop.publicationCount: 8` / `userErrors: []`；三個失敗範例皆 `count: 4` ⇒ 成功取消發布後 4→3。⚠️ **證明不了紀錄被刪**：`resourcePublicationsCount` 的 `onlyPublished` 預設 `true`，計數下降同樣相容於「紀錄仍在但 isPublished=false」。

### 1.7 變體層發布的既得契約（S5 必須一併吸收，層級 B）

全部來自 <https://shopify.dev/docs/apps/build/sales-channels/product-publishing.md>（2026-08-27）。

| 事實 | 逐字 |
|---|---|
| 🔴 **獨立性（雙向不連動）** | `Variant and product publishing states are independent:` / `Publishing or unpublishing a variant doesn't affect the parent product's publication state.` / `Publishing or unpublishing a product doesn't change any variant's publication state.` |
| 狀態持久 | `Variant publishing state persists across product publishing changes, so you can configure variant visibility before publishing the product.` |
| 可見性三合取 | `A variant is visible to buyers on a given sales channel or catalog when the following are all true:` 1) `The product has an Active status (or Unlisted on supported channels).` 2) `The product is published to that channel or catalog.` 3) `The variant is published to that channel or catalog.` |
| 可見性真值表 | `Published/Published→Yes`、`Published/Unpublished→No`、`Unpublished/Published→No`、`Unpublished/Unpublished→No`（🔴 這是**可見性表**不是狀態轉移表） |
| 🔴 **冪等語義** | `Use the publishablePublish mutation with a ProductVariant GID to publish a variant to one or more publications. **If the variant is already published to that publication, the mutation succeeds with no change.**` |
| unpublish 不刪資料 | `The variant data isn't deleted. You can republish the variant at any time.`；商品層同義句：`The product isn't deleted. It remains in your store but becomes unavailable to buyers on those channels.` |
| 新建變體預設 | `If you don't set published, or set it to true, the variant is created with the default state of published to all channels and catalogs where the parent product is published.`（適用 `productVariantsBulkCreate` 與 `productSet`） |

### 2.2 我方 S1 的硬刪對嗎？

我方現況（層級 F，`app/services/publications/write.rb:175-182`）：remove 分支 `.destroy_all`（走 model 逐列 DELETE、跑 callback），**硬刪整列**，不是把 `published_at` 設 NULL。

正確的理由鏈（**不是**「本尊也刪」——那是未取得）：
1. 我方 GraphQL 只出 **V2 投影**（`Types::Interfaces::Publishable#resource_publications_v2`），而 V2 的三個 scope 全部以 `published_at IS NULL` 為「不存在」：`currently_published` = `where.not(published_at: nil).where(published_at: ..at)`；`staged` = `where(published_at: (at + 1.second)..)`；`published_or_staged` = `where.not(published_at: nil)`（層級 F，`app/models/resource_publication.rb`）。

3. ⇒ **NULL 列在我方全部讀出面與「沒有列」不可區分**，正與官方訊號 J／K 的形態一致。
4. ⇒ 硬刪是自洽的；改成留 NULL 列在**對外行為上不產生任何差異**，只增加隱形狀態。

**保留列並設 NULL 的取捨（逐項）**

| 面向 | 硬刪（現行） | 留列設 NULL |
|---|---|---|
| 對外契約 | 等價 | 等價（V2 不收 NULL） |

### 3.2 🔴 `find_or_create_by!` 為什麼改不到既有列（機制證據）

我方現行 add 分支（`app/services/publications/write.rb:166-173`）：
```ruby
ResourcePublication.find_or_create_by!(
  shop_id: shop.id, publication_id: publication.id,
  publishable_type: record.class.name, publishable_id: record.id
) { |row| row.published_at = at }
```
Rails 8.1.3.1 實作（`activerecord-8.1.3.1/lib/active_record/relation.rb:238-240`，層級 F）：
```ruby
def find_or_create_by!(attributes, &block)
  find_by(attributes) || create_or_find_by!(attributes, &block)
end
```
⇒ **`find_by` 命中時 `create_or_find_by!` 根本不被呼叫，區塊隨之不執行**。⇒ 區塊形式的 `published_at = at` **只在 create 那一支生效**，既有列的任何欄位**在結構上不可能被改到**。
⇒ 這正是「重複 publish 是 no-op success」在我方成立的機制，也是**「改期」與「取消排程」在今天的程式碼裡沒有任何路徑可達**的根因。

🔴 **附帶並發缺陷（必須同批處理）**：`create_or_find_by!` 官方文檔逐字：`Columns with unique database constraints should not have uniqueness validations defined, otherwise #create will fail due to validation errors and #find_by will never be called.` 而 `ResourcePublication` **同時**有 DB 唯一索引 `uq_res_pub_target` 與 model 層 `validates :publishable_id, uniqueness: { scope: %i[shop_id publication_id publishable_type] }`（層級 F）。⇒ 並發窗（`find_by` 回 nil 後、`create!` 前另一交易插入同鍵）下拋的是 **`RecordInvalid`**（走 `write.rb:188` 的 rescue，回 `code: "INVALID"` 的 userError），**不是** `RecordNotUnique`（後者才會被 `create_or_find_by!` 吞掉並改走 find）。⇒ **「重複 publish 必須 no-op success」在並發下會破功，回一個假的驗證錯誤。**

### 3.4 `at` 與 `publishDate` 必須解耦（🔴 事故形態）

現行 `Publications::Write.update(…, at: Time.current)` 是**整批一個 scalar**，同時承擔「發布時刻」與「cache stamp 時刻」兩種用途，並在 `write.rb:184` 傳給 `bump_stamps!(shop_id:, records:, at:)` → `Product.bump_publications_stamp!(…, at:)` → `update_all("publications_updated_at = ?", at)`（**直接賦值**，不是 `Time.current`）。

🔴 ⇒ **把未來的 `publishDate` 傳進 stamp，會把 `products.publications_updated_at` 寫成未來時間**，之後的真實變動要嘛不讓 stamp 前進、要嘛讓它倒退——無論哪一種，stamp 語義都被污染。
**S5 必須**：`published_at` 逐目標帶值（tuple），`bump` 一律傳 `Time.current`。且官方 `publishDate` 是 **per-publication** 的（掛在陣列每個元素上），我方 scalar `at:` 形態**對不上契約**。
（現況佐證：目前**沒有任何呼叫端傳過非預設的 `at:`**——GraphQL 三支 mutation 都不傳，`app/graphql`／`app/frontend`／`app/controllers` 對 `publishedAt│published_at│publishDate` 零命中。）

### 3.5 時區

S2 §4.C 已登記官方對排程輸入的時區解讀**無正面陳述**（`[?]`）。我方四層分層（輸入層 `shops.timezone`／API 層只收帶 offset 的 ISO 8601／儲存判定 UTC／顯示層轉回）是 **ours 裁定**。
⚠️ `shops.timezone` **從未被讀取或寫入過** ⇒ dev doc **不得**寫成「沿用既有店鋪時區設定」。
官方唯一可用的形狀證據＝範例 variables 逐字 `"publishDate": "2999-01-01T00:00:00-00:00"`（層級 C，帶 offset）⇒ 支持「API 層只收帶 offset」。

### 5.1 兩支獨立 mutation 還是一支？參數形態？

**答：兩支獨立 mutation，參數形態照抄本尊。**

- 本尊就是兩支（鐵律 12 的 1:1 對齊）。合成一支（帶 `action: PUBLISH|UNPUBLISH`）會同時違反鐵律 12 與 `28 §0.3` 的 `resourceVerb` 慣例，且讓 `publishDate` 的「unpublish 時無效果」變成一個荒謬的欄位組合。
- 參數：`argument :id, ID, required: true` ＋ `argument :input, [ Types::Inputs::PublicationInput ], required: true`。**照抄本尊舊式 `input:`／扁平 `id:`**，引 `docs/dev/m2-publication-lifecycle.md` §5 #3 的既有豁免，**不重新裁定**（M14）。
- **命名偏離要登記**：`publishablePublish` 是 `interfaceVerb` 不是 `28 §0.3` 的 `resourceVerb`。照 `m2-publication-lifecycle` §5 #3 的先例明文登記為刻意選擇，不得靜默偏離。
- 形態範本＝**`productCreateMedia`**（`app/graphql/mutations/product_create_media.rb`）：全倉唯一與 `(id: ID!, input: [X!]!)` **結構同構**且語義是**累加（append）**的先例，錯誤路徑已是 `["<陣列名>", index.to_s, <欄位>]`。
  🔴 **必須刻意偏離它的一點**：`productCreateMedia` 的 `IDEMPOTENCY_KEY_REQUIRED` 硬擋**不抄**（§5.4）。
- 🔴 **不得**照 `productSet`／`collectionSet` 排版：那兩支是**宣告式全樹覆寫（未列出＝移除）**，語義與 S5 的累加**相反**。`publication_update_input.rb` 檔頭已有逐字警語：照那個習慣實作，「商家的一次勾選會清空整個管道」。
- `channelId` **不實作**（deprecated；第 12 包 §2.4 已裁定「deprecated 的不抄」，`28 §0.3.2` 的偏離「只減不加」）。
- **`shop` 欄位要不要跟**：本尊 payload 三欄含 `shop: Shop!`；`28 §0.3.3②` 明文允許 `Shop!` 出現；但我方三支 publication mutation 目前都只有 resource＋userErrors。⇒ **建議不跟**（我方 `Shop` type 目前無 `publicationCount` 欄，跟了要順帶新增一個零消費者欄位），在 dev doc §5 表登記為刻意偏離。

### 5.3 批次的部分失敗：整批 rollback 還是逐筆獨立？

**答：整批 rollback（all-or-nothing）。我方既有先例＝形態 A。**

**我方三種既有形態（層級 F）**

| 形態 | 代表 | 做法 | 為什麼那樣選 |
|---|---|---|---|
| **A 全有全無** | `Publications::Write.update`（**同一張表、同一組 GID 陣列、同一組 field path 慣例**） | 先 `resolve_publishables` 逐筆解析並收集帶索引錯誤 → 任一錯就整批不寫 → 才進 `ApplicationRecord.transaction` | — |
| B 逐筆部分成功 | `Storage::FileCreate` | 每列各自 rescue | 🔴 **理由是檔案系統不可回滾**，不是通用選擇 |
| C 驗證全收集→Guard→單 transaction | `Inventory::Adjust` | 唯一同時帶冪等鍵的批次先例 | 有錢／庫存動 |

🔴 **形態 A 是 S5 的直系先例，且已有 spec 釘死**：`spec/requests/publication_lifecycle_spec.rb:322` 逐字「🔴 任何一筆不合法 ⇒ 整批不寫入（不是寫一半）」，斷言 `expect(rows).to eq(0)`。
⇒ S5 走 A，**同一支 `Publications::Write` 內兩種語義不得分岔**。

**外部佐證（層級 E）**
- Shopify 的批次同步 mutation **預設全有全無**，逐筆獨立是明確 opt-in：`productVariantsBulkUpdate.allowPartialUpdates` 逐字 `When partial updates are not allowed, any error will prevent all variants from updating.`（<https://shopify.dev/docs/api/admin-graphql/latest/mutations/productVariantsBulkUpdate>，2026-08-27）。
- `metafieldsSet` 是**硬性 atomic**：`This operation is atomic, meaning no changes are persisted if an error is encountered.`（<https://shopify.dev/docs/api/admin-graphql/latest/mutations/metafieldsSet>，2026-08-27）⇒ 本尊**逐 mutation 裁定**原子性，不是全域政策。
- Saleor `errorPolicy` 預設 `REJECT_EVERYTHING`：`If a single error occurs, in at least one of the objects, the whole mutation fails and no data is saved.`（<https://docs.saleor.io/developer/bulks/error-policy>，2026-08-27）⇒ 兩家一致。
- ⚠️ 🔴 **`publishablePublish` 本身是否 all-or-nothing ＝未取得**（對 `partial`／`fails` 兩關鍵字在 mutation 頁皆 Not found，層級 D）。⇒ S5 取 A 是 **ours 裁定＋既有一致性**，**不得寫成「照抄本尊」**。
- 🔴 **不採用** Saleor 的第三級 `IGNORE_FAILED`（單筆內部分保存）——會讓資源落到半完成狀態。取捨登記 `docs/specs/107`。

**陣列上限**：用 `api.array_input_max_items: 250`（出處註釋指向 `28-api-contract.md:21`）。超限走 **userErrors `TOO_BIG`**（與 `publicationUpdate` 同線一致），**不走** `QueryType#nodes` 的 top-level `BAD_USER_INPUT`——理由要在 dev doc 寫明：**query 沒有 `userErrors` 可用，mutation 有**，這不是分岔。
🔴 **不得**引 `publication_bulk_products_max: 50`（M8）。

**🔴 不得用 `insert_all`／`upsert_all`／`update_all` 繞過 validation**：`resource_publications` 的 publishable 側**沒有 DB 外鍵**，唯一租戶守衛是 model validation `publishable_belongs_to_same_shop`（檔頭逐字：「擋不住 `insert_all`／`upsert_all`（Rails 一律跳過 validation）」）；同時 `future_publishing_supported_by_channel` 與 `variant_cannot_be_scheduled` 兩道排程守衛也會整組失效。N ≤ 250 逐列走 model 是既有裁定（`write.rb:127-132`）。

### 5.4 冪等：要不要進 `idempotency.required_for`？

**答：不進。但論證要換掉現有的那句。**

**判準（S1-F 既有，`docs/dev/m2-publication-lifecycle.md` §6）**：「重放會不會憑空多出一筆錢或一批庫存」。
- publish／unpublish 是**集合成員的 upsert／delete**，重放收斂到同一狀態 ⇒ 判準不命中 ⇒ 不進清單。
- 🔴 **但 `config/limits.yml:591` 給的理由不成立**（M5）：它說「那一類的併發防線是 `lock_version` 樂觀鎖」，而 `publications` 與 `resource_publications` **都沒有 `lock_version` 欄**（`db/schema.rb` 只有 6 張表有）。⇒ S5 若引 591 行，等於引用一條**不存在的保護**。
- **替代論述（S5 要寫進 dev doc 的）**：本表的併發防線是 ①`uq_res_pub_target` 唯一索引（擋重複列）②形態 A 的全有全無（擋半套）③**S5 新增的顯式 CAS／列鎖**（擋同列 `published_at` 的並發 UPDATE）。並在 `docs/specs/91` §3 登記「591 行的理由對 publication 線不適用」——🔴 **不改 `config/limits.yml`**（判準面，鐵律 18.3＋20.4：先登記候選、取得裁定後另開 18.3 PR）。

🔴 **`uq_res_pub_target` 擋不住的四件事**（S5 必須自己處理）：
(a) **同一列 `published_at` 的並發 UPDATE**（唯一索引不涉值 ⇒ last-write-wins）；
(b) 跨租戶 publishable（多型側無 DB 外鍵，唯一守衛是 model validation）；
(c) `insert_all`／`upsert_all`（跳過 validation ⇒ 連 (b) 也繞過）；
(d) 跨列不變量。
⇒ **S5 是全倉第一條 UPDATE 路徑**（S1／S2 全倉零 UPDATE），(a) 是本包新引入的風險。

**仍然必須做的兩件事**
1. 🔴 **resolve 開頭呼叫 `enforce_idempotency_contract!(nil)`**（沿用 `publication_create.rb:36`／`collection_set.rb:20` 寫法）——這是 CI 硬性：`spec/graphql/mutation_idempotency_call_spec.rb` 對 `app/graphql/mutations/**/*.rb` 每支具體 mutation 的 `resolve` **方法體**做靜態掃描，寫在註釋不算，不加就直接紅。
2. 🔴 **R9（取消排程＝寫 `Time.current`）不是收斂的**——重放兩次得到兩個不同值。這是「天然冪等」論述的**唯一例外**，dev doc 必須明寫，並在 §3.3 R10 選 reject（不讓 `null` 成為第二條非收斂路徑）。

**⚠️ 外部反向壓力（登記但不採納）**：Shopify 官方已在 2026-04 把冪等從可選升級為 **17 支 mutation 的 schema 層強制**（缺鍵 runtime error），涵蓋 refund 與**全部庫存調整**，理由逐字 `Duplicate inventory adjustments and duplicate refunds have long been a pain-point`（<https://shopify.dev/changelog/making-idempotency-mandatory-for-inventory-adjustments-and-refund-mutations>，2026-08-27）。**publishable 兩支不在該名單**。⇒ 正面支持我方判準；不構成 S5 要加鍵的理由。
**Guard 的結構限制（若日後要加）**：`idempotency_keys` 只有一組 `resource_type`／`resource_id` ⇒ **批量 replay 目前無實作**（`fileCreate` 已明文因此放棄 Guard）。S5 一次寫 N 列，只能把 `id` 指到的單一 publishable 當 result resource，N 列本身不可回放。**這一點要登記，不要在 S5 解。**
**Shopify 的批次冪等是 per row 不是 per bulk**（`idempotency is applied per row in your JSONL input file, not per the entire bulk operation.` / `reusing a single key across rows causes rows after the first to be treated as duplicates.`，<https://shopify.dev/docs/api/usage/implementing-idempotency>，2026-08-27）⇒ 若未來 S5 要加鍵，**必須每筆 item 各帶一把**，不是請求層一把。登記備查。

### 5.5 與 S1 三支的邊界：會不會有兩條路做同一件事？

**答：會，而且這是本尊的既有設計，鐵律 12 要求照抄。**

把 publishable P 加進 publication X，兩條路都合法：
- `publicationUpdate(id: X, input: { publishablesToAdd: [P] })`（S1，以 publication 為中心）
- `publishablePublish(id: P, input: [{ publicationId: X }])`（S5，以 resource 為中心）

官方自己也把兩者並列並給用法建議（層級 B）：`The mutations above are resource-centric… For the inverse pattern, picking a publication and managing which products it contains, use the publicationUpdate mutation.` / `Use publishablePublish when managing a single product's channel presence. Use publicationUpdate when managing a publication's product catalog.`（<https://shopify.dev/docs/apps/build/sales-channels/product-publishing.md>，2026-08-27）
⚠️ 官方對「同一配對經兩支寫入時的優先權／衝突」＝**未取得**（五頁皆無）。不得反向斷言「官方認為兩者等價」。

🔴 **功能邊界在 `publishDate`**：`PublicationUpdateInput` 無 `publishDate` ⇒ **排程只能經 S5 進入系統**。

**S5 必須交付的收斂（鐵律 7「數字同源」在規則面的等價要求）**
1. 兩支 mutation 都是 `Publications::Write` 的薄殼，共用**同一份**「哪些配對要建／刪／改期」規則與**同一份** bump 規則。
2. 🔴 **S5 交付 UPDATE 路徑後，必須回頭讓 `publicationUpdate` 走同一份**，否則同一件事經兩支得到兩種 `published_at` 結果（S2 §4-E4 已登記：`find_or_create_by!` 的 create-only 區塊在「先 remove 再 add」時會重寫 `published_at` 為現在＝**靜默取消排程**）。這是同一元件的狀態矩陣封閉，**在鐵律 20.5 的允許射程內**。
3. 復用既有私有工具，**不新寫第四份 GID parser**：`Publications::Write.parse_publishable_gid`（regex `\Agid://chilllove/([A-Za-z]+)/(\d+)\z` ＋ `PUBLISHABLE_TYPES` 白名單）解 `id`；`Publications::Lookup.call` 解 `input[].publicationId`；另復用 `resolve_publishables`（帶索引錯誤）／`bump_stamps_for_pairs!`／`reject`／`invalid_result`／`not_found_errors`。`lookup.rb` 檔頭已逐字劃定邊界：**不順手做全域 GID parser 重構**（鐵律 20.5）。
4. **`operation_status` 鎖**：`publications.operation_status` 已有欄位、validation 與 `operation_in_progress?` 謂詞，但**零消費者**（S1-B 逐字：「仍然零寫入者、恆為 null」），且 `publication.rb:56-65` 註釋逐字把消費者劃給「S1／S5」。⇒ **S5 要嘛同批接上寫入守衛，要嘛在 dev doc 誠實登記鎖仍空掛**，🔴 **不得默認它已生效**。⚠️ 其實地形態（進度數字、鎖住範圍）需安裝管道 app，使用者已裁定不安裝（S1-U2）⇒ 形態只能是 ours 裁定。

### 5.6 cache stamp 與事件要不要在這一步接上？

**cache stamp：要（義務性），且只准有一份規則。**
- `catalog_flow.cache_stamp_sources` 已把 `products.publications_updated_at` 列為正典（`config/limits.yml:2847`）⇒ S5 的 bump 是**履行既有義務**，不是新增機制。
- 🔴 **「哪些變動 bump 誰」目前已有兩份平行實作**：`Materialize.bump_publications_stamp!`（單筆）與 `Write.bump_stamps_for_pairs!`（批次），兩份都自陳「規則同一份」卻各寫一次 case 分派。**S5 不得寫第三份** ⇒ 走 `bump_stamps_for_pairs!` 單一入口，並把 `Materialize` 那份改成呼叫它（同一元件，鐵律 20.5 允許）。
- 兩條硬約束：①**不得動 `lock_version`** ⇒ 必須用 `update_all` 的**字串形式**（hash 形式會自動遞增，實測：發布列一建立，商家手上的 `product` 物件立刻 `StaleObjectError`）；②**Collection 不 bump**（`collections` 表沒有該欄）⇒ Collection 的發布變動**目前沒有任何 cache stamp 表達**，這是必須誠實登記的既有限制，🔴 **不得**順手加欄（schema 變更＋18.3）。
- ⚠️ dev doc **不得**寫「bump 了所以前台快取會失效」——`products.publications_updated_at` 目前**零讀取者**（消費端 W6 前台包尚未存在）。正確寫法：「正典已宣告它，S5 履行寫入側義務；讀取側尚無消費者」。
- 🔴 `at` 必須傳 `Time.current`，與 `publishDate` 解耦（§3.4）。

**事件：只在 S5 交付排程寫入時，才必須接上；且必須同批接消費者。**
- S2 §4.B 的正解已定：**在建立／更新排程列的同一個 transaction 內補一筆 outbox**，topic 用既有 `Events::Topics::PRODUCT_PUBLICATION_CHANGED`，**`available_at: published_at`**；消費者到點 bump cache stamp。
- 🔴 **S5 是 `event_outbox.available_at` 未來值的第一個使用者**（既有六個 producer 一律寫 `Time.current`）⇒ dev doc 必須明寫這一點；既有 spec 從未覆蓋該分支。
- 現況：`PRODUCT_PUBLICATION_CHANGED` 唯一生產者是 `Catalog::StatusTransition`，且 `Events::Consumers::REGISTRY` **零消費者**（現有四鍵：MEDIA_UPLOADED／PRODUCTS_CREATE／PRODUCTS_UPDATE／INVENTORY_ADJUSTED）。⇒ **只發不接＝製造第二個空掛件**。
- 🔴 生產端**只掛顯式 publish／unpublish 與排程列建立**，不掛 `Materialize` 的 `after_create`（M15）。
- **依賴**：S2 §7 的 PR-C（到點副作用機制）明文「🔴 必須等 S5 的寫入路徑合併後才開工」⇒ S5 至少要交付「會寫未來 `published_at` 的路徑」＋「該路徑會投出帶未來 `available_at` 的事件」，PR-C 才開得了工。
- ⚠️ 官方 webhook 面：product-publishing 指南頁**完全未提** webhook／event（層級 D，八節逐節檢查）。鄰頁的 `scheduled_product_listings/add`／`product_listing/add`／`SCHEDULED_PRODUCT_LISTINGS` 屬 **channel app 的 product listing 語義**，與 Publishable／publication 模型不是同一層（兩頁未說明關係），且該條 verbatim 為抓取層節錄。⇒ **不得**照抄任何 topic 名稱。

## 8. 建議的 PR 切分（鐵律 17.4 收斂模式，含依賴順序）
