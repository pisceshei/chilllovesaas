> 實測依據＝`docs/research/82-admin-channels.md` §10。

## §1 目標形態

本尊實測的四層（`82` §10.3，一個 payload 抓齊）：

```
Publication ──catalog──> AppCatalog ──apps──> App ──installation──> AppInstallation
                              └────channels──> Channel
```

我方對應（表名一律用**我方實際名字**，不抄本尊）：

```
publications ─sales_catalog_id─> sales_catalogs ─┬─(app 身分)
                                        └─> channels ──> app_installations
```

## §2 五張表逐表設計

### T1 `sales_catalogs`（租戶級）

**為什麼要它**：`publications.catalog_id` 已存在**兩週且恆為 NULL、無外鍵、無寫入者**
（決策文件 C-4）。本尊**每個 publication 都有 catalog**（`82` §9.5b／§10.3 兩次抓包），
我方的 `online_store` 沒有 ⇒ 三層 AND 的第三層永遠 no-op。

| 欄 | 型別 | 說明 |
|---|---|---|
| `shop_id` | bigint NOT NULL | 鐵律 2 |
| `catalog_type` | varchar(24) NOT NULL | `app` / `market` / `company_location`（對位本尊 `CatalogType`；`none` 不落庫） |
| `title` | varchar(255) NOT NULL | 🔴 **管道顯示名的權威來源**（本尊 `Publication.name` 已 deprecated → `Catalog.title`）。上限 255 是實測值（`82` §9.5c 的 `0/255` 計數器） |
| `status` | varchar(16) NOT NULL default `active` | `active` / `archived` / `draft`（本尊 `CatalogStatus` 三值；admin UI 只曝露前二） |
| `auto_include_new_products` | boolean NOT NULL default true | 對位 catalog 表單的 `Automatically include new products in this catalog`（`82` §9.5c 實測預設**開**）。⚠️ 與 `publications.auto_publish` **是兩層**，不得合併 |

**索引**：`uq_sales_catalogs_tenant_id (shop_id, id)` unique｜`ix_sales_catalogs_type (shop_id, catalog_type, status)`
**外鍵**：`fk_sales_catalogs_shop`

🔴 **不建 `price_lists`**：本尊的 `Catalog = publication + priceList` 是兩個獨立子物件
（`82` §9.5b 抓到 `CatalogCreate` 與 `CatalogPriceListCreate` 是**兩支操作**）。
定價屬 M5／S10 射程，本步只建 catalog 本體並在此登記方向，**不預留欄位**
（預留無人寫的欄正是 `catalog_id` 這次的教訓）。

### T2 `channels`（租戶級）

**為什麼要它**：`channel_handle` 目前掛在 `publications` 上，而本尊的 handle 在 `Channel`
（決策文件 C-2），且**帶每店後綴**（`82` §10.3 實測 Shop 的 handle 是 `shop-72` 不是 `shop`）。

| 欄 | 型別 | 說明 |
|---|---|---|
| `shop_id` | bigint NOT NULL | |
| `publication_id` | bigint NOT NULL | 🔴 **FK 在 channels 這一側**——本尊是 `Publication : Channel = 1 : N`（官方 SDL）。⚠️ 實測第一方管道上兩者共用 id、退化成 1:1（`82` §10.3），但 schema 照官方基數做，不照實測的退化形 |
| `app_installation_id` | bigint | 可 NULL：Agentic 型管道**不需安裝**（`82` §10.1／§10.5） |
| `handle` | varchar(64) NOT NULL | 每店唯一，可帶後綴 |
| `channel_type` | varchar(24) NOT NULL | `app` / `agentic`（對位 `Channel` vs `AgenticChannel` **兩個不同的 GraphQL 型別**，`82` §10.5） |
| `status` | varchar(16) NOT NULL default `active` | 實測 agentic 子管道顯示 `Inactive`（`82` §10.5） |
| `account_id` / `account_name` | varchar(255) | 多帳號連線用；v1 恆 NULL |
| `resource_feedback_state` | varchar(24) | `accepted` / `requires_action`；本尊 `ResourceFeedbackState` 恰兩值。v1 恆 NULL |

**索引**：`uq_channels_tenant_id (shop_id, id)` unique｜`uq_channels_handle (shop_id, handle)` unique｜
`ix_channels_publication (shop_id, publication_id)`
**外鍵**：`fk_channels_shop`｜`fk_channels_publication_id (shop_id, publication_id) → publications (shop_id, id)`｜
`fk_channels_app_installation_id (shop_id, app_installation_id) → app_installations (shop_id, id)`

### T3 `app_installations`（租戶級）

**為什麼要它**：「已安裝」這個狀態目前無處表達（決策文件 C-5）。
安裝＝INSERT publication、卸載＝DELETE publication 的做法會**連帶清掉全部發布列**
（`resource_publications` 對 `publications` 有 composite FK），重裝後商家的逐商品設定全消失。

| 欄 | 型別 | 說明 |
|---|---|---|
| `shop_id` | bigint NOT NULL | |
| `app_handle` | varchar(64) NOT NULL | 見 §3 的待裁定：這裡是 FK 還是 denormalized 字串 |
| `installed_at` | datetime NOT NULL | |
| `uninstalled_at` | datetime | 🔴 **軟刪**。四家外部平台無一硬刪管道（研究共同結論）。⚠️ 所有讀取都要帶 `uninstalled_at IS NULL`，漏一處＝卸載的管道還在發布 modal 裡 ⇒ 用 `default_scope` 不安全（`unscoped` 會繞過），改用**明確的 `scope :active`** 並在 model 註釋寫明 |

**索引**：`uq_app_installations_tenant_id (shop_id, id)` unique｜
`ix_app_installations_handle (shop_id, app_handle, uninstalled_at)`
**外鍵**：`fk_app_installations_shop`

### T4 `apps` —— 🔴 **本檔唯一需要裁定的子決定**，見 §3

### T5 `publications`（既有表，改語義不改結構）

| 動作 | 說明 |
|---|---|
| `catalog_id` 改名 `sales_catalog_id` ＋ 上 composite FK | `(shop_id, sales_catalog_id) → sales_catalogs (shop_id, id)`；回填後轉 NOT NULL（NOT NULL 屬 S1，見下） |
| `name` **降級為 legacy 唯讀** | 權威改為 `catalogs.title`（本尊 `Publication.name` 已 deprecated）。**不刪欄**：刪欄要改所有讀取端，屬 S1 射程 |

| 🔴 **新增五個能力旗標** | `supports_bundles` / `supports_combined_listings` / `supports_variant_fixed_bundles` / `supports_subscriptions` / `supports_publication_for_unlisted_products`，皆 boolean NOT NULL default true。實測本尊六個旗標我方只有一個（`82` §10.4） |
| 🔴 **新增 `operation_status`** | varchar(16)，NULL＝無進行中操作。對位本尊 `Publication.operation` 與 `ResourceOperationStatus`（**恰三值 `created`/`active`/`complete`，沒有 failed**）。`82` §9.5d 實測進行中會鎖住逐商品切換 |

## §3 🔴 待裁定：`apps` 要不要做成平台字典表

本尊的 `App` 是**全域**的（它是 App Store 的目錄），`AppInstallation` 才是每店的。

### 選項 ①：`platform_apps`（平台字典表，**忠於本尊**）

- 無 `shop_id`，自然主鍵 `handle`，隨版本部署 seed（形態抄現有的 `platform_locales`）
- 欄：`handle` PK｜`title`｜`developer`｜`has_channel_capability` boolean｜`first_party` boolean
- 🔴 **代價**：新增平台字典表要走**鐵律 2 配套條款③**——
  同時改 **CLAUDE.md 鐵律 2 本文** ＋ `docs/specs/71` §A G24 ＋
  `scripts/check-tenant-isolation.rb` 的 `NON_TENANT_TABLES`（該腳本的錯誤訊息逐字要求這三件事）
- ⇒ 該 PR 同時落入 **鐵律 18.3**（改 `scripts/` 與規範本文 ⇒ 人工合併）
  與 **鐵律 17.3**（改鐵律本文 ⇒ 必須停下來問使用者）
- ✅ 判準是滿足的：CLAUDE.md 的平台字典表段落逐字寫「表裡**一列都不屬於任何一家店**才算」，
  而 app 定義（handle／title／開發者）確實一列都不屬於任何店

### 選項 ②：不建 `apps`，把 app 身分放在 `app_installations` 上

- `app_installations` 加 `app_title`／`app_developer`／`app_first_party`
- ✅ 零鐵律變更、零腳本變更 ⇒ 不落入 18.3／17.3
- ❌ 每店重複一份 app 定義（v1 只有 3–4 個第一方管道 ⇒ 每店 3–4 列的重複）
- ❌ 與本尊的形狀有差：本尊 `App` 是獨立實體且 `AppCatalog.apps` 是 **connection**（1:N）

### 我的建議：**選項 ①**

理由：使用者裁定的就是「本尊全形」，而選項 ② 在最核心的那一點（App 是獨立實體）上偏離。
配套條款③ 的三件事都是**小改動且判準已經寫在鐵律裡**（平台字典表這個類別 2026-08-23
就為 `platform_locales` 建立了，本次是**套用既有規則**而不是新增規則）。

🔴 但它需要**改 CLAUDE.md 鐵律 2 的本文**，而鐵律 17.3 明文要求這件事停下來問。

## §4 施工順序（每一支 migration 都可獨立回滾）

| # | 內容 | 為什麼是這個順序 |
|---|---|---|
| M1 | 建 `sales_catalogs` | 無依賴。`publications.catalog_id` 已存在，先讓它有對象 |
| M2 | 回填：為每筆既有 publication 建一筆 `sales_catalogs`（`catalog_type: 'app'`，`title` 取自 `publications.name`），並寫回 `publications.sales_catalog_id` | 🔴 **必須有「先種既有資料再回填」的 spec**（第 11／12 包的固定處理） |
| M3 | `publications.sales_catalog_id` 轉 NOT NULL ＋ 上 composite FK | 回填完才能加約束 |
| M4 | 建 `app_installations`（依 §3 的裁定決定要不要先建 `platform_apps`） | |
| M5 | 建 `channels` ＋ 回填（為每筆 publication 建一筆 channel，handle 取自 `publications.channel_handle`） | 依賴 M4 |
| M6 | `publications` 加五個能力旗標 ＋ `operation_status` | 無依賴，可與 M1 合併 |

🔴 **`Shop#after_create` 要從建 1 列變成建 4 列**（app_installation → channel → catalog → publication），
且必須在**同一個 transaction**。順序不可倒：catalog 要先於 publication（`catalog_id` NOT NULL）。

## §6 本方案不做的（明文劃線）

1. **`price_lists`**——`Catalog = publication + priceList` 的另一半，屬 M5／S10
2. **catalog 成員的三值語義**（Included／Excluded／All，`82` §9.5c）——屬 S10
3. **非同步操作的實際行為**（只建 `operation_status` 欄，不做狀態機）——屬 S1
4. **`AgenticChannel` 獨立成表**——先用 `channels.channel_type = 'agentic'` 表達；
   本尊那是獨立 GraphQL 型別，但實體性**未取得**（決策文件 U-5）
5. **`agenticCatalogDiscoverable`**（商品層專屬布林，`82` §10.5）——屬 S7
6. **安裝／卸載的實際流程**——三條關鍵未取得都需要安裝管道才測得到，使用者已裁定不安裝

## §7 落地狀態（2026-08-26 更新）

### §7.1 🔴 表名更正：`catalogs` → `sales_catalogs`

本檔原文（同日稍早）把 T1 寫成 `catalogs`，模型名 `Catalog`。**實作當下證偽**：

```
TypeError: Catalog is not a module
  app/models/catalog.rb:33: previous definition of Catalog was here
  # ./app/services/catalog/media_sync.rb:3:in '<main>'
```

本倉庫的 `Catalog` 常數**已被服務層命名空間佔用**——`Catalog::SaveProduct`／`MediaSync`／
`SaveCollection`／`CacheStamps`／`HandleChange`／`OptionValuesDigest`／`ExternalVideoUrl`／
`DeleteVariant` 等掛在 `module Catalog` 之下，語義是「商家的**商品目錄**操作」；
本尊的 `Catalog` 是「publication ＋ price list 的容器」。**同字兩義。**
宣告 `class Catalog < ApplicationRecord` 讓 8 個 spec 檔在載入階段全數失敗。

⇒ 表名與模型名都加 `sales_` 前綴；`publications.catalog_id` 一併改名 `sales_catalog_id`
（該欄自建立以來 app 層零讀者零寫者，複驗指令：`grep -rn 'catalog_id' app/ lib/`）。
對外 GID Type 仍照鐵律 4 對齊本尊（`AppCatalog` 等），那是序列化層的事。
