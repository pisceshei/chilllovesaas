## 一、診斷結論（根因）

### 根因 1：散文被送進了沒有機械閘門的驗收迴圈
代碼有編譯器/測試/CI 當機械閘門，LLM 驗收方只需審增量；規格文檔沒有，驗收方每輪對全文重掃——文檔越厚掃描面越大，意見越多，修意見又讓文檔更厚。PR #52 跑到 25 輪、最近 12 個 commit 全是驗收輪次文檔修正、零功能代碼交付，是這個正回饋迴圈的直接產物。
⇒ **對策**：凡能機械驗證的斷言，先做成 CI 規則再寫進文檔。本方案每個工作包都指定機械判準。

### 根因 2：登記制度用「行號」與「自述計數」當主鍵，兩者都會腐化
原型行數 4,700→13,390，四份 UI 稽核檔全拿行號當主鍵，每輪重新定位＝制度性重工。**6 個確認的假數字**（50 表3 自述15實16/總計313實314；83 §0「7條」實10；84「81條」而71現值76；50 §P1「33」實32；48「63 token」實82宣告78新增；53「162」排除自己§6+§9 ⇒ 真實180）。**同一根因重複登記 8 組**。51 號唯一沒有複查檔，實測多數已修無人銷帳。83 §8.1 宣稱修6條，複驗至少3條未成立。
⇒ **對策**：登記簿主鍵改內容錨點；計數必附複驗指令；「已修」宣稱 CI 抽驗。

### 根因 3：權威文件的「指定」與「實際內容」脫節
鐵律 8 指定 `docs/design/23` 為 CSS 單一真相，實測只有 35 token/16 元件/64 格規格 56% 空白/對 47・48・64 引用 0 次。三份原型被迫各自發明 225/111/195 套 token。`tokens.css` 對原型實際消耗落地率 19%。
⇒ **對策**：權威文件同輪升版到與職責相符，否則改鐵律指向。

## 四、功能豐富化八領域（官方＋業界取證 2026-08-18；全文報告落入 `research/121`）

**跨領域三個結構性結論**：
① **Metaobject 是全案最大槓桿**——同時是自訂頁面核心、內容模型、GEO 結構化資料來源，排在所有豐富化領域之前做；
② **商品資料品質雙重收益**——GMC feed 驗證器（乾淨屬性/即時準確/結構化）恰好是接入 UCP/agentic 的前置條件（Q1 2026 AI 導流年增 8 倍、AI 訂單近 13 倍）；
③ **抄 Shopify 的參數、補 Shopify 的缺口**——參數（webhook 8 次/4 小時、feed 30 天新鮮度、metafield/metaobject 分界）直接抄；缺口（webhook replay、留言管理 UI、編輯行事曆、獨立作者、費用明細頁、flow 內 A/B 與 exit condition）就是差異化清單。

### 5.0 原型的擴充機制（實測結論：兩份原型都有明確的「登記表」，新功能＝照表掛載，不是自由發揮）

**admin-v2（13,390 行）新增一個模組頁的固定五步**：
① `NAV`（L2225–2248，`{id,name,icon,kids}` 陣列）加項 → ② `GROUP_OF`（L2249）登記高亮歸屬 → ③ 寫 `function xxxPage(){return listPage({...})}`（`listPage` cfg 全欄位：key/title/doc/actions/views/filters/cols/rows/bulk/empty 三件套/ai——現行 29 個模組全走此引擎）→ ④ `Object.assign(MODULES,{'m-xxx':{title,full:true,custom:xxxPage}})` → ⑤ 每個 `data-doc` 補 DOCS 四欄條目。
**詳情頁要同步五張表**：`DETAILS`（L9031）/`FORMSEL`（L9037，沒登記＝沒有 save bar）/`URL_OPEN`（L2353，冷開網址降級）/`GROUP_OF`/`afterRoute`（L9051，重繪後推回狀態）。

**storefront-v2（4,938 行）**：`ROUTES` 四元組表（L2296–2319，`[正則, view 函式, skeleton, 標題]`，順序敏感——長路徑在前）；會員區 `acctShell(active, body)`（L3682）的 nav 陣列（L3683）加分頁；市場×語言雙維度（`MARKETS`/`PACKS`/`rebindPackData()`），內容文案走 `sfTr()`、法域文案走 pack。

**lint 硬約束（新增 UI 的違憲條款，全部 CI 強制）**：
- 🔴 **死控件基準線零餘裕**（admin 43／storefront 55，現值恰好打滿）：每顆新 `<button>/<select>/<input>` 必須接線（inline handler／`data-f`／`data-val`／被選擇器讀到的把手／`data-read`），不得調高基準線（`check-baseline-raise.py` 硬擋）

## 九、部署與 CI/CD 方案（裁定 5：既有伺服器；裁定 6：自動合併）

### 9.1 架構
```
開發機（本地）──push──▶ GitHub（倉庫＋Actions）──deploy──▶ 既有伺服器
                          │                                  Docker（Kamal 2 管理）
   PR 分支 ──▶ 機械 CI（scripts/ 現行全部 check/test/lint 腳本＋rspec/typecheck/brakeman/schema drift）
           ──▶ Claude bot 判詞 ＋ Codex review（倒計時 15–25 分鐘自動輪詢）
           ──▶ 雙零意見 ∧ CI 全綠 ∧ 判詞格式驗證 ⇒ 自動合併 main
   main ──▶ deploy job：kamal deploy ⇒ /up healthcheck ⇒ 失敗自動 rollback＋開坑
```

### 9.2 要點
0. **起點現況（已核實）**：部署基建**完全空白**（無 Dockerfile/.kamal/deploy job/kamal gem），但 `config/database.yml` production 四庫（primary/cache/queue/cable）已齊、`force_ssl`/`solid_queue`/`solid_cache` production 設定已就緒；⚠️ `config.hosts` 仍註解——多租戶自訂網域上線前必須處理。
1. **技術選型**：Docker + **Kamal 2**（Rails 8 官方部署路線＝既定 M7 選型提前，不分岔）。伺服器上：MySQL 8 容器（或既有 MySQL）＋ web 容器 ＋ Solid Queue worker 容器；kamal-proxy 做零停機切換與 TLS。
2. **環境**：先立 **staging**（子網域，例如 `staging.<domain>`）；production 在 M3 成交閉環後開。secrets 走 `.kamal/secrets`＋GitHub Actions secrets（`KAMAL_REGISTRY_PASSWORD`/`RAILS_MASTER_KEY`/SSH key），**絕不入庫**。
3. **先部署 walking skeleton**：現有代碼（登入＋商品空態）第一週就上伺服器——「先部署、一邊開發、一邊 commit、驗收過再部署新內容」的字面落實；此後每次 main 合併自動部署。
4. **部署驗證自動化（鐵律 17 應用）**：deploy job 後自動輪詢 `/up`（2–5 分鐘倒計時）；紅 ⇒ `kamal rollback` ＋自動開坑條目＋通知。
   🔴 **rollback 的 DB 前提**：`kamal rollback` 只回退應用映像、不回退 schema ⇒ 全部 migration 採 **expand/contract**（先加後刪、新舊版共用 schema，前一版相容為部署硬前提；不可逆 DDL 由 strong_migrations 擋）——否則 schema 已前移時回退的舊映像照樣不可用；不採 contract 前不得刪欄/改欄語義。
5. **DB migration 紀律**：`kamal deploy` 前跑 migration（M 階段起用 strong_migrations 擋不可逆 DDL——原 M7 內容提前）。
6. **執行時需使用者提供**（一次性）：伺服器 SSH 位址/使用者、OS 與規格確認、要綁的網域、Docker registry 選擇（建議 ghcr.io，免費）。

### 9.3 自動化執行 SOP（單一任務的標準循環，鐵律 16/17/18 合成）
```
取下一個工作包 → （需要時：上網深度研究，斷言帶來源＋取證日期）
→ 實作 → 全部閘門逐支看退出碼——**正典入口＝`bin/ci`**（步驟集由 `config/ci.rb` 定義、
   `scripts/check-ci-parity.rb` 機械斷言其與 ci.yml 引用同步：「增刪 checker 不腐化本 SOP」
   由該機制保證；rubocop/rspec/brakeman/typecheck/pnpm 系與 schema drift 都在其內）；
   `ls scripts/ | grep -E '^(check|test|lint)-.*\.(rb|sh|py)$'` 枚舉的只是其中
   **scripts/ 檢查器子集**（純文檔改動的最小必跑集）、**不得稱「全部」**
   （第 11 輪依 #58 bot R10 🟡2 更正：舊寫法會讓動代碼的包 push 前漏跑 rubocop/rspec/
   brakeman/typecheck/pnpm 系與 schema drift——集合以 `config/ci.rb` 步驟表為準）
   → commit（鐵律 15 逐款）→ push → @codex review
→ 掛倒計時（15–25 分鐘）自動查判詞
   ├─ 有意見 ⇒ 只修點名處（可上網研究）⇒ 重跑閘門 ⇒ commit ⇒ push ⇒ 重掛倒計時
   ├─ 四條件齊（Codex 完成且零未清 ∧ bot 通過且零未清 ∧ CI 全綠 ∧ 判詞格式驗證）⇒ 自動合併
   │    🔴 本分支 **18.4 啟用後才可達**（P-8 交付＋真實 PR 實測＋信任邊界後才翻 `AUTO_MERGE`）；
   │      啟用前（現況）一切 PR 屬過渡期人工合併（CLAUDE.md 17.3／18.4），一律走下一條分支
   │    ├─ CD-1～CD-3 尚未收口（現況）⇒ **鏈路止於合併**，直接進下一個工作包（與 P-8 判準「止於合併」同界）
   │    └─ CD 已收口 ⇒ 自動部署 ⇒ healthcheck 綠 ⇒ 下一個工作包（不等確認）
   ├─ 雙零但屬人工合併類（18.3 清單，或 18.4 啟用前的一切 PR）⇒ 通知使用者、待人工合併；其依賴鏈暫停自動前進，無依賴任務可並行
   └─ 未收斂輪數**超過** MAX_FIX_ROUNDS（現值 3）的下一輪 ⇒ 機制自動掛人工裁定標籤停驗收，轉做下一包（不空等；與 CLAUDE.md 17.4 同義）
例外停下：憑證紅線／破壞性操作／改鐵律／不可逆 schema 裁定／產生費用
```
