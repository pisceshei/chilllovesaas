## ② 為什麼這樣改（含被推翻的假設）

- 🔴 **「權限」不是一張 checkbox 表，是一張有方向的依賴圖**。實測只看到「勾子自動補父」，
  help 補完另一半：**撤銷會往下連動移除**，而且 **Inventory／Catalogs 任一權限 → Products>View
  且不可取消**。照樹狀實作會漏掉撤銷傳播與不可取消的邊。
- 🔴 **角色是組織層資源，可跨店** —— 這與我方鐵律 2「全表帶 `shop_id`、複合索引以 shop_id 開頭」
  **正面衝突**。這不是 UI 差異，是資料分區的根本假設問題，**必須在 M1 動任何權限表之前裁定**。
  （這也解釋了為什麼本尊把使用者頁放在組織區塊而不是商店區塊。）
- **兩條「設定裡沒有」的事實推翻直覺**：**時區與語言是使用者層級**（本尊一般設定明文叫你去帳號設定）、
  **顧客看到的幣別在 Markets**（這裡只是店幣）。我方把時區做成商店級單一值——訂單時間顯示的
  語義會與本尊不同。
- **help 與實測互相打臉兩次，都以實測為準**：①權限分組 help 是扁平 19 群、實測是巢狀 17 群
  （同一批權限、不同邊界）⇒ 裁定「UI 照實測、語義照 help」②建立角色的 step-up auth
  **help 完全沒寫**，實測才發現。反過來，help 也補了實測拿不到的一大塊（座位上限、Groups、
  敏感權限 7 條、品牌欄位限制、活動記錄 250 筆）——**這一輪最能說明為什麼層⑤是雙源不是備援**。
- **G13 第三次複核維持**：Translate & Adapt 的 Adapt 是「同語言的市場專屬覆寫」，走
  「語言 × 市場」而非「翻譯表帶 market_id」——與 R10-DOC2 一致。
- **我沒有走完 12.2**：儲存角色被密碼再驗證擋下，我不輸入密碼（即使是測試店）。
  已明確登記為 R12-V2，沒有假裝流程走完。

## ④ 下一個人要注意什麼

1. **動權限表之前先看 STRUCT1**。角色跨店這件事會影響 migration 的第一張表；
   在裁定之前不要先寫 `role.shop_id`。
2. **依賴圖要雙向**：授予往上補齊祖先、撤銷往下連動移除，並標記「不可取消」的邊
   （庫存/目錄 → 產品·檢視）。`limits.users_and_roles.non_deselectable_dependencies` 已列。
3. **高敏動作要 step-up auth**：建立角色、移除使用者都需重新輸入密碼。這是 help 沒寫、
   只有實測看得到的東西——**下次遇到「儲存被擋」不要當成錯誤，先看它要什麼**。
4. **實測方法坑（本輪踩到）**：用 JS `element.click()` 測 React 受控 checkbox 會得到**假陰性**
   （DOM 變了但框架狀態沒變，表單還會報「至少必須授予一項權限」）。
   **測交互一律用真實滑鼠座標點擊**；JS 只用來讀取與定位。
5. **虛擬捲動列表要先捲到底再讀 innerText**（通知範本清單就是這樣漏了尾段）。
6. **設定頁只做了一半**，清單在 worklog 的 Pending 段。接手的人不要以為 R12 已經把設定掃完。
