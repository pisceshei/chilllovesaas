# 交接：第 3 包 共用遷移批次

分支 `m1/p3-shared-migrations`，base＝`main`。W5 塊 A 的第一包。

## ① 我改了什麼

**目標**：cache stamp 五欄＋`files.alt_source`＋`orders.locale_snapshot` 一次遷移到位，
並把**現有寫入者**全部接上 bump——欄位在、沒人 bump＝永久舊快取（靜默失敗）。

**遇到的問題與證據**：
1. **原清單六項有三項已由先前包落地**（unavailable buckets／冪等索引改型／actor），
   逐項對照現行 schema 的證據見配對 worklog 首節的表。
2. 🔴 **Rails 8.1 的 `update_all` 對有樂觀鎖的 model 自動 +1 `lock_version`**
   （實測 0→1；首輪被既有 C6 spec 的 destroy 撞 StaleObjectError 抓到）。
   不修的後果＝改一張共用圖的 alt 會讓所有正在編輯相關商品的人存檔撞 STALE_OBJECT。
3. MySQL DDL 不進交易：backfill 被 strong_migrations 擋下時欄已加、版本未記，
   重跑撞 Duplicate column ⇒ 遷移做成冪等（`if_not_exists`）。

**對抗式審查**：12 項確認、9 個根因全修（詳表見配對 worklog）。最痛的兩個＝
①我自己在檔頭點名「本模組最容易犯的錯」，第一版就在 `build_media!` 犯了（fileId＋alt
掛共用檔只 bump 目標商品）；②TOUCH 的 `CURRENT_TIMESTAMP(6)` 用 session 時區
（本機台北 +8），stamp 被讀成未來 8 小時——改 `UTC_TIMESTAMP(6)`。

**驗證輸出**（快照 2026-08-25 修復後，複驗＝重跑）：rspec 全綠、rubocop 0 offense、
vitest 全綠、tsc 乾淨。守衛（首輪 13＋修法 4）逐一突變驗證。

## ② 為什麼這樣改

- **stamp 欄 nullable**：`null: false` 會要求每個 `Product.create!` 帶值（炸全部
  factory）；null＝「立欄前未變動過」，快取 key 端當 epoch。backfill 用 `updated_at`
  （全樹鎖下任何儲存都 bump 它 ⇒ 是三個 stamp 的上界，誠實起點）。
- **`alt_source` 不 backfill**：存量 alt 來源未知，猜＝把未取證假設寫進資料（鐵律 19）。
- **`CacheStamps` 是唯一寫入面**：分散各處手寫 update_all 的話，「lock_version 釘住」
  這種坑要每處各修一次。TOUCH 字串（`…, lock_version = lock_version`）是 Rails
  官方的 opt-out 慣例，**不得改回 hash 形式**（有突變測試釘住）。
- **`from_state`／`to_state` 不建欄**：我方 ledger 是多桶 delta 形狀，移動＝同列
  -X／+X 兩個 delta，from／to 可導出；另立欄＝第二份真相，且現無任何寫入者。
- **SaveProduct 恆 bump variants stamp 不精算**：宣告式全量恆重寫變體樹，
  精算「這次有沒有真的變」漏一種形態就是舊快取。

**被推翻的假設**：
- 「六項都要做」——三項已落地（先盤點再動手救了三支白做的遷移）。
- 「`update_all` 不會碰 lock_version」——Rails 8.1 會，實測推翻。
- 「limits 的 stamp 清單在 `cache` 區」——實際在 `catalog_flow`。

## ③ 還有什麼沒解決

- **三個欄無寫入者**（刻意）：`publications_updated_at`（第 12 包）、
  `catalog_version`（第 32 包）、`locale_snapshot`（M3）。`known_pending` 現在是
  **綁未來表的真機制**（審查 DOC-3 後升級）：markets／price_lists 表一建，
  `cache_stamps_spec` 當場紅，逼你把來源換成帶前綴寫法並建 stamp 欄。
- **alt_source 殘餘風險**：未來 AI／匯入寫入者忘了顯式帶來源會被錯標 human
  （`StoredFile#stamp_alt_source` 註釋已寫明義務）。
- **bt3 實跑與線上驗收未做**（合併部署後）：要查 backfill 落到存量列、
  以及線上改一張共用圖的 alt 後兩個商品的 `media_updated_at` 都動了。

## ④ 下一個人要注意什麼

- **入口**：`app/services/catalog/cache_stamps.rb` 檔頭四條。新增會改變前台呈現的
  寫入路徑時，**必須**經過它 bump 對的欄——複驗接線全集＝`git grep -n "CacheStamps\." app/`。
- 🔴 **不得把 TOUCH 改回 hash 形式**（Rails 8.1 update_all 的樂觀鎖自動 +1）。
- 🔴 **第 12／32 包落地發布與市場 mutation 時要接 bump**；第 32 包建 markets 表的
  那個 commit，`cache_stamps_spec` 的表存在斷言**當場紅**（不是「該去看」而是
  機械強制）——那是設計，不要繞。
- **limits 的 stamp 正典在 `catalog_flow.cache_stamp_sources`**（不是 `cache.`）。
- **停止條件**：審查零未清 ∧ 閘門綠 ∧ CI 兩測綠 ⇒ 合併 ⇒ 部署（migration 在 bt3
  有資料實跑，#113 教訓）⇒ 線上驗收。
