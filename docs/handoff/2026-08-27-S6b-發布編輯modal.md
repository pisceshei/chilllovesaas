## ② 為什麼這樣改（含被推翻的假設）

- 🔴 **被推翻：「搜尋用子字串比對」**。本尊實測是**詞首前綴**，四格反例定死：
  `store`→命中 `Online Store`（⇒非整串前綴）、`tore`→無（⇒非子字串）、
  `line`→無（`Online` 的子字串但非詞首）、`of`→命中 `Point of Sale`（虛詞也算詞）。
  ⚠️ **附帶發現**：這條規則套到無空白的中文會退化成整串前綴（「線上商店」搜「商店」不命中）。
  照抄本尊並在測試中明文釘住此限制——要改善須先裁定，**不得靜默改成子字串**。

- 🔴 **被推翻：「群組總開關可以用 `role="switch"`」**。MDN 逐字
  "assigning a value of `mixed` to a `switch` instead sets the value to `false`"
  ⇒ 半選態會被螢幕閱讀器讀成「關」，而**畫面完全正常、任何視覺測試都不會紅**。
  改用 `role="checkbox"` ＋ 顯式 `aria-checked="mixed"`。
  ⚠️ 本尊走的是另一條路（原生 `<input>` 的 `indeterminate`，html-aam 會映射成 mixed）
  ——**AX 結果等價**，我方選可測的那條，並避開「React 官方完全沒有記載 `indeterminate`」
  的無依據區（react.dev 與 legacy 兩頁皆無此字串，2026-08-27 查證）。

- 🔴 **被推翻：「空的那一邊送空陣列就好」**。抓包顯示本尊用 GraphQL **`@include`** 逐向開關
  （`shouldPublish`／`shouldUnpublish`），且**`ProductSaveUpdate` 也帶同樣那兩個陣列但開關全 false**
  ⇒ 兩支 document 共用變數、不重複寫入。送空陣列會讓 `Publications::Write` 白跑一次
  transaction 並多 bump 一次 stamp。已改為 `@include`，變數名與開關名全對齊本尊。

- 🔴 **M5 突變沒轉紅，而那是「我對機制的理解錯了」不只是「測試不足」**。
  我把 `mediaOrder` 的 C8/C20（「快照不歸零 ⇒ 永遠不相等、SaveBar 不消失」）直接套到 delta 上，
  寫進了註釋。實際上 mediaOrder 有 `reloadMedia` 會把 `values.mediaOrder` 清成 `[]`，
  才會造成不相等；delta **沒有**那個機制 ⇒ 漏掉歸零時快照與 `values` 雙雙停在非空、彼此相等，
  **SaveBar 照樣消失**，真症狀只剩「下次儲存重送同一份 delta」且完全無聲。
  ⇒ 更正註釋 ＋ 補格 ＋ 複驗轉紅。**照抄先例時要先驗那個先例的失效機制在這裡成不成立。**

- 🔴 **M11 突變沒轉紅，原因完全不同：是測試選錯初始狀態**。第一版篩出**關著**的管道再全開，
  而其餘管道本來就開著 ⇒ 兩種實作結果相同。改寫成「篩出**開著**的管道再全關」才能區分。
  ⇒ **一個殺不掉的突變，要先分清是「實作沒問題」「理解有誤」還是「測試沒選對狀態」。**

- **M12 沒轉紅是預期內的**，我先界定再被證實：GID 不含空白 ⇒ `aria-controls` 的空白分隔解析
  在不轉義時也不會壞。轉義是防禦性的（防日後餵 `querySelector('#…')`），已誠實登記
  「現有測試證明不了它必要」。本尊在這裡是直接用**裸 GID** 當 host id。

- **為什麼 delta 進 `values` 而不是獨立 state**：`dirty` 是 `values` 與快照的比較，
  delta 在裡面才會讓 SaveBar 自動亮（本尊 §13.1 的行為）。**額外收益**是 `applyDiscard`
  走 `setValues(snapshot)` ⇒ 捨棄自動撤銷 modal 內的變更，正好滿足 Microsoft 對
  owned property window 的逐字要求。獨立 state 的話捨棄會漏掉它。

- **為什麼是 delta 不是完整期望狀態**：外部研究建議相反（理由是 React 官方
  「Avoid contradictions in state」），但**我方採 delta 正是為了同一條原則**——在有伺服器現況
  （`publicationRows`）的情況下，完整期望狀態才是那個會與現況矛盾的第二份真相。
  該研究自己也標明「前端該存哪一種＝無第一方推薦」⇒ ours 裁定。

- **`publish` 排在 `unpublish` 前面**：GraphQL 對 mutation top-level field 依序執行；
  順序相反且 publish 那半失敗，商品會落在「舊管道已移除、新管道沒加上」＝**意外全下架**。
  反過來最壞只是多發布一個管道。

## ④ 下一個人要注意什麼

1. 🔴 **「這個管道開著嗎」的判準永遠是「該列是否存在」，不是 `isPublished`。**
   V2 的 `false` 是「已排程未到點（staged）」。綁錯的 bug 在沒有任何排程的環境下
   **100% 測綠**——S6a 已釘死這條，S6b 沿用，S6c／S6d 也必須沿用。

2. 🔴 **逐資源 toggle（狀態設定）與批次 checkbox（累加）不得共用元件**（`82` §12.2）。
   把逐商品做成累加語義 ⇒ 商家取消勾選不會生效；把批次做成狀態編輯器 ⇒ 一次勾選清空整個管道。
   S6d（列表唯讀 popover）與日後的批次流程要各自檢查這條。

3. 🔴 **群組類控制項的作用域是「目前可見的子集」**，不是全集（§14.2 實測）。
   S6c 的系列 popover 若也有群組開關，同一條適用。
   ⚠️ 而且**測這條要選對初始狀態**——被波及與不被波及必須產生不同結果，否則突變殺不掉（M11）。

4. **S6c 之前要先做 popover 原語**：倉庫現有三份 inline 實作關閉語義各異、都缺點外關閉；
   列表 popover 還會被表格容器裁切 ⇒ 走 `Modal` 的 portal 解法。

5. ⚠️ **本尊的錯誤小卡是 portal 渲染在 dialog 之外**——
   `document.querySelector('[role=dialog]').innerText` **讀不到**那段文字。
   日後若要在 modal 內做 popover／tooltip，測試要記得這一點。

6. 🔴 **前端測試用 mock fetch ⇒ 驗不到 document 與 schema 是否相容**。
   `@include`、top-level field 位置寫錯這類問題，測試會全綠、上線才炸。
   新增或改動任何 GraphQL document 後，用 `ChillloveSchema.validate` 靜態驗一次
   （只讀、不寫入；本包三份 document 皆已驗過，指令見配對 worklog §7）。

7. **本機跑前端測試**：`npx vitest run`（不需要 MySQL）。後端 rspec 才需要，
   啟動方式＝`C:\Users\pisce\chilllove-mysql\start-mysql.cmd`。
