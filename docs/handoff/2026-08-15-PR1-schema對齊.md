## ② 為什麼這樣改（含被推翻的假設）

- 🔴 **三步的共同形態是「規格與實作已經互相矛盾」**，不是「要新增功能」。
  `limits.yml` 早就寫了 `sku_unique_per_shop: false`、早就是四態、88 §4 早就寫了
  「建立商店的流程**必須**連帶建立它」——實作全部沒跟上。
  ⇒ 這種矛盾修起來**不需要任何新裁定**，而且修完倉庫立刻比修之前更自洽。
  這也是我把它們排在寫入路徑地基**之前**的理由。

- 🔴 **被推翻的假設：「加一個狀態值就是加一個 enum value」**。
  `UNLISTED` 的存在本身就證明「可購買」與「可被發現」是**兩個獨立維度**——
  三態時兩維完全同步，所以一個 `published` 布林兼管兩件事剛好不出錯；
  補上第四態必定撞牆。這也是為什麼我**沒有**交付 `purchasable`／`discoverable` 具名 scope：
  13 §F1.2(d) 的 SQL 指向兩張不存在的表，照做會讓全站商品靜默變成不可購買，
  省略變體層又會讓 scope 的**名字在說謊**。

- 🔴 **被推翻的假設：「照抄鄰居的寫法就是合慣例」**。
  `Shop` 另外三個關聯都用 `dependent: :restrict_with_error`，
  `publications` 照抄看起來最合慣例——但 `after_create` 之後每間店恆有一列 publication
  ⇒ **連一間空店都永遠刪不掉**，而且沒有任何既有測試會紅。
  慣例要看**這個關聯是什麼**（附屬設定 vs 業務資料），不是看隔壁怎麼寫。

- 🔴 **「回報成功但什麼都沒做」在這一輪出現了兩次**，兩次都靠測試逼出來：
  ① `shop.destroy` 在**別間店**的租戶 context 下會把 publication 過濾成 0 列，
  一列沒刪卻回報成功 ⇒ 加 `around_destroy :within_own_tenant, prepend: true`；
  ② 建店缺 publication 時，新店看起來一切正常，只是所有商品都上不了架。
  這與上一輪 lint 規則那條「回報成功但什麼都沒讀」是**同一種病**。

- **每一步都做了負面驗證**：S1 還原唯一索引 → 5/9 紅；S2 enum 退回三值 → 5 條紅。
  綠不等於有效，這在上一輪（fixture 抓到兩個看不出來的 bug）已經證明過一次。

## ③ 還有什麼沒解決

- 🔴 **PR-1 的後半（S4–S8 寫入路徑地基）全部卡在三個規格缺口**，見 §④。
- 🔴 **88 §5 還有四項是活的**：`auto_publish` 的實際行為（**目前只是一個欄位，
  沒有任何行為掛在上面**——最容易被誤以為已完成的一項）、排程發布要求商品為 Active、
  商品表單的上架管道區塊、`ProductVariant`／`Collection` 主體展開。
- 🔴 **D12（變體×選項 join 表）尚未落地**，而它明文「必須在第一支商品 mutation 之前」。
  本輪的唯一義務是**不要建出擋住它的東西**，已遵守（特別是沒有先建
  `(product_id, option_values_digest)` 的兩欄唯一索引——13 §F1-2 的字面缺 shop_id，違反鐵律 2）。
- 🔴 **13 §F1.2 的六條驗收本輪只完成三條**，另三條（`unlisted_meta_robots` 注入、
  八個排除點、市場 catalog 排除）散在 M2 與 M5。
- **ARCHIVED 的 pip 與原型不符**：原型用 `blocked`，而 `23` §1 只定義三種 pip
  ——**原型與 CSS 規格本身不一致**，補第四種是視覺語言變更，登記待辦。
- **admin 商品列表的 status 篩選器**：13 要求「四態全顯示並提供 status 篩選」，
  但 `docs/research/60` 沒有實測任何篩選控件、原型也沒有，且 DOCS 條目措辭衝突
  ⇒ 需回頭實測本尊，登記為 V 項。
- **`Shop#destroy` 只驗了四種情境**（空店／有 staff／跨租戶／無租戶），
  **有商品／有 session 的店沒有驗**。

## ④ 下一個人要注意什麼

1. 🔴 **拆欄位的 migration 一定要連 model 宣告一起改。**
   `20260814000000` 從 `staff_members`／`sessions`／`roles` 拆掉 `shop_id`，
   卻沒改 `Shop` 的三條 `has_many` ⇒ **`Shop#destroy` 完全不能用**，
   而全庫沒有一條測試碰過它們，所以它安靜地壞著。
   **欄位沒了，宣告不會自己失效——它會留著，直到第一個人去用。**
   下一次改 schema 時，把「這張表被誰 `has_many` 到」列進檢查清單。

2. 🔴 **PR-1 後半的三個裁定已交由本尊考掘決定，不要自己猜**（使用者 2026-08-15 明示
   「深度分析和研究 shopify 的架構，然後我們和 shopify 一樣」）：
   - `userErrors.field` 的路徑語義（要不要 `input` 前綴、陣列索引怎麼表達）
   - `userErrors.code` 的 enum 結構（per-mutation vs 共用）與值域正典
   - 金額可否為負（`Money::Storage` 的設計取決於它）
   **這三條會被全專案抄**，猜錯的成本是之後每一支 mutation 都要改。

3. 🔴 **本輪實測到一條可用的旁證**：Shopify admin 的價格輸入框**在客戶端就吃掉負號**
   （輸入 `-5` 變成 `5.00`）。但**這只是 UI 層**，而且 admin 走的是內部
   persisted-query API（`admin.shopify.com/api/operations/{hash}/{Op}/`），
   **不是公開的 Admin GraphQL** ⇒ 不能拿它當 parity 依據，只能當佐證。
   要驗公開 API 的行為得走 shopify.dev 文檔或真的 API token。

4. **本機 `bin/rails db:migrate` 的老坑仍在**：`db/schema.rb` 版本等於最新 migration 時
   它會載入 schema 而不執行 migration。本輪新增 migration 時版本較新所以沒踩到，
   但驗證既有 migration 時仍要把 schema.rb 暫時移開。
   另：**test DB 要另外 `RAILS_ENV=test bin/rails db:migrate`**，否則 rspec 會
   `PendingMigrationError` 直接 abort。

5. **非交易式測試（`use_transactional_tests = false`）的清理要寫在 `before` 也寫在 `after`。**
   本輪 `after` 自己失敗過一次（外鍵刪除順序寫反），殘留資料讓**下一次整個 rspec 程序**
   在 sequence 重新從 1 開始時撞唯一索引，而失敗訊息出現在一條無關的 example 上。
