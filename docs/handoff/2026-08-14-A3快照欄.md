# 交接：A-3 商品維度雙軌（2026-08-14 第十九場）

> 本輪 worklog（1 份）：`2026-08-14-A3快照欄.md`（產出 `docs/specs/87`）

## ① 我改了什麼

84 號 A 桶第二條（R11-V7）落地：`line_items` 補上 `vendor` 與 `product_type` 兩個快照欄，
契約寫成 `docs/specs/87`。查證過程中另外挖到一個外鍵問題，登記為 R11-V7b。

## ② 為什麼這樣改（含被推翻的假設）

- **M0 的意圖是對的，只是沒做完**。`line_items` 的表註釋本來就寫著「下單當下不可回溯改寫的
  商品與金額快照」——所以這不是設計失誤，是**清單漏了兩項**。本尊有 5 個「售出時的」維度，
  我方做了 3 個。
- 🔴 **我刻意沒有回填**。新欄 nullable，既有列留 NULL。理由：既有列補不出正確的歷史值，
  用當前值回填會製造**看起來正確、實際錯誤**的歷史資料，而且事後沒有辦法分辨哪些是真的。
  **NULL 表示「不知道」，這比一個錯的值誠實。**
- 🔴 **附帶發現比原任務更重要**：查外鍵時發現 `fk_line_items_product_variant_id` 是
  `NO ACTION`（RESTRICT）——**賣過的商品變體永遠刪不掉**。
  這與快照設計互相矛盾：快照存在的前提就是「被參照的東西可能消失」。
  而**商品刪除正是 M1 的範圍**（本尊權限樹裡「產品 › 刪除」是獨立權限）。
- 🔴 **而且不能用最直覺的修法**。想改成 `ON DELETE SET NULL` 是自然反應，但外鍵是**複合**的
  `(shop_id, product_variant_id)`，MySQL 要求 `SET NULL` 時**所有** FK 欄可為 NULL，
  而 `shop_id` 是 `NOT NULL`。**這個改法在複合外鍵下根本不成立**——
  如果沒去查 `information_schema` 就直接寫 migration，會在 M1 才炸。
- **我沒有裁定 V7b**：它需要先回答「我方要不要支援商品硬刪除」，那是產品決策不是技術選擇。
  三個方向都列在 87 §4.3 了。

## ③ 還有什麼沒解決

- 🔴 **R11-V7b（商品刪除與外鍵）未裁定**——M1 做商品刪除前必答。
- **只保證欄位存在，不保證寫入正確**：複製邏輯在 M3 建單流程，屆時要有測試證明
  「改商品不影響既有 line item」。
- **其他資源的雙軌需求未盤點**：顧客名稱、地址、折扣標題可能也有同類問題。
  80 §1.2 的「售出時的」前綴只出現在商品五欄，但那不代表別的資源沒事。
- **報表預設走哪一軌未定**（M5）。本尊預設是**當前值**——改個廠商名會讓過去三年的報表分組全變，
  這是刻意設計不是 bug。
- 84 號 A 桶只剩 **A-5（發布模型三張表）**。

## ④ 下一個人要注意什麼

1. 🔴 **M3 建單時，這五個欄位要從 variant/product 複製一次，之後永不更新**。
   商品編輯不得回頭改 line item——這就是表註釋「不可回溯改寫」的意思。
2. 🔴 **動商品刪除之前先看 87 §4**。外鍵現在會擋住刪除，而且最直覺的 `SET NULL` 修法
   在複合外鍵下不成立。
3. **建任何「引用另一張表」的欄位時，問一次：被引用的東西會變嗎、會消失嗎？**
   會變 → 需要快照欄；會消失 → 外鍵的 DELETE_RULE 要想清楚。
   16 §159 的 `order_pickup_points`（「快照，不是外鍵——門市會關」）是這個專案裡的既有先例。
4. **查外鍵行為不要看 `schema.rb`**——它不顯示 `DELETE_RULE`。要查
   `information_schema.REFERENTIAL_CONSTRAINTS`（本輪就是這樣抓到的）。
