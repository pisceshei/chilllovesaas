## ② 為什麼這樣改（含被推翻的假設）

- 🔴 **我在同一份檔案裡，防住了 A 側的重複計算，卻在 B 側犯了同一個錯**。
  86 §3.2 我特地寫了「把 returns 也加進金額聚合會**雙重扣除**」，
  然後在上面三行把取消單全額直接加進去——而取消流程會產生退款。
  **寫下警告不等於套用了警告**；警告只擋住我當時正在想的那個案例。
- 🔴 **被推翻的假設：「換貨是唯一能抓到雙重扣除的形態」**。這句話我寫得很肯定，
  它是錯的。更糟的是它會讓人只補一個測試案例就以為守住了。
  🔴 **一般測資的取消單多半是未付款取消**，那條路徑兩項都是 0，公式怎麼寫都對——
  形態 2 只在「已付款才取消」的案例下現形。**這與 zero-decimal 幣別是同一種病：
  在最常見的資料上全綠。**
- **Codex 給的兩個選項我兩個都採**（命名檢查那條）：能擴大掃描的擴大，
  不能安全擴大的（裸 `returns` 在 app 代碼裡多半合法）**就把對外宣稱的契約寫實**。
  腳本的誠實聲明段現在明寫「不掃什麼、為什麼」——**宣稱守住三處卻只守一處，
  比只宣稱守一處更危險**。
- **白名單那件事是補 `docs/dev` 時查出來的**，這點值得記：
  我原本覺得那條 review 意見偏形式（純 schema 補欄要不要寫功能文檔）。
  結果補寫「資料表」段時逐張對照 `db/schema.rb`，**對照本身就查出了三個錯**。
  🔴 **功能文檔的價值不在文檔，在於逼你把實作與規格逐項對一次。**
- **workflow 只修身分、不放寬判定**。最省事的修法是「只要留言含【驗收結論】就算」，
  但那等於讓任何人或 diff 內的 prompt injection 偽造通過結論——
  正是該檔頂部 `AUTO_MERGE` 註解①寫的風險。允許清單必須留著。
- **jq 那個坑我沒有用推理帶過**：`index()` 對第一個元素回傳 `0`，而 `claude[bot]`
  正好排第一。若 jq 把 `0` 當假，這次修的目標本身就會失效。
  本機裝了 jq 實測確認 `select(0)` 通過，**並用舊過濾式跑同一份樣本得到空字串，
  正面證實誤報根因**。
