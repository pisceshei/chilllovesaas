## ① 我改了什麼

接上 `product.publication.changed` 的消費者，讓 S5 投出的排程事件在到點時真的做事。
消費者的寫入副作用只有 `Product.bump_publications_stamp!` 一處
（複驗：`grep -nE "update|create|destroy|bump_" app/services/publications/scheduled_publication_consumer.rb`
——除 `bump_publications_stamp!` 外應無其他寫入呼叫）。
新增兩個 service（消費者＋一次性 backfill）、一個 rake 入口、`REGISTRY` 一行、
24 格 spec、一份實作正典 `docs/dev/m2-publication-scheduling.md`。

驗證：本包 spec 24/0；**七個突變全部實跑轉紅**（M1–M7，逐條對映到被殺的格子，
表在 worklog）；全套 rspec 1265/0；rubocop、tenant-isolation、money-boundary、
limits-keys、reversal-naming、lint-prototype、doc-claims 逐支退出碼 0。

## ② 為什麼這樣改（含被推翻的假設）

- **判準取可見性軸不是 `== ACTIVE`**：這是 D53 F1 的核心，本輪 help 複驗又拿到
  **第二個獨立錨**（商家面 `Unlisted: …the product is available to be sold, but customers
  can't discover it.`）。寫 `!= ACTIVE` 的事故形態是「前台已可購買、快取永不失效、
  無錯誤無日誌」——`T02` 釘住它，M1 突變證明它真的擋得住。

- 🔴 **被推翻的假設：「T08 變體到點可以用真實生產者構造」**。裁定書寫的是
  「（若能構造）」，我一開始照字面當成可構造，spec 一跑就發現**排程根本沒被建立**
  （`published_at` 是 now、零事件）。查下去是 `validate_publish_date` 的 R12 在**寫入層**
  就 reject 了變體排程。⇒ 拆成 `T08a`（真實生產者證明封死）＋`T08b`（直呼驗防禦分支，
  **spec 內明文標註不是端到端**）。消費者的變體分支照 D53 §3.1 第 4 項保留。

- 🔴 **被推翻的假設：「T09 存成 ACTIVE 就會產生狀態轉移事件」**。商品 factory 建出來
  就是 active，存成 ACTIVE **不構成轉移**、`StatusTransition` 不被呼叫、零事件 ⇒
  spec 假失敗。必須先降 draft 再升。**這正是 T26「用真實生產者」紀律會抓到的東西**——
  自捏 payload 的話這一格會永遠綠著，而分流分支從未被真的走過。

- **自己抓到一條 D53 沒點名的坑**：`superseded` 的比對精度。payload 是秒級
  （`utc.iso8601`）、DB 是 `datetime(6)`。直接 `==` 會把每一筆合法事件誤判成 superseded
  ⇒ 到點永遠不 bump，而快樂路徑仍可能因 usec 恰為 0 而假綠。⇒ `same_second?`。

- **backfill 的冪等靠 `at: row.published_at` 而不是 `Time.current`**：用後者每跑一次
  stamp 前進一次，第二次呼叫的 `bumped == 0` 斷言（T22）就是釘這個，M7 突變證明。

- 🔴 **關卡②③（後台實測＋抓包）＝未取得**。Chrome 內 Shopify session 已登出：三次導航
  （`/products` ×2、store 根 ×1，各等 8/8/10 秒）全部 302 到 `accounts.shopify.com/lookup`，
  第二次起出現 hCaptcha。依鐵律 12.0 逐條排除後確認是**認證牆**，不是載入未完成／404／空白頁。
  登入需 ①完成 hCaptcha ②輸入密碼／密碼金鑰或 OAuth——三者都是執行方被明文禁止的動作。
  **兩組 fixture（`Product/9907126370539`、`Product/9911273160939`）完全未觸及。**
  ⇒ **不阻塞本包**（依據是 D53，其 M 層證據來自前一輪實測；本輪 help 複驗未推翻任何一條），
  但 **S6 動工前必須補做**（尤其到點後商家面到底看到什麼、時區呈現、per-channel 日曆 icon 值域）。

- 🔴 **stamp bump 仍是半掛的**：`publications_updated_at` 目前**沒有任何前台快取真的讀它**。
  接成真正的快取失效屬 **S7**、前台契約屬 **S9**、第三層 catalog 過濾屬 **S10**。
  **不得把「stamp 已 bump」講成「快取已失效」。**

- ⚠️ **線上驗證尚未執行**（本包尚未合併、未部署）。S1 的前例是本機 29 格全綠＋六突變全紅，
  正式庫仍印出 `cleanup: publication_left=0 catalog_left=1`。

- ⚠️ **§7.2 三條新事實只登記未落地**：N1 UNLISTED 不可發布到第三方管道且不進 feeds／
  Catalog／sitemap；N2 平台側 `Suspended`／`Pending suspension` 兩個商家不可設的 status；
  N3 channel markets 的 catalog 是第二道閘門。各自屬 S10 或未來包。

- ⚠️ **關卡④⑤（外部參考、關聯推理）本輪的研究代理仍在執行中**，結論尚未併入。

## ④ 下一個人要注意什麼

1. 🔴 **合併後**照兩步紀律部署 bt3，然後跑
   `bin/rails publications:backfill_scheduled_stamps`（照 handoff 的 `run_as_app` 一行，
   `RBENV_ROOT` 是 `/opt/rbenv`）。它冪等、可重跑、跑完即結案，**不是常駐 sweeper**。
   輸出 `scanned=N bumped=M` 供核對。

2. 🔴 **不要在 `relay.rb` 上動任何東西**。接消費者只動 `consumers.rb` 的 `REGISTRY`
   ——這是該檔檔頭的掛載縫契約。本包遵守了，下一包也要。

3. 🔴 **同一 topic 兩種 payload 形狀這件事會再咬人**。日後任何新的
   `product.publication.changed` 生產者，都必須先看消費者的分流分支能不能接住；
   加了第三種形狀而不改消費者，症狀是 `decision=unknown_payload` 的 log 靜靜長，
   **不會有任何測試轉紅**。

4. **`dev`／`test` 沒有 `events_relay` 排程**（`config/recurring.yml` 只有 `production:`）
   ⇒ 那裡的「到點」永遠不會自己發生，spec 一律直呼 `Events::Relay.drain!(now:)`。
   但**不得**因此把讀取面的到點語義（`published_at <= :at`）也排除——那是合法證據且已有矩陣。
