## §2 為什麼這樣改（含被推翻的假設）

### 2.1 研究反覆比驗收方更準——這不是巧合，是分工的結果

驗收方的**事實陳述**幾乎都對；**修法方向**經常錯。已記錄的實例：

- Codex[3]（#58 r37）給的複驗指令會讓 CI 轉紅（`rg` 不在 `RECHECK_CMD` 白名單）。
- bot🟡1（#58 r40）給「補 URL／降推論」二擇一，**第二案與 `91` §3 熔斷條已立的裁定相反**
  （逐字：「把一條證得出來的事實寫成猜測，登記簿只會更不可信」）。
- Codex[2]（#58 r40）的第二案「標成帶日期的快照」**正是第 20 輪試過並被推翻的路**。
- Codex[4]（#58 r40）的第二條出路「取得不會到期的方案」**在本專案不成立**——
  SHOPLINE development store 不到期，但屬**新全球版**（`.myshopline.com`），
  而 R-9 要 teardown 的功能全在**傳統版**（`shoplineapp.com`）。
- Codex[3]（#58 r40）的第二案「撤回禁行號判準」方向錯——`91` §3 已自登「禁行號是對的、`91` 該改」。

🔴 **根因**：驗收方看不到本輪對話脈絡與倉庫的既有裁定，所以它給的是「一般情況下的合理修法」，
而本專案的很多選擇是**裁定**不是機械修復。這正是 2026-08-15 廢止「自動 @codex 派修」的理由，
**不得回退**。

### 2.2 被推翻的假設：`${{ }}` 寫在 `prompt:` 裡是安全的

第 5 輪在 `prompt:` 塊裡加了 `${{ github.event.pull_request.number }}`。
**整份 workflow 從此無法解析**——一個 YAML 純量若含 `${{ }}`，**整個純量成為單一 template
expression**，而 Actions 對單一 expression 有 **21000 字元上限**。超過即整檔失效 ⇒
`pull_request` 觸發器**不再啟動**，症狀是「CI 全綠、Claude Review 消失」。

本機所有檢查（`ruby -ryaml`、`bash -n`、`@action-validator/cli`）**全過**——**只有 GitHub 判得出來**。
用 8 個丟棄分支二分定位，修法＝改走 step 層 `env: PR_NUMBER`、prompt 內用 `$PR_NUMBER`。

### 2.3 被推翻的假設：15.2「重拉留言」＝看最後一則

條文原文是「最新時刻的**每一則**」。第 7 輪我只看了最後一則，於是 review `4969100476`
（審 `32708a9`）**整整躺了兩輪**——複驗後兩條意見**都成立**。

⚠️ 附帶查到的工具陷阱：`gh api .../pulls/{N}/comments` **不加 `--paginate` 只回前 100 則**。
本 PR 的 inline 留言早已超過 100 ⇒ 不分頁會「查不到最新那批」而**誤判成 Codex 沒給 inline**。

### 2.4 被推翻的假設：`claude_args: |` 裡的 `#` 是註釋

那是**字面塊純量**，塊內的 `#` 是**字串內容**。22 行「註釋」實際是 prompt 的一部分，
沒出事純粹因為上游有 `stripShellComments()`——那是上游對 issue #802 的 bug 修法，
不是 `claude_args` 的輸入契約，而我們把 action 釘在**浮動 tag `@v1`**。

### 2.5 被推翻的假設：`set -uo pipefail` 表示這一步沒有 `-e`

GitHub Actions 未指定 `shell:` 時預設 `bash -e`，`set -uo pipefail` **關不掉**已經開著的 `-e`
（實測 `$-` ＝ `ehuB`）。同一份檔另一處的註釋是對的 ⇒ **兩種互斥的心智模型並存於同一份檔**，
而只有錯的那一個被寫成了推理前提。
