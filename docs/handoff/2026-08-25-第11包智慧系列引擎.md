## ② 為什麼這樣改

- **落地形照 limits（95 §1.1 修正）不照 spec 13 舊塊**：spec 13 §F4.1 的 SQL 塊是 UI
  形態（四型×極性），比 limits 的 2026-08-24 修正舊——本 PR 順帶回寫（D50 配套）。
- **求值公式 per-source 相減**：全域相減是靜默錯誤（只在 A 排除 X＋B 包含 X 的系列露餡，
  測試資料不會自然出現——與 zero-decimal 幣別同形態）。三條必測全釘。
- **觸發走 outbox 消費者**（P11-U17 ours）：鐵律 5＋不掛在寫路徑鎖持有時間上；
  重放冪等（resync 算「現值該不該在」，天生收斂）。
- **變更判定不用 affected_rows**：ON DUPLICATE 對既有列每輪記 2 ⇒ 零變更 rebuild 也會
  白打快取——煙測抓到後改 `created_at >= generation`。

**被推翻的假設**：①「affected_rows 可以當變更訊號」（上句）②「sanitize_sql_array 對
Integer 產生裸數字」——Rails 8.1 mysql2 adapter 對 Integer 也產生帶引號常量（實測），
MySQL 常量側折算一次、語義與索引不受影響，spec 註明。

## ④ 下一個人要注意什麼

- 🔴 **加條件型別＝三處一起動**：dev doc §1 值域表、`RuleCompiler` 常數（含 RELATIONS）、
  `SaveCollection` 白名單——RELATIONS tripwire spec 盯著鍵集合。
- 🔴 **智慧成員永遠不進 collection_products**（spec 釘住）；前台只查 memberships。
- 🔴 **`Rebuild`/`ResyncProduct`/規則編輯共用 collection 列鎖**——新增任何動 rules 或
  memberships 的路徑都要先 `Collection.lock`，否則併發窗重開（併發 spec 的人工閘可重現）。
- 🔴 **rebuild 對 rebuild 另有一把整場 advisory lock**（2026-08-26 F2）：列鎖只護單批；
  任何繞過 `Rebuild.call` 直接批量寫 memberships 的新路徑都會重開「交錯掃尾清空系列」
  的窗——寫入一律走 `Rebuild.call`，或至少複用同名 `GET_LOCK` ＋
  `GREATEST(COALESCE(rebuilt_at, 世代), 世代)` 單調帶（🔴 **`COALESCE` 不可省**：
  `GREATEST(NULL, x)` 在 MySQL 回 NULL，少了它就是 F7 修掉的不死列；掃尾也要收
  `IS NULL`。2026-08-26 收斂輪 H6：本句原文只寫 `GREATEST` 單調帶，照字面實作
  等於把 F7 重新做壞一次）。
- 🔴 **tag 條件的鍵一律過 `Tags::Normalize.key`**；product_tags 由 SaveProduct 同 tx 維護，
  繞過 SaveProduct 寫 tags JSON＝兩表分岔。
- 🔴 **本包三輪審查的共同教訓（下一包帶著）**：改一條規則時，**先列出該規則所在
  方法／元件的完整欄位矩陣與全部下游消費者，逐格確認再送驗**。三輪 10 條確認裡有 8 條
  是「同一個方法裡的鄰居欄位」或「同一條契約的下游消費者」沒跟上——不是新問題，
  是修法射程沒畫滿（鐵律 17.2／20.2 第 2 類）。第三輪**零否決**是最強的訊號。
  ⇒ 交付物＝dev doc §7 的狀態矩陣與消費者影響圖，**下次動這個檔先讀它**。
- 🔴 **突變輪要看的不只是「紅不紅」**：第三輪第一次跑 8 格只有 6 紅，兩格綠的原因不是
  守衛無效，而是**改了生產碼卻沒加測試**——兩者在突變表上長得一模一樣。
- 🔴 **求值路徑有三條，不是一條（第六輪最重要的結構教訓）**：`ResyncProduct`（增量）、
  `Rebuild`（規則編輯後的單系列全量）、`catalog:rebuild:collections`（兜底全量），
  外加「B 變了誰要跟著重算」這個維度。前五輪每次改求值語義都只改一條，另外兩條就
  分岔——六輪裡有四輪的 🔴 是這個形態（H4／K2／K8，加上 G4→H5→J3 三次都只改 resync）。
  ⇒ 已收斂成 `Collections::ReferenceGraph`（`topological` ＋ `referrers`），
  **新增任何求值路徑都必須接上這兩個**（dev doc §7 影響圖新增一列明文要求）。
- 🔴 **`SystemStackError` 不是 `StandardError`**（第六輪 K1）：任何在事件消費者裡跑的
  遞迴，深度都必須有界——`Events::Relay` 的 rescue 只接 `StandardError`，
  爆堆疊會變成**永久毒丸**並拖垮同一批裡其他商店的事件。本包已改為迭代 DFS。
- 🔴 **測試拓樸也會騙人（第五輪）**：測「依賴順序」的測試必須讓**被依賴方非空**，
  否則測的是空集合的交換律——本輪的拓樸序突變第一次是綠的就是這個原因。
  同理，被上層守衛遮住的下層防線（model 驗證）要在**它自己那一層**測。
- 🔴 **DB 欄寬必須鏡射到寫入層**（第五輪兩條 🔴 同一類）：任何 `varchar(N)` 欄，
  寫入層都要有對應上限檢查，否則 `ActiveRecord::ValueTooLong` 會**漏成 500**
  （它是 `StatementInvalid` 子類，不在服務層的 rescue 清單裡）。
  🔴 **而且要驗「真正落庫的那個值」**：`product_tags.tag_key` 存的是正規化後的字串，
  正規化會**變長**（NFKC 展開／casefold）⇒ 只驗原字串必漏。
- 🔴 **測試資料的形狀本身就是盲區（第四輪最貴的一課）**：H1／H2 兩條 🔴 從初始候選
  就在，四輪審查、947 個 spec、各輪突變與四次 CI 全綠都沒抓到（同上 J8 更正：
  不寫累計突變數），只因所有 fixture 的
  規則值都很「乾淨」——沒有一個含 `?`、沒有一個含連續空白。**下一包寫 fixture 時，
  自由文字欄位至少要有一個「髒」值**（標點、連續空白、Tab、引號、CJK 全形空白）。
- 🔴 **`sanitize_sql_array` 的產物不得再進另一個 `sanitize_sql_array`**：它用
  `count("?")` 對位且不分引號內外。本包的紀律寫在 `RuleCompiler#bind` 上方
  （產出者處），任何新的 SQL 片段生產者都照這條寫。
- 下一步入口：包 12（publication scopes——「發布過濾疊在成員之上」，discoverable ⊆
  purchasable 不變量）；它讀 memberships，不改本包。
