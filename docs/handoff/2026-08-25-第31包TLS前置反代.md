# 交接：第 31 包 TLS（前置機反代）

分支 `m1/p31-tls-frontproxy`，base＝`main`。

## ① 我改了什麼

**目標**：讓 `https://demo.chilling.com.hk/` 可用，取代 `http://…:28080` 的權宜入口。

**遇到的問題與證據**：

1. **問題被誤判過**。先前登記成「TLS 未就緒」，實際上憑證一直是好的——`.187` 對
   `demo.chilling.com.hk` 送的就是 `*.chilling.com.hk` 萬用憑證（Let's Encrypt，
   到期 2026-10-06），憑證檔的 SHA-256 指紋與線上送出的逐位元組相同。
   404 的真因是 `www.chilling.com.hk.conf` 的 `server_name` 含 `*.chilling.com.hk`，
   把 `demo.*` 一起吃掉，而它的 root 沒有 demo 的內容。
2. **`.187` 上沒有寶塔面板**。使用者以為有；從 bt3 掃完全部 65535 個埠，只有
   `21/22/80/443/888/5555/38682`——5555 是 Flask 應用（所有路徑都回 Werkzeug 的
   預設 404 頁）、38682 是另一個 nginx vhost。使用者登入的面板管的是 bt3。
3. 🔴 **`X-Forwarded-Proto` 透傳**（本包最容易出事的一條，見 ②）。

**重要動作**：
- 取得 `.187` 存取：使用者在 bt3 面板終端機跑 `ssh-copy-id`、**自行輸入**該機
  root 密碼（密碼不經過工作階段）。之後 `ssh bt3 → ssh root@192.168.31.187` 免密。
- 新增 `.187:/www/server/panel/vhost/nginx/demo.chilling.com.hk.conf`（**倉庫外**）。
- 改 `config/deploy/nginx-chilllove.conf` 的 X-Forwarded-Proto 處理。
- 移除 bt3 `/etc/chilllove/env` 的 `DISABLE_FORCE_SSL=1`。

## ② 為什麼這樣改

**vhost 放前置機而不進倉庫**：那是 `.187` 的設定，那台還跑著另外八個站
（chat／collect／erp／hktvmall／mail.chill.love／seo／strawberrynet／www）。
把別台機器的 nginx 設定收進本倉庫，會讓 `deploy.sh` 看起來像有權改它，實際沒有。

**照抄該機既有的 `erp.chilling.com.hk.conf` 寫法**（80＋443 合併 server、
`if ($scheme = http)` 導向、沿用既有憑證目錄）而不是套我自己的慣例——
那台機器有八個站在跑，一致性比我的偏好重要。

🔴 **`X-Forwarded-Proto` 必須透傳，不能用 bt3 的 `$scheme`**：
鏈路是 `瀏覽器 --https--> .187 --http--> bt3:80 --> puma`，第二段是明文
⇒ bt3 的 `$scheme` 恆為 `http`。若照抄 `$scheme`，開 `force_ssl` 的當下 Rails
會以為使用者走 http → 301 到 https → 前置機再以 http 轉進來 → **無限轉址迴圈**。
改用 `map $http_x_forwarded_proto`，缺該標頭時（LAN 直連）才回落 `$scheme`。

**`DISABLE_FORCE_SSL` 開關保留不刪**：它是 TLS 壞掉時把站救回明文的唯一退路。
判準那兩行沒動，只補了註釋。

**被推翻的假設**：
- 「TLS 沒就緒／要申請憑證」——憑證早就在，缺的只是一個 vhost。
- 「`.187` 有寶塔面板可以點」——全埠掃描證明沒有。
- 「改 bt3 nginx 用 `$scheme` 就對了」——那正是會造成迴圈的寫法。

## ③ 還有什麼沒解決

- 🔴 **`https://chilling.com.hk`（裸 apex）是壞的，但與本包無關**：落在寶塔的
  `0.default`、送自簽憑證（`verify error:num=18`）。萬用憑證的 SAN 是
  `*.chill.love, *.chilling.com.hk, *.chilllove.ca, *.chillnow.ca`——**萬用不涵蓋
  裸 apex**，這是 X.509 規則不是設定失誤。`http://` 版本正常。本包只加了
  `server_name demo.chilling.com.hk` 一個名字，動不到它。已登記 `91` §3.16。
- **LAN 直連 bt3 失效**：`force_ssl` 開啟後 `http://192.168.31.246/` 會 301 到
  沒有 TLS 的 `https://192.168.31.246/`。對外入口已改為
  `https://demo.chilling.com.hk/`，故不視為缺口。
- **憑證續期不在我方掌握**：萬用憑證在 `.187`、由該機既有流程續期，
  2026-10-06 到期。續期失敗 demo 站會一起失效，而我方**沒有告警**。
- **`demo` 店的 `custom_domain` 仍是 `192.168.31.246`**（LAN 直連時期的權宜值）。
  租戶解析走的是 subdomain＋`CHILLLOVE_BASE_HOST`，所以不影響現況；
  但它現在是個對不上的值，之後碰租戶網域那一包順手清掉。

## ④ 下一個人要注意什麼

- **前置機的設定不在倉庫**：路徑是
  `.187:/www/server/panel/vhost/nginx/demo.chilling.com.hk.conf`。
  進去的方法＝`ssh bt3` 之後 `ssh root@192.168.31.187`（金鑰在 bt3 上，
  **我的工作機沒有**，所以 `ssh -J bt3` 那種寫法不通，要兩段跳）。
- 🔴 **改 SSL 相關設定時，nginx 的 map 與 `DISABLE_FORCE_SSL` 是一組**：
  只動一邊必壞（見 ②）。`config/environments/production.rb` 的註釋已寫明。
- **改 `.187` 的鐵律**：那台有八個站在跑。一律①只新增檔案不改既有②`nginx -t`
  通過才 reload③失敗立刻刪檔還原。本次的部署腳本已內建這三步。
- **`nginx -t` 的既有 warning 不是你弄壞的**：`conflicting server name
  "www.chill.love"` 那批在本包之前就有（`mail.chill.love.conf` 與
  `www.chilling.com.hk.conf` 的 server_name 重疊），與 demo 無關。
- **重跑驗證**：
  ```
  curl -sS -o /dev/null -w "%{http_code} %{ssl_verify_result}\n" https://demo.chilling.com.hk/login
  ```
  期望 `200 0`（0＝憑證驗證完全正常）。
