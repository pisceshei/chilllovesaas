## ② 為什麼這樣改（含被推翻的假設）

- 🔴 **「進階模式」是我方的誤解，不是本尊的形態**。原型把 ShopifyQL 做成一個彈窗（`reportQL()`），
  預設「視覺化編輯是主線、QL 是進階選項」。**實測完全相反**：QL 編輯器常駐報告主欄，
  右側控制面板只是它的另一種投影，`?ql=` 還把整份查詢寫進 URL。
  **教訓**：把某功能歸類為「進階/選配」是一個**架構判斷**，不是 UI 細節——判錯會讓整頁的資料流反向。
  這是 R9「線上商店＝內嵌 app」之後第二次架構級誤判，兩次都出在「沒有先看它的狀態住在哪裡」。
- 🔴 **鐵律 3 沒被推翻，反而被正面佐證**。本尊在報表層把「支付款項金額」與「支付款項金額（付款貨幣）」
  當**兩個獨立指標**（另有幣別轉換費用／四捨五入後的付款淨額／現金進位原則）。
  而 `WITH CURRENCY` 只管顯示換算、`MONEY` dataType 對序列化格式完全沉默 ⇒
  **不能拿 Shopify 當單位契約的參照物**。65 號四型別維持（V9 當場判定）。
- 🔴 **鐵律 7 找到一個必須複製的官方例外**：AOV 的分子刻意排除 post-order adjustments，
  所以 `AOV ≠ net_sales / orders`。我方若照「同指標同一份 rollup」直覺實作，數字會與本尊對不上。
  **這條要回頭改鐵律 7 的條文**（加註例外），否則規則本身會誘導出錯誤實作。
- **自創控件第四次出現**（G12）：報告清單的 4 個 tab（全部/我的報告/Shopify 報告/最近檢視）是我方憑空加的，
  本尊只有兩個篩選器。**前三次分別是 R4 幣別設定、R6「所有商品」選項、R7 批次按鈕**——
  四次的共同形態都是「照著我對這個功能的想像補全 UI」。**下輪起：任何列表的 tab/檢視家族，
  先在 7x teardown 查有沒有登記，沒有就當它不存在。**
- **值域清單三份不相等是常態不是異常**：視覺化型別 UI 27 / API 23 / cohort 專屬 2，
  且 cohort 的 `retention_curve` 根本不在 freeform 清單裡。這代表 `visualization_type`
  必須帶 `mode` 維度——**一張 enum 表是抄不出來的**。

## ④ 下一個人要注意什麼

1. **先問「這個功能的狀態住在哪裡」再畫 UI**。分析模組的答案是 `?ql=` 字串；問錯就會像我一樣
   把主線做成彈窗。R9 的內嵌 app、R10 的三套覆寫模型也都是同一類問題。
2. **鐵律 7 有例外了**（AOV）。實作 rollup 時不要無腦共用分子；`80 §3` 有完整公式表，
   `總銷售額可以是負數`也在那裡。
3. **撤銷款項 sales reversals 是 2026 正式術語**，11 組欄名對照在 `80 §3.1`。
   `returns` 這個字**沒有消失**——它現在專指「實體退貨」，與 `sales_reversals`（廣義負值調整）
   是兩個概念，合併就錯。
4. **條件閘控要「降級展示」不要「過濾掉」**：本尊把不相容欄位掛在
   「根據現有選取項目無法使用」分組底下仍然顯示。過濾掉會讓使用者以為欄位不存在。
5. **DOM 收割的兩個坑**（本輪各踩一次）：①用 class 前綴找面板會撞到別的同類元件
   （我的 `_OptionList_` 選擇器先抓到幣別選單，誤點後把查詢改成 `WITH CURRENCY 'BGN'`）；
   ②用關鍵字排除面板會誤殺（我用 `/幣/` 排除幣別清單，結果把「財務與付款」類的指標一起殺掉）。
   **收割前先用文字錨定確認抓到的是哪一個面板**，並在每次點擊後驗證狀態再動作
   （固定延時的狀態機會差一拍，本輪重寫成狀態偵測型才跑通）。
6. **測試店寫入要收尾**：本輪建立的報告已刪除，店內無殘留。下一個人若也建資料，
   請同樣走完 create→delete，不要留測試資料污染後續實測。
