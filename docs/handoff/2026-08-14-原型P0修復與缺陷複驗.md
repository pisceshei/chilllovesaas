## ② 為什麼這樣改（含被推翻的假設）

- 🔴 **83 號的行號全部失效**。它寫於 2026-08-13 的另一個 session，原型此後改到 12,943 行。
  實測 `A:8136` 現在是目錄程式碼、`A:6553` 是庫存歷史。**照它的行號改會改錯地方。**
  ⇒ 89 號的存在理由就是這個：同一批發現，換成**當日現值行號**重新登記。
- 🔴 **我自己猜錯了一條，而且是用 grep 猜的**。啟動查證前我看到 `bulkbar` 有 19 處命中，
  在給使用者的訊息裡寫「PR-01 很可能已被修掉」。錯的——那 19 處屬於**其他 12 個模組**，
  商品列表正好是唯一沒有的。agent 的原話：「肉眼掃 grep 很容易誤判成已修好」。
  **這是本輪最該記住的一件事：grep 命中數不是證據。**
- **O-01 的形態比報告寫的還糟**：報告說「UI help 與 DOCS 雙錯」，實際是**三層各錯各的**——
  錯的規則被寫成文案（硬擋）、正確的規則一行都沒有（無軟上限）、
  **而它宣告的硬擋連 demo 都沒實作**（輸入 999999 照樣「成功」）。
- **C-01 的修法重點不是「把解析器寫對」，是「算不出來就明說」**。
  原本三條 regex 都不中就回全部顧客數——那是**錯誤數字不是佔位符**，長得像模像樣。
  新版無法求值時回 `ok:false`，UI 顯示「—」＋原因。
  🔴 **顯示一個算錯的人數，比顯示「—」危險得多。**
- **順帶修了一個沒人提的鐵律 3 違反**：`amount_spent > 5000` 的字面量是主單位、
  `c.spent` 是 cents，原本直接比較等於在問「消費超過 HK$50」。
  ⚠️ 因此**修好後的數字與 89 §1.3 所載「真值」不同**——是口徑被修正，不是算錯。
- **PR-01 刻意不共用訂單頁的 `.rowcb`**：本原型是 SPA、所有頁面同時在 DOM，
  共用 class 會讓 `bulk()` 把訂單列一起數進來。

## ④ 下一個人要注意什麼

1. 🔴 **本 PR 是驗收閉環的第一次真實驗證**。身分修正（`claude[bot]` 加進 `REVIEWERS`）
   已隨 #25 進 main，而本 PR **不碰 `claude-review.yml`**，所以這次會真的跑。
   判準兩條**都要成立**：①有 Claude 驗收留言 ②**沒有**「⚠️ 沒有產生結論」。
   **只有兩者都對，那條修正才算被證實**——在那之前它仍是未驗證的改動。
2. 🔴 **要修原型缺陷，先讀 89 不要讀 83**。83 的行號全數失效。
3. 🔴 **自動化點擊掃描前必須強制 `annot=false`**。「⌗ 註釋模式」開著時，
   `[data-doc]` 的 click 會被 `preventDefault(); stopPropagation()`，
   **inline onclick 根本不執行，掃出來全綠而且是假的**（89 §0）。
4. **驗互動行為要等渲染**：`openSegment()` → `goDetail()` 是非同步，
   同步讀 DOM 會拿到上一個分群的結果，看起來像「數字全錯」。
5. **lint 守得住「onclick 指向不存在的函式」（實測 0 條），但守不住「死控件」**——
   控件畫出來卻沒接 handler 那一類 **lint 沒有規則，25 條全部漏光**。
   要不要把它機制化，是下一個值得做的判斷（同 G24／撤銷命名那兩次的思路）。
