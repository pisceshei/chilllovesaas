## ② 為什麼這樣改（含被推翻的假設）

**被推翻的假設一：「環境變數逐個轉交就好」。**
第一次部署死在 `assets:precompile` 的 `KeyError: CHILLLOVE_BASE_HOST`。真因不是漏設，
是 `config/application.rb:66` **在 class body** 就呼叫 `TenantResolver.base_host`
⇒ 缺這個變數時**任何 `rails` 子命令都跑不動**，不只 web 進程。
改法不是補一個變數，是換轉交機制：`env -i` 清空後由子行程自己 source env 檔——
逐個轉交漏一個就炸在部署中途，而且會把秘密寫進 argv 讓 `ps aux` 全機可見。
`sudo -E` 不能用：本機 sudoers **靜默忽略**它（訊息只在 stderr 一行）。

**被推翻的假設二：「健檢紅＝服務沒起來」。**
步驟 1–6 全過、puma `active`、Solid Queue worker／scheduler 都在跑，健檢卻 30 次全 403。
真因是 `curl http://127.0.0.1/up` 的 `Host: 127.0.0.1` 被 `HostAuthorization` 擋掉
（`config.hosts` 只放行 `.$CHILLLOVE_BASE_HOST` 與已驗證 custom domain）。
🔴 **這個形態要記住：健檢本身可能是壞的那一個。** 判斷「服務死了」之前先看
`systemctl is-active` 與 journal——journal 每 2 秒一行 `Blocked hosts: 127.0.0.1`
才是真話，而健檢的輸出（403）完全沒提到 host 這回事。

**被推翻的假設三：「force_ssl 關掉就能在明文下登入」。**
關了之後登入仍一律 422。真因在**第三個地方**：`session_store.rb` 的
`secure: Rails.env.production?` 硬編。Secure cookie 在 http:// 下拿不到 session
⇒ 每個 request 都是新 session ⇒ CSRF 永遠對不上。
🔴 症狀的誤導性極高：畫面是正常的登入頁，日誌只有一行
「Can't verify CSRF token authenticity.」，**沒有任何一處會提到 cookie**。
決定性證據是 `GET /login` 連 `Set-Cookie` 都沒發出（改掉後立刻出現）。
⇒ 教訓：**「明文過渡」不是一個開關能表達的狀態**，它散在 assume_ssl／force_ssl／
cookie secure 三處；任何一處沒跟上就是靜默失效。三處現在都綁同一個變數。

## ③ 還有什麼沒解決

- 🔴 **對外入口**：WAN 80／443 實際落在 **192.168.31.187**（LAN 內另一台 nginx，
  對 `*.chilling.com.hk` 一律 404）；八個候選埠都沒轉發到 bt3。
  ⇒ 需使用者二選一：①路由器加 80→192.168.31.246:80 轉發；②在 .187 加反代 vhost。
  在那之前**只有 LAN 可見**（`http://192.168.31.246/`，已實測可用）。
- TLS 未終結 ⇒ `DISABLE_FORCE_SSL=1` 仍掛著。**接真資料前必須先做 TLS 並移除它。**
- 異地備份、CD-2（Actions 觸發部署）、CD-3（rollback 演練）＝120 §6 待辦。
- libvips 等 apt 依賴手裝，未進 bootstrap 腳本（重建機器會漏）。

## ④ 下一個人要注意什麼

- **demo 商店的 `custom_domain` 被設成 `192.168.31.246`**，這是為了讓 LAN 直連能過
  TenantResolver 的權宜；正式入口就緒後應改回 `demo.chilling.com.hk` 走 subdomain 路徑。
- 登入帳密在 `/etc/chilllove/env`（`SEED_ADMIN_EMAIL`／`SEED_ADMIN_PASSWORD`）。
  🔴 seed 是 `find_or_create_by!`：**改 env 裡的密碼不會改既有帳號**，會印
  「Preserved owner」而你以為新密碼生效了——第一次登入 422 就是這個原因。
- 每次部署一律 `bash scripts/deploy.sh origin/main`（在伺服器上以 root 跑）。
