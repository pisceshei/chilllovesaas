## ② 為什麼這樣改（含被推翻的假設）

- 🔴 **「管道」和「app」不是兩個平行概念，管道是 app 的一個 subtype**。實測 href 直接證明：
  代理式＝`/apps/agentic`、銷售點＝`/apps/point-of-sale-channel`。設定層雖然分兩頁，
  但 `⋯` 選單完全相同、安裝走同一個 App Store、權限是同一條。
  ⇒ 我方若建兩張平行表，會在「解除安裝管道」「管道權限」「管道計費」三處各寫一遍同樣的邏輯。
- 🔴 **上架不是一個布林值，是三層 AND**：Publishable × Publication × Catalog。
  「已發布到管道」與「在該管道市場的目錄內」是**兩個獨立條件**。
  這條同時牽動商品頁、目錄、市場、代理式目錄四個掛載點——是本輪對 M1 影響最大的一條。
- 🔴 **代理式的兩軸**：管道詳情浮卡把「**發現來源**（catalog 有沒有開放）」和「**結帳位置**
  （代理內直接結帳 vs 導回商店）」寫成兩行，這不是文案而是模型——Copilot 支援 direct checkout、
  ChatGPT 只做 discovery。做成單一「啟用」開關就抄錯了。
- 🔴 **B-7／UCP 從「未知」變成「已知」**：規格全文在 ucp.dev，Shopify 與 Google 共同開發，
  五個 MCP 端點、能力協商、checkout 四態都有官方文檔。**剩下的純粹是產品決策**。
  另外一條對主題引擎的硬約束：`agents.md.liquid` 是**受限 render context**
  （只有 `request` + `agents` 兩個物件、不可為 JSON template）——我方 M2/M6 必須支援這種 context。
- 🔴 **POS 的權限模型和 admin 完全不是同一套**（補完 R12 的權限全貌）：走 organization role、
  **只能指派角色不能指派單一權限**、粒度以**「裝置所在地點」為軸**。
  照 admin 的資源樹去套，會做不出「檢視裝置所在地點的分析」這種權限。
- **層ⓠ紀律兩次奏效**：①POS 頁首次載入空白、重載一次就出來 ②我猜的
  `/settings/point_of_sale` 得 404 —— 依鐵律 12.1 **不寫「本尊沒有這頁」**，登記為條件閘控未驗證。
- **我自己踩的坑**：新頁面 key 用了 `ch-*` 前綴，但 `go()` 只認 `m-`／`d-` 前綴決定容器，
  於是 `classList of null`；改成 `m-*` 後又漏了 `full:true`（函式型 custom 必須配它），
  於是 `M.cols.map of undefined`。**兩個都是沒先讀 `go()`/`renderModule()` 的約定就直接加東西。**

## ④ 下一個人要注意什麼

1. 🔴 **三個 PR 的合併順序**：R11／R12／R13 各自從 main 開分支，**互相不含對方的改動**。
   三者都動了 `chilllove-admin-v2.html` 與 `config/limits.yml`，合併時會衝突。
   **建議依序合併 R11 → R12 → R13**，每次合完重跑 lint 與煙霧。
2. **加新模組頁前先讀 `go()` 與 `renderModule()` 的約定**：key 必須 `m-` 前綴（否則找不到容器）；
   函式型 `custom` 必須配 `full:true`（否則會走列表分支去 map `M.cols`）。本輪兩個都踩了。
3. **管道建模從 `App` 出發**，`Channel` 是它的 capability，不要開兩張表。
4. **上架邏輯要寫成三層 AND**，且四個掛載點（商品頁／目錄／市場／代理式）共用同一份判定。
5. **代理式不要做成單一開關**：發現來源與結帳位置是兩個獨立維度。
6. **POS 權限別套 admin 的資源樹**：它是 organization role、角色制（不可逐權限）、以裝置地點為軸。
7. `agentic_sales_channel` 這個識別字**官方文檔查無**，是 R11 從實測維度清單取得的——引用時註明來源是實測。
