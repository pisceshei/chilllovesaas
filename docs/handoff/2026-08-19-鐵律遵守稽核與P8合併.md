**被推翻的假設一：「靠機制就好」。** 原 §7 的立場是把第 2／4／5 條的遵守責任推給

R4／R5 只是 warning（不擋）**；同一個工作階段、同一批檔案：R1／R3 零違反出庫（兩次紅都

在機制擋不擋。** 正確結論是兩道都要：紀律第一道、機制第二道。

## ④ 下一個人要注意什麼

🔴 **最重要的一條**：本階段的主要缺陷不是技術判斷，是**程序紀律**。稽核出 11 條款違反
（15.1／15.2／15.3／15.4／16.1／16.2／17.2／AGENTS §2／§3／§4／交接文件），
而遵守的那些全是「禁令」（不抄 GPLv3、不用 polaris、不啟用自動合併）——**遵守成本為零**。
違反的全是「在動作前收費的義務」。⇒ 接手時請預期：**壓力下最先退化的是要花時間的檢查**，
而且退化形態是「儀式做了、檢查沒做」（例如跑了重拉指令但只看時間戳）。

具體紀律（本階段實測換來的）：
1. **只修點名處**。每一處改動要能回答「服務哪一條被點名的意見」；答不出來就不要改。
   範圍外的一律登記 ⚪ 進 `docs/specs/91-pit-register.md`。
2. **push 前的重拉要單獨執行**，不得與 push 放同一批指令——否則看到新意見時已經推出去了。
   且完成定義是**抓到 inline 意見逐條**，不是「確認有一則 review 存在」。
3. **commit 之後重跑 doc-claims，警告必須為 0**。
4. **刪除操作先印出待刪內容再執行**，不得用跨行正則刪表格列——本階段用 `re.S` 刪一列
   表格，`.*?` 跨行吃掉 133 行（§八各階段段落全部連坐），`git checkout --` 才救回來。
5. **跨 PR 的完成式斷言一律錨定**，並記住：**被引用的 PR 一合併，那些錨定全部要回寫**
   （#59 合併當下九處變假）。
