## ② 為什麼這樣改（含被推翻的假設）

### 🔴 本輪的主線：**每一層防線都有一個「測試會全綠」的破口**

這不是九件互不相關的事，是同一種病在九個地方發作：

| 破口 | 為什麼測試看不到 | 怎麼抓到的 |
|---|---|---|
| `Data` 的 `.[]`／`#with`／`allocate` | 規格只說關 `.new`；**只斷言 `.new` 的測試會全綠**，而 `allocate` 產出的物件 `is_a?` 為真、欄位全 nil ⇒ 直接穿過 L3 | 逐條實測 `Data` 的公開 API |
| `format("%.2f", big_decimal)` 走 Float | 只在 **BIGINT max** 失真；一般金額測試全綠 | T10 邊界值 |
| 指紋的 `idempotencyKey` 每層都排除 | 巢狀同名欄位被靜默丟掉 ⇒ 兩個不同請求同指紋，**參數不符永遠偵測不到** | 自家 spec 的反向斷言 |
| registry 的鍵型別 | fixture 是 String 鍵、生產是 Symbol 鍵 ⇒ **整份矩陣證明不了生產路徑** | 上一輪 review 的 F5 |
| `Shop#destroy` 的三條死關聯 | 全庫沒有一條測試碰過它們 | 寫「空店可以刪除」的驗收 spec |
| 跨租戶 `shop.destroy` | default scope 過濾成 0 列，**一列沒刪卻回報成功** | 想「錯租戶下會怎樣」 |
| controller 的方法層 `rescue TypeError` | 金額閘門的 P1 事故被渲染成「variables 格式錯」 | 上一輪 review |
| fixture 讓套件變 **0 examples** | 只要那些檔是「合法但什麼都不做的 Ruby」就是 **0 examples ＋ exit 0** | 跑全套時數字不對 |
| C4 抓到自己 | 唯一正確實作 C4 的檔案被 C4 判違規 | 第一次跑檢查器 |

**共同的教訓：綠不等於有效。** 本輪每一步都做了負面驗證——把防線改壞一次，
確認測試真的會紅。九步全部做了，沒有一步例外。

### 🔴 被推翻的假設：「規格寫了就等於實作了」

S1／S2／S3 三步的共同形態**不是「加功能」，是「規格與實作已經互相矛盾」**：
`limits.yml` 早就寫了 `sku_unique_per_shop: false`、早就是四態、
`88` §4 早就寫了「建立商店的流程**必須**連帶建立它」——實作全部沒跟上。
⇒ 這種矛盾修起來**不需要任何新裁定**，所以排在寫入路徑地基之前。

### 🔴 被推翻的假設：「照抄本尊」可以不查就抄

使用者對三個待裁定問題的回覆是「深度分析和研究 shopify 的架構，然後我們和 shopify 一樣」。
考掘之後發現我方規格有 **8 條與本尊不符**，其中最貴的一條是
**`CONFLICT` 不是樂觀鎖碼**——本尊那裡它是「折扣屬性互斥」的**輸入驗證**。
`63` §L-3 原本要把它「提升為泛用碼」，本輪**以相反方向結案**。

**教訓：把一個碼「提升為泛用」之前要先查它在本尊那裡是什麼意思。**
`CONFLICT` 這個英文詞看起來當然像樂觀鎖——**光看名字推語義是本輪最容易犯的錯**。

### 🔴 被推翻的假設：「守衛越嚴越好」

「0 examples 不是通過」那道守衛改了三版：
① 無條件檢查 ⇒ 單跑一個檔被誤擋——**一個妨礙日常操作的守衛會在第一天被拿掉**；
② 「載入的檔數 < 5 ⇒ 跳過」⇒ **判斷反了**，「載入的檔案很少」正是要抓的那個 bug 的
**症狀**不是反例，於是 pattern 壞掉時守衛被自己的條件跳過；
③ 「ARGV 沒有路徑也沒有 `-e`／`--tag`」⇒ 四情境實測全對。

**守衛要活得下來，它就不能妨礙日常操作；而它的觸發條件不能與它要抓的症狀重疊。**

### 🔴 對自己的清單做斷言之前要先 grep 自己的倉庫

S3.5 我在 `limits.yml` 寫「我方對 `orderCreate` 強制冪等是加嚴」——
但全庫 grep `orderCreate` **只命中那行註解本身**，我方根本沒有這支 mutation
（訂單成立走 `draftOrderComplete`）。照抄考掘報告的措辭而沒有核對自己的倉庫。

## ③ 還有什麼沒解決

- 🔴 **claim/replay 完全沒做**，五個未決點（表形狀與 `11` §2.1(a) 不一致且**缺
  `mutation_name` 欄**／claim 的 transaction 邊界／缺 key 的 code 不在任何 enum／
  兩份清單待合併／**本尊沒說業務失敗算不算成功而被快取**）。
- 🔴 **`Types::MutationType` 刻意沒掛上 schema**。掛上去**必須同批處理 claim/replay**，
  guard spec 會擋。
- 🔴 **`Money::Storage` 不能相加相減**（`65` §F.3 只講 SQL rollup，值物件層空白）。
- 🔴 **往返自檢沒有掛在轉換路徑上**（規格要的是「非生產環境每次轉換都跑」）。
- 🔴 **`purchasable`／`discoverable` 具名 scope 延後**（`13` §F1.2(d) 的 SQL 指向不存在的表）。
- 🔴 **D12（變體×選項 join 表）尚未落地**，而它明文「必須在第一支商品 mutation 之前」。
  本輪的唯一義務是**不要建出擋住它的東西**，已遵守。
- 🔴 **`88` §5 還有四項是活的**，其中 `auto_publish` **目前只是一個欄位、
  沒有任何行為掛在上面**——最容易被誤以為已完成的一項。
- 🔴 **`enforce_idempotency_contract!` 要由子類主動呼叫**，忘記就等於沒有檢查，
  **而沒有任何機制會發現**。
- ⚠️ **本層仍然沒有任何生產呼叫端**：`app/` 的 `Money::` 只出現在自己，
  `Psp::BaseAdapter` 沒有子類，`ProductType` 連價格欄位都沒有。
- ⚠️ 規格待修三處：`28` §6 的「20 個泛用碼」與清單對不上（24 才對）；
  `65` §C.3 的 C1 白名單描述是空的；`limits.yml` 的 UNLISTED catalog 鍵值與註釋不一致。

## ④ 下一個人要注意什麼

1. 🔴 **每一層防線都要問「有沒有一個測試會全綠的破口」**，然後**把防線改壞一次**確認會紅。
   本輪九步全做了負面驗證，抓到的東西比任何一次 code review 都多。

2. 🔴 **拆欄位的 migration 一定要連 model 宣告一起改。**
   `20260814000000` 拆了三張表的 `shop_id` 卻沒改 `Shop` 的 `has_many`，
   `Shop#destroy` 壞了一整天而沒有人知道——**欄位沒了，宣告不會自己失效。**

3. 🔴 **查 shopify.dev 時注意版本陷阱**：只保留最近四個 stable 版，
   `/2024-01/` 這類舊路徑會**靜默回傳 latest 且不報錯**（實證：它自報 `api_version 2026-07`）。
   所有「跨版本逐字相同」的結論都是假證據。對齊基準版是 **2026-07** 不是 2026-04。

4. 🔴 **測試店的 admin 走內部 persisted-query API**（`/api/operations/{hash}/{Op}/`），
   **不是公開 Admin GraphQL** ⇒ 在後台操作抓到的 payload **不能當 parity 依據**。
   要驗公開 API 得走 shopify.dev 文檔或真的 API token。

5. 🔴 **`__build` 與 `MutationType` 是兩個「靠註釋與 CI 撐著」的地方**：
   前者是 Ruby 表達不了 friend class（C5 守），後者是刻意不掛 root（guard spec 守）。
   兩者的守衛都把**理由寫進斷言**，改動它的人一定會讀到。

6. **`bin/ci` 現在跑六支自訂檢查**（本輪補齊）。改 CI 時**兩邊都要改**——
   落差的後果是「本機全綠 → 推上去被擋，而擋下來的理由是本機沒有機會發現的」。

7. **非交易式測試的清理要寫在 `before` 也寫在 `after`**：`after` 自己失敗過一次，
   殘留資料讓下一次整個 rspec 程序在**無關的地方**紅。
