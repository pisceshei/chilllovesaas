## ② 為什麼這樣改

- **先用 workflow 窮舉再動手**：alt 是跨切面語義，讀寫兩面漏一邊的症狀是
  「寫進去了、讀不出來」——而兩邊各自的測試都會綠。派了六個維度平行盤點
  ＋獨立反駁複查，反駁方抓到第一輪盤點**漏了整整六個 backend 檔**（全是讀取面），
  並指出「照那份清單改完，寫入面全落 files、讀取面仍讀 media，
  症狀正是 D48 要消滅的那一個」。
- **Presenter 收成單成員是刻意的**：`Data.define(:file)` 讓「傳某個 media 的 alt」
  在型別上不可表達。遷移期最可能的錯是照舊傳兩個參數，少一個成員就直接炸，
  不會靜默讀舊值。
- **不套 `fileUpdate` 的 ready 前置**：我一度加上去（「同欄同規則」聽起來有道理），
  但官方那條限制的理由是 `fileUpdate` 能換 `originalSource`——換內容與管線衝突。
  只寫 alt 沒有這個衝突，套上去只是多一個本尊沒要求的失敗態。**已撤回並記下理由。**
- **被推翻的假設**：①「`media.alt_text` 是權威」（D48 推翻）②「同欄同規則所以要一起
  加 ready 閘」（推理錯，見上）③「`GROUP_CONCAT` 取第一筆很方便」
  （`group_concat_max_len` 1024 bytes vs 512 CJK 字＝1536 bytes，第一筆就會被截斷）。

## ③ 還有什麼沒解決

- **停用欄沒有機械守衛**：`media.alt_text` 現在靠 spec 擋，沒有 CI 判準。
  依鐵律 20.4 不得在本 PR 逕自加 `scripts/`，候選已登記 `91` §2 **G-05**，等裁定。
- **線上驗收未做**：合併部署後要驗——遷移在 bt3 的 14 個檔上實際搬了幾筆、
  同檔掛兩商品時改 alt 是否兩邊都變、缺 alt 數是否仍算得對。
- **`files.alt_source` 未建**（62 §F.1 的 AI 標記稽核欄），歸第 3 包遷移批次。
- **傳播語義仍是 schema 推論**，非官方逐字；測試店複驗未做。
- D48 通則的其餘三項未做（見 §①）。

## ④ 下一個人要注意什麼

- 🔴 **任何新的 alt 讀寫端一律走 `files.alt_text`**。判準很簡單：看到
  `media.alt_text` 就是錯的，除非你在寫遷移或 schema。
- 🔴 **`ProductType#preloaded_media` 是 `media` 與 `mediaMissingAltCount` 共用的**。
  不要讓其中一個改回 `object.media.to_a`——單筆路徑會變 N+1（守衛在
  `media_pipeline_flow_spec` 的「單筆路徑」那例，已做突變驗證會轉紅）。
- **`UpdateMediaInput.alt` 的 `key?` 語義不得退回取值**：沒送 ≠ 送空字串，
  退回去會讓沒送 alt 的呼叫清掉全站那一份。
- 🔴 **第 29 包分支 rebase 時會撞兩處**（`m1/p29-variant-subpage`，後端已完成）：
  ①`ProductVariantType#image` 還在呼叫 `Presenter.new(file:, alt: row.alt_text)`
  ——兩個參數。Presenter 收成單成員之後這裡會直接 `ArgumentError`。
  **這正是把它做成型別守衛的用意**：不是靜默讀舊值，是當場炸。改成
  `Presenter.new(file: row.stored_file)` 即可。
  ②`variant_subpage_surface_spec` 有一條 fixture 把 alt 寫在媒體列上
  （`Media.create!(… alt_text: "變體圖" …)`），要搬到它的 `StoredFile`。
  ⚠️ 該欄位目前**沒有其他 spec 覆蓋**，漏改①不會有第二道紅燈。
