## ② 為什麼這樣改（含被推翻的假設）

### 前面三輪只看到全站三分之一的 DOM

44／47／59 號都寫「`s-` 前綴是**封閉** shadow root，讀不到」。**錯的。** `element.shadowRoot` 可存取，穿透後節點數 **4,893 → 15,169**。

47 號因此才發明「CSS transform 放大 ＋ 高倍率截圖 ＋ 目視判讀」那套；59 號因此把類別 picker 與更多動作選單記為「拿不到」。**那套方法現在整個退役**——`getComputedStyle` 直接讀，精度更高且不會像 CDP 截圖那樣逾時（本專案已逾時 3 次）。

兩個必踩的坑：`s-internal-*` host 是 `display:contents` 所以量到 0×0（要量 shadow 內第一個有尺寸的後代）；slotted 內容的 `textContent` 是空的（要從 host 取文字）。

### 「無變體商品」根本不存在

59 號在無變體商品頁量到的 pill 分組 id 是 `product_variant_collapsible_*`。當時只當成命名。本輪拆了變體詳情頁——**同樣三組、同樣 id、同樣組成**。

名字解釋了架構：**那三張卡從來都是變體的卡。** 有變體時商品頁的價格／庫存／運送整組消失、移到變體詳情頁。61 號從官方拿到更硬的證據：`Product` **沒有** `price` 欄位（只有衍生的 `priceRangeV2`）、`ProductVariant.price` 是 non-null、`hasOnlyDefaultVariant` 欄位存在。

原型已照此重建：三張卡抽成 `pdPriceCard/pdInvCard/pdShipCard` 三支，商品頁與變體詳情頁各自帶入自己的變體物件，**共用同一支 `pillSet()`**。

### 會收錯 100 倍錢的那條，根因不是粗心

裁定二讓所有幣別顯示兩位小數、儲存一律 ×100。JPY `¥1,480` 儲存 `148000`，**直接送 Stripe 就是收 ¥148,000**。

它之所以危險不在於難懂，而在於：**在 HKD／USD 這些 exponent=2 的幣別下，錯的實作與對的實作輸出一模一樣。** 本地開發、CI、staging 全綠。

所以處置不是寫註釋而是四層防呆，其中**最關鍵的一條是「值物件不實作 `to_i`」**——只要實作了，`Integer()`、多數序列化器、字串插值都會自動呼叫它，上面三層全部作廢。

修這條時衍生抓到三處同根因，最嚴重的是 **`15 §F4-5` 逐字寫「JPY 等零小數幣別不乘 100」**——那是裁定二*之前*的儲存模型，照現行規格文字實作出來就是那個 100 倍。

### 順豐：使用者是對的，但結論反而更保守

我上一輪判定「文檔站是 SPA 抓不到」。使用者指出免登入可拿。**確實拿到更多**：V-38（官方 SDK PDF 把端點網域印錯了，DNS 查 `sfapi.sfexpress.com` 連 apex 都無 A 記錄）、V-49（去重鍵是 `orderid` 不是 `requestID`）、V-47（舊世代推送**根本沒有驗簽欄位**）。

順帶抓到既有 bug：`msgDigest` 演算法被誤標成 `V-40`（那是 ZPL），**從未被登記**，於是 `enable_gate` 漏掉最硬的阻塞項——算不出簽章一個請求都送不出去。

**但香港的結論更保守了**：香港作**目的地**（內地寄出）✅ 同一套 API；香港作**寄件地** ❌ 未確認——**而我方首發要的正是後者**。不要為了「有一個真的 carrier」先接內地丰橋，它點不亮任何一條我們要的 lane。

### §D.5 銷號帳：換樑不拆屋

「取了號不用會被計費」在官方文檔中**沒有任何依據**，而且這問題不會由文檔回答（屬月結合約）。原文把它寫成事實，該事實地位已撤銷。

**但整節保留**，因為換了一根更硬的樑：不是「號有價所以要記帳」，是**「號不可回收所以要記帳」**——官方明載訂單號取消後不能重複利用。就算順豐一毛不收，「同一張 FO 掛著兩個都無法回收的識別」仍是資料正確性事故（倉庫兩張面單對同一批貨，拿哪張都看起來對）。

### 髮絲線：47 §C 的解釋被自己的量測推翻

47 §C 判定髮絲線＝「1 個裝置像素」（dpr 1.5 → 0.667px），並要求配 dpr 媒體查詢。**64 號在 dpr=1 的螢幕上量到 `0.66px`** ⇒ 它是寫死的次像素常數，與 dpr 無關。

`r_hairline` 規則因此反轉：**有 dpr 媒體查詢反而是錯的**。三份原型都已改成固定值。

## ③ 還有什麼沒解決

### 🔴 最該優先

1. **`15 §F4-5` 是 P0 且未修**（65 §J M-1）。逐字寫著「JPY 等零小數幣別不乘 100」，照做就是 100 倍。連帶 `16 §F5`、`55 §A` 兩個交叉引用。**它不在本輪任何 agent 的可改清單裡，所以沒人動它。**
2. **`27 §8-3` 的變體切換參數是錯的**（66 §G-1）。規格與原型註釋都寫 `?variant=&section_id=`，Ella 實際 AJAX 送的是 **`option_values=`**。照現規格做，商家每點一次選項都選不中變體。
3. **`36 §3` 與 `39:2225` 的 `platform_daily_rollups` 形狀互相矛盾**（63 §L-2），兩者不可能同時成立。

### 拿不到的（是「沒拿到」不是「沒有」）

- **前台商品詳情頁**：商店有密碼保護，而我**不能代輸密碼**（安全規則，即使使用者提供也一樣）。已改由 Ella 源碼推導，但實際渲染結果未親眼驗證。
- **主題編輯器 UI**：整個在跨來源 iframe（`online-store-web.shopifyapps.com`），父頁 JS 讀不進去。同樣改由源碼推導。
- **順豐**：V-37／V-39／V-41／V-44／V-48 仍開。**這台機器有 Chrome 連著，用瀏覽器開一次 API 目錄頁可一次結案大半**——我沒動是因為要由使用者指定用哪個瀏覽器。
- **外層控件盒的焦點環**（64 §5 / V-127）：只確認「不畫在 `<input>` 上」，真正承載的節點沒找到。
- 類別分類法樹層級、`更多動作` 選單逐項、大量編輯器、採購單／轉移／禮品卡的完整建立流程。

## ④ 下一個人要注意什麼

1. **量測一律用 `getComputedStyle` 穿透 shadow，不要再開截圖。** 方法與兩個坑寫在 60 §0 與 64 §0。CDP 截圖在本專案已逾時 3 次，不是偶發。

2. **「顯示位數」「儲存尺度」「對外單位」是三件事。** 這是本輪最容易致命的一條，而且**它在 HKD 下永遠測不出來**。任何碰金額的 PR，先問「這個數字要送去哪裡」。不得用 `currency_format.exponent` 當換算基數——那一欄自裁定二起語義是顯示位數。

3. **註釋不算防呆。** 三個理由：不進 CI、不在事故現場、且錯的實作在主力幣別下輸出正確。要擋就用型別（65 §C）。

4. **子字串比對整份樣式表是雙向假陽／假陰的來源。** `r_hairline` 舊版用 `"dppx" not in style`，結果**任何在註釋裡提到 dppx 的檔案都會讓 WARN 靜默消失**——本輪真的發生了，是執行者自己誠實回報才發現的。寫 lint 規則時先剝註釋。

5. **agent 誠實回報「我這條是巧合不是設計」的價值極高。** 本輪 §③ 的第 4 條就是這樣來的。驗收時要看實跑證據，但**更要獎勵這種主動揭露**。

6. **「沒拆到」與「沒有」要分清楚。** 60 §9、64 §5、66 §④、58 附錄 B 都是「沒拿到」的登記。不要據此刪我方既有功能，也不要據此宣稱對齊完成。

7. **本輪有 4 個 agent 併行改同一批檔案**（`limits.yml` 被三個 agent 動過）。最後 YAML 合法、lint ERROR 0、三份原型 `node --check` 通過。但**併行改共用設定檔是這輪的運氣不是流程**——下次要嘛分檔，要嘛序列化。
