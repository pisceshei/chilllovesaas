**遇到的問題與證據**（三個，都不是規劃時預期的）

0. 🔴 **本包自己的第一版有兩個 🔴 級缺陷，靠對抗審查才抓到**（詳見 worklog）：
   ①`Audit` 的 `--fix` 會把「sanitize 後變空」的列寫成空字串，**製造出本包存在的理由
   （鬼列）**，而且 fix 不冪等；②`recompute_status` 只改文字時不推進 `updated_at`，

   ——**突變測試只證明「拿掉守衛會紅」，不證明「守衛守的是對的東西」**。

1. 🔴 **譯文 `body_html` 完全不 sanitize**。在 bt3 正式環境 rev `1a75ceb` 以 `rails runner`
   實跑：同一段 `<p>ok</p><script>alert(1)</script><img src=x onerror=alert(2)>`
   走 `descriptionHtml` 落庫 `<p>ok</p>alert(1)<img>`，走 `translations[body_html]`
   **原樣落庫**。`SaveProduct` 的註釋逐字寫「譯文原樣帶下去（驗證在 `Translations::Upsert`）」，
   而 Upsert 只驗長度與欄位白名單。⇒ 第 30／34 包渲染的那一刻就是儲存型 XSS。
2. 🔴 **`CsvImport` 全程沒有任何 `recompute_status` 呼叫**。⇒ 經 CSV 進來的譯文不反映在
   後台進度，也不推進 `translation_status.updated_at`——而那正是 67 §G.3 建議拿來當
   `translations` cache stamp 載體的欄位。
3. 舊 `Upsert#blank_value?`（regex）在 24 格對照矩陣裡**判錯 8 格**，全部同一方向
   （該判空的判成非空）⇒ fallback 永不觸發、商家看到空白區塊。本機 `bundle exec ruby` 實跑。

## ② 為什麼這樣改

**證據鏈**

- 截尾鏈「截到 `zh` 就停」＝與 CLDR 同構，不是我方自創：CLDR `parentLocales.xml` 把
  `zh-Hant` 的 parent 寫成 `und`，官方理由逐字
  `If the locale is written in the non-default script for the language, it needs to have the
  parent specified as root, for example, zh_Hant and sr_Latn need to fall back to root (not to
  zh and sr which are in different scripts).`
  （<https://github.com/unicode-org/cldr/blob/main/common/supplemental/parentLocales.xml>，2026-08-25）
- HTML parser 選 HTML4：實測 `"<p><img src=x"` 在 HTML4 判非空、HTML5 判空，而判空的動作是
  `delete_all` ⇒ 錯誤代價不對稱 ⇒ 選假陰性側。而且 `Loofah.fragment` **就是** HTML4，
  與既有 sanitizer 同源，零新依賴。
- 批載不把 `field_key` 放進 IN：MySQL 官方「兩個 IN 清單的等值 range 數是乘積」＋
  `eq_range_index_dive_limit` 預設 200；50×3×4=600 會讓執行計畫無預警改變。
- 遙測 payload 不放 `resource_id`：Prometheus 官方明文禁止無界集合當 label。

**被推翻的假設**

0. ❌ 「初始的 18 格突變全紅 ⇒ 守衛都對」——**最大的教訓**。兩個 🔴 級缺陷（見①的第 0 點）
   都在那 18 格之下存活：突變測試證明的是「這行程式碼有測試在看」，不是「這行程式碼
   做的是對的事」。真正抓到它們的是**對抗審查的 e2e 重現**（跑一次 fix、再跑一次 audit）。
1. ❌ 「`sr-Latn-RS → ["sr-Latn"]`」——我寫測試時假設它會像 `zh-Hant` 一樣停。
   實跑得 `["sr-Latn", "sr"]`：**實作是對的，我的期望值錯了**。我方只把 `zh` 放進禁用表，
   所以 `sr-Latn → sr` 仍會發生，與 CLDR 對 `sr-Latn` 的處理不同構。已登記為刻意的射程限制。
2. ❌ 「研究建議的 `read_path_blank_check: text_only` 該照做」——**否決**。量級不成比例
   （省 85µs vs 買回讀寫兩種答案的漂移）。limits 改記 `single_implementation_for_read_and_write`。
3. ❌ 「`<script>` sanitize 後會整段消失」——實測**文字內容會保留**
   （`<script>alert(1)</script>` → `alert(1)`）。我第一版的「長度上限量 sanitize 後的值」
   測試因此前提錯誤，改用 `style` 屬性（不在白名單，整個屬性被移除）才造得出「變短」。
4. ❌ 「`title` 送 `<p><br></p>` 該被判空」——這是**既有測試的斷言**，而 67 §C.4(b) 原文
   把 HTML 那一條明文限定在**富文本欄位**。舊實作不看欄位型別。⇒ 改測試不改規格。
5. ❌ 「CLDR 的 `parentLocales.xml` 有那段官方逐字理由」——**該檔案路徑 404、該引文在
   CLDR 全文找不到**（審查 D1）。已撤回並改引三個親自複驗的來源。教訓：外部引文要
   **當場抓取複驗**，不能憑印象寫路徑與「逐字」。
6. ❌ 「用 `blank?` 判 raw 就能知道 sanitize 有沒有毀掉內容」——兩者走同一個 parser、
   撞同一個深度懸崖，偵測器與被偵測的失效共用盲點。改用 parser-independent 的
   `text_bearing?`。
7. ❌ 「`platform_locales` 有地區變體，截尾鏈馬上就會生效」——實查 28 列，
   **沒有任何一列的截尾目標也在表內** ⇒ 鏈在今天的生產資料上不可達（見③）。

**未採方向**

- 不加 `nokogiri` 到 Gemfile：`Loofah` 已在用，加了只是重複宣告。
- 不在本包開 migration（`translations_updated_at`／`shop_locales_version`）：欄位歸第 3 包，
  本包只登記需求與前提（dev doc §5）。
- 不碰 `poc/`：PoC 的三個反例是第 34 包的事。

## ③ 還有什麼沒解決

1. 🔴 **截尾鏈在今天的生產資料上不可達**（P7-L1）。`shop_locales belongs_to :platform_locale`，
   而 `platform_locales` 的 28 列裡 `pt-BR`／`pt-PT` 的父 `pt` 不在表內、`zh-Hant`／`zh-Hans`
   的父 `zh` 是禁用碼。複驗＝`bin/rails runner "puts PlatformLocale.pluck(:tag).inspect"`。
   ⇒ §C.4 步驟 2 目前只在單元測試（helper 自行補平台字典列）中生效。補字典是 **ML-0**。
2. 🔴 **繁簡誤借稽核未做**，卡在 OpenCC 的 Apache-2.0 授權裁定（鐵律 9 ＋ 17.3 例外）。
   **本包需要使用者裁定的只有這一件**（本檔③的其餘各條都是登記／待下游，不需裁定），
   dev doc §7 有選項與代價。
   目前形態＝介面就位、明文棄權、**絕不回報 0 筆**（有突變守衛）。
3. ~~U14~~ **已解**：bt3 `@@eq_range_index_dive_limit = 200`（＝推導所用的官方預設值）、
   `range_optimizer_max_mem_size = 8388608`、MySQL 8.4.10、`sql_mode` 為 strict。
4. **P7-L2 未取得**：本尊的內容譯文 fallback 鏈形態。我方是 ours 分歧，
   **不得寫成「對齊本尊」**。取得方法＝鐵律 12 到測試店 `chill-love-u5q5mnzq` 實測。
5. **`Resolve` 零生產消費者**：只有單元契約被驗證，**整合面尚未被驗證**。
   第 30／33／34 包接上時才會知道 API 形狀對不對。
6. **既有 digest 落差**（P7-L10）：`Translation.digest_for` 與 `limits.i18n.digest_normalization`
   不相符、`severity_for` 與 67 §C.5(b) 不同。鐵律 20.5 ⇒ 不在本包射程，登記另案。
7. **下游影響**：第 3 包立 stamp 欄時**必須**把 `translations` 加進
   `limits.catalog_flow.cache_stamp_sources`，否則 63 §D.3 紀律 2 的自檢會在第一次渲染
   翻譯欄位時 raise。本包刻意不加（現行清單每一項都指向實際存在的欄位，加一個指向
   不存在欄位的來源名＝把假設寫成事實）。


突變驗證腳本在 scratchpad（不入庫）；18 格的清單在 worklog 的突變表，
要重做就照那張表逐格改回無效寫法再跑對應 spec。
🔴 **還原時不要用 `git reset --hard`**——第 6 包踩過，會連未提交的修復一起清掉；
用「讀原檔 → 寫突變 → 寫回原檔」的成對操作。

**紅線（不得外推）**

1. 🔴 **後台 GraphQL 的 `translations` 永遠是精確比對，不接 `Resolve`**。接了之後商家
   一按儲存就會把來源語言原文寫成該語言的「真譯文」，`outdated` 與進度數字全部失真。
   有兩格反向 spec 盯著。
2. 🔴 **`resolve()` 不收 market 參數**（I18N-6）。想加回來先讀 67 §C.2 的沿革註釋。
3. 🔴 **`translations.value` 的任何新寫入路徑都必須經 `sanitize` ＋ `BlankValue`**，
   順序是 sanitize → 判空 → 量長度。三者對調各有一種靜默毀資料的形態（見 `Upsert#sanitize` 註釋）。
4. 🔴 **遙測 payload 不得放 `resource_id`**（無界集合）。
5. 🔴 **`translations:fix` 是不可逆刪除**，因此強制要求指名商店。不要為了方便把它改成
   可以不帶參數跑全平台。
6. 🔴 **欄位中繼資料只有 `Translations::Fields` 一處**（消費者導出＝
   `git grep -n "Fields\.\(kind\|missing\|limit\|measure\|base_value\)" -- app/`）。
   新增可翻欄位＝改那一張表，不是在各消費者各加一行。

🔴 **線上驗收的前提（bt3 現況）**：`demo` 店的 `published` 語言**只有 `en`**（＝來源語言）
⇒ 用 `scope: :published` 驗任何非 en 請求都會直接落 base，**驗不到鏈也驗不到 translation
命中**。線上驗收必須二擇一並在記錄裡寫明用的是哪一種：①先 publish 一個語言（測試資料，
可還原）②用 `scope: :enabled` 走預覽形態。不得含糊寫「線上驗過了」。

**停止條件**：本包的 DoD＝上列 spec 全綠 ＋ 兩輪突變全紅 ＋ CI `quality`／`test` 兩綠
＋ 線上（bt3）以 `rails runner` 走一次 Resolve 與 audit（依上述前提）。
**不包含**「Resolve 被真的接上」——那是第 30／34 包。
