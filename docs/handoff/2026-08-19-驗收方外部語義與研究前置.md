## ② 為什麼這樣改（含被推翻的假設）

**被推翻的假設一：「驗收方說的照做就好」。** 本輪十四條意見裡，研究查出**四條的方向會出事**：
- Codex[3] 照字面補路徑前綴會**把 CI 打紅**（補完前綴這些路徑才第一次進入 R1 視野，
  而 121 那格缺「尚未建立」錨定）——它漏了配套。
- Codex[2] 給的兩個選項只有一個成立（gem 早已安裝且在生效，選另一個等於為既有機制重複立包）。
- bot🔴3 給「二選一」，實測證明**兩條都要**（單用任一條都留下無判定力的複驗式）。
- #60 那條「`require_last_push_approval` 是真正的解」——**與官方敘述反向**，官方自承
  它在 hijack 情境比 dismiss-stale 弱。
⇒ **驗收意見的「事實陳述」幾乎都對，但「修法方向」需要獨立查證**。這正是使用者裁定
「修復之前先到網上搜索⋯進行比較是否適用」的價值所在，而且**純內部一致性的那些也一樣**——
bot🔴3、Codex[2] 都是內部一致性題，卻都靠外部證據（detect-secrets baseline、
strong_migrations 官方 README）才找到比建議更好的解。

**被推翻的假設二：「把外部事實寫進倉庫就不會再錯」。** 我在寫 `external-facts.md` 之前
另派了一輪**獨立複核**（重查每個 URL、比對逐字原文），結果 16 條裡 **1 條原斷言是 WRONG、
6 條原本會寫成過度宣稱**。⇒ 一份專門用來防止憑印象斷言的檔案，作者自己在寫它的時候
仍然產生了 7 處問題。**證據紀律不是對別人的要求。**

**被推翻的假設三：「釘死期望命中集合就有判定力」。** bot🔴3 要求複驗式要能判定，
我照做釘了「恰 6 行」；**同一輪重建 Changes 表時，內容欄逐字寫進了那個舊寫法，
命中當場由 6 變 10**。⇒ 最終改成**類別謂詞**（每條命中都必須是引述／更正註／歷史敘事，
不得有活的複驗式），附快照數字但不以它當判準。

## ④ 下一個人要注意什麼

1. 🔴 **驗收意見要分兩半讀**：「事實陳述」與「修法方向」。前者近乎都對（他們會跑命令），
   後者要獨立查證——本輪十四條裡有四條的方向會出事。
2. 🔴 **改一行之前先確認它在不在 fenced code block 裡**。我在總方案 `:103` 加了粗體與反引號，
   而該行在 ``` 圍欄內 ⇒ 標記會原樣顯示。這條的依據就在本輪新建的 `external-facts.md` B5，
   我自己寫的，自己隔一小時就違反了。
3. 🔴 **多處改動一律由大索引往小索引動**。我先替換了 `wait_for_reset`（行 405）再刪除
   行 462–484，前者位移了後者的索引，**刪錯 3 行**。備份還原後改成降序才對。
   同族教訓已有一條（跨行正則刪表格列吃掉 133 行），這是第二條。
4. 🔴 **刪除／替換前先印出將被動到的內容**。本輪每一次批次改動都先跑 dry-run 印出行範圍與原文，
   兩次因此當場發現定位錯誤（`idx("}\n")` 子字串比對撞到 `${1:-0}`；old 字串縮排算錯而零命中）。
5. **檢查器本身要做突變驗證**。我新寫了一支抽出 workflow 每個 `run:` 區塊跑 `bash -n` 的檢查，
   跑完全綠——但全綠不代表它有用，**注入一個未閉合的 `if` 確認它會轉紅**之後才敢依賴它。
6. **釘死的數字／集合會腐化**。要判定力就寫**類別謂詞**（「每條命中都必須是引述」），
   數字只當快照、不當判準。
