## ② 為什麼這樣改

**為什麼先做 catalog 而不是先做 channels**：`publications.catalog_id` 已經**空轉兩週**
（無外鍵、無寫入者、恆 NULL），而本尊每個 publication 都有 catalog（`82` §9.5b／§10.3
兩次抓包）⇒ 這是**現存的**功能缺口，不是預備未來。`channels` 解的 C-1／C-2 要到第二個
管道才會出事。

**為什麼拆兩個 PR**：`platform_apps` 走平台字典表要改鐵律 2 本文（配套條款③明文要求
同時改三處），落入 18.3 人工合併 ＋ 17.3 必須停下來問。把不需要裁定的那一半先合併，
可以讓 catalog 這個現存缺口立刻收口，也讓 PR B 的 diff 只剩真正需要人工審的部分。

**為什麼 `sales_catalog_id` 不轉 NOT NULL**：`20260814200000`／`20260815000010` 兩支既有
migration 在重跑舊庫時仍會先建 publication 再建 catalog。轉必填會讓那條路徑炸。
約束改由外鍵 ＋ model validation 擔保。

**為什麼 `has_one :publication` 沒有 `dependent:`**：FK 已經擋住刪除，而 FK 連 `delete_all`
都擋（`restrict_with_error` 只擋 `destroy`）。加 `dependent:` 會製造「以為有兩道其實只有
一道」的錯覺。兩格 spec 分別釘住 `destroy` 與 `delete_all` 都拋 `InvalidForeignKey`。

**被推翻的假設**：

| 假設 | 怎麼被推翻 |
|---|---|
| 表可以叫 `catalogs`、模型叫 `Catalog`（設計文件原文） | 建檔後 8 個 spec 載入失敗，`Catalog` 是既有服務命名空間 |
| migration spec 可以直接呼叫 `up`（照 `p12_backfill_publications_spec` 的形態） | 那支 migration 純資料無 DDL；本支有 `create_table` ⇒ 隱式提交打斷交易 |
| `migration.down` 可以直呼 | `strong_migrations` 把 `remove_column` 當新增操作擋下；要用 `migrate(:down)` |
| `db:rollback` 之後 `db/schema.rb` 會回退 | 沒有。rollback 成功但 schema.rb 仍留 +15 行 |

**未採方向**：抽共用 `purge_tenant_data!` helper 取代六份清單——屬跨元件重構，
不在本根因影響圖內（鐵律 20.5），登記 `91` §3.19。

## ④ 下一個人要注意什麼

**入口**：`docs/plans/2026-08-26-S0-方案D-schema設計.md` §7.2 有落地狀態表（哪些 M 做了、
哪些沒做）。決策背景在 `docs/plans/2026-08-26-S0-管道身分模型-決策文件.md`。

**前置**：PR A 合併並部署驗證後才做 PR B——PR B 的 `channels` 對 `publications` 有 FK，
而 PR A 動了 `publications` 的欄位。鐵律 17.3：**依賴鏈上的包等合併完成才開工**。

**重跑方法**：

```bash
bundle exec rspec spec/migrations/s0_backfill_sales_catalogs_spec.rb spec/models/sales_catalog_spec.rb
```

🔴 **`scripts/` 的 bash 與 workflow 兩類閘門一律用 Git Bash 跑**，PowerShell 裡的 `bash`
可能解析成 WSL，拿到的是**假失敗**（`No such file or directory` 與 `bash -n 不通過`）。

**紅線**：

1. 🔴 **不要把 `SalesCatalog` 改回 `Catalog`**——服務層命名空間會炸（理由見模型檔頭）。
2. 🔴 **不要把 `.channel_catalog_title` 改成本尊的 `Channel Catalog {id} for {name}` 格式**
   ——catalog 先於 publication 建立，建立當下沒有 publication id。這是登記在案的分岔。
3. 🔴 **不要在 `shop.rb` 把 `has_many :sales_catalogs` 移到 `has_many :publications` 之前**
   ——`dependent:` 按宣告順序註冊，倒過來會被 FK 擋住且錯誤訊息指不出根因。
4. 🔴 **新增任何租戶表時，六份併發 spec 的 `purge!` 都要補**（複驗指令見 `91` §3.19）。
5. 🔴 **`db:rollback` 之後不要相信 `db/schema.rb`**，先 `git checkout -- db/schema.rb`。

**不得外推的範圍**：本 PR **沒有**改變可見性判定、**沒有**做 catalog 成員語義、
**沒有**做能力旗標的消費者。任何「既然 catalog 有了就順手接上第三層」的改動都不在射程內
（那是 S10，需要成員表）。

**停止條件**：PR A ＝ CI `quality`＋`test` 兩個 job 綠即自合併（D40）——**已完成**。
PR B ＝ **不得自動合併**，CI 全綠也要停下來通知使用者（18.3）。

6. 🔴 **不要把 `app_installations` 的 `installed_at`／`uninstalled_at` 當成「與本尊不一致的
   缺口」修掉**——官方 `AppInstallation` 確實沒有這兩欄（取證 2026-08-26），
   那是我方為了「卸載不得刪 publication」而定義的語義，已由 D52 明文登記。
7. 🔴 **不要加 `channels.name` 或 `channels.supports_future_publishing`**——本尊兩邊都有，
   我方刻意各只留一個產生處（鐵律 7）。理由寫在 `app/models/channel.rb` 檔頭。
8. 🔴 **新增任何租戶表時，六份併發 spec 的 `purge!` 都要補**——這件事在 S0 同一天中了兩次
   （PR A 一次、PR B 一次），登記在 `91` §3.19。
