## ② 為什麼這樣改（含被推翻的假設）

**核心設計：譯文一張表、每語言不建表。** 使用者問過「新增語言是否要建對應表格」，答案是不建——
`translations` 一列＝(shop_id, resource_type, resource_id, locale_tag, field_key, value)＋六個稽核欄。
理由不是省事：每語言一表意味著**每加一種語言就要一次 migration ＋一次部署**（商家在設定頁點一下按鈕，
後端卻要改 schema），表數是「語言數 × 資源種類」的乘積；更關鍵的是**欄位級的 outdated 偵測會做不到**，
而那正是「改了英文原文，其他語言要標需更新」的實作基礎。匯出／匯入反而因為共表而變成一支 CSV 通吃。

**被推翻的假設（四個，全部是實測推翻的，不是想出來的）：**

1. 🔴 **「spec 綠＝行為對」** —— ML-2 的 outdated 偵測在 spec 全綠，線上卻永遠不標記。
   根因：spec 送最小 input，而 SPA **每次都送全樹**（含未變更的譯文），於是比對基準被無條件覆寫。
   ⇒ **宣告式 API 的測試必須用前端真正送出的 payload 形狀**，不是最小可用 input。

2. 🔴 **「`pluck` 回的順序就是我給的順序」** —— 不是，是 DB 順序。症狀是「拖曳排序存檔後又跳回去」。

3. 🔴 **「交易 block 裡 raise、block 外 rescue 就會回滾」** —— joined 巢狀下**不會**。
   實測（MySQL 8.4.10／Rails 8.1.3.1）：joined 殘留列數 **1**、`requires_new: true` 為 **0**。
   而且 **request spec 驗不到**——RSpec 測試交易是 `joinable: false`，兩種寫法都綠。

4. 🔴 **「parity spec 綠＝語言包對」** —— parity 只問「五語一不一樣」。
   兩個鍵被**一致地**放錯位置（`en.yml` 有兩個 `handle_taken:`，插入配對到第一個），
   五檔一致地錯 ⇒ parity 全綠，線上顯示 `Translation missing`。
   成因是 parity 用 `.slice(:product, :staff)` 白名單挑子樹，而 `errors.collection` 從未在名單裡。

## ④ 下一個人要注意什麼

- 🔴 **改 `Translations::Upsert` 前先讀它開頭兩條硬規則**：①未帶譯文時 outdated 偵測**照樣要跑**
  ②值沒變時**不得重寫** `source_digest`。這兩條各自對應一次真實事故，拿掉任何一條都會讓
  「改原文→標記過期」在**線上**失效而**測試仍綠**。
- 🔴 **驗收要驗到訊息本身，不只驗 code**：`I18n.t` 缺鍵會**回傳字串**而不是 raise，
  只斷言 `code`／`field` 的測試對這一類 bug 永遠是綠的。現在有 `spec/config/locales_spec.rb`
  第二例（掃 app/ 內字面 key）擋著，但它掃不到動態 key。
- 🔴 **每個新守衛都要做突變驗證**：把被守的東西拿掉，確認測試真的轉紅。本輪四個新守衛都做了，
  其中「巢狀交易」那條在 request spec 裡**無論如何都綠**，正是靠突變驗證才發現要另立 service spec。
- 部署後的線上複驗一律用 `rails runner`（伺服器上要先 `set -a && . /etc/chilllove/env`，
  缺 `CHILLLOVE_BASE_HOST` 連 boot 都不行）。
- demo 店現有一個 `live-check-collection`（標題 Spring Picks，五語譯文齊全）可直接開來看。
