## ② 為什麼這樣改（含被推翻的假設）

### 「拿掉欄位」把商家的設定權變成了寫死的行為

這是本輪最值得記住的一條。上一輪看到「香港不使用郵遞區號」，就把欄位拿掉了。裁定指出正確做法是**做成後台設定**——商家自己決定哪些國家強制。

**HK 預設選 `optional` 而不是 `hidden`** 的理由要記住：「香港不用郵遞區號」本身**就是那條未查證的假設**。用 `hidden` 當預設，等於把同一條假設換個位置繼續寫死。`optional` 兩邊都不賭，等 V-34 查證後再調。

一般化：**遇到「某地不需要 X」，先問「這是法域事實還是商家選擇」。** 是後者就做成設定，不要做成行為。

### 「換成 HK$」與「拿掉郵遞區號」是同一個錯誤的兩個版本

上一輪已經學到「NT$ 換 HK$ 只是把同一個錯誤搬到另一個國家」（56 §513）。這一輪的郵遞區號是**同一個病**：把一個法域的形態硬編成系統行為。兩次都是**在修正法域問題時，用另一個法域的硬編去取代**。

### 實站佐證了兩條裁定，不是我方臆造

拆解使用者的真實 Shopify 商店時發現：**商店本身就是香港**，且金額**全部兩位小數**（`HK$2,000.00`、`HK$1,100.00 HKD`）。鐵律 11 的香港基準與裁定二的兩位小數，與實站一致。

### 商品頁最重要的發現：pill 收合模式

實站把卡片內的**次要欄位收合成 pill**，pill 顯示「標籤＋目前值」——**不展開也知道填沒填**。點任一 pill 展開該卡片**共用的一個** collapsible。我方原型 `aria-expanded` / `aria-controls` **皆為 0**，完全沒有這個模式。

它解決的是真問題：商品頁欄位太多。比「全部展開」和「摺疊成一個標題」都更省視覺成本。已做成可複用元件並補進 48 號 §33。

**利潤／利潤率是衍生唯讀欄位，算不出時顯示 `--` 不是 `0`** —— 與本輪稍早 P0-17 的「未計算 ≠ 0」是同一條原則，實作直接沿用 `draftTaxState()` 的語彙。

### 建立頁與詳情頁是同一個元件

實站兩者**版面、卡片順序、pill 分組 id 完全相同**，差異只有預設值與空態。所以合併成 `isNew` 兩態。

**這一步風險最高**——合併兩條既有路徑最容易產生同名覆蓋，而本專案的頭號事故正是這個。執行者合併前 grep 出四類風險，其中一類特別隱蔽：**`pdProfit` 是既有元素 id，會形成隱式全域 `window.pdProfit`**，新增同名函式會靜默打架。

### 58 號的四個最容易做錯的判定

1. **carrier ≠ fulfillment service**（判準：誰持有庫存、誰決定接不接單）。誤接會讓自營 FO 離開 `UNSUBMITTED`，違反 `16-F3.1(d)` 的 DB 不變量
2. **`EXTERNAL` 不得被 carrier 借用**（46a:275 綁 fulfillment service）。借了 guard 邏輯就得漏回前端
3. **沒有任何 FO 狀態轉移會呼叫 carrier**——carrier 掛在狀態機**旁邊**。carrier 失敗時 FO 狀態不變；進 `CANCELLED` 會依 46a:236 產生替代單，**每次逾時多一張 FO**
4. **`unknown` ≠ `transient_error`**，逾時**禁止自動重試**

還有 §D.5 **銷號帳**：運單號取了不用物流商會計費，最隱蔽的觸發是「換物流商重取號」。以及 §F 三段式編排——外部成功而 txn 回滾 ⇒ 號取了但 DB 無紀錄，**這張運單永遠不會被銷號**。

### 一次跨 agent 的語義衝突（值得記住的協作教訓）

58 號與裁定二**同時在改 `limits.yml`**。裁定二把 `currency_format.exponent` 的語義從「ISO 4217 minor unit」改成「顯示位數」（TWD 0→2）；58 號原本寫 `minor_unit_source: …currency_format.exponent`，改完之後那條會在 zero-decimal 幣別上算出 **100 倍誤差**。58 號的執行者自己發現並改成 `storage_multiplier: 100`。

**教訓**：同一個欄位被兩個並行任務賦予不同語義，型別檢查與測試都抓不到。**欄位改語義時，要 grep 全倉庫誰在讀它。**

## ③ 還有什麼沒解決

### ⚠️ 最該優先處理的一條

**`exponent` 這個欄位名現在不是 exponent 了。** 它的值是「顯示位數」，儲存一律 ×100。這正是本輪已經咬過人一次的坑（58 號執行者中招）。**建議改名為 `display_decimals`**——留著一個名實不符的欄位，同樣的 bug 一定會再發生。本輪沒改是因為要動三份原型＋limits＋規格，不想跟商品頁工作撞車。

## ④ 下一個人要注意什麼

1. **遇到「某地不需要 X」，先問是法域事實還是商家選擇。** 是後者就做成設定。本輪兩條裁定（郵遞區號、支付方式）都是在糾正「把選擇做成行為」。

2. **未查證的結論不要拿來當預設值的依據。** HK 郵遞區號選 `optional` 不選 `hidden`，就是因為 `hidden` 會把未查證假設換個位置繼續寫死。

3. **欄位改語義時要 grep 全倉庫誰在讀它。** `currency_format.exponent` 從「ISO minor unit」變成「顯示位數」，在同一天就讓另一份規格算出 100 倍誤差。而且**這個欄位名到現在還是名實不符**（見 §③ 第一條）。

4. **合併兩條既有路徑前先 grep 同名。** 不只是函式——**元素 id 也會形成隱式全域**（`pdProfit`）。本專案頭號事故就是同名靜默覆蓋。

5. **「沒拆到」與「沒有」要分清楚。** 59 §6 的 5 項、58 號的 13 條 V-編號都是「沒拿到」。實站商店剛好沒有多變體商品，不代表 Shopify 沒有變體 UI——**不要據此刪我方既有功能**。

6. **順豐文檔站是 SPA，別再派 agent 去抓。** 兩個站都試過了，只回得到 `<meta>`。要 API 目錄就得申請帳號。

7. **實站拆解的法律邊界**：行為與結構事實（有哪些欄位、`aria-expanded` 怎麼掛）等同拿尺量畫面，可用；**`Polaris-*` class 名與 CSS 一律不抄**（鐵律 9）。59 號的 pill 分組 id 刻意用我方命名不沿用實站的。

8. **驗收看證據不看宣稱。** 本輪五個 agent 全部附了實跑證據，我另外獨立 grep 驗證每一項關鍵宣稱。`python3 scripts/lint-prototype.py` 現在 14 條規則，ERROR 必須為 0。
