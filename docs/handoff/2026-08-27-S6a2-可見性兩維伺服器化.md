# 交接：S6a-2 可見性兩維伺服器化（2026-08-27）

> 本包 worklog＝`docs/worklog/2026-08-27-S6a2-可見性兩維伺服器化.md`
> 分支 `m2/s6a2-purchasable-discoverable-fields`，base＝main `6c54f3d`

## ① 我改了什麼

把 `Product.purchasable` / `.discoverable` 出到 GraphQL（各帶選用的 `publicationId`），
前端的可見性兩維改讀伺服器答案。這是 S6a 開出來的 GraphQL 缺口第一條。

驗證：後端 8/8、前端 155/155；**六個突變，五個轉紅、一個沒轉紅而那一個是真發現**
（見 §②）；閘門逐支退出碼 0。

## ② 為什麼這樣改（含被推翻的假設）

- 🔴 **被推翻的假設：「復用 `Publications::Lookup` 就等於有租戶隔離」**。
  我在註釋裡這樣寫了，M4 突變（換成裸 `Publication.find_by`）**跨租戶那格仍然綠**
  ⇒ 保護實際上來自 `acts_as_tenant` 的預設 scope，不是 `Lookup`。
  `Lookup` 的顯式 `with_tenant` 是第二層，只在 `without_tenant` 情境下才是唯一防線，
  而本路徑不在那種情境裡 ⇒ **現有 spec 沒有涵蓋那一層**。註釋已改成精確版本。
  ⇒ **一個沒轉紅的突變不一定是「測試不足」，也可能是「我對機制的理解錯了」。**

- **為什麼欄位不自己算**：`91` 已登記「同一條已發布規則有兩份實作」的事故
  （`ResourcePublication#published?` vs `Product.published_on`）。自己算就是第三份，
  而 `discoverable ⊆ purchasable` 在 model 層是**定理**（由 purchasable 導出），
  繞過 scope 會讓它退化成靠測試盯著。

- **為什麼 `STATUS_DIMENSIONS` 不刪**：它還有兩個伺服器答不了的用途——建立態
  （商品尚不存在）與「使用者剛改了狀態下拉還沒存」（伺服器答的是**已儲存**的狀態，
  此時顯示它會與畫面上的下拉矛盾）。角色由「判準來源」降級為 fallback（判準改由伺服器欄位提供），註釋已改寫。

- 🔴 **被推翻的假設：「request spec 綠就代表租戶取得方式沒問題」**。第一版用
  `Publication.online_store`（靠 `acts_as_tenant` 隱式租戶），request spec 全綠，
  被 `mutation_context_shop_spec` 的守衛擋下——直呼 `ChillloveSchema.execute` 時
  隱式租戶是 nil ⇒ 查不到管道、兩維**靜默回 false**。已改為 `context.fetch(:current_shop)`。

- **M7 是一個「預期內沒轉紅」的突變**：我先在測試註釋自我界定「這格不證明租戶
  取自 context」，M7 果然沒轉紅 ⇒ 證實那句界定準確。**與 M4 相反**——M4 是我宣稱了
  不成立的事，M7 是我先界定清楚再被證實。⚠️ 由此登記既有守衛的射程缺口：
  靜態掃描只抓字面 `Current.shop`，抓不到「靠隱式租戶」的寫法。

## ③ 還有什麼沒解決

- ⚠️ **列表上會是 N+1**：每個欄位一次 `EXISTS`。`ProductsPage` 目前不顯示這兩維，
  故本包不做批次解析；日後列表要用必須另做（一次查出整批可購買集合）。
- ⚠️ **答案是上界**：`Product.purchasable` 只做三層 AND 的**前兩層**，第三層 catalog
  在成員表落地（S10）之前恆真 ⇒ 本欄位在那之前偏寬。
- ⚠️ **`Lookup` 的 `with_tenant` 那一層無 spec**（見 §②）。要覆蓋需要一個在
  `without_tenant` 情境下呼叫本欄位的測試，本包不做。
- 🔴 **S6b／S6c／S6d 仍未做**；S6c 之前要先做 **popover 原語**。

## ④ 下一個人要注意什麼

1. 🔴 **要顯示可購買性一律問伺服器**。前端的 `STATUS_DIMENSIONS` 現在只是 fallback，
   **不得**把它擴充成完整判定——分岔的症狀是「後台說可購買、前台買不到」。
2. 🔴 **突變沒轉紅時，先問「我對機制的理解對嗎」**，不要直接補測試。
   本輪 M4 就是這個形態：測試沒問題，是我的註釋在說一件不成立的事。
3. **列表要用這兩個欄位前先做批次解析**，否則 250 列＝500 次 `EXISTS`。
4. **S10 落地後要回頭複驗**：第三層 catalog 進判準後，本欄位的答案會收窄，
   現有 spec 的期望值可能要跟著改（那不是回歸，是判準變準了）。
