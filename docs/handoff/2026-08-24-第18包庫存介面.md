## ② 為什麼這樣改（含被推翻的假設）

**第八式的 SQL 形狀不是風格問題，是對錯問題。**
`quantityAfterChange`（期後值）＝ledger delta 的 window running sum。
正確形狀是 **CTE 先在整條 ledger 上開 window、外層才套保留期過濾**。
直覺寫法（把 `created_at >= …` 一起寫進 CTE 的 `WHERE`）會讓 window 只看得到窗內的列，
於是期後值變成「窗內累計」而不是真實庫存——窗外 +100、窗內 +5 時，正確 105、錯誤給 5。
🔴 **這個錯誤在測試資料只有一週時完全測不出來**，它要等到保留期邊界被跨過才出現。
所以 spec 裡刻意造了一筆窗外的列。

**被推翻的假設①：「注入後測試還是綠 ⇒ 守衛是空殼」。**
本輪做五個守衛的注入回歸，前兩個注入都拿到綠，我一度要判它們是空殼。
實際是**注入本身壞了**：
- 一個把 `locationId` 用在它的 `const` 宣告之前（TDZ），整個檔案收不到，
  vitest 印的是「no tests」而不是「passed」——我把它讀成綠。
- 一個在 `setPending` 的 updater 裡呼叫 `save()`，而 `save` 閉包住的是**舊的** `pending`
  （空 Map），`if (pending.size === 0) return` 直接返回，等於什麼都沒注入。

⇒ **「注入後綠」有兩種成因：守衛是空殼，或注入沒生效。先驗第二種。**
判別法很便宜：注入後看測試**數量**有沒有變（no tests／少跑）、
以及注入的那條路徑有沒有真的被執行。換成語義正確的注入（M1′／M2′）後兩者都紅。

**被推翻的假設②：「商品頁的庫存調整當然掛頁面 SaveBar」。**
本尊是這樣，我原本也要照抄。寫到一半發現商品頁的 SaveBar 屬於 `productSet` 那棵樹，
把庫存併進去等於**一顆按鈕觸發兩條非原子的 API**——`productSet` 成功、庫存 mutation
失敗（或反過來）時，商家看到的是一個「儲存了」的畫面和一半沒存進去的資料。
⇒ 改成卡內自己的儲存鈕，並把這條當**刻意差異**登記（PR 假設清單第 1 條）。
🔴 這不是「本尊做不到所以我們不做」，是**我們的寫入邊界跟本尊不同**：
本尊的商品頁儲存是單一 mutation，我方是兩棵樹。要跟本尊一致，得先把兩棵樹合成一支
mutation，那是另一輪的事。

**順手修的真 bug 是測試算出來的，不是看出來的。**
商品頁卡的測試斷言「儲存後重讀 ⇒ 查詢共 2 次」，實跑是 3 次。追下去發現 mount 時抓兩次
（`locationId` 從 `""` → 抓 → 設成 L1 → 又抓）。白抓只是浪費，但**第二次回應會蓋掉
使用者在等待期間 stage 的東西**。
⇒ 拆成「選取地點」（`selection`，只在使用者主動改選時有值）與「資料屬於哪個地點」
（`resolvedLocationId`，由回應自己說）兩個 state。
🔴 教訓：**精確的計數斷言會抓到你沒在找的東西**。若當初寫成 `toBeGreaterThan(0)`，
這個 bug 會活到上線。

## ④ 下一個人要注意什麼

1. 🔴 **改 `Inventory::HistoryQuery` 的 SQL 之前先讀第八式那段註釋**。
   看起來可以「順手把日期條件挪進 CTE 少一層」——那就是 bug 本體。有 spec 守著，
   但你要知道它為什麼在那裡，否則會去改測試。
2. 🔴 **做注入回歸驗證時，先確認注入真的生效**。看 vitest 印的是「1 failed」還是
   「no tests」；後者是你的注入讓檔案收不到，不是守衛沒問題。
3. **`app/frontend/admin/lib/inventoryLimits.ts` 是鏡像不是真相**。要加 reason
   得先改 `config/limits.yml` ＋後端 inclusion，前端只是選單。同
   `app/frontend/admin/api/pagination.ts` 的既有形態。
4. **`InventoryAdjustPopover` 是三處共用**（A 塊、B 塊、第 29 包變體子頁）。
   改它的 props 契約要同時看三處；`StagedAdjustment` 的 `compareAgainst` 語義是
   「畫面上當時看到的值」，**不是**「後端最新值」——改這個語義等於拆掉 CAS。
5. **前端不預擋 CAS stale**，也不本地推算寫入後的值。看到 `CHANGE_FROM_QUANTITY_STALE`
   就是 toast ＋ 重讀。想加「先檢查再送」的人請先想清楚那是前端自己跑一次 race。
6. **第 19 包（events/outbox relay）之後才回來做 CSV**（D43 的順序）。
