## ② 為什麼這樣改（含被推翻的假設）

- 🔴 **被推翻的假設：「D53 是使用者裁定，實測與它不同時以裁定為準」**。
  使用者這輪明示「按照 shopify 的處理方式做」⇒ **實測優先於先前的 ours 裁定**。
  處置方式是**原文保留＋日期更正註記**（歷史層不回頭改），不是改寫 D53 本文。

- 🔴 **被推翻的假設：「更正一落地就完事了」**。更正一一落地 `T13` 立刻紅——
  到點清空 `published_at` 後，光改 status 回 ACTIVE **不會**讓商品可購買。
  而**改動前 T13 是綠的**。⇒ **是我的改動破壞了原本正確的端到端結果**，
  補上更正二才算完成。這不是鐵律 20.5 禁止的擴修，是把自己的改動做完。

- **為什麼補發布是安全的**：NULL 列的**唯一**來源是本消費者的到點不合格分支
  ——`Publications::Materialize` 建列時一律帶時間戳。⇒ 針對性補發布，不會誤發。
  （這一條有查證：`app/services/publications/materialize.rb` 的 `published_at: at`。）

- 🔴 **被推翻的假設：「突變綠了就是沒有防線」**。M10 第一版沒轉紅，查下去是
  **突變本身寫壞了**：`republished = 0; ActsAsTenant.without_tenant do …` 只改變數賦值，
  `update_all` 的副作用仍然執行。⇒ **突變要改的是副作用，不是回傳值。**
  重寫成真正移除 `update_all` 後才轉紅（殺 T12／T13）。

- 🔴 **被推翻的假設：「改動前綠、改動後紅 ⇒ 是我造成的」**。全套跑出 5 個失敗、
  乾淨 main 跑出 0 個，我一度據此寫下「已確認是我造成的」。**那是錯的**——
  死鎖是機率事件，n=1 vs n=1 沒有鑑別力。真正解決的是**讀失敗訊息本身**
  （全部是 `ActiveRecord::Deadlocked`，不是斷言失敗）＋**查 `docs/specs/91`**
  （`Shop#enable_launch_locales` 偶發死鎖是第 11 包引入的既有 flake，
  觸發率 12–20%／run，失敗位置隨機落在無關格子——三項特徵逐一吻合）。
  同分支再跑一次即 1265/0。⇒ **看到「改動前綠、改動後紅」時，先讀失敗訊息的類型再談歸因。**

## ④ 下一個人要注意什麼

1. 🔴 **`published_at` 現在是三態語義**：列不存在＝不在通路；`NULL`＝在通路但未發布；
   有值＝已發布或已排程（未來值）。**改任何讀取面之前先確認你處理了 NULL 那一態**
   ——`Product.published_on` 的 `published_at <= :at` 對 NULL 自然為假，目前正確。
2. 🔴 **突變測試要改副作用不要改回傳值**。本輪 M10 的假綠就是這個形態，
   而它看起來完全像「這條防線不存在」。
3. **D53 的閱讀順序**：先看更正註記再看原文——原文的 §3.2「不 UPDATE published_at」
   已被推翻，照原文實作會與本尊不符。
4. **合併部署後重跑線上驗證**，因為語義變了：新增的斷言應含「到點不合格 ⇒ published_at
   變 NULL」與「改回 ACTIVE ⇒ 被補發布」。
