## ② 為什麼這樣改（含被推翻的假設）

- 🔴 **`products.published_at` 就是 A-5 要防的那個扁平模型**。我在 84 號分流時寫的是
  「若把上架做成 `product.published: bool`，之後拆三層是結構改造」——**它已經是了**，
  只是型別是 datetime 不是 boolean。所以這條不是「預防」，是「修正」。
- 🔴 **我把 `published_at` 移除而不是保留成快取**。保留會產生兩個事實來源，
  兩處都能寫，遲早不一致——這正是鐵律 7 存在的理由。排程發布的語義沒有消失，
  它搬到 `resource_publications.published_at` 而且**變成 per channel**（本來就該是）。
- **命名改了**：82 號與原型 DOCS 寫的是 `product_publications`，我改成 `resource_publications`。
  理由：Publishable 由 Product／Collection／ProductVariant **三者**實作，
  叫 `product_*` 會讓後兩者看起來像硬塞進來的。對應本尊的 `ResourcePublication` 型別。
- **第三層我沒做，而且明說了**。88 號標題寫「三層」但實作只有兩層——
  catalog 是**讀取時的過濾條件**，加它不需要改動這兩張表的結構，所以可以安全延到 M5。
  這是分期不是漏做，§6 有寫。
- **A-2 的處理方式值得說**：查下去發現 schema 本來就對（`unsigned` 0 個、CHECK 0 個）。
  可以直接結案，但我多做了一步——**加 CI 規則**。理由：現在對不代表以後對，
  而「為了省空間或防呆而加 unsigned」是很自然的念頭，
  **而且它在只有正常銷售的測試資料上完全測不出來**。

## ④ 下一個人要注意什麼

1. 🔴 **M1 現在可以動工了**，但動工前把 88 §5 的五項排進去——尤其**建店時要建 publication**，
   漏了的話新店的商品無處可發布。
2. **`ResourcePublication#published?` 只是三層的第二層**。model 註釋已寫，但還是要說：
   拿它當「商品是否可購買」會漏掉市場目錄那一層。
3. **建任何「同一件事有兩個地方可以寫」的欄位前，先問值不值得**。這次移除 `published_at`
   的理由就是這個；A-3 那次保留 NULL 不回填也是同一種思路——**寧可少一個來源，
   也不要多一個會漂移的**。
4. **查證發現「本來就對」時，考慮多加一道機制**。A-2 就是例子：現在對不代表以後對，
   而且那個錯誤形態測不出來。
5. **strong_migrations 這次擋了四處**（新表外鍵×2、兩段 execute、remove_column）。
   它擋的都是對的，逐一包 `safety_assured` 時要寫清楚安全理由——
   骨架階段列數小、專案未上線是理由，**上線後同型改造要改走線上 DDL**。
