## ② 為什麼這樣改（含被推翻的假設）

### 「跑完複查」與「複查沒跑」長得一模一樣

第一次跑複查，六個 finder **全部死在 API 529**，workflow 回傳 `{confirmed:[]}`。
這個回傳和「複查跑完、沒找到缺陷」**在字面上無法區分**。若照字面讀，
我會向使用者宣布「對抗式複查全綠」——而實際上一個 agent 都沒跑起來。

⇒ 腳本已改成：死掉的視角回報成 `dead_lenses`，非空即代表覆蓋不完整。
併發從 6 壓到 2，每個 agent 最多重試三次。重跑後 111/113 完成。

🔴 **這個形態值得記住：任何「聚合出空結果」的 harness，都要能分辨「沒有」與「沒跑」。**

### 被推翻的假設：全綠代表守住了

PR #112 加上租戶閘之後，整個測試套件**仍然 457 全綠**。我一度以為閘沒接上。
實際是 `staff_member` factory 早就會建 `UserStoreAssignment`——
**測試資料一直是對的，缺的是 production 資料**（正式站實測 `assignments=0`）。

所以「加了安全閘、測試全綠」在這裡**完全不能證明閘有效**。
把 `can_access_shop?` 改成恆 false，request specs 紅 97/113，才證明它真的在跑。

### 我自己寫出了一組空炮，就在剛抓完別人的空炮之後

PR #112 最初的恢復側測試是「A 店登入 → cookie 帶去 B 店 → 應該被擋」。三條全綠，
**但把那道閘整個拿掉還是全綠**——admin cookie 是 host-only
（`config/initializers/session_store.rb` 刻意不設 `domain:`），
測試客戶端根本不會把 cookie 送過去。那是在測 **cookie scope**，不是測閘。

恢復側的閘真正管得到的是**「session 還活著但指派被撤銷」**。改成測這個，注入才會紅。

🔴 這件事發生在我剛用注入回歸抓完 P18 一堆空炮之後。**方法知道不等於每次都會用**——
所以「每個守衛都要注入驗證」必須是機械紀律，不是想到才做。

### 兩個「源碼看起來完全正常」的坑

1. **`.squish` ＋ SQL 的 `--` 行內註釋**：squish 把換行壓成空白 ⇒
   `--` 之後的 `WHERE`／`ORDER BY`／`LIMIT` 全部變成註釋。
   **查詢照樣「成功」**，只是語義全變（期後值順序反了、保留窗失效）。
2. **`private` 放在 GraphQL field 解析方法之前**：後面的欄位在執行期直接「不存在」。

兩個都是靠 spec 紅了才發現，靠讀源碼發現不了。

### 為什麼租戶閘不改 `can?` 的 owner 短路

兩層是 AND：第一層＝**能不能進來**，第二層＝**進來能做什麼**。
owner 在自己有指派的店裡本來就該無所不能。缺的是第一層就補第一層——
把租戶歸屬塞進第二層會讓兩層語義糊在一起，而且要改的地方會散到每個 policy。

## ③ 還有什麼沒解決

1. **GraphQL 對未認證請求回 200 ＋ top-level `errors`**，鐵律 4 第三層要求非 200。
   既存契約不符，改它要動 API 契約與前端三層錯誤處理。
   相關 spec **刻意只斷言安全性質**，不斷言狀態碼（理由見該檔註釋）。
2. **建店 onboarding 必須同時建 owner 指派**——目前沒有 production 建店路徑，
   做 onboarding 時這是硬前提，漏了就是「建完店的人自己進不去」。
3. **多店環境的 backfill 需人工**（migration 在 `shops > 1` 時一列都不建，刻意 fail-closed）。
4. **完整 RBAC 等 M5**：`roles` 空表、`assignment.role_id` 全 nil，非 owner 等於沒權限。
5. 第 18 包 §5 的「明文不做」12 條仍然成立（CSV／批量編輯器／Move UI／篩選器／行動版⋯）。
6. `Inventory::ItemsQuery` 在 tenant 未設時丟 `NoTenantSet`（與 `resolve_levels` 的處置不一致）。
7. 我在 demo 店建了一個 **「驗收用倉 B」** 地點來驗多地點隔離（`Location/2`，庫存 7 件）。
   要清掉隨時可刪；留著的話多地點功能在 demo 上看得到。

## ④ 下一個人要注意什麼

1. 🔴 **改 `Inventory::HistoryQuery` 的 SQL 前先讀第八式那段註釋**，
   而且**不要在 `.squish` 的 heredoc 裡寫 `--` 註釋**（要註只能 `/* */` 或寫在外面）。
2. 🔴 **每個守衛都要注入回歸驗證**，包括你自己剛寫的那個。
   判別「注入後綠」的兩種成因：守衛是空殼 vs 注入沒生效——先驗第二種
   （看 vitest 印的是「1 failed」還是「no tests」；看 rspec 例數有沒有變）。
3. 🔴 **測試全綠不代表安全控制有效**。安全控制的測試資料往往本來就是「正確」的，
   要靠注入才知道控制在不在。
4. **改登入／session 路徑時記得兩側都有閘**（`SessionsController#create` 與
   `ApplicationController#resume_admin_session`），少一側就有繞法。
