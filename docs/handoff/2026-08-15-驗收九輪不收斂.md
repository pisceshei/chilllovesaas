## ② 為什麼這樣改（含被推翻的假設）

### 🔴 被推翻的假設一：「再修一輪就會過」

我修了五輪，每輪都認真照著意見改。**九輪 15 條 🔴 裡，12 條是文檔敘述類、0 條是代碼缺陷**，
而兩邊的檢查器與回歸測試從第 3 輪起一直是綠的。

決定性的一擊：第 5 輪那條 🔴 是該 PR **第一個 commit** 帶進來的，而第 2／3／4 輪
都聲稱「docs 全讀」卻沒標它。⇒ **缺陷不是被修出來的，是每輪抽樣抽到不同切片。**

配上「累積新增 313 → 1000 行、66% 是 docs、刪除率 6%」——
**未被抽樣過的散文池長得比清掉的還快**。這個閉環在結構上沒有終點。

### 🔴 被推翻的假設二：「更小心一點就不會再犯」

九輪之後我用機械檢查掃同一批（已被人工審過九次的）檔案，30 分鐘內找到 3 條全新的
同型缺陷，**全部出自我自己的修正 commit**——其中一條的 commit message 還寫著
「實跑 `git ls-files` 確認」，而那個「確認」的結果是錯的。

⇒ 這是**紀律型條款的固有失效率**，與 `config/ci.rb` 那條「兩邊要同步」在寫下的隔天
就被違反是同一形態。本倉庫對這種東西的既定處置是**讓機器擋**。

### 為什麼不直接把文檔類降級成 🟡

本倉庫有實例證明文檔錯誤會造成錯誤行為：`config/ci.rb` 一句錯註釋
（把 schema drift 說成在 quality job）會誘導出一個「結構上不可能失敗」的 CI 步驟。
⇒ **換執法者，不是換標準。**

### 為什麼範圍要收這麼窄

初版掃全樹對 `main` 一次噴 552 條、收窄一次後仍 183 條，**幾乎全是誤報**——
`docs/research/**` 大量描述 Shopify 本尊與第三方 gem 的檔案結構，
`docs/design/**` 寫的是還沒做的計畫，而本倉庫慣用編號簡稱（`docs/research/22`）。
**一個噪音比訊號多的檢查器會在一週內被關掉。** 收窄後對 `main` 是 0 條。

## ③ 還有什麼沒解決

1. 🔴 **這是真的鬆綁。** 腳本抓不到的語義錯誤（「假逐字引用」——檔存在、行號對，
   但那句話不在裡面）會降級成 🟡 放行。緩解只有 R5 警告與 Codex 這第二驗收方。
2. ⚠️ **R4 是列舉式 pattern**，只認燒過的五種形態，新形態會漏而症狀是「通過」。
3. ⚠️ **R1／R3 不管 research／design／specs**——要納管得先解決「本尊路徑 vs 我方路徑」。
4. ⚠️ **「同一項目不重提」沒有機制驗證它有沒有被遵守**，是 prompt 指示。
5. 🔴 **本 PR 改了 `claude-review.yml` ⇒ 它自己不會被驗收**（反竄改）。
   四項改動的效果**要等合併後的第一個 PR 才驗得到**。
6. ⚠️ **`review:需人工裁定` label 尚未存在**，靠 `--add-label` 自動建；建不起來時
   留言仍會貼但**閘門不生效**。
7. 🔴 **`#39`／`#40` 的既有 🔴 不會自動消失**——終態層仍需依新規範回寫一次。

## ④ 下一個人要注意什麼

- 🔴 **寫完 worklog／handoff，先跑 `ruby scripts/check-doc-claims.rb`**，
  不要靠重讀一遍。重讀的失效率這個倉庫已經量過了。
- 🔴 **文檔分三層**（`AGENTS.md` §工作記錄與交接文件的寫法）：
  **歷史層敘事不回頭改**（發現錯誤加更正註記）、**終態層每輪必回寫**、
  **契約層跟著代碼同一個 commit 改**。
  ⚠️ 我這五輪之所以越修越糟，正是因為只做「追加」而從不回寫終態層——
  追加得越詳細，摘要與終態的落差越大，而摘要是接手的人唯一會讀的那一段。
- 🔴 **不要在散文裡手寫可由代碼算出的數字**。要寫就附複驗指令或標成快照。
  這一條不是潔癖：2026-08-15 **兩次「修掉過期數字」的修正本身都寫進了新的錯數字**。
- 🔴 **引用別的分支的檔要錨定**（PR 號 ＋ 日期 ＋ 未來式），但**不要為了通過檢查而刪掉
  交叉指引**——交叉指引本身有價值，錯的只是把「另一個分支上有」寫成「現在就有」。
- ⚠️ **驗收再次連續打回時，先問「這一輪的 🔴 是新引入的，還是一直都在？」**
  用 `git log -S '<那句話>' -- <檔>` 三十秒就能判斷。若是後者，
  那是抽樣問題不是品質問題，**再修一輪不會收斂**——去看 `MAX_FIX_ROUNDS` 那道閘門。
