### 🔴 三條最容易做錯的

1. **判準不是 `== ACTIVE`**。`ProductStatus` 自 2025-10 有第四值 `UNLISTED`，官方逐字
   `The product is active but you need a direct link to view it.`
   寫 `!= ACTIVE` 的事故形態：UNLISTED 商品到點時 `Product.purchasable`（含 UNLISTED）**已放行**、
   `published_at` 已是過去 ⇒ **前台實際上已可購買**，但因非 ACTIVE 而未 bump stamp
   ⇒ **前台快取繼續供舊內容、無錯誤、無日誌**。
2. **不合格分支一律 `return`，禁止 `raise`**。`Events::Relay#deliver` 只有兩條出口：
   正常返回 ⇒ delivery done；拋 `StandardError` ⇒ 退避 8 次後 dead。
   用 raise 表達「條件不合」會讓每一筆不合格排程燒掉約 254 秒重試、
   在 `event_outbox.last_error` 留下**假錯誤**、最終進 dead 表被營運當真事故追查。
3. **payload 有兩種形狀**。同一個 topic `product.publication.changed` 上，
   S5 投的是 `{scheduled: true, publication_id: ...}`，
   既有 `Catalog::StatusTransition` 投的是 `{status_transition: {...}, product_id: ...}`
   ——**後者沒有 `publication_id`**。假設一定有這個鍵 ⇒ 每一次商品狀態變更都 KeyError
   ⇒ 燒 8 次重試 ⇒ dead 表每天增長，而測試若只用自捏 fixture 會全綠。

## ⑦ 🔴 這條線上已經踩過的坑（不要再踩一次）

### 方法論

1. **突變測試會抓到真缺陷，不只是驗測試**。S5 靠它抓到
   `ChillloveSchema.resolve_type` 少了 `ProductVariant` 分支 ⇒ 變體成功走完時回傳炸 500。
   缺了兩包沒人發現，因為**只有「真的成功」那一格踩得到**（回 userErrors 的格子全綠）。
2. 🔴 **突變首跑全綠 ≠ 沒有防線**，也可能是**測試拓樸沒涵蓋到防線唯一會被觸發的狀態**。
   S5 首跑四個突變全綠，四個根因都是這個形態（逐條在
   `docs/worklog/2026-08-27-S5發布寫入API.md` 的突變表）。
3. 🔴 **spec 一律用真實生產者產生事件，不得自捏 payload**。
   `Collections::ResyncConsumer` 初版讀錯 payload 鍵 ⇒ 兩鍵皆 nil ⇒ return ⇒
   relay 記 done、事件 published、無錯誤無重試，**整條觸發鏈靜默死掉**；
   而單元測試自捏的 fixture 與真實生產者不符 ⇒ **假綠**。
4. **線上驗證真的會抓到東西**。S1 的 29 格 spec 全綠＋六個突變全紅，正式庫仍印出
   `cleanup: publication_left=0 catalog_left=1`（刪 publication 留下孤兒 catalog）。
   ⇒ 每包合併後照兩步紀律部署 ＋ 用 `rails runner` 在正式庫實跑服務層（自我清理）。

### 併發與機制

5. 🔴 **併發 spec 的 gate 不能下在取鎖之後**。S5 第一版下在 `SELECT ... FOR UPDATE` 回傳之後，
   對手 INSERT 卡 50 秒 `LockWaitTimeout`——InnoDB 在 REPEATABLE READ 下對**不存在的列**
   取**間隙鎖**。gate 要下在取鎖**之前**。
6. **MRI 的 GIL 下單純開兩個執行緒會自然序列化**，競態窗必須人工撐開，
   否則把守衛全刪掉仍然全綠（`spec/services/catalog/handle_change_concurrency_spec.rb` 檔頭有逐字警告）。
7. 🔴 **新增租戶表 ⇒ 六份併發 spec 的 `purge!` 都要補**（FK 順序）。S0 同一天中了兩次。
8. 🔴 **新增平台字典表 ⇒ 補 `spec/support/<表名>_seed.rb`**：`db:schema:load` 不跑 migration 的種子段，
   漏掉會讓一堆**無關的** spec 一起紅（症狀完全指不出根因）。規則已寫進鐵律 2。

### 工具鏈

9. **`config/recurring.yml` 只有 `production:`** ⇒ dev／test 沒有 `events_relay` 排程，
   那裡的「到點」永遠不會自己發生。🔴 但**不得**因此把讀取面到點語義
   （`published_at <= :at`）的 dev／test 觀察一併排除——那是合法證據且已有測試矩陣。
10. **`every 5 seconds` 解析成 `*/5 * * * * *`**（牆鐘 0,5,10…秒對齊），不是「上次跑完後 5 秒」。
    正式庫實測（2026-08-27）確認 `events_relay` 執行時點落在 `:35 :40 :45 :50 :55`。
11. **`RBENV_ROOT` 是 `/opt/rbenv`**。寫成 `/usr/local/rbenv` 會撿到系統 ruby 3.3
    然後 `Bundler::GemNotFound`。
12. **CI 的 `startup_failure` 不能用 `gh run rerun`**（回 403）且不產生任何 check-run
    ⇒ `gh pr checks` 回空集合，看起來像「還沒開始」。正確做法＝`gh pr close` 再 `gh pr reopen`
    （不動 tree、head SHA 不變）。🔴 **空的 checks 集合不是全綠**（鐵律 15.2）。
    CI 卡住先查 GitHub 是不是在事故中，不要先懷疑自己的 PR。
13. **doc-claims 的 R1 會掃反引號內的路徑，連 HTML 註釋裡的也掃**。
    寫「原本引用的那個檔名不存在」這種更正註時，**不要給那個檔名加反引號**
    ——否則更正註自己會被判違規（S5 踩過一次）。

### 文檔紀律

14. 🔴 **全稱句要嘛列舉、要嘛附複驗指令**。「某某是唯一實作處」「N 條全收」這類句子
    在 doc-claims 會被標 🟡，而且它們常常**被寫下它的那一句話自己推翻**。
15. **易腐數字必附複驗指令**，連解釋括號裡也不例外。
16. 🔴 **引用不在本分支樹上的檔案要錨定**（`（PR #NN，尚未進 main）`），否則 doc-claims 直接紅。
