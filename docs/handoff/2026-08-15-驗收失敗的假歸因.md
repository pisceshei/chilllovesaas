# 2026-08-15 交接 — 假診斷比沒有診斷更貴

**本輪產生的 worklog**：
- `docs/worklog/2026-08-15-驗收失敗的假歸因.md`

---

## ① 我改了什麼

`.github/workflows/claude-review.yml` 的 `REVIEW_OUTCOME != success` 分支：

- 原本貼**寫死的猜測**（「最常見原因＝`--max-turns` 用盡」＋「annotation 會直接寫
  `Reached maximum number of turns`」）。
- 改成從 `execution_file` 撈 result payload（`is_error` / `num_turns` /
  `total_cost_usd` / `duration_ms`）貼上，並附兩條讓人自行對號入座的判準。
- 刪掉那句已被證偽的 annotation 斷言；`gh run view` 帶上真實 run id。

---

## ② 為什麼這樣改（含被推翻的假設）

**被推翻的假設：「寫死最常見原因，比只說『去看 log』有幫助」。**

那個假設是上一輪（2026-08-14，PR #26 事故）得出的，當時的判斷完全合理——
原本兩種失敗都印同一句「可能失敗或逾時」，把人指去看 log 卻沒說看哪一行。
但修正**矯枉過正**：從「不夠具體」跳到「替讀的人決定答案」。

PR #33 實測打臉（連續兩次 attempt 完全相同）：

```json
{ "is_error": true, "num_turns": 1, "total_cost_usd": 0, "duration_ms": 654 }
```

一個回合都沒燒、零花費、654 毫秒——**與 max-turns 用盡在數據上完全相反**，
而 annotation 裡根本沒有它叫人去找的那句話。

🔴 **假診斷比沒有診斷更貴**：沒有診斷時人會去查；有假診斷時人會先花時間**否證一個錯的方向**，
而且因為訊息講得很肯定，通常會先懷疑是自己看錯。

**這一輪特別要記的**：我在寫這個修正時，**差一點製造出同型的新假診斷**。
jq 濾鏡若不加 `select(. != null)`，在「撈不到 result」時會印出一整行
`is_error=null num_turns=null…`——**看起來像有診斷，實際上什麼都沒撈到**，
而它會取代 fallback 訊息。三種輸入的渲染結果都跑過才發現這件事。
⇒ **診斷機制自己也要有「撈不到就要說撈不到」的分支**，不能讓空值長得像資料。

**為什麼不順手讓 job 真的 fail**：驗收步驟失敗時 job 層 conclusion 仍是 `success`
（被下游 `exit 0` 吞掉），副作用是 `rerun-failed-jobs` API 回 403、只能整個 workflow rerun。
但改它會牽動 AUTO_MERGE 與留言水位邏輯的其他分支，風險大於收益 ⇒ 只在註釋登記。

**為什麼與引用保真／執行位元那組分成兩個 PR**：
動 `claude-review.yml` 的 PR **自己不會被驗收**（反竄改機制，該檔 31–40 行有實測記錄）。
綁在一起會讓那組本來可以正常受檢的修正**也**逃過驗收。

## ③ 還有什麼沒解決

1. 🔴 **本 PR 自己不會被驗收**，修正**只有合併進 main 之後才生效**。
2. **job 沒有真的 fail**（見上），`rerun-failed-jobs` 仍會 403。
3. **判準表本身也是斷言**——`num_turns`／`total_cost_usd` 的語義若被 action 改掉就要重驗。
   它比上一版好在：留言裡數據與判準並陳，讀的人能當場發現兩者對不上。
4. **「第一個 API 請求就失敗」的更細根因沒查出來**（配額／額度／認證／模型可用性）。
   annotation 與 execution log 都只給到 `is_error: true`，沒有錯誤字串
   ⇒ 判準只寫到「帳號側」，**刻意不再往下猜**（再猜就是重蹈本輪修的那個錯）。

## ④ 下一個人要注意什麼

- 🔴 **真正的驗證機會是「本 PR 合併後開的第一個 PR」**。在那之前，
  本檔的任何修改都無法在它自己的 PR 上驗證——run 只跑十幾秒且 job 顯示 success，
  **非常容易誤判成「Claude 逾時」**。判別方法：run 時長（正常驗收 3–4 分鐘）。
- 🔴 **改本檔時，`YAML.load_file` ＋ 抽出 `run` 腳本跑 `bash -n` 兩步都要做。**
  這支 244 行的閉環腳本歷史上被 YAML block scalar 與 heredoc 各咬過一次，
  兩次都是「YAML 仍能解析、但 shell 語法壞掉」或反之。本輪的做法寫在 worklog。
- 🔴 **要在留言裡寫「原因是⋯⋯」之前，先確認那句話能從當次資料推出來。**
  可以貼數據、可以列判準，但不要替讀的人決定答案——這正是本輪修掉的東西。
- **驗收步驟失敗時的實用起手式**：`gh run view <run-id> --log`
  撈出 `"type": "result"` 那個 JSON。瀏覽器的 log 檢視器是虛擬捲動＋gzip，拿不到。
