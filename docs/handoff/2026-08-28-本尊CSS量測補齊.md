## ② 為什麼這樣改

**為什麼要排查而不是直接量**：排查結果顯示既有量測**不是沒做**，而是做了之後
在 `47` §6／§H2-1／§8-89 與 `80` §5 明文裁定「色值改用自有調色／不得取用本尊色值」。
不先找出這四處，量再多也會被同一條裁定擋在門外。

**被推翻的假設（我自己的）**：

1. 我原以為「只有 2/11 個 teardown 有量測」。**錯**——`80`／`81`／`82` 也有，
   只是各只有 7–8 列且完全沒有狀態樣式。
2. 我原以為 `tokens.css` 有 131 個 token，據此算出「31 個映射 token 不存在」。
   **三個數字全錯**（實際 223／46／27）——根因是 grep 用行首錨，而該檔大量把多個 token
   寫在同一行以 `;` 分隔。已在 `110` §3 記錄更正並改用可重跑的 python 命令。
3. 我原以為 doc-claims 會守著新增的量測文件。**錯**——突變測試（注入不存在的路徑）
   **沒有轉紅**；腳本檔頭自陳「research／design／specs 的路徑錯誤本檢查普遍不管」。
   改用手動腳本核 94 個路徑宣稱。

**被推翻的假設（既有文件的）**：

4. `47` §A 記「`s-internal-*` 的 shadowRoot 是 closed、無法由 JS 讀取」——**實測是 open**。
   §D 整節因此是在錯誤前提下**目視判讀**出來的，其「次級按鈕＝白底＋兩層陰影」已證實有誤
   （直接量測是 `#e3e3e3`、無陰影），且錯誤來源可定位到「讀到 `--p-shadow-button` 這個
   token 的值，但該 token 並未套用在該繪製盒上」。
5. `47` 與 `64` 對按鈕排版**本來就互相矛盾**（12/16/550 vs 13/20/500）。
   原因不是誰量錯，而是**本尊有兩套設計系統世代並存**，同名元件在兩層值不同。
   兩邊都對；我方只取新層（`s-*`）。

**為什麼不執行換值**：`112` 只到計畫。原因——①語義色有三族的**配色模型**與我方不同
（本尊 `warning`／`caution`／`info` 的 fill 是淺色配深字，我方一律深色配白字），
不是換色值就能對；②字重 500 的來源規則未查明；③`--col-main/aside` 固定欄寬 vs 本尊
內容區 `max-width: none`，改動會牽動全站佈局。三項都需要先取證或裁定。
