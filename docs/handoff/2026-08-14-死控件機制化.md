# 交接：死控件機制化 —— **規則抓到的比人工稽核多**（2026-08-14 第二十四場）

> 本輪 worklog（3 份）：`2026-08-14-死控件lint規則.md`（規則本體）、
> `2026-08-14-死控件lint-review二輪.md`（第二輪四條）、
> `2026-08-14-死控件lint-review三輪.md`（第三輪兩條）｜規格：`docs/specs/89` §7

## ① 我改了什麼

把 89 §2 那 25 條「控件畫出來卻沒接行為」從紀律變成機制：新增 `r_dead_control` lint 規則，
用那 25 條當測試案例（正面不得誤報、負面必須抓到），並加**存量基準線**讓它擋得住新增。

## ② 為什麼這樣改（含被推翻的假設）

- 🔴 **判準不是「必須有 onclick」**。89 §2 修好的控件多數沒有 inline handler
  （`querySelectorAll('.mkt-country')`／`getElementById('rfOverOK')`／
  `input[name="expfmt"]:checked`／`data-set` 事件委派）。
  天真規則會把**本輪剛修好的東西全部誤報**，然後被人關掉——**比沒有規則更糟**。
- 🔴 **被推翻的假設：「token 有出現在 script 就算有人讀得到」**。
  本原型的 markup **寫在 `<script>` 的模板字面量裡**，所以任何屬性值本來就在 script 字串中——
  這個判斷是**自我滿足**的，永遠成立。負面測試直接打臉：把 Cookie 橫幅 radio 退回舊寫法，
  寬鬆版規則抓不到。改成只認 `getElementById`／`querySelector`／`dataset.X` 等**真正的 DOM API 上下文**。
- 🔴 **被推翻的假設之二：「token 對得上就算命中」**。
  `querySelectorAll('.tgl[role="switch"]')` 用到 `tgl`，但一個只有 `class="tgl"`、
  沒有 `role` 的開關**不會被它選中**。加了「選擇器的 `[attr]` 條件控件也要有」才抓得到。
- **逃生口刻意設計成會自我說明**：`data-read="<函式名>"` 要寫出**誰**讀這個控件，
  而且那個函式必須存在（實測：亂寫函式名照樣報）。純靜音的逃生口會被拿來搪塞。
- 🔴 **基準線不是妥協，是讓規則活下去的條件**。規則一上線抓到 73 條存量，
  全報 WARN 的話 lint 會從 13 個警告變成 86 個——**沒有人會讀 86 個警告**，
  規則就等於白做。存量報 WARN、超過基準線報 ERROR，
  機制要咬得住的是「不要再長出新的」，不是「一次還清歷史債」。

- 🔴 **兩輪 review 之後補上的第三個假設推翻：「少報才是這條規則的風險」**。
  前六種漏看全是少報，於是我把注意力全放在「會不會看不到壞東西」。
  Claude 第二輪指出第七種形態是**誤報**——`_attr_ok` 掃整串選擇器，
  `querySelectorAll('.mkt-country, .tgl[role="switch"]')` 會要求靠 `.mkt-country`
  當把手的控件也得有 `role="switch"`。
  **誤報比少報危險**：少報只是規則沒發揮價值，誤報會讓人把規則關掉——
  這正是 §7.1 一開始避開「必須有 onclick」的同一個理由，我卻在自己的修正裡重蹈一次。
  🔴 **而且修一次不夠**：第二輪修掉「跨逗號」，第三輪 Claude 又指出它還會**跨後代組合子**
  （`'[data-form="prod"] .cb'` 把祖先的條件加到把手頭上，這種寫法原型裡真的有）。
  **同一個根因（`_attr_ok` 的作用範圍抓太大）有兩種形態，我只修了先被指出的那一種。**
  教訓：修一個範圍性 bug 時要問「這個範圍還會在哪裡越界」，不是只堵住舉例的那個。
- 🔴 **本 PR 自己示範了「紀律寫在註釋裡等於沒寫」**。`DEAD_CONTROL_BASELINE` 的註釋
  要求「調高必須同時有量表修正」，但那條規則自己只靠 review 肉眼看 diff 方向——
  而這一節的標題就叫「把死控件從紀律變成機制」。Claude 第二輪點名後才補上
  `scripts/check-baseline-raise.py`。**寫規則的人最容易對自己的規則豁免。**

## ③ 還有什麼沒解決

- 🔴 **123 條存量未修**（admin 43／platform-admin 25／storefront 55；
  首版報 73 是量表有 bug，修正後同一份原型量出 124，再修一輪成 123）。
  其中 **storefront 那 55 條所在的檔案從未被稽核過**。
  **本輪最大的發現是這個**：規則抓到的比人工稽核多，而且多在沒人看過的檔案裡。
  歸屬：storefront 屬 M2、platform-admin 屬 M8，本輪刻意不動。
- 🔴 **`check-baseline-raise.py` 只擋得住「只改數字」**，擋不住
  「改了掃描邏輯又順手多調幾個」——後者仍需 review。
  它的 `SCANNER_FNS` 是**硬編的函式名清單**，往後把掃描邏輯搬到新函式而忘了同步，
  機制會**靜默失效**（方向是少擋，所以不會有人發現）。
- **class 把手仍是啟發式**，無法真的做 CSS selector matching。
- **`data-read` 只驗函式存在**，不驗它真的讀了那個控件（同 `r_dangling_onclick` 的限度）。
- **admin 以外兩個原型檔的 80 條沒有人工複核過。**

## ④ 下一個人要注意什麼

1. 🔴 **看到 `DEAD_CONTROL_BASELINE` 的數字被調高，要當成紅旗**。
   調降＝清了存量（好）；調高＝把新增的死控件就地合法（壞）。
   最容易發生的形態（只改數字、掃描邏輯不動）**已由
   `scripts/check-baseline-raise.py` 在 CI 硬擋**；
   「改了掃描邏輯又順手多調幾個」機制分不出來，**那一半仍要你看 diff 方向**。
2. 🔴 **加 lint 規則前先想「它會不會把現有的正確寫法誤報」**。本輪如果沒有先做
   25 條的正面測試，規則會在上線第一天就噴掉自己剛修好的東西。
   **規則的第一個測試案例應該是「已知正確的程式碼」，不是「已知錯誤的程式碼」。**
3. **改 lint 規則要用檔案寫 patch，不要用 heredoc**——本輪因為 heredoc 吃掉 `\b`／`\$`
   踩了三次，每次都要重來。（環境事實：這台機器的 Bash heredoc 會處理反斜線跳脫。）
4. **lint 掃三個原型檔**，不是只有 admin。看 lint 輸出時先確認是哪一個檔案的行號——
   本輪我兩次把別檔的行號套到 admin 上，得出「規則在亂報」的錯誤結論。
