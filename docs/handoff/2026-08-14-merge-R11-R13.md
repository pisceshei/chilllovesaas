## ① 我改了什麼

依 R13 handoff 裡自己給的建議順序，把三個 parity 分支依序併進 main 並推送：
**R11 → R12 → R13**，每一次合完都跑 lint ＋ 原型煙霧才提交。
main 現在含三輪的全部產出（研究檔 80/81/82、71 §F 55 條、limits 十一節、原型三個新頁與 27 條 DOCS）。

## ② 為什麼這樣改（含被推翻的假設）

- 🔴 **「三個衝突都是檔尾追加」這個假設在最後一次被推翻**。前兩次確實是純追加（保留雙方就對），
  但 R13 那次有一處是**真正的語義衝突**：**R11 刪掉了 `reportQL()`**（R11-BUG1 的修正——
  本尊沒有「ShopifyQL 進階模式」這個模式），而 **R13 是從舊 main 開的分支、還帶著這個函式**。
  如果照前兩次的做法「保留雙方」，**會把 R11 才剛修掉的 bug 原封不動帶回來**，
  而且 lint 與大部分煙霧都不會報錯（函式存在但沒人呼叫，只是死碼）。
  ⇒ **教訓：merge 衝突的處理方式不能從前幾次外推**。「一邊刪除、一邊保留」在 diff 上長得
  和「兩邊各自新增」很像，但語義相反。
- 因此我給衝突腳本加了**安全閥**：偵測到兩側有同一鍵時不自動合併（改逐列取非佔位版並列印重疊），
  真語義衝突一律人工處理。§E 表格那三列正是靠這個閥抓出來的（三邊都寫過同一列）。
- **合併驗證抓到一個殘留**：`DOCS['set-perm-cats']` 還寫「13 類顆粒權限」，
  但 R12 已經把 `permCats` 換成實測 17 群組／115 權限。這種數字不一致 lint 抓不到、
  煙霧也抓不到（因為兩邊都在、只是說法不同）——**只有讀過內容的人會發現**。已修。

## ④ 下一個人要注意什麼

1. 🔴 **R14 直接從最新 main 開分支**（已含三輪）。若又從舊 main 開、又動 §E／§F／limits／原型這四個檔，
   會再撞一次同樣的檔尾衝突。
2. **合併衝突不要外推前一次的做法**：先判斷是「兩邊各自新增」還是「一邊刪除一邊保留」。
   後者在 diff 上看起來一樣，但保留雙方＝把已修的 bug 帶回來。
3. **合併後要做的不只是 lint**：lint 只驗結構（DOCS 對應、token、斷點），
   數字與語義的一致性（例如 DOCS 寫 13 類但資料是 17 群）要靠讀。本輪就抓到一個。
4. **煙霧測試要涵蓋所有被合併的輪次**，不能只測最後一輪——本輪 15 項是 R11 五＋R12 四＋R13 四＋跨輪二。
