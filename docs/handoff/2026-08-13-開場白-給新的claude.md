## 第二步：把 GitHub 補上（🔴 最優先，做完才動別的）

remote 已經設好是 `https://github.com/pisceshei/chilllovesaas.git`，但**一次都沒推過**。在推上去之前，那個 bundle 檔是唯一的備份——這是目前最大的單點風險。

```
git remote set-url origin https://github.com/pisceshei/chilllovesaas.git
git push -u origin main
```

**認證這一步要我本人做**（你不能代我輸入 GitHub 帳密或 token，這是硬限制，不要嘗試繞過）。所以：

1. 你先把上面的指令準備好，**跟我說要我做什麼**（例如要我先在本機跑一次 `git push` 完成認證、或要我建 PAT）。
2. 我完成認證後跟你說一聲。
3. 之後的每一次 push 由你負責，**不要累積**——每完成一個部分就 commit + push，不要再出現「69 個 commit 躺在本機」這種事。

推成功之後，跑 `git ls-remote origin` 確認 remote 真的有 `refs/heads/main`，**不要只看 push 沒報錯就當作成功**。

## 工作規則（硬性，不是選配）

### 1. 每完成一個部分就寫工作記錄

`docs/worklog/YYYY-MM-DD-<功能>.md`，**三段固定**，與該部分的改動一起 commit：

```markdown
## 已完成的工作 (Done)
- [條列這次實作了哪些功能、修復了什麼 bug]

## 修改的檔案與核心邏輯 (Changes)
- [列出異動的檔案路徑，並簡述關鍵函式或架構變動]

## 尚未完成或需注意的風險 (Pending / TODO)
- [列出還沒寫的邊際條件、潛在 bug 或待補的單元測試]
```

- **「一個部分」＝一個可獨立驗收的單位**（一個 spec 章節／一個畫面／一支 API／一次修復），**不是一整輪工作**。做完就寫，不要累積到最後補。
- 🔴 **Pending 段不得留空。** 真的沒有待辦就寫「無，理由是⋯⋯」。空白讀起來像「沒檢查」，不是「檢查過沒有」。
- 🔴 **Changes 段要寫「為什麼」**，不只是 `git diff` 的白話版。檔案路徑 git 自己有，worklog 的價值在於記下當時的判斷。

### 2. 每輪工作結束前寫交接文件

`docs/handoff/YYYY-MM-DD-<主題>.md`，四段固定：①我改了什麼 ②為什麼這樣改（**含被推翻的假設**）③還有什麼沒解決 ④下一個人要注意什麼。要列出本輪產生的所有 worklog 檔名。
**這和 worklog 並存，不互相取代**：worklog 是「這個部分做了什麼」，handoff 是「這一輪的判斷與教訓」。

### 3. 其他

- **改過原型就跑 `python3 scripts/lint-prototype.py`**，ERROR 必須為 0。
- **不要用「應該可以」交差。** 要嘛實際跑起來給我看證據，要嘛老實說「這個環境做不到」。前一輪有好幾條結論是被實測推翻的，我要的是這種誠實。
- **來源分級**：`src`（原始碼）>`std`/`google`（標準）>`help`/`dev`（Shopify 官方文檔）>`alt`（競品官方）>`press`（第三方）>`blog`。🔴 **`press` 級只能「登記為未知」，不足以翻面一條已生效的預設**——前一輪違反這條，同一條規格一天內改了兩次。
- 規格沒寫到的才問我；寫到的自己去讀。

## 環境注意事項

- 前一輪容器出站被 proxy 以 403 CONNECT 擋掉大部分主機，`gem install` 與 `gh` 不可用。**要做任何抓網頁／裝套件的事，先確認出站權限再排計畫**，不要做到一半才發現不通。
- `Shopify/liquid` gem **沒有 `handleize`**，「讀官方原始碼推 handle 演算法」這條路永久不通，已掛帳。
