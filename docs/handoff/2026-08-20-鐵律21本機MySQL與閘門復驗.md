# Handoff — 2026-08-20：鐵律 21 本機 MySQL 與閘門復驗

## ① 我改了什麼

本步驟處理的問題是 Rails specs 因本機 `127.0.0.1:3306` 沒有服務而無法執行。依使用者提示與
既有 worklog 找到 `C:\Users\pisce\chilllove-mysql\start-mysql.cmd`，以隱藏背景程序喚起既有
MySQL 8.4；`mysqladmin ping` 回 `mysqld is alive`，TCP 查詢顯示監聽
`127.0.0.1:3306`。修正一次 PowerShell runner 假綠後，以實際 `bundle.bat` fail-closed 重跑，
Rails 輸出為 `284 examples, 0 failures`，其餘 production 命令與 scripts 閘門各自退出 0。

配對 worklog：`docs/worklog/2026-08-20-鐵律21本機MySQL與閘門復驗.md`。

## ② 為什麼這樣改（含被推翻的假設）

- **被推翻：本機沒有 MySQL 環境。** 既有 worklog 與 launcher 證明環境已部署，只是程序沒有
  啟動；喚起後 ping、監聽埠與 Rails migration／specs 都取得實跑證據。
- **被推翻：runner 印出 `EXIT=0` 就代表命令真的跑過。** 不存在的 `bundle.cmd` 觸發的是
  PowerShell 非終止錯誤，`$LASTEXITCODE` 沿用舊值；必須先解析真實命令並讓啟動失敗立即中止。
- **被推翻：Windows 可直接以 `bin/setup` 複製 Unix 執行路徑。** 原生 Ruby 的
  `Kernel#system` 無法執行 extensionless `bin/rails`；本輪依 `bin/setup` 原始內容逐項執行等價
  命令，沒有改 script 來掩蓋環境差異。

## ③ 還有什麼沒解決

- Windows 的 `bin/setup` wrapper 仍是已登記缺口；未修改 `bin/`，也沒有把等價步驟宣稱為
  wrapper 本身通過。
- MySQL 背景程序的存活只在本步時間點有 ping 與 TCP 證據；後續測試前需要重新查活。
- 新鐵律本文尚未落地；完成規則修改後仍要重跑閘門並取得新 head 的 GitHub 驗收。

## ④ 下一個人要注意什麼

1. 手動啟動入口是 `C:\Users\pisce\chilllove-mysql\start-mysql.cmd`；先跑 `mysqladmin ping`，
   不要看到既有 datadir 就假設服務正在運行。
2. Windows 請用 `bundle.bat exec rspec` 與 `ruby bin/rails ...`；不存在的命令必須使 runner
   立即失敗，不能只讀殘留的 `$LASTEXITCODE`。
3. `bin/setup` 的缺口只登記在 `91` §3.5；若要修，會修改 `bin/` 的開發入口，必須另定射程、
   補 Windows／Unix 兩側承重測試並依適用規則驗收。
4. 這份 handoff 是環境復驗步驟，不取代後續鐵律 21 落地步驟自己的 worklog／handoff。
