## §5 工程陷阱彙編（源碼看起來全對、行為錯）

1. 🔴 `.squish` 的 SQL 禁用 `--` 行內註釋——squish 壓成一行後 `--` 吃掉後面整條
   （WHERE／ORDER BY／LIMIT 全失效，查詢照樣「成功」）。要註只能 `/* */` 或寫在 heredoc 外。
2. 🔴 GraphQL type 裡 `private` 必須在**所有 field 解析方法之後**——插中間，
   後面的欄位執行期「不存在」。
3. 🔴 第八式：running sum 的 window 必須開在**日期過濾之前**（CTE 全量開窗、外層裁窗）。
   反過來寫，期後值變「窗內累計」，測試資料不跨保留期就全綠。
4. 🔴 SQL 取現在時間一律 `UTC_TIMESTAMP(6)` 不用 `NOW()`（created_at 是 UTC 寫入、
   NOW 跟 session tz 走；bt3 現在是 UTC 純屬環境巧合）。**寫入端 migration 還有未修落點**：
   `grep -rln "NOW(6)" db/migrate/`——改它們要另寫 migration 修既有列，屬需裁定射程，別順手做。
5. Zeitwerk 一檔一類：同檔第二個類在求值時不存在；`config.autoload_lib(ignore:)`
   要含非 app 執行期的 lib（rubocop cop 曾因此在 CI 炸）。
6. Limits.enum 回大寫；API 識別字要 `.downcase`。
7. 前端 EmptyState 的 action 是必填 prop；IndexTable 表頭首格是空的選取欄
   （斷言表頭時 `.filter(Boolean)`）。
8. workflow YAML 的 prompt 內寫 `${{ }}` 會讓**整份 workflow 無法解析**，
   且只有 GitHub 判得出來（本地檢查全綠）。
9. en.yml 有過重複鍵（兩個 handle_taken）——regex 定位 locale 鍵必須驗唯一性。
10. migration 的資料狀態分支 CI 驗不到（CI 庫是空的）——`if <資料狀態>` 的每個分支
    都要在該狀態下實跑（#113 的教訓）。

## §6 驗證紀律（本專案用血換來的，全部強制）

- **守衛要紅了才算守衛**：每個新守衛（測試、cop、checker）做注入回歸——
  注入缺陷 → 紅 → 還原 → 綠，記進 worklog。空集斷言測不到缺席。
- **「注入後綠」有兩種成因**：守衛是空殼，或**注入沒生效**。先驗第二種
  （看 vitest 印「no tests」還是「1 failed」、rspec 例數有沒有變）。
- **測試全綠不能證明安全控制有效**：控制的測試資料往往天生「正確」（factory 會建指派）。
  租戶閘上線時全套綠、閘改恆 false 才紅 97 條 request specs。
- **「聚合出空結果」的 harness 要能分辨「沒有」與「沒跑」**：對抗式複查曾六個 finder
  全死於 API 529 而回 confirmed=[]——與「沒缺陷」字面全同。
- 線上驗收照 SPA 真正送出的 document 跑，並帶**反向案例**（驗閘會拒絕，不只驗放行）。
