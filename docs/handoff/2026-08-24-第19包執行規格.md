## ② 為什麼這樣改（含被推翻的假設）

- **dedupe_key 的形狀**：最初傾向「豁免筆用 event_id 當 key」，推翻——那會讓唯一索引
  同時承擔兩種語義。改用 NULL（MySQL 官方逐字 "This constraint does not apply to NULL values"，出處見同 PR worklog Done 段），豁免判準與索引語義
  解耦，且「published 清 key」的 release-on-terminal 讓「窗只在 pending 內」由 schema
  保證而不是靠查詢條件。代價＝依賴 MySQL 特性，規格要求 spec 釘住（§6-2、§8-7）。
- **租戶 A 案而非 B 案**：B 案（逐店 enqueue）仍需先全表掃出有 pending 的店，
  等於 A 案之上再疊一層佇列——複雜度沒有換到隔離收益。
- **歷史 pending 三選一收斂成一**：因為本包消費者路由表＝空，「照常 drain」與
  「標 published 不投遞」是同一件事——不需要裁定第三案。
- **lock timeout 不定案**：總交接明文「規格沒給值，要裁定、不得靜默發明」——
  給了提案值 300s＋理由，走假設清單讓使用者裁，不寫死成事實。
