## ② 為什麼這樣改

**證據鏈**：每一條設計決策都能追到 `82` §8 的某一小節或某一句官方原文。三條最關鍵的：

- **兩個 EXISTS（商品層 ∧ 至少一個變體層）** ← 本尊官方可見性真值表逐字
  （Published/Published=Yes，其餘三格皆 No）＋ help 的「全部變體下架 ⇒ 父商品整個隱藏」。
- **層與層不連動、可見性在讀取時算 AND** ← 實測：商品層取消發布 POS 後，變體層的列原封不動。
  這一條決定了不變量**不能**靠寫入時串聯維持。
- **生產者掛 model callback 而非 service** ← 與 `Shop#after_create :create_default_publication`
  同一條理由（涵蓋每一條建立路徑），該處註釋已寫明。

**被推翻的假設（兩個，都值得下一個人知道）**：

1. 🔴 **「本尊的變體發布不跟父商品，實測為證」——我第一版這樣寫，是過度解讀。**
   官方文檔明文說跟父商品；我的實驗分辨不了「不跟父商品」與「新變體繼承自前身
   `Default Title` 變體」這兩個假說。補做 UI 觀察後才看清：變體在父商品未發布的管道上
   **確實有列**（toggle 開），只是被灰掉並附提示「Product must be published to the channel
   before variants can appear」⇒ **官方講的是生效狀態、我量的是儲存狀態**，不衝突。
   最終採「全部 auto_publish 管道」但四處標明是 **ours**。全文＝`m2-publication-model.md` §4。
2. 🔴 **「拿掉 `without_tenant` ⇒ 正式環境會 `NoTenantSet`」——我在 migration 與 spec
   都這樣寫，審查員實測證偽了。** 初版讀取全走 `.unscoped`（連 default scope 的 raise
   一起拿掉）、寫入全走 `insert_all`（不經 model）⇒ 拿掉照樣跑完。那句是從第 11 包
   `20260826058000` **誤植**的：該包走 `find_or_create_by!`（model 寫入）所以成立，本支不成立。
   ⇒ 現行版**刻意移除 `.unscoped`** 讓那個守衛真正承重，並由行為測試守住。
   教訓：**把別的包的因果搬過來時，要先確認機制相同**。
3. 🔴 **「Collection 也該自動發布」原本沒有證據。** 官方 `Publishable` 頁逐字說
   "Collections are unpublished by default"，而 `autoPublish` 的語義只講 **products**。
   我因此一度打算移除 Collection 的 callback；實測本尊的「Add collection」表單**在存檔前就顯示
   「3 channels」**（admin 會預發布到全部管道）⇒ 保留 callback，對齊的是 admin 行為。
   API 層預設 unpublished 是另一回事，兩者並存。

**未採方向**：
- 不加 advisory lock／世代標記／拓樸序。這裡沒有跨實體的順序依賴，一個既有的唯一索引就夠。
  （第 11 包的教訓：修法需要新機制時，先問這個功能 v1 有人用得到嗎。）
- 不做 publish／unpublish mutation——超出權威計畫表第 12 列，且無 v1 消費者。

## ③ 還有什麼沒解決

1. 🔴 **`insert_all`／`upsert_all` 繞過 callback**。匯入器（第 20+ 包）若走批量寫入，
   匯進來的商品**全部沒有發布列 ⇒ 前台全部看不到，且不拋任何錯**。
   本包做不到（匯入器不存在），已寫進 `m2-publication-model.md` §6 當作該包的前置條件。
2. **`Collections::RuleCompiler` 仍用 `p.status <> 'archived'`**，未改用 `purchasable`。
   刻意不改（語義變更需裁定），已登記 `91` §3。
3. **第三層 catalog 完全沒做**（88 §3.2 延後到 M5）。本包的三層 AND 只有兩層。
4. **未取得四項**：新增 publication 是否回填既有商品／`auto_publish` 的 admin UI 入口／
   ARCHIVED 商品的發布列是否仍存在／變體生產者的替代假說。逐條在 `m2-publication-model.md` §8。
5. **未取得一項新發現**：系列建立頁的 Collection items 篩選出現 **Suspended** 這個狀態值，
   不在 `ProductStatus` 值域內，不知道它是什麼。已登記 `91` §3。
6. **測試店被刻意留在兩個非預設狀態**（鐵律 12.2 全權授權，但下一個人要知道）：
   - `Product/9907126370539`（實測用 T恤）的變體 **S** 被關掉 Point of Sale；
   - `Product/9911273160939`（P12 發布模型實測用商品）是 **Unlisted**、商品層只在
     {Online Store, Shop}、三個變體在全部 3 個管道。
   這兩處合起來構成「三層彼此不一致」的活體 fixture（商品 status／商品層管道集合／
   變體層管道集合三者兩兩不同），刪掉要重做一次實驗才能複驗。
   複驗法：在該商店 admin 開這兩個商品的 Publishing 卡與變體子頁對照，或重放
   `VariantsPublications` persisted query（取法見 `docs/research/82` §8 檔頭）。

## ④ 下一個人要注意什麼

**入口**：`docs/dev/m2-publication-model.md`。動這個模型前先讀它的 §3（寫入契約狀態矩陣）
與 §6（消費者影響圖）。

**三條紅線**：

0. 🔴 **不要把 `spec/migrations/p12_backfill_publications_spec.rb` 改回「抄一份邏輯副本」，
   也不要把行為守衛換成掃字串的 source-guard。** 那正是這一包被抓到的根因：
   規則有三份實作、測試守自己那一份；而字串守衛可以被一行註釋騙過（兩者都已實測）。
   改這組測試後請至少對「拿掉 `after_create`」「拿掉 `publication_id` 條件（**單側**）」
   「拿掉 `where(shop_id:)`」「`published_at` 改 nil」四個突變重跑一次確認轉紅。
1. 🔴 **不要把 `ProductVariant#materialize_publications` 「修好」成跟隨父商品。**
   那看起來明顯是對的，而它是刻意的裁定，理由在 model 註釋與 `m2-publication-model.md` §4。
   （兩種選法對可見性的結果相同，所以就算要改也不急——但要改就得同步改四處說明。）
2. 🔴 **不要對 `published_on` 的謂詞直接取反**做「未發布」scope。
   那裡是正向 EXISTS，NULL 安全；取反會讓 NULL 變 UNKNOWN 而靜默漏掉整批列。
   要反向必須 `NOT COALESCE(<expr>, FALSE)`。第 11 包在三值邏輯上踩了三次。

**重跑方法**：
- 全套：`bundle exec rspec`
- 本包：`bundle exec rspec spec/models/product_spec.rb spec/migrations spec/models/resource_publication_spec.rb`
- 回填 migration 在**有既有資料的庫**上才會執行迴圈本體——空庫回填 0 列也是 exit 0，
  那正是第 11 包部署事故的機制。

**不得外推的範圍**：本包只做兩層 AND ＋ 生產者 ＋ 回填。
GraphQL 寫入面、前台消費、catalog 第三層、發布 UI 都不在內。

**停止條件**：CI `quality`＋`test` 兩個 job 綠即可合併（D40）。
🔴 審查輪次紀律（第 11 包教訓）：**一輪對抗審查抓初始候選的真缺陷，修完即合併**；
之後再發現的登記進 `91` 由後續包處理，不在同一個 PR 內無限收斂。
