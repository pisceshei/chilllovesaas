## ② 為什麼這樣改（含被推翻的假設）

**被推翻的假設：「上一輪補了回歸測試，這塊就守住了」。**

上一輪（PR #33 第 3 輪）引 65 §K.7「檢查本身也要被測試」補了
`test-limits-key-rules.rb`，還做過 meta 驗證（把判定改成 `if false`，測試確實 exit 1）。
看起來完備。

**本輪把改壞的形態從一種擴到六種，三種存活**：

| 存活的突變 | 意義 |
|---|---|
| 只認 TrueClass | FalseClass／NilClass／Date 三個分支**從未被執行過** |
| 刪掉 Sequence 遞迴 | 真實 limits.yml 有 17 處陣列內 mapping，**整片沒掃到** |
| ERB 閘門收窄成單一字面 | 閘門實際已放行其他所有 ERB 寫法 |

🔴 **教訓：「有沒有測試」和「測試有沒有效」是兩個問題，而前者會讓人以為後者也成立。**
上一輪的 meta 驗證只試了**一種**改壞法，剛好是被覆蓋到的那一種 ⇒ 得到了「有效」的錯誤結論。
⇒ 驗證一個檢查器時，**要試多種改壞法，而且要刻意去想「哪一種改壞不會被抓」**。
那個答案就是缺的 fixture。

**其中一條特別值得記**：`no:` 是**挪威的 ISO 3166 代碼**。
鐵律 11 要求法域 pack 可插拔、以代碼當鍵 ⇒ 新增挪威 pack 就會踩到 FalseClass 那條路徑，
而那正是補之前**完全沒被守住**的分支。這不是理論風險，是排隊等著發生的事。

**`limits_erb` 那條是另一種形態：檢查器被自己的文字騙過。**
fixture 的註釋裡寫了完整的 ERB 標籤 ⇒ 把真正的違規行刪掉，checker 仍然打紅。
那份 fixture 從來沒有證明過「擋 ERB 鍵」，它只證明了「檔案裡有 `<%` 這兩個字」。
同型的預防**寫在 PR #39 的 `check-ci-parity.rb` 裡**（刻意只認 `step` 開頭的行，不認註釋）——
⚠️ 那支腳本在本 PR 送審時（2026-08-15）**還沒進 main**，本行不是對現況的斷言，
是「另一個分支上有同型解法」的交叉指引；#39 合併前照著找會找不到檔案。

**順帶一個我自己犯的同型錯**：驗證 `limits_erb` 修好時，我寫的一行 shell 是
`grep -c '<%' file && ruby checker ... && echo ✅ || echo 🔴`。
`grep -c` 找到 0 個時**退出碼是 1**，`&&` 鏈在到達 checker 之前就斷了，`||` 直接印紅字——
**一個「檢查」報出了它根本沒量到的結果**。實際 checker 是 exit 0 通過的。
這與本輪修的東西是同一件事，只是發生在我的驗證工具上。

### 🔴 被推翻的假設（第 2／3 輪，兩條都是我自己的）

**假設一：「同一個 commit 裡先做的實測，後面再改也還算數。」——錯。**
第 2 輪加 `limits_missing_target` fixture 之後跑突變，M14 記為「被抓 ✅」。
接著在**同一個 commit** 的後半段又加了 `scanned.empty?` canary，
而那個 canary 讓 M14 重新變成存活——表格沒有重跑，於是 worklog 裡留下一格**已經失效的實測結果**。
⇒ 突變測試的結果只對**當下那個版本**有效；同輪之後又動了被測對象，**整張表都要重跑**。
這與本 PR 上半段修掉的 `limits_erb` 自我觸發同一族：證據看起來還在，但它證明的東西已經變了。

**假設二：「兩條路徑訊息不同，斷言字串就分得出來。」——錯。**
fail-closed 與 canary 的訊息**都含 `TARGETS`**，而且 fail-closed 的 `warn`
在 `next` 之前就印出去了 ⇒ **任何**取自該行的 needle 在 M14 下都會命中。
⇒ 唯一結構性的解是退出碼三分（1 有違規／2 跑不了／3 沒生效）。

## ③ 還有什麼沒解決

1. ⚠️ **突變測試沒有進 CI**，它是本輪的一次性工具。日後**新增**檢查規則時，
   不會自動被提醒「你的新規則沒有 fixture」。兩條機制化路徑寫在 worklog Pending 1，都沒做。
2. ⚠️ **突變清單不完備**（六種是我想到的，不是窮舉）。
   「6/6 抓到」的正確讀法是「**這六種**會被抓到」，不是「改壞一定會被抓到」。
3. ⚠️ **`limits_clean` 仍是唯一的反向斷言**——夠用，但只有一條。
4. ⚠️ **同批驗收還有 6 條未處理**（Y4/Y5/Y6 執行位元閘門、Y7/Y8 驗收 workflow、
   Y12 workflow 語法閘門），登記在 `docs/worklog/2026-08-15-CI對等性機制化.md` Pending 2。

### 🔴 第 2／3 輪新增（本段原本只有上面 4 條，漏掉了本輪唯一自承存活的突變）

5. 🔴 **M17 存活，而且無解：`scanned.empty?` canary 的 `exit 3` 沒有任何測試在守。**
   把它改回 `exit 2`，15 條全綠——**而那一改會讓 M14 重新變成存活**
   （fail-closed 與 canary 的退出碼又相同了，兩條路徑再度無法分辨）。
   ⇒ 本輪修好的東西，被一個「沒有測試在守的常數」保護著。
   原因：canary 走不到 fixture（`TARGETS` 是腳本內常數，fixture 目錄影響不到它）。
   已在該段與 `spec/fixtures/ci_violations/limits_missing_target/README.md` 寫明理由，
   **但那是註釋不是機制**。要真正關掉得讓 fixture 有辦法影響 `TARGETS`
   （例如改吃環境變數），那會擴大 checker 的可設定面 ⇒ 本輪判斷不值得，登記為**已知且刻意**的缺口。
   （全文：worklog Pending 9。）
6. ⚠️ **退出碼三分只做在 `check-limits-keys.rb` 一支上**，其餘 `check-*` 仍是 0/1，
   它們同樣把「跑不了」與「沒生效」混在 1 裡。**這是不一致**，
   下一個人可能誤以為三碼是專案慣例（worklog Pending 10）。
7. ⚠️ **行號斷言與 fixture 行數是硬耦合**，沒有機制守著；本輪加 `null:`／`NULL:` 時
   第一次就踩到（`~` 由第 5 行移到第 9 行，斷言得跟著改）。worklog Pending 5。
8. ⚠️ **`limits_missing_target` 只靠 README 保護**：有人在該目錄下建一個
   `config/limits.yml`，這條測試會退化成又一個 clean case。worklog Pending 6。

## ④ 下一個人要注意什麼

- 🔴 **往 `check-limits-keys.rb` 加新的違規判定時，先問自己：「把這條規則改壞成什麼樣子，
  現有的 fixture 抓不到？」** 那個答案就是你要補的 fixture。
  本輪的三個缺口全部是這樣被找出來的，沒有一個是讀代碼讀出來的。
- 🔴 **寫 fixture 的註釋時，不要在註釋裡寫出「會被檢查器命中的字面」**。
  `limits_erb` 踩過：註釋裡的 ERB 標籤讓 fixture 永遠會紅，因此證明不了任何事。
- **新增法域 pack 時**（鐵律 11），代碼是 `no`（挪威）、`on`（無此國碼但同形）等的一律加引號。
  忘了會被 `Check limits.yml key types` 擋下來，而 `limits_false_key` 這份 fixture
  保證那道閘門不會在某次重構後靜默失效。
- **本輪的突變測試腳本沒有進版控**（在 scratchpad）。要重跑的話做法很簡單：
  把 checker 的關鍵判定逐一改壞、每次跑一遍 `test-limits-key-rules.rb`、記錄 exit code。
  worklog 有**四張**突變表（第 1／2／3／4 輪各一張）可直接沿用，共 20 餘種形態。
  <!-- 🔴 原文寫「六種形態的完整清單」，那是第 1 輪的數字（第 5 輪驗收指出）。 -->
  🔴 **沿用時注意**：突變表的結果只對**當時那個版本**有效。本 PR 第 2 輪就吃過這個虧——
  同一個 commit 的後半段讓前半段的「M14 被抓」失效，而表格沒重跑。
