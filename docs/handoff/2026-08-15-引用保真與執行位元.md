## ② 為什麼這樣改（含被推翻的假設）

**被推翻的假設一：「引用轉述得語義正確就沒問題」。**
不是。「§K.7 **逐字**是⋯⋯」是一個**斷言**，而且是一行 `git grep` 就能證偽的那種。
語義忠實（§K.7 確實要求檢查本身要被測試）不能替代引用正確——
下一個人拿著那句話去 65 號裡找，會找不到，然後開始懷疑其他引用。

**被推翻的假設二：「補上那 4 個執行位元就修好了」。**
這是本輪最該記的一點。真正的問題不是那 4 個位元，而是
**`Verify bin/ scripts are executable` 這道閘門只掃 `scripts/*.sh`**——
它就住在 `scripts/` 目錄裡，卻擋不住同目錄 `.rb`／`.py` 的同一種錯。
只補位元＝下一支新腳本照樣可以 100644 進來。⇒ 改判準才是修復，補位元只是清現場。

新判準選「**帶 shebang 就必須可執行**」而不是「`scripts/` 下全部必須可執行」，
理由是前者**自證**：帶 shebang 是檔案自己宣告「我可以直接跑」，
宣告了卻沒有執行位元是自相矛盾；而後者會誤傷未來放進去的資料檔。

**為什麼與 `claude-review.yml` 的修正分成兩個 PR**：
`anthropics/claude-code-action` 有反竄改機制——**動到 `claude-review.yml` 的 PR，
驗收步驟整個跳過**（該檔檔頭 31–40 行有實測記錄：run 只跑十幾秒且 job 顯示 success）。
綁在一起會讓本 PR 的修正**也**逃過驗收。

## ③ 還有什麼沒解決

1. **新閘門的誤判面**：`scripts/` 下帶 shebang 卻刻意不可執行的檔會被打紅。
   目前不存在這種檔；日後若要放，加白名單或換目錄，**不要用拿掉 shebang 來繞**。
2. **`bin/` 的判準沒動**（仍是該目錄下所有檔都要 755）——刻意維持較嚴。
3. **`docs/worklog/2026-08-15-金額CI執法.md` 的同一句話沒改**——worklog 是歷史紀錄。
   ⇒ 全倉 grep 仍會命中該檔與各處的更正註記本身，這是預期結果。
4. **本 PR 與 PR #33 都動 `ci.yml`**，但區段不同（本 PR＝檔案前段的 `Verify …` 與 money 註釋；
   #33＝quality job 尾端新增步驟），預期可自動合併。先合哪個都行，第二個要確認 CI 綠燈。

## ④ 下一個人要注意什麼

- 🔴 **新增 `scripts/` 下的腳本時，記得 `git update-index --chmod=+x`**。
  忘了也沒關係——CI 現在真的會擋（本輪已用反向測試證明它會紅），訊息裡直接給修法。
  在 Windows 上開發尤其容易踩到（`core.filemode=false`）。
- 🔴 **寫「逐字」兩個字之前，先跑一次 `git grep`。** 本輪修的兩處、以及 PR #33 修的五處，
  全都是同一句話被轉述後冠上「逐字」再擴散出去的。轉述請用轉述的句式。

  654ms），annotation 裡根本沒有它叫你去找的那句話。
