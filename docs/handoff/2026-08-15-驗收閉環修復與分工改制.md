## ② 為什麼這樣改（含被推翻的假設）

### 假設一：「alias `opus` 會自動跟上最新版」——**錯的**

第一版把模型寫成 `--model opus`，理由是「升版自動跟上」。
官方明文：「Opus 5 requires Claude Code v2.1.219 or later」，且
「Before v2.1.219, `opus` resolved to Opus 4.8」。而 action 內建 CLI 的版號
**官方沒有公布 SDK↔CLI 對應** ⇒ 我們無從得知拿到哪一個，**而且它不會報錯**。
⇒ 改成釘完整名。代價是升版要手動改，換來的是「失效會叫」。

同一個判斷後來又用了一次：**沒有採用 alias `best`**（「有 Fable 5 就用，否則用最新 Opus」）。
它更聰明，但仍然是 alias ⇒ 仍然「不知道自己在跑什麼」。

### 假設二：「風險②只在 Claude 步驟失敗時發生」——**範圍寫窄了**

`claude-review.yml` 頂部的 `AUTO_MERGE` 註解②早就寫過「舊通過會被沿用」，
但把觸發條件寫成「Claude 步驟失敗時」。Codex 的 review 指出**它與 outcome 無關、每一輪都發生**：
`LATEST` 取自 PR 的**全部**留言，只要任何一輪貼過結論，之後每一輪都非空。
後果三重：新加的回收分支從第二輪起就是**死碼**；舊「通過」會 **auto-approve 未審過的 head**；
舊「需修改」會拿過期意見再派一次工。

⇒ 修法是**留言 id 水位**（驗收前記錄最大 id，只認之後的結論）。
🔴 **刻意沒用「留言內嵌 head SHA 比對」**——那要靠 prompt 叫模型自己寫對 SHA ＝ 賭模型配合。
水位由 workflow 自己量。

### 假設三：「Codex 修比較快」——**改制推翻**

觸發點是閉環修好後第一次真實運作：Claude 判需修改 → workflow 自動 `@codex` 派修 → Codex 接單。
使用者裁定改成「Codex 只做驗收」。
🔴 **理由不是 Codex 修得不好**，而是**修法選擇往往是裁定而不是機械修復**——
那一次驗收方自己就給了兩條方向（fail-closed 最小修 vs 補齊語義），
選哪條要看規格要不要一併改。把這種選擇交給看不到本輪對話脈絡的代理，等於讓它替專案下裁定。

⚠️ 實作時發現**光刪「請修復」四個字沒用**：Codex 對任何 `@` 提及都會接單
⇒ 規則寫成「workflow 產生的留言**不得包含 `@` 開頭的代理呼叫**」。

### 假設四：「A6 擋住位數就夠了」——**只擋了一半**

A6 原本只有上限（`> 2` ＝ 精度謊報）。宣告 `0` 或 `1` 是**完全合法的 pack**，
而 `to_psp_decimal` → `fixed_string(major, decimal_places)` → `value.round(digits)` **靜默四捨五入**：
`decimal_places: 1` ＋ HKD 14.85（儲存 `1485`）⇒ 送出 `"14.9"`，**差額 0.05 沒有任何一張表記得住**。

🔴 三件事讓它難發現，而且**每一件都是本 PR 主線在講的那種病**：
①與 `minor_units` 側**不對稱**（那側有 A3 餘數 raise 順手擋住，這側沒有等價物）；
②**在 HKD 這個基準法域上就會發生**，不像 A1／A2 只在 zero-decimal 幣別現形；
③**§H 矩陣證明不了它**——矩陣裡每個 pack 都宣告 2 位，那條路從沒被走過。

## ④ 下一個人要注意什麼

- 🔴 **改 `claude-review.yml` 的 PR，自己不會被驗收**（反竄改機制），而且**合併進 main 之前完全不生效**。
  判別方法：Actions run 時長——正常 3–20 分鐘，被跳過只有 **17–22 秒**（本輪 PR #30 六個 run 全是）。
- 🔴 **`--effort max` 讓驗收從 3–4 分鐘變成約 20 分鐘**（`timeout-minutes: 30` 的三分之二）。
  下次 diff 更大時可能要調 **timeout 而不是降 effort**；`--max-turns 200` 這次沒撞到，
  但那個數字訂於較低 effort 時代，**回合數與 effort 要一起重算**。
- 🔴 **負面驗證的前提是「破壞真的發生了」**。本輪做 A6b 的負面驗證時，
  字串替換沒匹配到而測試沒紅，我差點讀成「斷言是假的」。
  ⇒ **破壞那一步本身也要有斷言**（腳本裡加 `assert old in s`），
  否則「測試沒紅」有兩種讀法而你分不出是哪一種。
- 🔴 **錯的註釋比沒有註釋更糟**。本輪兩條都是這個形態：
  `canonical_json` 規則④宣稱「`1480.0` 與 `1480` 必須是同一個指紋」（實作是 raise）、
  `Money::Storage#<=>` 的 `@raise` 宣稱 TypeError（實際 private ⇒ NoMethodError）。
  ⚠️ **後者連測試都證明不了**——既有測試只用 `a < b`，而 `Comparable#<` 是**內部**呼叫，
  **不受 private 限制**。寫 mixin 相關的註釋時要特別確認「public 真的可用」。
- ⚠️ **Codex 只做驗收是「約定 ＋ 機制」不是純機制**：Codex 那側沒有「只驗收」的開關，
  任何人手動 `@codex` 它還是會來改代碼。
- ⚠️ **`Money.fixed_string` 現在接受任意非負 `digits` 且對每個值都正確**，
  但它**擋不住政策層的疏漏**——新增第三個呼叫端時要自己確認先過了 pack 驗證。
