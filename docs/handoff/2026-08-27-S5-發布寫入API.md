## ① 我改了什麼

**目標**：交付 `publishablePublish` ／ `publishableUnpublish` ——S1 與 S2 都登記為阻塞前置，
因為在它之前**全倉沒有任何路徑能修改既有列的 `published_at`**（設排程／改期／取消排程無路可達）。

**輸入 ref**：base `b740b24`；本包第一個 commit `b97dae1`（把 §13 admin 實測先入庫，
因為鐵律 19.4 不准引用未 commit 的文件作實作依據）。

**遇到的問題與證據**：

1. **根因確認**（機制證據，不是推測）：S1 的 add 分支用 `find_or_create_by!` 帶 create-only 區塊，
   Rails 8.1.3.1 的實作是 `find_by(attributes) || create_or_find_by!(attributes, &block)`
   ⇒ `find_by` 命中時區塊**根本不執行**，既有列在結構上不可能被改到。
2. **真缺陷（本輪突變測試抓到）**：`ChillloveSchema.resolve_type` 少了 `ProductVariant` 分支，
   `publishableUnpublish` 對變體成功時回傳炸成 **500**。只有「變體真的成功走完」那一格踩得到。
3. **併發測試的設計陷阱**：gate 下在取鎖之後 ⇒ 對手 INSERT 卡 50 秒 `LockWaitTimeout`
   （InnoDB 在 REPEATABLE READ 下對不存在的列取**間隙鎖**）。gate 改下在取鎖之前才量得到東西。

**做過的重要動作**：三路研究工作流（12 agent）→ 測試店實測並還原 → 寫程式 →
18 個突變逐個實跑 → 四個全綠的逐個追根因並補測試拓樸 → 全 1241 examples 綠。

**異動**：見 worklog 的 Changes 表（17 個檔，其中 8 個新增）。

**驗證輸出**：
- `bundle exec rspec` ⇒ **1241 examples, 0 failures**
- `ruby scripts/check-doc-claims.rb` ⇒ OK，警告 0
- 突變 18 個 ⇒ 17 紅；剩 1 個由第二層獨立防線接住，複合突變令三格轉紅

## ② 為什麼這樣改

**證據鏈**：全部外部斷言帶 URL＋取證日期 2026-08-27，版本錨點＝`api_version: 2026-07`
（逐字取自 `publishableUnpublish.txt` front-matter）。查不到的一律標「未取得」，
清單在 dev doc §9 與 worklog Pending。

**選案理由（三個關鍵的）**：

1. **三個 PR 合成一個**：草案 §8 建議切三個。實際合成一個——三者全在
   `Publications::Write` 一個元件、一份狀態矩陣，切開會讓 main 帶著
   「兩條路對既有 NULL 列給出相反結果」這個**已知分岔**過一輪（17.4＋20.5）。
2. **五格 ours 裁定由執行方定**：草案建議送使用者裁定。它們是官方沉默處的語義選擇，
   **不屬鐵律 17.3 例外**（不改鐵律本文、非不可逆 schema、無費用），且草案已給出
   fail-closed 建議與論證 ⇒ 依建議裁定並逐格登記（worklog 的五格表）。
3. **不加 `lock_version`，改顯式列鎖**：`resource_publications` 是關聯表，加樂觀鎖欄會
   打穿所有 `update_all` 路徑（含 migration 原生 SQL 與 `Materialize` 批量回填），
   且需 schema 變更＋18.3。顯式 `SELECT ... FOR UPDATE` 達到同樣目的且無 schema 成本
   ⇒ **草案的 N43 裁定請求因此消失**，不是被忽略。

**被推翻的假設**：

- 🔴 **「重複 add 是 no-op success 的官方逐字未複驗」**（S1 登記）——**已推翻**：
  S5 的官方第六路在**指南頁**逐字命中。已回寫 `write.rb` 的 `source_url` 並加日期更正註。
  ⚠️ 保留射程限制：該句主詞是 **variant**，未涵蓋「已排程」態（那正是 R7 取 fail-closed 的理由）。
- 🔴 **「`userErrors.field` 是否剝殼沒有官方範例可證」**（`28 §0.3.6` 登記）——**已推翻**：
  官方 fixture 逐字 `["input","0","publicationId"]`。已同批更正 §0.3.6：補上該條 fixture，
  並把小節標題裡那個計數形容詞拿掉（新增內容使它不再成立）。
  複驗：`grep -n "0.3.6" docs/research/28-api-contract.md`。
- **「rescue `RecordNotUnique` 是常規並發路徑」**——**推翻**：REPEATABLE READ 的間隙鎖
  已把建列競態序列化 ⇒ 它是縱深防禦。改用故障注入測，並誠實這樣標。

**未採方向**：Saleor 的軟移除（前提是 listing 列上有 per-channel 售價要保，我方只有
`published_at` 一欄 ⇒ 前提不成立）；Saleor 的 `IGNORE_FAILED`（會讓資源落到半完成狀態）。
逐項登記 `docs/specs/107` 的 S5-1／S5-2。

## ③ 還有什麼沒解決

1. 🔴 **outbox 的消費者不存在**。`Events::Consumers::REGISTRY` 沒有
   `PRODUCT_PUBLICATION_CHANGED` ⇒ S5 投的排程事件在到點時會被 relay 取出、
   派給零個消費者、標記完成。**S2 PR-C 必須處理「在它之前已被消化掉的排程事件」。**
2. 🔴 **`publications.operation_status` 仍空掛**（零寫入者、恆為 null）。本包沒接，
   理由是形態需安裝真實管道 app 才觀測得到，而使用者已裁定不安裝。登記 `91` §3.22。
3. **到點的 ACTIVE 檢查未做**，歸 PR-C；且其正典鍵無行內出處註釋，**要先補出處**
   才能拿它當生效判準（鐵律 19）。
4. **`collections` 無 cache stamp 欄**、**`resolve_type` 與 `PUBLISHABLE_TYPES` 是兩份清單**、
   **`limits.yml` 的免冪等理由不成立** ⇒ 三條都登記 `91` §3.22，都需要動判準面或 schema
   （18.3＋20.4），本包只登記候選。
5. **未取得（外部）**：本尊 admin 的 `ProductSavePublishablePublishUnpublish` variables／
   回應形狀（persisted query 不可觀測）；`publishablePublish` 的陣列上限與原子性語義；
   `publishDate: null` 的官方語義；「取消發布後紀錄的去向」。清單在 `82` §13.4 與 dev doc。
6. **風險**：`ISO8601DateTime` 對不帶 offset 的輸入當 UTC ⇒ 商家若送本地時間字串會偏移。
   這是 ours 裁定（官方無正面陳述），且 `shops.timezone` 至今零讀取者。
   S6 前端接上時**必須**送帶 offset 的字串。
7. **本包尚未部署／線上驗證**（截至本檔寫成時）。S1 的教訓是**線上驗證真的會抓到東西**
   （29 格 spec 全綠＋六個突變全紅，正式庫仍印出孤兒 catalog）⇒ 合併後照兩步紀律部署，
   再用 `rails runner` 在正式庫實跑 `Publications::Write.publish/.unpublish`（自我還原）。

## ④ 下一個人要注意什麼

**下一步入口**：S5 合併並部署驗證後，依分步方案往 **S6（Admin UI）** 或 **S2 PR-C
（到點副作用機制）**。⚠️ PR-C 需要使用者裁定 S2 §4.F 的五格補償語義
（到點非 ACTIVE 的處置／是否 catch-up／失敗退避／到點延遲窗／ResourceFeedback 等價物）
——那一節明文「送使用者裁定，不得由執行方自定」，**與 S5 這五格不同**（S5 那五格是
純語義選擇，PR-C 那五格牽涉補償行為與資料修復）。

**前置**：鐵律 17.3——PR 未實際合併進 main 前，其依賴鏈不得自動開工。

**重跑方法**：
```bash
bundle exec rspec spec/requests/publishable_write_spec.rb spec/services/publications/
```
突變清單與各自該打紅哪一支 spec，逐條在 worklog 的突變表；
併發 spec 是 `use_transactional_tests = false`，**新增租戶表時六份 `purge!` 都要補**（FK 順序）。

**🔴 紅線（動這塊之前必讀）**：
1. **`apply_publication!` 是狀態矩陣的唯一實作處**，`publicationUpdate` 也走它。
   複驗呼叫端集合：`grep -rn "apply_publication!" app/`（應恰得三處：定義一處、
   `write_publishable` 一處、`.update` 的 add 分支一處）。
   改任何一格之前先讀 dev doc §2 的表與依據欄——**R7 與 R10 是 fail-closed 裁定，
   反面選項會靜默毀掉商家設好的排程**。
2. **`bump_stamps!` 的 `at` 永遠是 `Time.current`**，絕不傳 `publishDate`
   （`bump_publications_stamp!` 是直接賦值，寫進未來時間會污染 stamp 語義）。
3. **不得用 `insert_all`／`upsert_all`／`update_all` 寫 `resource_publications`**
   ——會同時打穿多型租戶守衛與兩道排程守衛。
4. **不得用 `update_all` 的 hash 形式** bump stamp（會遞增 `lock_version`
   ⇒ 商家手上的 product 立刻 `StaleObjectError`）。
5. **加第四種 publishable 時要改三處**：`ResourcePublication::PUBLISHABLE_TYPES`（正典）、
   `ChillloveSchema.resolve_type`、`spec/requests/publishable_write_spec.rb` 的三型別迴圈。
   目前**沒有機制**擋漏改，只有那格行為守衛。
6. **不得在規格或程式碼寫「發布後即可見」**——三層 AND 的第三層 catalog 判定式仍未做（88 §6）。

**不得外推的範圍**：本包對 `publicationUpdate` 的改動**只限 add 分支走同一份寫入規則**
（同根因影響圖內，20.5 允許）。`Materialize` 的 bump 收斂、全域 GID parser 重構、
`limits.yml` 的重複鍵清理**都不在本包**，各自登記在 `91` §3。

**停止條件**：CI 的 `quality` ＋ `test` 兩個 job 綠（D40）⇒ 自合併 ⇒ 部署 bt3 ⇒ 線上驗證。
線上驗證若印出非預期狀態（S1 的孤兒 catalog 那種），**那是真缺陷不是雜訊**，回頭修。
