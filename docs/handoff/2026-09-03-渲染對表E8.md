## ② 為什麼這樣改

- 正規化只准抹「身分形」，任何不確定的差異都留在報告裡（鐵律 19）；相似度用 token 多重集合而非固定分塊（單一插入不會把後面全判不同）。
- 每條形差先找本尊原始位元組再看官方文件，兩者衝突以位元組為準並登記（例：`inline_asset_content` 照檔輸出；F8 隱藏欄位無分隔）。
- 被推翻的假設：①資產檔尾換行被修尾（錯，toolbar 的 `\r` 來自 setting 字串）；②整數取屬性回空字串（錯，子 media block 走佔位分支證明整數仍 nil；真正為真的是空字串）；③`content_for 'blocks'` 不加 LF（錯，36 個 wrapper 後全是 LF）；④資源型 setting 只有一種「blank」（錯，未選＝空字串、查無＝nil、動態純量＝blank）。
- block 實例前綴值不可觀測 ⇒ 只對形（`A`＋17 碼、重複尾綴、LF），值為 ours 並登記。

## ④ 下一個人要注意什麼

- 本機對表流程：`bin/rails "render_parity:mirror[mirror]"` → 起 dev server（`CHILLLOVE_BASE_HOST=localhost`，port 3000；preview 工具的 launch.json 會秒退，改用 Bash 背景起）→ `curl --resolve mirror.localhost:3000:127.0.0.1 -L http://mirror.localhost:3000/` → `REF_HOST=hoko.vip CAND_HOST=mirror.localhost CAND_PREFIX=zh-hans-tw bin/rails "render_parity:diff[…]"`。`CAND_PREFIX` 不帶前導斜線（MSYS 路徑轉換）。
- 每次改引擎檔都重啟伺服器再抓頁；`Rails.cache.clear` 可排除頁快取疑慮。
- 不要把 §3 已登記差異塞進正規化來讓報告變綠；新差異先讀 hoko 原始位元組（`newline=''` 讀檔看 `\r`）。
- 突變輪前先 commit（`git checkout --` 會沖掉未提交修法）。
